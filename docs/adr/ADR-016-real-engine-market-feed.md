# ADR-016 실전 엔진 시세 전달(게이트웨이 → 실전 엔진)과 보유 종목 구독 보장

- 상태: 제안(D-143). 작성 data-engineer, 교차 검토 architect(모듈 경계·프로토콜), risk-ops(실전 보호 경로·알림 수준). 실전 경로의 입력을 정하므로 실전 관련 PR로 다룬다: risk-ops 검토 → 독립 QA → **사용자 머지**(지침 10·11장).
- 날짜: 2026-10-26
- 단계: 7단계 준비 묶음 G([7단계 준비 계획](../team/stage-7-readiness-plan.md) 2.4장 D11·D12·D13, 3장). **문서만**이며 코드는 바꾸지 않는다. 구현은 5장 순서(G1~G5)로 나눈 PR에서 한다.
- 닫는 것: [ADR-010](ADR-010-live-feed-and-session.md) 5장 "실전 엔진 시세 전달"·N5(엔진의 `marketdata.feed` 금지)·N6(받는 쪽 자리) 행, ADR-010 QA(PR #87) R1(수신 꼬리 지연)·R3(받는 쪽 자리와 인코딩 비용)의 엔진 쪽, [ADR-003](ADR-003-market-data.md) 5장 "게이트웨이 → 실전 엔진·실험실 실시간 전달(IPC)" 행의 실전 엔진 쪽, "구독 거절(`SUBSCRIBE_REJECTED`)" 행과 "`unservedHeld` 경보 알림 연결" 행의 설계 부분.
- 참고: [ADR-015](ADR-015-real-engine-store.md)(실전 엔진 저장소, D-141)는 PR #239로 머지됐다. 이 문서가 ADR-015를 가리키는 곳(2.2 writer.lock, 2.3 부팅 번호, 2.6·6장 주문 의도 기록)은 ADR-015가 바뀌면 같이 본다.
- 정하지 않는 것: watchlist 구독 상한(D13, **Q-060 사용자 결정 대기**, 2.10에 선택지만), 보호 폴링 클라이언트 구현(D10, 묶음 D·E), 엔진 계좌 워커 구조(묶음 E).
- 근거 결정: D-013(프로세스 4개), D-024(실시간 우선순위·보유 종목 보호 폴링), D-059(토스 토큰은 엔진만), D-076(ADR-010), D-122(watchlist 100종목), D-140 ⑥(첫 실전 증권사 한국투자), 지침 4장 6번(실전 매매는 다른 기능에 영향받지 않음)·7번(주문은 계좌의 증권사로만)
- 실전 주문 경로·RealTradingGuard·블랙리스트·리스크 한도 코드는 바꾸지 않는다. 게이트웨이는 주문 API를 부르지 않는 그대로다(MD-01).

## 1. 배경(지금 코드)

- [사실] 실전 엔진에는 시세 입력이 없다. `autotrade-app-engine`의 운영 코드는 `EngineMain`·`EngineSelfCheck`와 `command`·`order` 패키지뿐이다. 엔진은 `autotrade-marketdata` 모듈 전체에 의존할 수 있다(`autotrade-app-engine/build.gradle.kts` dependencies).
- [사실] 게이트웨이의 구독 대상은 기동 때 한 번 읽는 `watchlist.json`(`held`·`candidates`)뿐이다(`GatewayMain.java:96`, `WatchList`). 실행 중 보유 종목이 바뀌어도 게이트웨이는 모른다. 실전 엔진이 장중에 산 종목은 지금 구조로는 구독되지 않는다.
- [사실] 게이트웨이는 계좌번호까지 설정된 실전 계좌가 있는 증권사를 시세 소스에서 뺀다(`GatewayMain.reservedForRealTrading`, `:97`, D-024). D-140 ⑥으로 첫 실전 증권사가 한국투자이므로, 실전 계좌를 설정하면 게이트웨이 소스는 **키움 하나**(FAILOVER, 예비 소스 없음)가 된다. 토스는 D-059로 게이트웨이가 쓰지 않는다.
- [사실] 보유 종목을 받을 소스가 없을 때(`unservedHeld`)는 ERROR 로그만 남긴다(`MarketHub.java:135-138`). 증권사가 구독을 거절하면 소스는 건수만 세고 경고 로그를 남기며(`StreamingMarketDataSource.java:454-457`, `Decoded.Control.SUBSCRIBE_REJECTED`), 거절된 종목이 무엇인지는 허브에 알리지 않는다. 그래서 허브는 거절된 종목도 "배정됨"으로 본다.
- [사실] 실험실 전달(ADR-010)은 받는 쪽 4자리를 아무 같은 OS 사용자 프로세스나 차지할 수 있고(`FeedServer.MAX_SUBSCRIBERS = 4`), 받는 쪽마다 큐 50,000줄·30초 멈춤 한도이며, `publish`가 게이트웨이 수신 스레드에서 받는 쪽마다 `synchronized offer`와 `Item` 할당을 한다(`FeedServer.java:114-126`, `:241-259`). 인코딩은 받는 쪽마다 쓰기 스레드에서 따로 한다. QA PR #87 탐침에서 읽지 않는 받는 쪽 4개일 때 `publish` 최대 14~52ms(기준선 4ms)였다(R1).
- [사실] 보호 시세 경로 계약 `PollingQuoteSource`는 있고 구현은 토스뿐이며 어느 프로세스에도 연결돼 있지 않다(`marketdata.polling`, 7단계 계획 D10).
- [사실] 장애표([broker-and-fault-design.md](../team/broker-and-fault-design.md) 6장): #1 "1순위 끊김 → 2순위 전환, 보유 종목은 종목별 마지막 수신 시각 기준 초과 시 즉시 보호 시세 경로", #2 "모든 실시간 끊김 → 신규 진입 전면 중단, 보유 종목은 REST 폴링으로 손절 감시", #9 "게이트웨이 크래시 → 실전 영향 없음(#1·#2로 처리)". 5.1장 그림은 게이트웨이 → 실전 엔진을 로컬 큐로 잇는다.

## 2. 결정

### 2.1 공급 구조: 실시간은 게이트웨이 전용 엔진 채널, 보호는 엔진 자신의 REST 폴링

- 실전 엔진의 **실시간 시세는 게이트웨이**에서 받는다(D-013 프로세스 분리 유지). 엔진은 시세용 WebSocket을 직접 열지 않는다(대안 B, 3장).
- 게이트웨이 시세가 끊기거나 늦거나 그 종목이 구독되지 않으면, 엔진은 **실전 계좌 증권사 키로 REST 현재가를 직접 폴링**한다(보호 시세 경로, D-024·장애표 #1·#2, 구현은 D10). 이 키는 원래 엔진 전용이므로(D-024, broker-and-fault-design 4.2) 새 공유가 생기지 않는다.
- 그래서 게이트웨이가 죽어도 보유 종목 보호는 계속된다(장애표 #9 그대로). 게이트웨이는 "빠르고 넓은 입력", 보호 폴링은 "느리지만 엔진 혼자 지키는 입력"이다.

### 2.2 채널: 엔진 전용 소켓 `run/engine-feed.sock`, 받는 쪽 하나

- 실험실 소켓(`run/market-feed.sock`)과 **다른 소켓·다른 서버**다. 같은 설정 폴더 `run/` 아래(폴더 700·소켓 600, ADR-006·ADR-010과 같은 가정, Windows는 ACL 기본값 `[가정]`).
- 받는 쪽은 **하나**(실전 엔진)다. 이미 붙어 있으면 새 연결은 인사 없이 닫고 게이트웨이가 ERROR 로그를 남긴다. 엔진은 연결이 닫히거나 인사가 5초 안에 오지 않으면 연결 실패로 보고 2.7의 "전달 끊김" 처리를 한다. 엔진이 둘 뜨는 일은 엔진 쪽 기동 거부(D-142 C6, ADR-015 writer.lock)가 막는다.
- 게이트웨이는 1초마다 `run/engine-feed.sock`이 자기 소켓 파일인지 확인한다. 지워졌으면(장애 테스트 3-R의 `run` 폴더 삭제 등) 다시 만들고 ERROR 로그를 남긴다. 이미 붙은 엔진 연결은 끊지 않는다. 다른 프로세스가 그 경로를 잡았으면 빼앗지 않고 ERROR 로그만 남긴다(엔진 쪽에는 재접속 실패·인사 불일치로 드러나 긴급 알림). D-142 C6 제어 소켓과 같은 방식이다(QA PR #245 Q4). 3-R 확인 항목에 "엔진 시세 연결이 다시 붙음"을 넣는다(6장 6번).
- 패키지(architect 확정, PR #245 검토 R2): `autotrade-marketdata` 안에 둘로 나눈다(순수 Java·스프링 없음).
  - `com.autotrade.marketdata.enginefeed`: 받는 쪽(엔진용)과 줄 형식.
  - `com.autotrade.marketdata.enginefeed.server`: 서버. 게이트웨이만 쓴다.
- ArchUnit(클래스 단위): 엔진은 `marketdata.feed`(실험실 전달)·`marketdata.live`(증권사 WebSocket)·`marketdata.enginefeed.server`와, `marketdata.recording` 중 `RecordingCodec` 밖의 클래스(쓰기 클래스 등)를 쓰지 못한다(ADR-010 N5, 엔진이 게이트웨이 행세 금지). 실험실·수집기·실험 명령은 `enginefeed`와 `enginefeed.server`를 모두 쓰지 못한다(엔진 행세 금지).
- 게이트웨이는 기동 때 엔진 소켓도 연다. 못 열면 ERROR 로그를 남기고 **녹화·실험실 전달은 그대로** 한다(ADR-010 2.1과 같은 원칙). 엔진 쪽에는 연결 실패로 보이고 보호 폴링으로 넘어간다.

### 2.3 줄 형식(엔진 전달 형식 버전 1)

한 줄에 JSON 하나, UTF-8, `\n`. 줄 상한 64KB(ADR-010과 같음). 이벤트 줄은 **녹화 형식 그대로**(`RecordingCodec`, 형식 하나 원칙). 제어 줄은 이벤트 줄과 겹치지 않게 최상위 키 하나로 구분한다(이벤트 줄에는 `t`가 있고 제어 줄에는 없다).

엔진 → 게이트웨이

1. 인사(연결 직후 1회, 5초 안): `{"hello":"autotrade-engine-feed","formatVersion":1,"client":"engine","boot":"<엔진 부팅 표지>"}`. `boot`는 `[A-Za-z0-9-]{1,40}`(ADR-015의 부팅 번호를 쓸 수 있으면 그것, 아니면 기동 시각). 로그 대조용이다.
2. 관심 종목(인사 뒤 언제든, 여러 번): `{"interest":{"rev":12,"protect":["KRX:005930"],"entry":["KRX:000660"]}}`
   - **전체 교체**다(차분이 아님). 같은 줄을 두 번 보내도 결과가 같다(멱등). `rev`는 연결마다 1부터 늘어난다. 줄어들거나 같은 `rev`는 무시하며, 이 비교는 **같은 연결 안에서만** 한다(재접속한 엔진의 `rev:1`은 앞 연결의 마지막 `rev`와 비교하지 않고 받는다).
   - `protect`: 실전 계좌의 보유 종목 ∪ 미체결 주문 종목(매수·매도 모두). 보호 대상이다.
   - `entry`: 실전 계좌가 오늘 신규 진입을 볼 수 있는 종목(조합 지정 S1의 선정 결과).
   - 상한: `protect` 64종목, `protect`∪`entry` 128종목 `[가정]`, 줄 16KB. 넘거나 형식이 틀리면 게이트웨이는 **앞의 관심을 그대로 두고** 상태 줄에 `"rejected":"<이유>"`를 실어 답한다(앞 관심을 지우지 않는다: 보호 대상이 빠지는 쪽으로 실패하지 않게).
   - 엔진은 관심 종목만 보내고 수량·가격·계좌는 보내지 않는다.

게이트웨이 → 엔진

1. 인사: `{"feed":"autotrade-engine-feed","formatVersion":1,"recordingFormat":<RecordingCodec.FORMAT_VERSION>}`. 엔진은 두 버전 중 하나라도 다르면 끊고 긴급 알림.
2. 이벤트 줄: 관심 종목(`protect`∪`entry`)의 이벤트만, 녹화 형식. `seq`는 연결마다 1부터 빈틈 없이, `src`·`srcSeq`는 녹화와 같다(엔진 판단을 녹화와 대조할 수 있게). 소스 전환·끊김 공백(`GAP`)과 상태 변화(`STATUS`, VI 등)도 그대로 온다.
3. 상태 줄: `{"status":{"rev":12,"at":"…Z","sources":{"KIWOOM-WS":"CONNECTED"},"served":{"KRX:005930":"KIWOOM-WS"},"unserved":{"KRX:000660":"CAPACITY"},"rejected":null}}`
   - 관심을 적용한 뒤, 그리고 관심 종목의 배정이 바뀔 때(재배분·소스 끊김·구독 거절)마다 보낸다.
   - `rev`는 **이 연결에서** 마지막으로 적용한 관심의 `rev`다. 이 연결에서 관심을 아직 적용하지 않았으면 0이다(엔진 끊김 뒤 60초 유지 중인 앞 연결의 관심으로 나간 배정이어도 0).
   - 엔진은 `status.rev`가 그 종목을 넣어 보낸 관심의 `rev` 이상일 때만 그 종목의 `served`를 구독 확인으로 쓴다. 재접속 직후 앞 연결의 관심으로 나간 `served`를 새 관심의 확인으로 오인하지 않기 위해서다("관심 → `served` 확인 → 주문" 순서, 2.6).
   - `unserved` 이유: `CAPACITY`(한도), `NO_SOURCE`(쓸 수 있는 소스 없음), `REJECTED`(증권사가 구독을 거절), `PENDING`(구독 요청 중, 확인 전).
   - `served`의 뜻: 그 종목이 소스에 배정되고 **그 종목이 담긴 등록 요청의 성공 응답을 받았거나 배정 뒤 그 종목 이벤트를 받은 상태**다. 배정만 된 동안은 `PENDING`이다. 키움 등록 응답은 성공·거절만 오고 종목이 없으므로(`KiwoomStreamProtocol.java:179-180`) 그 요청에 담긴 종목 전체에 같은 응답을 적용한다(QA PR #245 Q1).
4. 생존 줄: 1초마다 `{"hb":{"at":"…Z","sources":{"KIWOOM-WS":{"state":"CONNECTED","lastRx":"…Z"}},"dropped":0}}`. 장 밖이나 이벤트가 없는 때도 온다. `dropped`는 이 연결에서 버린 누계.
   - `lastRx`는 그 소스가 **시세 메시지**(체결·호가·상태, 관심 종목뿐 아니라 그 소스가 받는 모든 종목)를 마지막으로 받은 게이트웨이 시각이다. PING·PONG·등록 응답 같은 제어 메시지는 넣지 않는다(서버가 시세만 멈추고 PING을 계속 보내는 경우를 잡기 위해). 소스 상태(`state`)는 지금 코드 그대로(`idleTimeout` 90초 기준)라 연결된 채 시세가 멈추면 `CONNECTED`로 남으므로, 엔진은 `lastRx`로 판단한다(2.6, QA PR #245 발견 1).
   - 생존 줄은 이벤트 줄과 **같은 큐**를 탄다(앞지르지 않음). 그래서 큐가 밀리면 생존 줄의 `at`도 늦게 도착하고, 엔진은 그 나이로 전달 지연을 안다(2.6).

### 2.4 관심 종목의 구독 순위(`SourcePlanner` 확장)

종목을 네 등급으로 놓고 앞 등급부터 자리를 준다.

| 등급 | 내용 | 한도를 넘으면 |
|---|---|---|
| P0 | 엔진 `protect` | 활성 소스가 차면 FAILOVER라도 쓸 수 있는 다음 소스로 넘긴다(지금 `held`와 같은 규칙). 그래도 자리가 없으면 `unserved`(`CAPACITY`/`NO_SOURCE`). P0는 다른 등급 때문에 빠지지 않는다 |
| P1 | `watchlist.json`의 `held` | 지금 규칙 그대로 |
| P2 | 엔진 `entry` | 뒤에서부터 뺀다. 빠지면 `unserved`(`CAPACITY`) |
| P3 | `watchlist.json`의 `candidates` | 지금 규칙 그대로(뒤에서부터 제외) |

- P1과 P2의 순서, 그리고 P0·P2를 위해 소스 한도에서 미리 비워 둘 자리 수(실전 몫)는 **Q-060의 결정**이다(2.10). Q-060 전 구현 기본값은 위 표(P0 > P1 > P2 > P3, 미리 비워 두는 자리 없음)이고, 실전 활성화는 Q-060 결정 뒤에만 한다(7단계 계획 D13).
- 장중에 P0가 늘어 자리가 모자라면 P3(실험실·녹화용 후보)가 뒤에서부터 빠진다. 빠진 종목에는 지금 코드 그대로 녹화·실험실 쪽에 공백(`SOURCE_SWITCH`)이 남는다(녹화 형식·`GapReason` 불변). 실험실이 실전에 양보하는 방향이라 절대 규칙 6과 맞다. 실시간 모의 계좌의 `boards` 종목이 빠지면 6단계 결과에 공백으로 드러난다(2.9).
- 관심 변경은 **1초에 한 번까지** 모아서 적용한다 `[가정]`(증권사 등록 요청 폭주 방지). 다만 P0에 **새로 들어온 종목**은 모으지 않고 바로 적용한다(매수 주문 직후 보호 공백을 줄이기 위해).
- 엔진 연결이 끊겨도 마지막 관심은 **60초 동안 유지**한다 `[가정]`(엔진 재기동 사이 구독을 풀었다 다시 거는 일을 없앰). 60초 안에 엔진이 다시 붙어 관심을 보내면 그것으로 바꾸고, 지나면 P0·P2를 비운다. 게이트웨이는 관심을 파일로 남기지 않는다. 게이트웨이가 재기동하면 엔진이 다시 붙을 때 관심을 다시 보낸다(관심의 원본은 엔진이다).
- 허브가 배정 변경 때 직접 만드는 공백(`MarketHub.recordGap`, `SOURCE_SWITCH`·`DISCONNECTED`)도 녹화·실험실과 같이 엔진 전달에 넣는다(관심 종목이면).
- 소스 쪽 구독 변경은 **바뀐 종목만** 등록·해제해야 한다(지금 `MarketHub.apply`는 소스별 전체 집합으로 새 `Subscription`을 만든다. 소스가 실제로 증권사에 차분만 보내는지 G2에서 확인하고, 아니면 차분 등록으로 고친다). 남는 종목의 수신이 끊기지 않아야 한다.

### 2.5 게이트웨이는 기다리지 않는다, 엔진 몫을 먼저 넣는다

- 수신 콜백 순서: **엔진 전달 → 녹화 → 실험실 전달**. 셋 다 큐에 넣기만 한다. 녹화 내용·순번은 바뀌지 않는다(순서는 같은 콜백 안의 넣는 순서일 뿐).
- 엔진 전달 `publish`는 예외를 던지지 않는다. 안에서 난 예외(`Error` 제외)는 잡아 로그 횟수만 세고, 같은 콜백의 녹화·실험실 전달은 그대로 이어진다(실험실 `FeedServer.publish`와 같은 격리, risk-ops PR #245 R5). G1 시험으로 고정한다.
- 엔진 전달 `publish`는 수신 스레드에서 ① 관심 집합 확인(불변 스냅샷을 volatile로 바꿔 끼움, 잠금 없음) ② 고정 크기 큐에 넣기만 한다. 관심 밖 종목은 큐에 넣지 않는다(엔진 쪽 양이 관심 종목만큼으로 줄어 R3 인코딩 비용이 작다).
- 큐 20,000줄 `[가정]`(관심 128종목 × 초당 수십 건을 몇 초 버팀). 차면 그 줄을 버리고, 종목마다 처음 버린 시각만 기억했다가 다음에 넣을 수 있을 때 `GAP(CONSUMER_OVERFLOW, src "ENGINE-FEED")`를 먼저 넣는다. 버리는 경로는 종목별 고정 칸에 시각만 적어 **버릴 때마다 객체를 만들지 않는다**(QA R1의 원인으로 본 할당 줄이기).
- 쓰기 스레드는 높은 우선순위 데몬 하나. 한 줄 쓰기가 10초 넘게 끝나지 않으면(엔진이 읽지 않음) 연결을 끊는다 `[가정]`(실험실 30초보다 짧게: 엔진은 끊김을 알아야 보호 폴링으로 넘어간다).
- **지연 합격 기준(QA R1)**: 읽지 않는 실험실 받는 쪽 4개와 녹화가 함께 도는 조건에서 ① 수신 스레드의 엔진 `publish` 한 번 p99.9 ≤ 50µs, ② 수신 콜백 진입 → 엔진 받는 쪽 줄 해석 끝 p99 ≤ 10ms, 최대 ≤ 200ms `[가정]`. 컨테이너 시험(G1)과 사용자 PC 측정(7단계 절차서 I1)으로 확인한다. 못 넘으면 G5(실험실 전달을 수신 스레드 밖으로)를 실전 활성화 전에 한다.

### 2.6 엔진 쪽 받는 계약(묶음 E가 구현, 여기서는 입력 계약만)

- 받는 스레드 하나가 줄을 읽어 ① 종목별 **최근 가격 표**(마지막 체결가·호가·수신 시각·출처)를 바로 고치고 ② 계좌 워커 큐에 이벤트를 넣는다. **손절 감시는 최근 가격 표를 읽는다.** 계좌 큐가 밀려도 보호 판단은 밀리지 않는다. 계좌 큐가 넘치면 그 계좌는 신규 진입만 멈추고(공백 표시) 보호는 계속한다.
- 종목 상태와 보호 폴링 시작 조건. 아래 중 하나면 그 종목은 **바로 보호 폴링**으로 감시하고 신규 진입을 막는다(장애표 #1·#2를 종목 단위로 푼 것):

| 상태 | 조건 |
|---|---|
| 전달 끊김 | 연결 없음, 인사 실패, 생존 줄이 3초 넘게 없음(장애표 #1 "수신 간격 > 3초") |
| 미구독 | 상태 줄 `unserved`에 있음(이유 무관), 또는 관심을 보냈는데 3초 안에 `served`에 안 나타남 |
| 소스 끊김 | 그 종목 담당 소스 상태가 `CONNECTED`가 아님, 또는 **정규장 접속매매 구간에 그 소스 `lastRx`가 3초 넘게 지남**(장애표 #1 "수신 간격 > 3초", 소스가 연결된 채 시세만 멈춘 경우, QA PR #245 발견 1). 단일가 구간(장 시작·마감 동시호가)과 장 밖은 이 3초 조건을 쓰지 않고 상태만 본다(그 구간에는 거래소가 체결을 내지 않아 수신 간격이 길다 `[추론]`). 구간 판단은 `MarketRules`·캘린더의 보호용 질의(S6)로 한다 |
| 전달 지연 | 받은 이벤트 줄의 `rx`(게이트웨이 수신 시각)나 생존 줄 `at`이 엔진 시계보다 1초 `[가정]` 넘게 늦음(큐가 밀림). 그 종목(생존 줄이면 모든 보호 대상)을 지연이 풀릴 때까지 공백처럼 다룬다(QA PR #245 Q2). 두 프로세스는 같은 PC 시계를 쓴다 |
| 공백 | 그 종목 `GAP` 줄을 받음(어느 이유든). 공백 뒤 첫 이벤트가 올 때까지 |
| 조용함 | 정규장 중 그 종목 마지막 이벤트가 T_quiet보다 오래됨 |

- 소스 단위 3초("소스 끊김")와 종목 단위 T_quiet("조용함")은 따로 둔다. T_quiet을 거래가 드문 종목에 맞춰 늘려도 소스 전체가 멈춘 경우는 3초로 잡는다(QA PR #245 발견 1 시나리오 3). G0은 종목 단위와 함께 **소스 단위 시세 수신 간격 분포**(정규장 접속매매 구간 p99·p99.9·최대)도 재서 3초가 오탐을 내지 않는지 확인한다. 오탐이 나면(감시 종목이 적어 소스 전체가 3초 조용한 때가 있음) risk-ops가 값을 정하되, 장애표 #1을 바꾸는 일이므로 그 변경 제안과 함께 한다.
- T_quiet의 **기본값은 장애표 #15·기획서 RSK-08의 `market-data.symbol-gap`(기본 30초 `[가정]`)** 이다. 조용함 조건은 #15를 엔진 입력 계약에 옮긴 것이고, 새 기준을 만들지 않는다(risk-ops PR #245 R1). G0에서 LIVE01 녹화로 정규장 종목별 이벤트 간격 분포(p99·p99.9)를 재고, risk-ops가 그 근거로 T_quiet(종목별로 다르게 둘지 포함)을 확정한다. **확정 전에는 실전 활성화를 하지 않는다**(7단계 절차서 I1의 활성화 전 확인 항목). 30초는 소스는 연결된 채 한 종목만 조용히 빠진 경우를 잡는 데 길 수 있어서(그동안 마지막 가격으로 손절을 판단: 손절이 늦어지는 방향) 줄이는 쪽이 기본이다. 조용함 폴링은 종목이 정말 조용한지(구독이 조용히 빠졌는지)를 가르는 확인용이다.
- 보호 폴링이 실패하거나(한도·오류) 그 종목 가격이 T_fail(10초 `[가정]`) 넘게 아무 경로로도 없으면 그 계좌는 장애표 #2 대응(신규 진입 전면 중단)과 긴급 알림(2.8).
- 신규 진입은 그 종목이 `served`이고 위 표 어디에도 해당하지 않을 때만 낸다. 매수 주문 전에 그 종목을 `protect`에 먼저 넣는다(관심 → `served` 확인 → 주문). `served` 확인이 3초 안에 오지 않으면 그 진입은 보류한다.
- 엔진은 받은 이벤트 전체를 따로 기록하지 않는다(디스크·저장소 크기, ADR-015는 시세를 담지 않음). 대신 주문 의도 기록에 **그 판단에 쓴 이벤트의 `src`·`srcSeq`·`rx`**(보호 폴링이면 폴링 소스·응답 시각)를 남겨 게이트웨이 녹화와 대조한다(변경 제안 6장 2번, ADR-015 B4).

### 2.7 연결 수명

|---|---|---|
| 엔진 기동 | — | 접속 → 인사 → 관심 전송. 실패하면 1초 간격으로 다시(로그는 1·2·4·8…번째만, ADR-010 R3과 같음) |
| 엔진 재기동 | 끊김 뒤 60초 관심 유지(2.4) | 다시 붙어 관심 전송. 처음 상태 줄을 받을 때까지 보유 종목은 보호 폴링 |
| 게이트웨이 재기동·크래시 | 기동 때 `watchlist.json`만으로 배분, 엔진이 붙으면 관심 반영 | 끊김 감지 → 모든 보호 대상 보호 폴링, 신규 진입 중단, 재접속 시도. 다시 붙으면 관심 재전송 → `served`와 이벤트가 오면 종목별로 실시간으로 돌아감 |
| 엔진이 느림 | 큐 넘침 → 버림·공백, 10초 멈춤이면 끊음 | 공백 받은 종목은 보호 폴링(2.6) |
| 소스 전환(키움 끊김 등) | 지금처럼 재배분·`GAP` + 상태 줄 | 해당 종목 보호 폴링 → 새 소스 이벤트로 복귀 |

### 2.8 D11: `unservedHeld` 알림과 구독 거절

- 수준은 risk-ops 검토(PR #245)로 아래와 같이 고쳤고, 최종 확정은 재검토 판정으로 한다.
- **알림은 엔진이 보낸다.** 엔진이 실전 보유 여부와 보호 폴링이 덮고 있는지를 아는 유일한 프로세스라서다. 게이트웨이에 알림 라이브러리를 넣지 않는다(게이트웨이는 가볍게, 알림 연결은 D-100의 감시·엔진 두 곳 그대로).
- 알림 수준:
  - **실시간으로 받는 보호 대상이 0개**(모든 보호 대상이 보호 폴링 중)인 상태가 3초를 넘음: **긴급**(URGENT). 전달 끊김(생존 줄 3초 없음)과 유일한 게이트웨이 소스(첫 실전 구성에서는 키움) 끊김이 여기에 든다. 장애표 #2 "모든 실시간 시세 끊김 → Slack 긴급"과 같다(risk-ops PR #245 R2). 다시 하나 이상을 실시간으로 받으면 **정보**로 회복 알림.
  - 일부 보호 대상만 실시간에서 빠졌고 보호 폴링이 가격을 받고 있음: **정보**(INFO). 같은 종목·같은 이유는 30분에 한 번 `[가정]`.
  - 보호 대상 종목이 T_fail 넘게 어느 경로로도 가격이 없음: **긴급**.
  - 관심 줄 거부(`rejected`), 형식 버전 불일치, 엔진 소켓에 다른 받는 쪽이 붙어 있어 연결 거절: **긴급**.
- 게이트웨이는 `watchlist.json`의 `held`만 못 받을 때 지금처럼 ERROR 로그만 남긴다(실전 보유가 아님).
- **구독 거절 처리**(G3): 프로토콜이 거절 응답에서 종목을 알아낼 수 있으면(한국투자 응답의 `tr_key` 되돌림 `[가정]`) 그 종목을, 알아낼 수 없으면(키움 `REG` 응답 형식 미확인) **그 등록 요청에 담긴 종목 전부**를 "그 소스에서 거절됨"으로 허브에 알린다. 허브는 그 종목을 그 소스에서 빼고 다시 배분한다(다음 쓸 수 있는 소스). 그 소스의 한도는 지금 등록된 수로 낮춰 보고, 소스가 다시 연결되면 원래 한도로 돌린다. 같은 종목·같은 소스 재시도는 60초에 한 번까지 `[가정]`. P0 종목이 모든 소스에서 거절되면 `unserved`(`REJECTED`)로 엔진에 알린다. 거절 응답 형식은 Q-015 실측(사용자 PC)으로 확인한다.

### 2.9 6단계(LIVE01) 영향과 배포 시점

- 엔진이 붙지 않으면 P0·P2가 비어 있어 배분·녹화·실험실 전달이 지금과 같다. G1·G2 PR은 "엔진 없음일 때 녹화 줄과 실험실이 받은 줄이 바이트로 같음" 시험을 넣는다(기존 `GatewayFeedTest` 확장).
- 그래도 게이트웨이 jar 교체는 재기동이 필요하고 LIVE01 녹화에 재기동 공백이 생길 수 있다. 실전 엔진이 시세를 받기 시작하는 것은 묶음 E(1월 `[추론]`)이므로, **사용자 PC의 게이트웨이 교체는 LIVE01 종료(2026-12-18) 뒤**를 기본으로 한다. 그 전에 교체해야 하면 6단계 스레드와 맞춰 장 시간 밖(주말)에만 한다(7단계 계획 5장 위험).
- 구독 거절 재배분(G3)은 키움 등록이 거절될 때 LIVE01 종목의 배정을 바꿀 수 있다. 지금은 거절돼도 아무 일도 안 하는(녹화에 그 종목이 비는) 상태라 결과가 나빠지지는 않지만, 녹화 동작이 바뀌므로 G3도 같은 배포 시점을 따른다.

### 2.10 D13: watchlist 구독 상한(Q-060, 선택지만)

이 ADR은 Q-060을 정하지 않는다. 각 선택지가 2.4 표에 어떻게 들어가는지만 적는다(추천과 근거는 [7단계 준비 계획](../team/stage-7-readiness-plan.md) 4.2 Q-060 그대로).

| Q-060 선택지 | 2.4에 들어가는 방식 | 이 설계에서 생기는 차이 |
|---|---|---|
| ① 상한 = 세션 한도 − 실전 몫(추천) | 실전 몫 K자리를 P0·P2에 미리 비워 두고, P1+P3 합계 ≤ 한도 − K를 게이트웨이 기동 검사로(실전 계좌가 있을 때 넘으면 기동 거부) | 첫 실전이 한국투자라 게이트웨이 소스는 키움 하나: 한도는 키움 세션 한도(200종목 `[사실]` 또는 따로 세면 100 `[가정]`) 하나로 계산된다. FAILOVER 넘김 자리가 없다 |
| ② 실전 동안 watchlist를 `boards`로 줄임 | P3를 사용자가 줄임, 순위 규칙은 그대로 | 단타 선정 실험이 멈춤 |
| ③ 상한 없이 `unserved` 알림·보호 폴링으로만 | 위 표 기본값 그대로 | 장중 P0 증가 때 P3가 빠지는 일이 잦아지고, 자리가 끝나면 보호를 폴링에 기댐(버림 쪽) |

- P1(`held`)과 P2(`entry`)의 순서도 Q-060과 같이 정한다: ①이면 P2를 실전 몫 안에서 보장, ②·③이면 표 기본값(P1 > P2).

### 2.11 장애 테스트 1번(1순위 시세 강제 차단)을 이 구성에서 시행하는 방법

- 첫 실전 구성(실전 계좌 한국투자, 게이트웨이 소스 키움 하나)에는 2순위 실시간 소스가 없어 장애 테스트 1번의 "3초 내 전환"을 그대로 시행할 수 없다(risk-ops PR #245 R3).
- 이 구성에서 1번은 다음으로 시행하고 합격을 판정한다: 장중 키움 연결을 강제로 끊으면 **3초 안에 모든 보호 대상이 보호 폴링으로 넘어가고, 모든 실전 계좌의 신규 진입이 멈추며, 손절 감시 공백이 없고(보호 폴링 가격으로 손절 판단이 이어짐), 2.8의 긴급 알림이 나간다.** 키움이 돌아오면 종목별로 실시간 복귀, 신규 진입 재개, 회복 정보 알림.
- 실전 계좌가 게이트웨이 소스 증권사(키움·한국투자, D-059로 토스는 게이트웨이 소스가 아님)에 없어 게이트웨이 소스가 둘인 구성에서는 원래 1번("3초 내 전환")을 그대로 쓴다(architect PR #245 재검토 N5).
- 주입은 **두 가지를 모두** 시행해 각각 합격해야 한다(QA PR #245 발견 1 시나리오 2): ① 연결 닫힘(게이트웨이 쪽 키움 소켓을 닫거나 프로세스가 연결을 끊음) ② 무응답(키움 서버 주소로 가는 패킷을 방화벽으로 버려 FIN 없이 수신만 멈춤). ②는 소스 상태가 90~135초 `CONNECTED`로 남으므로 `lastRx` 3초 조건(2.6)으로만 합격할 수 있다. 정규장 접속매매 구간에 시행한다.
- 장애표 7장 1번 행 문구 변경은 변경 제안(6장 1번)이다. **그 변경이 원본 장애표에 반영되기 전에는 이 구성의 실전 활성화 판정을 하지 않는다**(판정 기준이 둘이 되지 않게, QA PR #245 Q5, 2.12).

### 2.12 실전 활성화 전 확인 항목(7단계 절차서 I1로 옮길 것)

이 설계가 실전 활성화 전에 끝나 있어야 한다고 정하는 것들이다. I1 절차서에 항목으로 옮긴다(risk-ops PR #245 재검토 N1, QA Q3·Q5).

1. T_quiet 확정(G0 근거, 2.6). 확정 전 활성화 안 함.
2. 소스 단위 3초 기준이 G0 분포에서 오탐을 내지 않음(2.6).
3. 보호 폴링 예산: **실전 보유 종목 수 상한 × (1 / 폴링 주기) ≤ 실전 계좌 증권사 REST 한도 중 보호 폴링 몫**(주문·조회 몫을 뺀 것). 첫 실전 구성(한국투자 REST 초당 20건 `[사실: 공식 샘플 주석]`, market-data-limits.md 1장)에서 `protect` 상한 64종목을 1초 주기로 돌 수 없으므로, 보유 종목 수 상한(Q-008)과 폴링 주기를 이 식으로 정한다. 64는 게이트웨이 줄 형식 상한일 뿐 보호 가능 수가 아니다.
4. 2.11 두 가지 주입 합격, 그리고 장애표 7장 1번에 2.11 기준 반영(6장 1번).
5. 3-R 뒤 엔진 시세 연결이 다시 붙음(2.2).
6. Windows에서 `run/engine-feed.sock` 열기·권한(4장).

## 3. 대안 검토

| 대안 | 내용 | 판단 |
|---|---|---|
| A. 채택 | 엔진 전용 소켓 + 관심 종목 전체 교체 + 상태·생존 줄 + 엔진의 보호 폴링 | 프로세스 분리(D-013)와 장애표 #1·#2·#9를 그대로 따른다. 엔진이 "구독됐는지·살아 있는지"를 종목 단위로 알 수 있다. 실험실과 자리·정책이 섞이지 않는다 |

| C. 실험실 소켓에 `client:"engine"`으로 붙음 | 코드가 가장 적음 | 4자리를 아무 프로세스나 차지(N6), 실험실 버림·30초 정책을 그대로 받음, 관심·상태가 없어 장중 보유 종목을 구독시킬 수 없음, 엔진의 `marketdata.feed` 의존(N5). 버림 |

| E. 엔진이 느리면 게이트웨이가 기다림(진짜 무손실) | 공백 없음 | 엔진이 느려지면 게이트웨이 수신 스레드가 멈춰 증권사가 연결을 끊고(무응답), 녹화·실험실까지 멈춘다. 결국 엔진도 시세를 잃는다. 버림. 이 ADR의 "무손실"은 **모르게 잃는 것 0**(잃으면 종목마다 공백으로 알리고 보호 폴링으로 넘김)이다 |

| H. 상태 줄 없이 엔진이 이벤트 유무로 판단 | 줄 형식이 단순 | 조용한 종목과 구독이 빠진 종목을 가를 수 없다. 버림 |

## 4. 위험과 한계

- **게이트웨이 소스가 하나**: 첫 실전이 한국투자라 게이트웨이는 키움만 쓴다. 키움이 끊기면 모든 보유 종목이 보호 폴링으로 간다(장애표 #2). 보호 폴링 속도는 한국투자 REST 한도(초당 20건 `[가정]`, [market-data-limits.md](../research/market-data-limits.md) 1장·5장)를 주문·조회와 나눠 쓴다. 보유 종목 N개를 1초마다 물으면 초당 N건이라, 실전 보유 종목 수 상한(Q-008·Q-060)과 보호 폴링 몫(ADR-003 R8)을 함께 정해야 한다.
- **같은 OS 사용자 프로세스**: 엔진보다 먼저 소켓 자리를 차지하면(1자리) 엔진은 실시간을 못 받고 보호 폴링으로 돈다(서비스 거부, 긴급 알림으로 드러남). 게이트웨이보다 먼저 같은 경로에 가짜 서버를 열면 거짓 가격을 줄 수 있다. 같은 사용자 권한의 악성 프로그램은 ADR-006 위협 표와 같은 범위 밖 `[가정]`이지만, 거짓 가격은 두 방향으로 위험하다: 낮은 가격으로 거짓 손절 매도가 나거나, 정상처럼 보이는 가격으로 실제 급락에도 손절이 나지 않는다. **손절 발동 전 REST 현재가 한 번 대조**(앞 방향)와 **보유 종목 주기적 REST 표본 대조**(뒤 방향)를 묶음 C·E에서 risk-ops가 검토한다(6장 4번, risk-ops PR #245 R4).
- **관심 → 구독 사이 공백**: 증권사 등록 응답까지 수백 ms~수 초 `[가정]`. 매수 전 `protect` 먼저·`served` 확인 뒤 주문(2.6)으로 줄이지만, 부분 체결로 보유가 생긴 직후 구독이 거절되면 그 종목은 보호 폴링으로만 감시된다.
- **T_quiet·T_fail·큐 크기·지연 기준**은 `[가정]`이다. G0(녹화로 이벤트 간격 측정)와 G1 시험, 사용자 PC 측정으로 바꾼다.
- **구독 거절 종목 식별**: 키움 거절 응답에 종목이 없으면 등록 묶음 전체를 거절로 보아 실제보다 많은 종목을 다른 소스·보호 폴링으로 보낸다(보수 쪽).
- **Windows**: AF_UNIX 소켓 권한·경로 길이는 ADR-006·ADR-010과 같은 `[가정]`. 6단계 실험실 소켓이 사용자 PC에서 열린 것이 같은 방식의 실측 근거다(ADR-010 5장).
- **게이트웨이 재기동 때 P0가 잠시 없음**: 게이트웨이는 관심을 파일로 남기지 않으므로 재기동 직후부터 엔진 재접속·관심 재전송까지 엔진 보유 종목은 구독되지 않는다. 그 동안 엔진은 전달 끊김으로 보호 폴링 중이다.

- **같은 PC 시계**: 전달 지연 판단(2.6)은 게이트웨이와 엔진이 같은 시스템 시계를 쓴다는 가정에 기댄다. 시계가 바뀌면(NTP 보정) 잠깐 지연·공백으로 보일 수 있다(보호 쪽 오탐).

1. 엔진 소켓에 두 번째 연결 → 인사 없이 닫힘, 첫 연결은 계속 받음.

5. 엔진이 읽지 않음 → 게이트웨이 `publish`가 기다리지 않고(10초 상한 안) 녹화 줄 수 그대로, 다시 읽으면 종목별 `CONSUMER_OVERFLOW`(`ENGINE-FEED`) 공백, 10초 멈춤이면 끊김.
6. 지연 기준(2.5): 읽지 않는 실험실 받는 쪽 4개 + 녹화 + 엔진에서 엔진 `publish` p99.9·전달 지연 p99·최대.
7. P0 우선: 소스 한도가 찬 상태에서 P0 추가 → P3 뒤에서 빠지고 P0는 `served`. P0가 한도를 넘으면 다음 소스로, 없으면 `unserved`(`CAPACITY`).
8. 엔진 끊김 60초 안 재접속 → 증권사 등록 해제·재등록 0회. 60초 뒤 → P0·P2 해제.
9. 엔진 없음 → 녹화 줄·실험실 받은 줄이 지금 코드와 바이트로 같음(`GatewayFeedTest` 확장).
10. 생존 줄 1초 간격, 소스 끊김이 `sources`에 반영.
11. 구독 거절(가짜 프로토콜): 거절 종목이 다른 소스로 옮겨지고 `GAP` 남음, 모든 소스 거절이면 `unserved`(`REJECTED`), 같은 종목 재시도 60초 간격.
12. 엔진: 생존 줄이 3초 없으면 모든 보호 대상이 보호 폴링으로, 신규 진입 거부(G4).
13. 엔진: `unserved`·`GAP`·소스 끊김 종목만 보호 폴링, 나머지는 실시간 유지(G4).
14. 엔진: 계좌 큐가 넘쳐도 최근 가격 표로 손절 판단이 늦지 않음(G4).
15. 엔진: 버전 불일치·관심 거부·소켓 선점 → 긴급 알림(G4).
16. 재접속 `rev`: 엔진 끊김 뒤 60초 안에 다시 붙어 `rev:1`을 보내면 게이트웨이가 받고, 그 관심 적용 전 상태 줄은 `rev:0`. 엔진은 `rev:0` 상태 줄의 `served`로 새 관심 종목의 매수를 내지 않음(G1·G4, architect PR #245 R3).
17. 엔진 전달 안에서 예외가 나도 같은 이벤트의 녹화·실험실 전달은 그대로(G1, risk-ops R5).
18. 배정 변경 때 남는 종목의 수신 공백 0(소스별 전체 재구독이 남는 종목을 끊지 않음, G2, architect N3).
19. 엔진: 소스 연결은 정상인데 한 종목 이벤트만 T_quiet(기본 `symbol-gap`) 넘게 없으면 그 종목만 보호 폴링·신규 진입 막음(G4, risk-ops R1).
20. 엔진: 유일 소스 끊김·전달 끊김으로 실시간 받는 보호 대상이 0개가 3초 넘으면 긴급 알림 한 번, 회복 때 정보 알림(G4, risk-ops R2).
21. 소스 상태가 `CONNECTED`인 채 시세 수신만 멈춤(가짜 소스가 PING만 보냄): 생존 줄 `lastRx`가 멈추고, 엔진은 정규장 접속매매 구간이면 3초 안에 그 소스 담당 보호 대상을 보호 폴링·신규 진입 중단, 유일 소스면 긴급 알림. 단일가 구간에는 이 조건으로 넘기지 않음(G1·G4, QA 발견 1).
22. `served`는 등록 성공 응답 또는 그 종목 이벤트 뒤에만. 배정만 되고 응답 전이면 `PENDING`, 엔진은 그 종목 매수를 내지 않음(G2·G4, QA Q1).
23. 엔진 큐를 일부러 밀리게 해 이벤트 `rx`·생존 줄 `at`이 1초 넘게 늦으면 그 종목(생존 줄이면 전체) 보호 폴링, 따라잡으면 복귀(G4, QA Q2).
24. 실행 중 `run/engine-feed.sock` 삭제 → 게이트웨이가 1초 안에 다시 만들고, 붙어 있던 엔진 연결은 유지, 새 연결도 받음(G1, QA Q4).

## 6. 변경 제안(다른 역할 산출물, 이 PR에서 고치지 않음)

3. **config-keys.md(architect)**: 이 ADR은 새 설정 키를 만들지 않는다(값은 상수, `[가정]`). Q-060 ①이 정해지면 실전 몫 K 키를 그때 제안한다.

## 7. 검증

- 이 PR은 문서만이다. 1장의 [사실]은 main `53482a5` 코드를 직접 읽은 결과다(파일·라인 표기). 줄 형식과 순위 규칙은 G1·G2 시험(5장)으로 검증하고, 지연 기준은 G1 시험과 사용자 PC 측정 전에는 **검증하지 못했다**.
