**판정: 승인** (막는 항목 없음. 권고 R1~R6은 이 ADR에 고치거나, 늦어도 PR C 구현에서 반영하고 PR C strategy-researcher 검토에서 확인한다)

## 권고

### R1. LIVE02 N 표가 끝나지 않거나 999를 넘는 경우를 정할 것(5.3)

`[사실]` 5.3 정의는 "N_k = 21m − 1 이상인 가장 작은 N 중 P(이항(N, 1 − q) ≤ 20m − 2) ≤ 0.01"이다. 대조군 시드가 모두 왕복 0건(x = N)이면 q = 1이라 그런 N이 없고, q가 0.5 근처만 돼도 N이 수백이 넘어 F3 상한 999를 넘을 수 있다. 계획 6.2 1번은 점추정 x/N ≥ 0.5 묶음을 빼라고 한다. 그래서 N 표에서 (가) 점추정 ≥ 0.5 묶음은 N 대신 "묶음 빼기(계획 6.2 1번)"로 적고 계산하지 않으며, (나) 그 밖에도 999까지 찾아 없으면 "999 초과(F3로 등록 불가)"로 적게 정할 것. 시험에 x = N과 999 초과 경우를 하나씩 넣을 것.

### R2. P2·판정 불가 경계를 L10과 같은 정확 산술로 정할 것(5.3 끝 글머리)

5.3 끝은 "p 값과 Clopper–Pearson 상한은 `double`로 계산해도 결정론적"이라 적어 P2 통과 비교도 `double`로 하라는 것으로 읽힌다. 지금 등록 값(alpha 0.05, family-size 4, N′ + 1 = 80, k = 0이면 p = 0.0125가 문턱과 정확히 같음)에서는 `double`도 같은 답을 낸다(분수와 대조해 family-size 1~10, alpha 0.01·0.025·0.05·0.1, N′ ≤ 2000에서 어긋남 없음, 직접 계산). 그래도 판정 경계는 L10처럼 정수·`BigDecimal`로 하는 것이 안전하다: 통과 ⇔ (k+1)·family-size ≤ alpha·(N′+1), 판정 불가 ⇔ N′ + 1 < ⌈family-size ÷ alpha⌉(`BigDecimal` 나눗셈 올림). `double`은 화면에 쓰는 p 문자열에만 쓰도록 적을 것.

### R3. 이항·베타 계산에 `StrictMath`(또는 정확 산술)를 쓸 것(5.3 끝 글머리)

"Java 17 이후 엄격 부동소수라 결정론적"은 사칙연산에만 맞다. `Math.pow`·`Math.exp`·`Math.log`는 명세상 1 ulp 오차를 허용하고 JIT 내장 구현이 플랫폼마다 달라도 된다(`StrictMath`만 비트 단위로 고정) `[사실]`(Java SE `Math`·`StrictMath` 클래스 설명). 같은 PC에서는 같지만 CI와 사용자 PC가 다르면 Clopper–Pearson 이분법 끝자리나 N 표의 "≤ 0.01" 경계가 드물게 갈릴 수 있다 `[추론]`. `StrictMath`나 `BigDecimal` 정확 누적을 쓰도록 계약에 적을 것.

### R4. N 표에 쓰는 q의 반올림 방향을 정할 것(5.3 q̂·N 표)

q̂ 상한을 "소수 4자리 반올림"으로 적는데, N 표가 반올림 전 값을 쓰는지 반올림 값을 쓰는지 없다. 반올림으로 q가 내려가면 경계에서 N이 하나 작아져 "판정 불가 확률 ≤ 1%" 보장이 깨질 수 있다. N 계산에는 반올림 전 값(또는 4자리 올림 값)을 쓰고, 파일에 적힌 q와 N을 사람이 다시 셀 때 같은 답이 나오도록 그 규칙을 표 아래에 적을 것(계획 6.2 "등록 PR에 같은 계산 스크립트 출력을 붙인다"를 이 표가 대신하므로).

### R5. 사전 검사 등록 값 검증을 채울 것(5.1 거절 목록)

다음이 거절 목록에 없다: `p3-min-segments`가 1 이상 `segments` 개수 이하, `min-round-trips` ≥ 1, `p3` 왼쪽 계좌가 같은 이름을 두 번 쓰지 않음, `p2` 계좌 묶음에 대조군이 있음(판정 대상 묶음 대조군 필수 규칙으로 이미 걸리면 그렇다고 적기). 결과 전 고정 값이 오타로 판정 불능이 되는 것을 막는 항목이라 4.3 "빨리 실패"와 같은 이유다.

### R6. 7.1 나란히 보기 칸의 출처를 바로 적을 것(3.2 마지막 글머리)

"판정 명령은 4장 '함께 적을 것' 표에 참고 계좌도 이미 같은 칸으로 내므로 그 값을 쓴다"인데, 계획 7.1 칸(총수익률, 왕복당 순손익, 왕복 수, PF, 장중 노출, 하루 평균 후보 수) 가운데 PF와 하루 평균 후보 수는 `judgement.md` 4장 표에 없다 `[사실]`(`LiveJudgement.java` 754~755행 칸: 총수익률·벤치마크·장중 노출·마감 노출·왕복·왕복당 순손익·블랙리스트 거절). PF는 2·3장(L2), 후보 수는 9장 선정 표에서 가져와야 한다. 문장을 "2·4·9장 값"으로 고치거나 4장에 두 칸을 더하는 것을 PR B 범위로 정할 것(더하면 키 없는 등록의 바이트 동일과 충돌하므로 고치는 쪽이 낫다 `[추론]`).

- D-131은 "상태: 확정", ADR-014와 ADR 목록은 "제안(D-131)"이다. 상태 표기는 architect 판단 영역이라 지적만 남긴다.
