# D-115 6단계 주간 점검·리플레이 확인은 녹화를 날마다 줄 단위로 읽는다(메모리가 기간과 상관없게)

- 날짜: 2026-10-19
- 상태: 확정 · **추천안 채택(자율)**(지침 8장). 실험 명령 쪽(`autotrade-sim`)만 바꾼다. 결과(보고서 바이트·종료 코드·데이터셋 버전)는 바꾸지 않는다. 실전 경로, 보호 경로(marketdata 포함), 장 시간 보호·정지 요청 관문(D-063·D-085)의 동작은 바꾸지 않는다.
- 담당: sim-engine 결정·구현. 교차 검토: architect(코드)
- 근거: 6단계 계획 선행 과제 T1(PR #175 `docs/strategy/stage-6-plan.md` 5장), [D-088](D-088-stage-6-weekly-check.md) 되돌릴 조건("8주 분량 누계 리플레이가 힙 4GB를 넘으면"), [D-076](D-076-live-feed-and-session.md) 리플레이 확인

## 문제

`runLiveWeeklyCheck`(D-088)와 `runLiveReplayCheck`(D-076)는 운용 기간 전체를 메모리에 올렸다 `[사실]`.

- `RecordedMarketDataSet`(입력 기록 리플레이)은 모든 날 이벤트를 목록으로 든다.
- `LiveWeeklyCheck`는 계좌 대조용 녹화(boards) 이벤트를 운용 시작부터 목록에 쌓고, 날마다 기록·녹화를 `RecordedDay`로 통째로 올리고 줄 열쇠(줄 전체 문자열)를 두 벌 만든다.
- 10단계 호가 이벤트 하나가 힙 약 1.6KB다(PR #175 실측). 3종목 하루 약 53만 건이면 하루 약 0.8GB이고 10종목 8주(LIVE01 10-26~12-18)는 수십 GB다 `[추론]`. 기본 힙 4GB면 LIVE01 첫 주간 점검(10-30)부터 모자랄 수 있었다.

## 결정

1. **녹화일을 줄 단위로 읽는다**: `RecordedDayStream`(sim)이 녹화일 하나를 줄을 쌓지 않고 순서대로 넘긴다. 검사(순번 연속, 정상 종료 녹화의 SHA-256, 비정상 종료의 잘린 마지막 줄·깨진 gzip 머리)와 요약(건수·공백 수·표시 없는 재기동 경계)은 `RecordedDay`(marketdata)와 같다.
2. **녹화 → 실험 입력 규칙을 한 곳으로**: `RecordingDayAdapter`(순번 매기기·재기동 공백 끼워 넣기, `REC-ADAPTER-V1` 그대로)를 목록 입력 `RecordedMarketDataSet`과 날마다 다시 읽는 입력 `StreamedRecordingDataSet`이 함께 쓴다. 같은 녹화면 이벤트·sequence·버전·녹화일 기록이 같다. `StreamedRecordingDataSet`은 열 때 한 번 다 읽어 검사하고, 다시 읽을 때마다 날마다 파일 해시가 그때와 같은지 본다(다르면 그날 이벤트를 넘기기 전에 멈춤).
3. **실행기는 목록이 아닌 입력에서 모든 Run을 함께 진행한다**: `MarketEventStream`(목록 입력 `MarketDataSet`도 이것을 따른다)을 받은 `SimulationExperimentRunner`는 입력을 두 번 읽는다. 첫 읽기로 순서를 확인하고 기간 안 이벤트의 거래일·첫 수신 시각·벤치마크를 구하고, 두 번째 읽기에서 이벤트마다 모든 Run을 조합 순서대로 한 걸음씩 진행한다. Run은 아무것도 공유하지 않으므로 Run별 결과는 목록 입력과 같다. 한 스레드로 돌고(병렬 수는 원래 결과에 영향 없음), 예열은 목록 입력만 받는다. 목록 입력(`MarketDataSet`)의 경로는 그대로다(다른 모든 실험 명령은 바뀌지 않음).
4. **주간 점검 하루 대조를 줄 단위로**: 기록을 읽어 공백·세션 구간·열쇠 수를 모으고, 녹화를 읽으며 녹화 줄마다 기록과 맞추고(녹화 순서), 기록을 다시 읽으며 기록 줄마다 녹화와 맞춘다(기록 순서). 같은 열쇠가 여러 번이면 앞에서부터 짝을 지으므로 목록으로 맞추던 때와 같은 줄이 빠짐·남음으로 나온다. 열쇠는 줄 문자열 대신 그 SHA-256 앞 128비트다. 계좌 대조용 녹화는 날짜·파일 해시·줄 수만 남기고 계좌 대조 때 같은 파일인지 확인하며 다시 읽는다. 읽기 전후 해시가 다르면 예전처럼 "아직 쓰이는 중"으로 거부한다.
5. **리플레이 확인**: 입력 기록을 `StreamedRecordingDataSet`으로 연다. 호가 단위 검사와 종목 모으기는 여는 읽기에서 한다(예전처럼 실행 전에 실패).
6. **실험실 세션 되살리기**(`LiveSession` 재기동): 이미 날마다 읽었지만 하루를 통째로 올렸다. 같은 어댑터로 줄 단위로 읽어 바로 계좌에 준다. 10종목 하루치(수 GB `[추론]`)를 실험실 힙(4GB)에 올리지 않는다. 읽다가 실패하면 예전처럼 세션을 열지 않는다.
7. **marketdata는 고치지 않는다**: `autotrade-marketdata`는 보호 경로라(지침 11장) 줄 단위 읽기를 sim에 두고, `RecordedDay`와 같은 결과인지 시험으로 고정한다. sim에 `jackson-databind`(meta.json 읽기)를 더했다. marketdata가 이미 런타임에 넣는 같은 라이브러리라 실행 클래스패스는 그대로다.

## 대안

| 대안 | 판단 |
|---|---|
| ① 줄 단위 읽기 + 실행기에서 Run 함께 진행(채택) | 메모리가 날 수·종목 수와 상관없다(아래 실측). 결과는 바이트 단위로 같다. 대신 같은 파일을 여러 번 푼다 |
| ② 하루씩만 올리기(날짜별로 목록을 바꿔 끼움) | 계좌 대조 목록은 없어지지만 10종목 하루치가 수 GB `[추론]`라 하루 대조(기록·녹화 두 날을 함께 듦)도 힙 4GB를 넘을 수 있다. 버림 |
| ③ 목록처럼 보이는 지연 목록(`get(i)`가 디스크를 읽음) | 실행기를 안 바꾸지만 Run마다 전 기간을 다시 풀어(8계좌면 10번 넘게) 훨씬 느리고, 여러 스레드가 위치를 따로 가져야 한다. 버림 |
| ④ 계좌 대조를 주 단위 창으로(D-088 되돌릴 조건) | 메모리는 줄지만 "운용 시작부터 누계" 비교(D-088)를 바꾸고, 하루 대조의 메모리 문제는 남는다. 버림 |
| ⑤ 줄 단위 읽기를 marketdata에 두고 `RecordedDay`가 그것을 쓰게 | 읽기 규칙이 한 벌이 되어 가장 깔끔하지만 보호 경로 변경이라 실전 관련 PR(사용자 머지·독립 QA)이 된다. 10-30 전에 끝내야 해서 버림. 후속 변경 제안으로 남김 |
| 줄 열쇠를 문자열 그대로 | 하루 줄 수백만 개 × 수백 바이트 × 두 벌이라 GB 단위 `[추론]`. 128비트 해시는 하루 수백만 줄에서 겹칠 확률이 무시할 만큼 작다 `[추론]` |

되돌릴 조건: 주간 점검이 너무 오래 걸리면(아래 시간 추정) 실행기의 첫 읽기를 없애거나(선정 없는 실험은 Run 시작을 첫 이벤트까지 미룸) 열 때 읽기와 합친다. 녹화 형식 버전이 바뀌면 `RecordedDayStream`도 함께 바꾼다.

## 위험과 한계

- **읽기 규칙이 두 벌**이다(`RecordedDay`와 `RecordedDayStream`). 같은 결과를 시험(`RecordedDayStreamTest`: 정상 종료·재기동·표시 없는 이전 녹화·잘린 마지막 줄·깨진 gzip 머리·순번 끊김·해시 불일치)으로 고정했지만, 한쪽만 고치면 어긋난다. 후속으로 marketdata에 옮긴다.
- **시간이 더 걸린다**: 같은 파일을 여러 번 푼다(주간 점검은 기록 3번 + 녹화 1번(대조), 입력 기록 3번 + 녹화 2번(계좌 대조)). 이 횟수는 압축 풀기만 센 것이고, 파일 지문·SHA-256 확인(어댑터 앞뒤 해시, 정상 종료 녹화의 해시 선검사, 주간 점검 지문 앞뒤)으로 같은 파일을 날마다 몇 번 더 읽는다(압축 안 푼 바이트라 풀기보다 가볍다 `[추론]`, architect N2). 컨테이너 실측으로 줄 풀기는 약 7.7만 줄/초다(10단계 호가, 96만 줄 12.5초). 10종목 하루 약 176만 줄 `[추론]`(3종목 53만 줄 비례)이면 LIVE01 8주차(40일 약 7천만 줄) 주간 점검은 약 2~3시간 `[추론]`이다. 첫 주간 점검(5일)은 약 20분 `[추론]`. 주말 점검이라 받아들이고, 6단계 첫 2주 실측 시간을 주간 점검과 함께 적는다(D-088 N4의 힙 실측과 같이).
- 열쇠 해시가 겹치면 서로 다른 두 줄을 같은 줄로 맞춘다. 확률은 하루 n줄에서 약 n²/2¹²⁹(n=10⁷이면 10⁻²⁵ 수준) `[추론]`.
- 주간 점검 도중 파일이 바뀌면(세션·게이트웨이가 아직 쓰는 중) 예전처럼 거부한다. 다만 거부가 그 파일을 다 읽은 뒤에 나므로 예전보다 늦게 알 수 있다.
- 실행기의 목록이 아닌 입력 경로는 Run 병렬을 쓰지 않는다. 계좌 수가 많은 실험(최대 128)을 이 경로로 돌리면 느리다. 지금 이 경로를 쓰는 것은 6단계 점검 명령뿐이다(계좌 8개).
- 게이트웨이 녹화 확인 명령(`:autotrade-app-gateway:replayCheck`, D-085)은 녹화일 하나만 읽어 이번 문제(기간 누적)에 해당하지 않아 바꾸지 않았다. 다만 그 하루를 통째로 올리므로 10종목 하루치는 PC 기본 힙(실제 메모리의 1/4)에 빠듯할 수 있다 `[추론]`. marketdata 후속과 함께 줄 단위로 바꾼다.

## 검증

- 결과 동일(결정론, 지침 5장)
  - 고치기 전 코드(main 5eaeabd)와 이 브랜치에서 `LiveWeeklyCheckTest`·`LiveSessionTest`를 돌려 주간 점검 보고서 12건과 리플레이 확인 결과 파일 7건을 뽑아 비교: **19건 모두 바이트 일치**(개발 쪽 직접 실행, 시험 코드에 덤프를 잠시 넣고 뺌).
  - `SimulationExperimentRunnerTest`: 목록이 아닌 입력과 날마다 다시 읽는 녹화 입력이 3단계 골든과 바이트 일치, 계좌 실패 격리·기간 자르기가 목록 입력과 같음, 두 번째 읽기가 다르면 결과 없이 실패, 정지 확인(첫 읽기 거래일마다·선정 전·Run 시작 전·Run 안 거래일 바뀜), 예열 거부.
  - `RecordedMarketDataSetTest`: 날마다 다시 읽는 입력이 이틀치·재기동·표시 없는 이전 녹화·줄 없는 구간 낀 이전 녹화에서 목록 입력과 이벤트·버전·녹화일 기록이 같음, 연 뒤 파일이 바뀌면 그날 이벤트를 넘기기 전에 멈춤.
  - `RecordedDayStreamTest`: `RecordedDay`와 줄·요약·거부 규칙이 같음.
  - `LiveWeeklyCheckTest`: 같은 내용 줄이 여러 번 나오는 날의 빠짐·남음 수가 개수 맞추기와 같음(`sameLineSeveralTimesIsMatchedByCountLikeTheOldListComparison`), 하루 대조 뒤 녹화가 바뀌면 계좌 대조가 이벤트를 넘기기 전에 거부(`recordingChangedAfterTheDayComparisonIsRejectedBeforeAnyEventReachesTheReplay`). architect R2.
- 메모리 실측(컨테이너 JDK 21, 개발 쪽 직접 실행): 2종목 × 하루 12만 줄 × 8일(기록·녹화 각 96만 줄, 10단계 호가 90%)을 주간 점검(계좌 대조 포함)으로 돌림.
  - 고치기 전: 힙 768MB에서 2일차 대조 뒤 `OutOfMemoryError: Java heap space`.
  - 고친 뒤: 힙 768MB 134초, **힙 256MB 145초**로 끝나고 두 보고서가 바이트로 같다(날 수를 늘려도 힙은 하루 열쇠 표 크기에만 따른다 `[추론]`).
- `./gradlew build`(ArchUnit·순수 모듈 검사 포함) 통과.

## 후속(변경 제안)

- **data-engineer(보호 경로, 실전 관련 PR)**: 줄 단위 읽기를 `autotrade-marketdata`로 옮기고 `RecordedDay.open`이 그것을 쓰게 해 읽기 규칙을 한 벌로 만든다. 같은 PR에서 게이트웨이 `replayCheck`도 줄 단위로 바꾼다. 그 뒤 sim의 `RecordedDayStream`과 jackson 의존을 지운다.
- **6단계 스레드(PR #175 후속)**: `docs/strategy/stage-6-plan.md` 5장 T1 행을 "D-115로 처리"로, 6장 또는 7장에 주간 점검 예상 시간(위)을 적는다. `docs/runbooks/stage-6-live-session.md` 주간 점검 절에 "힙은 기간과 상관없음, 시간은 기간에 비례"를 적는다. 이 PR은 두 파일을 고치지 않는다(6단계 스레드 몫).
- 다른 실험 명령(`runRecordingExperiment` 등)은 여전히 목록 입력이다. 녹화 기간이 길어지면 같은 입력(`StreamedRecordingDataSet`)으로 바꾼다. 그 전에 목록이 아닌 입력 경로에서 선정 있는 조합(`spec.hasSelections()`)의 골든 대조를 더한다(지금 이 경로를 쓰는 6단계 점검 명령은 선정 없이 돌아 닿지 않음, architect N1).
- 실행기 입력 계약과 실행 방식은 [ADR-004](../adr/ADR-004-simulation-engine.md) 2.4·3장에 반영했다(architect R1).
