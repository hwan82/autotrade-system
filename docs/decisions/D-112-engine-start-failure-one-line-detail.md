# D-112 실전 엔진 기동 실패 원인을 한 줄로 접어 표시(PR #169 독립 QA Q1·R2)

- 날짜: 2026-10-19
- 상태: 확정 · **추천안 채택(자율)**(지침 8장). 실전 엔진(`autotrade-app-engine`, 보호 경로)의 기동 실패 출력에서 원인 메시지의 줄바꿈 처리만 바꾼다. 판정(설정 오류·명령 채널·프로그램 오류), 종료 코드(2/1/1), 첫머리 문구, 로그에 예외 흐름을 남기는 범위(프로그램 오류만), 기동 순서, RealTradingGuard(모든 계좌 OFF로 시작), 명령 채널·잠금, 주문 경로는 바꾸지 않는다. 보호 경로라 사용자 머지로 확정한다.
- 담당: risk-ops 결정·구현. 교차 검토: architect(코드), risk-ops(실전 관련)
- 근거: [PR #169 독립 QA](../reviews/pr-169/qa.md) Q1·R2, [D-107](D-107-engine-start-failure-kinds.md) 4번과 "후속 반영(2026-10-18, PR #165 ...)" 남은 한계

## 문제

1. **R2(D-107 남은 한계)**: D-107 4번은 기동 실패를 로그 ERROR 한 줄과 표준 오류 한 줄로 남긴다고 약속하지만, `StartFailure.report`는 원인(`detail`)을 그대로 붙여 원인 메시지에 줄바꿈이 있으면 두 출력이 여러 줄이 된다. runbook(docs/runbooks/README.md 종료 코드 표)은 "로그의 ERROR 줄"을 보라고 안내하므로, 로그를 줄 단위로 걸러 보는 운영자(예약 실행)는 원인 뒷부분을 놓친다 `[추론]`. 지금 기동 단계에서 던지는 예외(경로 형식 오류, `ControlServer` 잠금, 알림 채널 이름 검사) 메시지는 코드상 한 줄이지만, 앞으로 기동 단계에 들어올 예외(JSON 파서, 운영체제 오류 등)는 보장이 없다 `[추론]`.
2. **Q1**: 표준 오류 시험이 첫머리와 줄 개수만 봐서, 줄 끝이 빠지거나(`println`→`print`, QA 변이 P3) 원인 뒤에 다른 글자가 붙어도(P8) 통과했다.

## 결정

1. 원인 메시지에 줄바꿈(`\R`: `\n`, `\r\n`, `\r`, VT(U+000B), FF(U+000C), U+0085, U+2028, U+2029)이 있으면 앞뒤 공백·줄바꿈을 걷고, 줄바꿈과 공백이 섞인 묶음을 " / " 하나로 바꾼다(유니코드 줄바꿈이 이어져도 구분자는 하나)(`EngineMain.StartFailure.oneLine`, 정규식 없이 한 번 훑음). 줄바꿈이 없으면 글자 그대로 둔다(앞뒤 공백도 그대로). `null` 메시지는 예전처럼 "null"이다.
2. 세 종류 모두 같은 규칙을 쓴다(`StartFailure.of`에서 `detail`을 만들 때 한 번). 로그 ERROR 줄과 표준 오류 줄이 같은 `detail`을 쓰므로 둘 다 한 줄이다.
3. 프로그램 오류의 로그 예외 흐름(스택)에는 원래 예외 객체가 그대로 넘어가 원래 메시지(줄바꿈 포함)가 남는다. 설정 오류·명령 채널 실패는 지금처럼 예외 흐름을 남기지 않는다(비밀값이 실릴 수 있는 원인 예외, D-107).
4. 시험이 세 경우의 표준 오류 전체를 줄 끝(`System.lineSeparator()`)까지 글자로 고정한다(Q1).

## 대안

| 대안 | 판단 |
|---|---|
| A. 줄바꿈을 " / "로 접음(채택) | 원인 글자는 모두 남고 한 줄이 된다. 구분자가 보여 원래 줄 경계를 짐작할 수 있다. 알림 채널 이름 검사 문구 "kakao / kakao-x"처럼 원래 " / "가 들어간 메시지와 섞일 수 있으나 표시용이라 영향 없다 |
| B. 첫 줄만 남기고 나머지는 버림 | 가장 짧지만 원인 뒷부분(예: 파서의 위치 정보)을 잃는다. 설정 오류·명령 채널 실패는 로그에 예외 흐름이 없어 원문을 볼 곳이 없다. 버림 |
| C. 줄바꿈을 `\n` 글자(이스케이프)로 표시 | 한 줄이 되지만 운영자가 읽기 어렵고, Windows 경로의 `\`와 섞인다. 버림 |
| D. 그대로 두고 문서에 한계로 남김(D-107) | 앞으로 기동 단계 예외가 늘면 runbook 안내("ERROR 줄을 본다")가 틀어진다. 출력 한 곳만 바꾸면 되므로 지금 고친다. 버림 |

되돌릴 조건: 실전 엔진 로그를 구조화 형식(JSON 등)으로 바꿔 줄 단위 거르기가 의미 없어지면 원문 그대로 싣는 쪽을 다시 본다.

## 위험과 한계

- 원래 메시지 안의 " / "와 접은 줄바꿈을 글자만으로는 가를 수 없다. 프로그램 오류는 로그 예외 흐름에 원문이 있다.
- 줄바꿈이 있을 때만 앞뒤 공백을 걷으므로, 같은 원인이라도 줄바꿈 유무에 따라 앞뒤 공백 처리가 다르다. 표시용이라 판정에 영향 없다.
- 탭 등 다른 제어 문자는 바꾸지 않는다(한 줄은 유지된다).
- 감시(`WatchdogMain`, D-106)의 같은 출력은 이 결정 범위 밖이다. 감시 파일은 다른 작업이 맡고 있어 손대지 않았다. 감시도 같은 규칙이 필요하면 다음 감시 PR에서 본다.

## 검증

- 시험(`EngineMainTest`): `#기동_실패_표준_오류는_첫머리부터_줄_끝까지_정해진_한_줄이다`(세 경우 표준 오류 전체 `isEqualTo`, QA 변이 P3·P8), `#기동_실패_원인에_줄바꿈이_있어도_로그_ERROR와_표준_오류는_한_줄이고_예외_흐름은_원문을_남긴다`(`\n`·`\r\n`·끝 `\r`·줄 앞 공백, 로그 ERROR 줄과 표준 오류 전체 비교, 예외 흐름은 같은 객체·원래 메시지), `#기동_실패_원인의_줄바꿈은_세_종류_모두_한_줄로_접는다`(세 종류, 빈 줄 연속, U+2028, 줄바꿈 없는 원인의 공백 유지, `null`). 기존 D-107 시험은 그대로 통과해야 한다.

## 검토 반영(2026-10-19, PR #172 risk-ops K1·architect N1·N2)

첫 구현은 `\s*\R\s*`로 접어, `\s`에 들지 않는 U+2028이 이어지면 "a /  / b", 끝에 U+0085가 있으면 "a / "가 됐다(한 줄은 지켜짐). 묶음을 `(?:\s*\R)+\s*`로, 앞뒤 걷기를 공백·줄바꿈 둘 다로 바꿨다. 결정 1번의 줄바꿈 목록에 VT·FF를 더했다(코드 동작은 처음부터 접었다).

## 재검토 반영(2026-10-19, PR #172 risk-ops 재검토 K4)

위 검토 반영의 앞뒤 걷기 정규식 `^(?:\s|\R)+|(?:\s|\R)+$`는 반복이 글자마다 재귀해, 공백·줄바꿈이 약 2000자 이어진 원인에서 `StackOverflowError`를 냈다. 그러면 `launch`가 `exit`를 부르지 못해 판정·종료 코드(설정 오류 2 포함)·안내 줄이 모두 사라졌다(엔진은 뜨지 않아 Guard는 OFF 그대로). `oneLine`을 정규식 없이 한 번 훑는 반복문으로 바꿨다. 규칙(결정 1번)은 같다: 줄바꿈 글자는 `\R`과 같은 집합, 공백은 스페이스·탭과 줄바꿈. 시험 `#기동_실패_원인에_긴_공백과_줄바꿈이_있어도_판정과_종료_코드와_한_줄_안내가_남는다`가 수만 글자 묶음으로 접기 결과와 설정 오류(2)·프로그램 오류(1) 종료 코드·표준 오류 한 줄을 본다(바꾸기 전 코드에서는 `StackOverflowError`로 실패함을 확인).
