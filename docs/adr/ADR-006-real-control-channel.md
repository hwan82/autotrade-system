## 1. 배경

[사실] 실전 엔진(`EngineMain`)은 설정을 읽고 Guard를 만든 뒤 바로 끝났다. ADR-002는 Guard를 올리는 조작을 `com.autotrade.app.engine.command` 패키지에만 허용했지만 그 패키지는 비어 있었다(ADR-002 2.2).

[사실] UI 웹 서버는 실험실 프로세스에 있다(ADR-005, UI-01). 실험실과 실전 엔진은 서로 참조할 수 없다(ArchUnit `PROCESSES_ARE_INDEPENDENT`, D-013).

[사실] 증권사 주문 연동(인증, 주문 세션, 대사, 매도)은 7단계 작업이라 아직 없다.

이 ADR은 화면 → 실전 엔진 명령 경로, 2차 확인 검증, 운영 화면을 정한다. 경로 끝(증권사 호출)은 비워 두되, 비어 있는 동안에도 **실전 주문 세션이 절대 만들어지지 않는 쪽으로** 끝나게 한다.

## 2. 결정

### 2.1 구조

```
브라우저 ──HTTP(127.0.0.1, Host·Origin·CSRF 검사)──▶ 실험실 RealOpsController (/api/real/*)
                                                        │ 형식·길이만 검사, 값 저장·기록 안 함
                                                        ▼ ControlClient (요청 하나 = 연결 하나, 대기 상한 15초, 상태 조회 2초)
                                    <설정 폴더>/run/engine-control.sock (Unix 도메인 소켓, 폴더 700·파일 600)
                                                        ▼ ControlServer (올림·PANIC은 단일 명령 스레드·대기 2개, 상태·내리기는 바로, 연결 8개, 읽기 5초, engine.lock)
실전 엔진 EngineCommandHandler ── OperatorAuthenticator(비밀번호 해시·확인 문구·잠금) ── RealTradingGuard
                                └─ ActivationStepRunner / PanicLiquidator (지금은 "증권사 연동 전" 구현)
```

| 코드 | 모듈 | 이유 |
|---|---|---|
| `ControlRequest`·`ControlResponse`·`EngineStatus`·`PanicStepResult`, `ControlCodec`·`ControlClient`·`ControlServer`·`ControlSocket` | **autotrade-control**(새 순수 모듈, config·Jackson만 의존) | 서버(엔진)와 클라이언트(실험실)가 같은 메시지 형식을 써야 하는데 프로세스 모듈끼리는 참조할 수 없다 |
| `EngineCommandHandler`, `OperatorAuthenticator`, `OperatorPasswordHash`, `ActivationStepRunner`, `PanicLiquidator`, `PanicSteps`, `CommandAuditLog` | autotrade-app-engine `app.engine.command` | ADR-002가 정한 명령 채널 패키지 |
| `RealOpsController`, 운영 화면(`js/pages/real.js`), 모드 띠 | autotrade-app-lab, autotrade-ui | UI는 실전 엔진 프로세스에 두지 않는다(UI-01) |

### 2.2 전송: 설정 폴더 안 Unix 도메인 소켓

- 위치: `<설정 폴더>/run/engine-control.sock`. 실험실과 엔진이 같은 `AUTOTRADE_CONFIG_DIR`을 쓰면 따로 맞출 값이 없다.
- 네트워크 포트를 열지 않는다. POSIX에서는 폴더 700·소켓 600으로 같은 OS 사용자만 연결할 수 있다. Windows 10 이상과 macOS도 JDK 16+ Unix 도메인 소켓을 지원한다 `[사실: JEP 380]`. Windows의 접근 제한은 사용자 프로필 폴더 기본 ACL에 기댄다 `[가정]`.
- **엔진은 설정 폴더당 하나(잠금 파일이 남아 있는 동안)**: `run/engine.lock`을 `FileChannel.tryLock`으로 잡지 못하면 기동을 거부한다(종료 코드 1). 소켓 파일을 누가 지워도 두 번째 엔진이 뜨지 않는다. 잠금을 잡은 뒤 남은 소켓 파일은 죽은 엔진 것이라 지운다(그래도 듣는 쪽이 있으면 거부). 종료 신호(SIGTERM)에서 소켓을 지우고 잠금을 푼다. 소켓 폴더가 심볼릭 링크면 거부한다. **한계**: 리눅스·macOS는 잠긴 파일도 지울 수 있어, 엔진이 도는 중에 `run` 폴더나 `engine.lock`을 지우면 두 번째 엔진이 새 파일로 잠금을 얻어 함께 뜬다(risk-ops 재현). 이 경우와 대응은 4장 위험 표, 7단계 완료 조건은 6장.
- 서버 스레드는 모두 데몬이다. **올리는 명령과 PANIC**(ACTIVATE, PANIC_ACCOUNT, PANIC_ALL)은 단일 명령 스레드에서 하나씩 처리한다. ACTIVATE는 대기열 2개(실행 중 포함)까지만 받고 넘치면 `BUSY`. **PANIC은 `BUSY`로 거절하지 않고** 기다렸다가 실행한다(동시 연결 상한이 전체 수를 묶는다). **STATUS와 DEACTIVATE는 대기열을 거치지 않고 연결 스레드에서 바로** 처리한다. 긴 명령이 돌고 있어도 상태를 볼 수 있고 즉시 내릴 수 있어야 하기 때문이다(D-023 원칙 2). Guard는 계좌별로 동기화되어 있고 검증기의 공개 메서드도 동기화했다. 동시 연결은 8개까지(넘으면 즉시 닫음).
- **오래 기다린 ACTIVATE는 버린다**: 대기열에서 10초(실험실 대기 상한 15초보다 짧게) 넘게 기다렸으면 실행하지 않고 `STALE`. 실험실이 이미 "응답 없음"으로 처리한 뒤에 사람이 모르게 실전이 열리는 것을 막는다. PANIC은 기다렸어도 실행한다(내리는 방향).
- 명령 채널이 막히거나 죽어도 Guard 판정(주문 경로)은 잠금 없이 스냅샷만 읽으므로 영향이 없다(ADR-002 2.1).
- 잠금 파일에는 엔진 PID를 적는다. 실험실은 소켓에 닿지 못하면 이 PID의 프로세스가 살아 있는지 보고, 살아 있으면 `NOT_RUNNING`이 아니라 `UNKNOWN`으로 본다(엔진은 도는데 누가 소켓 파일을 지운 경우에 "가상"으로 보이지 않게). PID가 재사용돼 다른 프로세스가 살아 있거나, 잠금 파일을 읽지 못하면(Windows는 엔진이 잡은 잠금 때문에 읽기가 막힐 수 있음 `[추론]`) `UNKNOWN`이 되는데, 이는 안전한 쪽이다. 잠금 파일이 아예 없을 때만 `NOT_RUNNING`이다. 엔진이 지워진 소켓을 스스로 다시 만드는 것은 7단계 완료 조건(6장).
- 경로가 약 100바이트를 넘으면 OS가 소켓을 만들지 못한다. 엔진은 기동을 중단하고 짧은 `AUTOTRADE_CONFIG_DIR`을 쓰라고 알린다.

### 2.3 명령과 메시지

JSON 한 줄(UTF-8, 줄바꿈 포함 최대 64KB) 요청 하나에 응답 하나. 요청은 엄격하게 읽는다: 모르는 필드·명령, 중복 필드, 숫자로 쓴 명령, 문자열 자리의 숫자·불리언, 줄 뒤에 더 보낸 바이트는 `BAD_REQUEST`로 거절하고 처리기를 부르지 않는다. 응답은 모르는 필드를 무시해 엔진을 먼저 올려도 실험실이 깨지지 않는다. 오류 메시지에 요청 원문을 넣지 않는다.

| 명령 | 확인 | 동작 | Guard 전이 |
|---|---|---|---|
| `STATUS` | 없음 | 계좌별 상태·통과 단계·계좌번호 설정 여부, 비밀번호 설정 여부, 잠금 시각 | 없음 |
| `ACTIVATE` | 비밀번호 + 계좌 별칭 입력 | 상태(OFF·PROTECTIVE)와 계좌번호 확인 → 2차 확인 → `beginActivation` → 단계 3개 순서대로 수행 → 모두 통과하면 OPEN, 하나라도 실패·예외면 `failActivation`(출발 상태로) | 올림 |
| `DEACTIVATE` | 없음(사유 선택) | `deactivate`: OPEN → PROTECTIVE, ACTIVATING → 출발 상태 | 내림 |
| `PANIC_ACCOUNT` | 1단계는 확인 없이, 2단계부터 비밀번호 + 계좌 별칭 입력 | RSK-13 순서(2.5) | 내림만 |
| `PANIC_ALL` | 1단계는 확인 없이, 2단계부터 비밀번호 + 문구 `전체 청산` | 모든 계좌 1단계(보호 모드 고정)를 먼저 한 뒤 2차 확인, 계좌별 2~6단계 | 내림만 |

응답 코드는 `ControlCodes`(OK, BAD_REQUEST, UNKNOWN_ACCOUNT, PASSWORD_NOT_CONFIGURED, CONFIRMATION_FAILED, LOCKED, INVALID_STATE, BUSY, STALE, INTERNAL). 실험실 REST 매핑(ADR-005 오류 목록에 추가):

| 엔진 코드 | HTTP | REST `code` |
|---|---|---|
| BAD_REQUEST | 400 | `INVALID`(다른 화면과 같은 이름) |
| UNKNOWN_ACCOUNT | 404 | 그대로 |
| CONFIRMATION_FAILED | 403 | 그대로 |
| LOCKED | 423 | 그대로 |
| PASSWORD_NOT_CONFIGURED, INVALID_STATE, STALE | 409 | 그대로 |
| BUSY(ACTIVATE만) | 503 | 그대로 |
| INTERNAL 등 | 502 | 그대로 |
| (엔진에 닿지 못함) | 503 | `ENGINE_UNREACHABLE` |

엔진에 닿지 못하면 "반영 여부를 모르니 다시 보내지 말고 상태를 새로 읽으라"고 알린다(지침 4장 2번과 같은 원칙). 실험실은 명령을 다시 보내지 않는다. **예외**: 2차 확인을 통과하지 못한 PANIC은 1단계가 이미 일어났으므로 HTTP 200에 `ok: false`, 거절 코드, 단계 결과를 함께 돌려준다.

상태 조회(`GET /api/real/status`)는 엔진 상태를 셋으로 나눈다(`engineState`): `UP`, `NOT_RUNNING`(소켓이 없거나 연결 거절이고, 잠금 파일이 없거나 거기 적힌 엔진 PID가 죽음: 엔진 프로세스 없음, 다시 뜨면 모든 계좌 OFF), `UNKNOWN`(그 밖의 모든 경우: 연결은 됐지만 2초 안에 답이 없거나 끊김, 소켓이 없는데 엔진 PID는 살아 있음, 잠금 파일을 읽지 못함. 엔진이 살아 있고 실전 계좌가 열려 있을 수 있음). 판단할 수 없으면 언제나 `UNKNOWN`이다. 조회 시각 `asOf`를 함께 준다.

`UP`일 때 엔진 스냅샷(`EngineStatus`)에는 `configWarning`이 있다: 엔진이 기동할 때 `runtime-config.json`·`secrets.json`을 버렸거나 일부를 무시한 이유(`LoadedConfig.warning()`, 파일 이름·JSON 경로·규칙만, 값 없음), 문제가 없으면 빈 문자열. 파일을 버리면 실전 계좌 목록과 비밀번호 해시도 같이 빠지므로 운영 화면은 이 경고를 계좌 상태 위에 눈에 띄게 보인다(1단계 QA 권고 R3, `docs/reviews/gates/stage-1.md` S1). 표시용이며 Guard 전이와 명령 검증에는 쓰지 않는다. 이 필드가 없는 옛 엔진의 응답은 빈 문자열로 읽는다(응답은 모르는·빠진 필드에 관대, 2.3). 모든 명령 응답이 상태를 싣고 한 메시지는 64KB를 넘을 수 없으므로, 경고는 2,000자에서 자르고 `…(잘림, 전체는 실전 엔진 로그)`를 붙인다(PR #100 QA Q1). `runtime-config.json`에 비밀값이 있어 버릴 때 맵 비밀값(`real-trading/account-numbers/*`)은 키 이름 대신 패턴과 개수만 쓴다(별칭 자리에 계좌번호를 적었을 수 있음, QA R2).

### 2.4 2차 확인 (RSK-01)

- **운영자 비밀번호 해시**: 새 설정 키 `real-trading.operator-password-hash` 🔒(secrets.json). 형식 `pbkdf2-sha256$<반복>$<salt>$<해시>`, PBKDF2-HMAC-SHA256, 반복 600,000회 `[사실: OWASP Password Storage Cheat Sheet 권고값]`, salt 16바이트, 상수 시간 비교. 평문은 어디에도 저장하지 않는다. 해시는 `autotrade-engine hash-password`(터미널에서 화면에 보이지 않게 두 번 입력, **15자 이상**: 이 비밀번호 하나로 실전을 여는 단일 인증 요소라 NIST SP 800-63B-4의 단일 요소 최소 15자를 따른다 `[가정: 2차 자료로 확인, 원문 미확인]`)로 만들어 사용자가 secrets.json에 넣는다. 실시간 변경 불가(엔진 재기동, `RuntimeConfigHolder`가 real-trading 변경을 거부). 해시가 없거나 형식이 틀리거나 반복 횟수가 100,000 미만·10,000,000 초과면 비밀번호 미설정으로 보고 **올리는 명령과 PANIC 2단계 이후를 거절**한다(PANIC 1단계 보호 모드 고정은 한다).
- **확인 문구**: 계좌 별칭을 그대로 입력(전체 PANIC은 `전체 청산`). 앞뒤 공백을 빼고 NFC로 정규화해 비교한다(macOS 등은 한글을 NFD로 보낼 수 있음). 비밀번호와 문구 중 무엇이 틀렸는지 알려 주지 않는다.
- **잠금**: 5번 연속 실패하면 15분 동안 2차 확인을 모두 거절한다 `[가정]`. 내리기와 PANIC 1단계(보호 모드 고정)는 잠금·비밀번호 미설정·확인 실패와 상관없이 된다. 잠금이 사람을 위험 쪽에 묶어 두지 않게 하기 위해서다. 잠금은 메모리에만 있어 엔진 재기동으로 풀리지만, 재기동하면 모든 계좌가 OFF라 위험이 늘지 않는다.
- **`SecondConfirmation` 생성 제한**: 검증기(`OperatorAuthenticator`)만 만들 수 있고, 직전 검증이 **그 계좌 별칭으로** 통과했을 때 한 번만 만든다. 다른 계좌나 `전체 청산` 문구로 통과한 검증으로는 만들 수 없고, 쓰지 않은 검증은 검증을 쓰는 명령(ACTIVATE·PANIC)이 끝날 때 버린다. 대기열을 거치지 않는 DEACTIVATE는 버리지 않는다(동시에 진행 중인 활성화의 검증을 지우지 않게). ArchUnit `ONLY_AUTHENTICATOR_CREATES_CONFIRMATION`이 명령 채널 패키지 안의 다른 클래스도 막는다(위반 픽스처 2건). ADR-002 3장 "되돌릴 조건"(검증기만 만들 수 있는 타입)을 이 규칙으로 충족한다.
- 실험실은 비밀번호를 그대로 넘기기만 한다. 요청 객체의 `toString`은 비밀번호를 가리고, 응답·로그에는 명령 이름과 결과 코드만 남는다. 화면은 보낸 즉시 입력란을 비운다.

### 2.5 PANIC SELL 처리 순서 (RSK-13)

| 단계 | 처리 | 지금 동작(증권사 연동 전) |
|---|---|---|
| 1 보호 모드 고정 | **2차 확인 전에** 한다. OPEN → `deactivate`(PROTECTIVE), ACTIVATING → `failActivation`. PROTECTIVE·OFF는 건너뜀. 2차 확인이 실패·잠김·비밀번호 미설정이면 여기서 멈추고 2~6단계는 SKIPPED | 실제로 동작 |
| 2 미체결 전부 취소 확인 | `PanicLiquidator` | 수행 불가(NOT_AVAILABLE) |
| 3 서버 측 손절 취소 확인 | 〃 | 〃 |
| 4 매도(국내 시장가, 미국 지정가+여유폭, 장 외 시간 매도 안 함, 블랙리스트·수동 보유 제외) | 〃 | 〃 |
| 5 체결 확인 | 〃 | 〃 |
| 6 Guard OFF | 2~5가 이 순서로 **모두 DONE**일 때만 `shutdown`. 아니면 보호 모드 유지. 설명은 실제 단계 결과로 쓴다: 3단계(서버 측 손절 취소)가 DONE인데 매도가 끝나지 않았으면 "서버 측 손절이 취소된 상태라 엔진 손절 감시만 동작"을 **긴급(`urgent`)**으로 표시 | 건너뜀: 보호 모드 유지(손절·서버 측 손절 계속) |

- **매도를 낼 수 없을 때(장 외 시간, 거래정지·VI·LULD 정지 등)**: 3단계(서버 측 손절 취소)를 하지 않고, 2단계는 미체결 매수만 취소한다. 서버 측 손절은 엔진·연결 장애 때의 마지막 방어선이라(broker-and-fault-design.md 6.1, 장애표 #11·#12, 해외 O8) 매도가 나가지 못하는 동안 지우지 않는다. Q-017 결정 전에도 적용한다(D-037, PR #25 risk-ops 검토). 계좌 안 일부 종목만 매도할 수 없을 때 그 종목만 건너뛸지 계좌 전체를 멈출지는 7단계 구현에서 정한다(어느 쪽이든 Guard OFF는 일어나지 않음).
- OFF 계좌는 주문 세션이 없어 2~6단계를 모두 건너뛴다(7장 Q-016).
- `PanicLiquidator` 계약(7단계 구현이 지킬 것, 인터페이스 주석): 앞 단계가 DONE이 아니면 뒤 단계를 하지 않는다. 서버 측 손절을 취소한 뒤 매도나 체결 확인이 실패하면 남은 보유에 서버 측 손절을 다시 걸거나 그 실패를 FAILED로 알린다. 예외 대신 결과로 알린다.
- 장 외 시간: 기획서 v13·v14 RSK-13은 "장 외 시간에는 미체결 취소와 Guard OFF만"이라고 적었었고(v14.1에서 Q-017로 남김), 이 구현은 매도가 끝나지 않으면 Guard를 끄지 않는다(보호 모드 유지). 둘이 다르므로 Q-017로 사용자 결정을 받는다(7장).
- 감사 로그: Guard 전이는 `GuardAuditLog`, 명령 시도와 결과는 `CommandAuditLog`(명령, 설정에 있는 계좌 별칭만, 결과 코드). 모르는 계좌 값은 남기지 않는다. 둘 다 지금은 프로세스 로그이며 영속 저장은 7단계(ADR-002 6장).

### 2.6 증권사 연동 전 기본 구현

`ActivationStepRunner.BROKER_NOT_CONNECTED`는 첫 단계(인증)에서 실패를 돌려준다. 그래서 지금은 활성화를 끝까지 시도해도 **ACTIVATING → OFF**로 돌아오고, `RealOrderGateways`가 열 수 있는 허가(`OrderSessionPermit`)는 한 번도 발급되지 않는다(테스트로 고정). 명령 채널, 2차 확인, 잠금, Guard 전이, 감사 로그는 실제로 끝까지 돈다. 7단계에서 이 두 구현만 바꾼다.

### 2.7 운영 화면 (UI-05)

- 메뉴 "실전 운영"(`#/real`): 계좌별 Guard 상태 배지, 활성화 중 통과 단계, 계좌번호 설정 여부, 명령 버튼(실전 활성화·내리기·PANIC SELL), 전체 PANIC SELL. 엔진이 `NOT_RUNNING`이면 "실전 엔진이 실행 중이 아닙니다"만 보이고 버튼이 없다. `UNKNOWN`이면 마지막으로 확인한 상태표를 "지금 상태와 다를 수 있음" 경고와 함께 보여 주고, 활성화는 막고 PANIC·내리기는 남긴다.
- 2차 확인 대화상자: 결과를 먼저 설명하고(활성화: 실제 주문이 나감, 재기동 시 꺼짐, 서버 측 손절 지원 여부 미표시 / PANIC: 4단계 순서와 Guard OFF 조건), 확인 문구가 정확히 같고 비밀번호가 비어 있지 않을 때만 실행 버튼이 켜진다. 내리기는 비밀번호를 묻지 않는다.
- PANIC 버튼은 비밀번호 미설정·잠금 중에도 켜져 있다. 그때는 "보호 모드 고정만 됩니다"를 버튼 옆과 대화상자에 적고, 확인 문구만 맞으면 "보호 모드 고정"으로 보낼 수 있다. 결과표에서 긴급 단계는 강조한다.
- 모드 띠: 실전 계좌 하나라도 OFF가 아니면 파랑 해칭(가상) 띠가 **해칭 없는 적갈색 띠 "● 실전 가동 중 · 실전 계좌 N개"**로 바뀌고 계좌별 상태를 적는다. 색과 무늬가 둘 다 달라 색 구분이 어려워도 구별된다. 모든 화면에서 5초마다 엔진 스냅샷을 읽는다(SSE는 후속).
- 엔진이 `UNKNOWN`이거나 실험실 서버가 답하지 않으면 띠를 "가상"으로 바꾸지 않는다. 주황 사선 띠 **"! 실전 상태 확인 불가 · 마지막 확인 hh:mm:ss"**로 바꾸고, 마지막 확인 때 열린 계좌가 있었으면 그 목록을 적는다. `NOT_RUNNING`일 때만 "실험실 · 가상 계좌만"(엔진이 없으면 실전 주문이 나갈 수 없음).

## 3. 대안 검토

**A. 화면 → 엔진 전송**

| 대안 | 장점 | 단점 | 판단 |
|---|---|---|---|
| A1. 설정 폴더 안 Unix 도메인 소켓 | 포트 없음, OS 파일 권한으로 같은 사용자만, JDK 표준, 엔진에 웹 서버 불필요 | 경로 길이 제한(약 100바이트), Windows ACL은 기본값에 기댐 | **채택** |
| A2. 엔진에 루프백 HTTP(JDK HttpServer) + 공유 토큰 | 디버깅 쉬움, 브라우저 도구로 볼 수 있음 | 같은 PC의 모든 사용자·프로그램이 포트에 닿음, 브라우저 DNS rebinding 방어를 엔진에 다시 구현해야 함, 실전 엔진에 HTTP 서버가 생김 | 버림 |
| A3. 파일 명령 큐(폴더에 명령 파일, 엔진이 폴링) | 구현 단순 | 응답·결과 전달이 늦고 복잡, 폴링 지연, 부분 쓰기·중복 처리 위험 | 버림 |
| A4. 시세용 메모리 매핑 큐 재사용 | 이미 계획된 큐 | 시세 큐는 생산자가 소비자를 기다리지 않는 단방향 설계(D-013). 요청-응답에 맞지 않음 | 버림 |

되돌릴 조건: 경로 길이 제한이나 Windows 권한 문제로 실제 사용 PC에서 쓸 수 없으면 A2를 새 ADR로 검토한다(그때는 엔진 HTTP에 Host 검사·토큰·루프백 바인딩을 모두 둔다).

**B. 2차 확인 검증 위치**

| 대안 | 판단 |
|---|---|
| B1. 실전 엔진이 검증 | **채택**. 실험실의 **웹 계층**이 뚫려도(CSRF, 요청 위조) 비밀번호 없이는 올릴 수 없다. 단, 해시는 4개 프로세스가 같은 secrets.json에서 함께 읽으므로(설정 로더 공통) 실험실 **프로세스**가 장악되면 해시를 가져가 오프라인 대입하거나, 사람이 입력하는 비밀번호를 가로채거나, secrets.json의 해시를 바꿔 넣을 수 있다. 이 위험은 4장에 둔다 |
| B2. 실험실이 검증하고 엔진에 "확인됨"만 보냄 | 버림. 실험실(저우선, 웹 노출)이 Guard를 올릴 권한을 갖게 된다 |

**C. 비밀번호 해시 알고리즘**: (C1) PBKDF2-HMAC-SHA256 600,000회 **채택**: JDK 내장이라 의존이 늘지 않고 OWASP 권고값이 있다. (C2) Argon2id: OWASP 1순위지만 외부 라이브러리(네이티브 포함)가 실전 엔진 클래스패스에 들어온다. 로컬 단일 사용자, 오프라인 공격 시 해시 파일 접근이 전제라 C1로 충분하다고 판단 `[추론]`. 되돌릴 조건: 형식 접두어(`pbkdf2-sha256$`)로 구분하므로 새 알고리즘을 추가해도 기존 해시와 공존할 수 있다.

**D. PANIC 매도가 끝나지 않았을 때**: (D1) 보호 모드 유지 **채택**: D-023 원칙 1(보호 동작은 막지 않음), 서버 측 손절과 손절 감시가 계속된다. (D2) 그래도 Guard OFF: 남은 보유분에 대한 주문 세션이 닫혀 손절도 못 한다. 버림.

## 4. 위험과 한계

| 위험 | 영향 | 대응 |
|---|---|---|
| 같은 OS 사용자로 도는 악성 프로그램은 소켓에 연결할 수 있음 | 상태 조회·내리기·PANIC 1단계(보호 모드 고정)는 가능(모두 안전 방향). 올리기와 PANIC 청산은 비밀번호가 필요. 다만 틀린 확인을 5번 보내 15분 잠금을 반복하면 그동안 사람의 PANIC도 보호 모드 고정까지만 된다(청산 서비스 거부) | 비밀번호 + 잠금. 비밀번호를 키로거로 훔치는 수준은 범위 밖 `[가정]`. 잠금 남용 대책은 6장 표(7단계 완료 조건) |
| 실험실 프로세스가 장악됨(의존 라이브러리 취약점 등) | 해시 탈취 후 오프라인 대입, 화면 입력 비밀번호 가로채기, secrets.json 해시 교체 후 엔진 재기동 시 공격자 비밀번호로 실전 열기 | 15자 이상 비밀번호와 PBKDF2 600,000회로 대입 비용을 올림. **7단계 완료 조건**: secrets.json·해시 변경과 엔진 재기동을 감시 프로세스가 알림(MON), 실전 활성화마다 외부 알림(문자·메신저), 가능하면 해시를 엔진만 읽는 별도 파일로 분리 |
| 비밀번호가 실험실 메모리와 소켓을 평문으로 지난다 | 같은 PC 메모리 덤프 위험 | 로컬 전용, 로그·응답 미기록, 엔진은 검증 후 배열을 지움. Java 문자열은 GC 전까지 남을 수 있음(한계) |
| 엔진 재기동으로 잠금이 풀림 | 대입 시도 속도는 재기동 시간에 묶임 | 재기동 시 모든 계좌 OFF. 반복 횟수 600,000회로 시도당 약 0.5초 이상 `[추론]` |
| 실험실 대기 상한(15초) 안에 활성화가 끝나지 않으면 503 | 화면은 결과를 모름 | 다시 보내지 않고 상태를 읽게 안내. 7단계에서 활성화가 길어지면 비동기 진행 + 상태 폴링으로 바꾼다 |
| 명령 채널 단일 스레드라 긴 활성화 중에는 PANIC도 기다린다 | 7단계에서 활성화 단계가 길어지면 PANIC 청산이 늦어짐(상태 조회·내리기는 이미 대기열을 거치지 않음) | 지금은 단계가 즉시 실패해 문제없음. **7단계 완료 조건**: 활성화 단계를 비동기로 돌리고 PANIC은 계좌별로 바로 처리(계좌끼리도 서로 기다리지 않음), 감시 프로세스 긴급 경로(MON-02) |
| 엔진이 답하지 않을 때(UNKNOWN) 화면은 마지막 상태만 앎 | 그사이 상태가 바뀌었을 수 있음 | 띠·화면에 "확인 불가 · 마지막 확인 시각"을 표시하고 가상으로 바꾸지 않음. 활성화 버튼은 막음 |
| OFF 계좌(재기동 직후 보유 있음)는 PANIC으로 매도할 수 없음 | RSK-13 매도가 안 됨 | Q-016으로 risk-ops·사용자 결정. 그 전까지는 화면에서 "Guard OFF라 주문이 나가지 않습니다"로 명시 |
| 증권사 연동 전 활성화는 항상 실패 | 실전을 열 수 없음(의도) | 7단계에서 `ActivationStepRunner`·`PanicLiquidator`를 바꾼다 |
| 장 외 시간·블랙리스트 제외·감시 프로세스 긴급 경로(MON-02) 미구현 | RSK-13 일부 인수 조건 미충족 | `PanicLiquidator` 계약에 명시, 7단계 risk-ops 작업 |

## 7. 사용자 결정 항목(이 PR 머지로 결정)과 질문

추천안으로 구현했다. 실전 영향 항목이라 자율 채택이 아니며 머지가 곧 결정이다.

1. 명령 채널은 설정 폴더 안 Unix 도메인 소켓(대안 A1).
2. 2차 확인 검증은 실전 엔진이 한다(B1). 운영자 비밀번호 해시 키 `real-trading.operator-password-hash` 🔒 추가, PBKDF2-HMAC-SHA256 600,000회(C1), 비밀번호 15자 이상.
3. 확인 문구는 계좌 별칭(전체는 `전체 청산`), NFC 정규화.
4. 5회 연속 실패 시 15분 잠금 `[가정]`. 잠겨도 내리기와 **PANIC 1단계(보호 모드 고정)는 허용**: 확인 실패·잠김·비밀번호 미설정이어도 PANIC을 누르면 신규 주문은 막히고 청산은 하지 않는다.
5. 내리기는 비밀번호를 묻지 않는다(D-023 원칙 2의 해석: 내려가는 전이는 즉시).
6. PANIC은 증권사 단계가 모두 끝나야 Guard OFF, 아니면 보호 모드 유지(D1). 전체 PANIC은 모든 계좌를 먼저 보호 모드로 고정한 뒤 계좌별로 진행.
7. 실험실 → 엔진 응답 대기 상한 15초(상태 조회 2초) `[가정]`, 응답이 없으면 다시 보내지 않는다. 엔진 대기열에서 10초 넘게 기다린 활성화는 버린다.
8. 엔진이 응답하지 않으면 화면은 "가상"으로 바꾸지 않고 "실전 상태 확인 불가"로 표시한다.

**Q-016 (risk-ops, 사용자 결정)**: 재기동 직후 보유가 남은 OFF 계좌에서 PANIC SELL을 누르면 어떻게 할까? 추천: PANIC 2차 확인을 보호 모드 진입 확인으로도 보고 OFF → PROTECTIVE로 올린 뒤 매도한다(주문 세션이 열림). 대안: 지금처럼 건너뛰고 사용자가 먼저 "보호 모드로 열기"를 하게 한다. 보유 조회가 생기는 7단계 전까지는 결과가 같아 결정을 미룰 수 있다. 추천안을 고르면 지킬 조건(risk-ops): 매도 전에 보유 대사를 먼저 하고, 전체 PANIC에서 OFF 계좌를 올리는 것은 계좌마다 확인을 받으며, 어느 단계든 실패하면 PROTECTIVE에 남긴다(OFF로 되돌리지 않음).

**Q-017 (risk-ops, 사용자 결정)**: 장 외 시간에 PANIC SELL을 누르면 Guard를 끌까? 기획서 v13 RSK-13은 "장 외 시간에는 미체결 취소와 Guard OFF만 하고 매도는 개장 후 다시 실행"이라고 적었다. 추천: **보호 모드 유지**(미체결 매수만 취소하고 서버 측 손절은 그대로 두며 Guard를 끄지 않음). 이유: 장 외에 Guard를 끄면 개장 직후 갭 하락 때 엔진 손절이 동작하지 않는다. 대안: 기획서대로 Guard OFF. 이 구현은 추천안(매도가 끝나지 않으면 OFF 안 함)으로 되어 있고, 증권사 단계가 생기는 7단계 전에는 결과가 같다. 결정되면 기획서 RSK-13 문구를 고친다.
