# D-032 가상·실전 공통 리스크 검증 체인(RiskChain)과 실험 실행기 적용

- 날짜: 2026-10-09
- 상태: 확정, **추천안 채택(자율)** (project-instructions.md 8장). 블랙리스트·리스크 검증 코드를 건드리므로 실전 관련 PR로 취급하고 risk-ops·architect 검토, 독립 QA 후 **사용자가 머지**한다(10·11장). 실전 리스크 한도 값은 정하지 않는다(Q-008 그대로)
- 근거: 기획서 v13 SIM-12, RSK-02, RSK-12, 7장 공통 원칙(D-023) 1·3, 안전 불변식 6·7, ADR-002 2.1, PR #14 architect 검토 L1, D-027 변경 제안
- 담당: risk-ops. 검토: architect, risk-ops(원문 docs/reviews/)

## 배경

[사실] 4단계 비교 실험은 모든 주문을 승인하는 정책으로 돌았다(`StudyMain.java:82` `(order, account) -> RiskDecision.approve()`, main 2dcea43). 저장소에 `RiskPolicy` 실구현이 없었다(`implements RiskPolicy`는 sim 테스트의 `TestBlacklist`뿐). 합성 종목에는 제외 종목이 없어 지금 결과에는 영향이 없지만, 녹화 데이터 실험부터는 가상과 실전이 같은 블랙리스트·리스크 코드를 써야 한다(SIM-12).

## 결정

1. **`RiskChain`(autotrade-risk)** 이 가상·실전 공통 주문 전 검증 체인이다. 평가 순서는 고정이다.
   1. 블랙리스트·수동 보유 필터: 진입·청산·손절 **모든 의도**에 적용(RSK-02 "어떤 경로로도", 안전 불변식 6 "청산 로직에도"). 거절 규칙 ID는 `BLACKLIST`(MANUAL), `MANUAL_HOLDING`(AUTO_ASSET). **청산·손절까지 막는 부분은 Q-018 결정 전까지 잠정**이다(아래 위험과 한계 첫 항목).
   2. 보호 주문(`OrderIntent.isProtective()`: 청산·손절) 승인. 진입 규칙은 보호 주문을 막을 수 없다(D-023 공통 원칙 1).
   3. 진입 규칙: 등록 순서대로, 첫 거절에서 멈춤. RSK-03 계좌 한도·RSK-11 세션 구간 같은 규칙이 여기 붙는다.
2. **블랙리스트 없는 체인은 만들 수 없다.** `RiskChain.builder(BlacklistSnapshot)`만 있고 null은 거절한다. 실제 종목이 없는 합성 실험만 `BlacklistSnapshot.EMPTY`를 쓴다.
3. **닫힌 쪽 실패**: 진입 규칙이 예외를 던지거나 null을 돌려주면 그 진입을 `RISK_RULE_ERROR`로 거절한다. 주문 계좌와 계좌 스냅샷 계좌가 다르면 모든 의도를 거절한다.
4. **`BlacklistSnapshot`**: 불변, 종목(시장 포함) 순 정렬, 같은 종목이 두 유형이면 AUTO_ASSET을 남긴다(보유 중 해제 불가가 더 강한 등록, RSK-12). 종목·유형으로 만든 SHA-256 지문을 갖는다(사유 문구는 제외). 리플레이는 실험 시작 때 찍은 스냅샷 하나로 끝까지 돈다.
5. **실험 실행기 계약 변경**: `SimulationExperimentRunner`와 `StrategyStudy`는 `RiskPolicy` 대신 `RiskChain`만 받는다. 승인만 하는 람다나 블랙리스트를 건너뛰는 정책은 타입으로 넣을 수 없다. `StudyMain`은 `RiskChain.builder(BlacklistSnapshot.EMPTY).build()`로 돈다.
6. **ArchUnit `RISK_POLICIES_LIVE_IN_RISK_MODULE`**: `RiskPolicy`를 구현하는 운영 클래스는 `com.autotrade.risk..`에만 둔다. 위반 픽스처 `archfixture/ApproveAllRiskPolicy`를 잡는지 테스트한다.

## 대안 비교

| 선택 | 대안 | 판단 |
|---|---|---|
| 실행기가 `RiskChain` 타입만 받음 | A. `RiskPolicy`를 그대로 받고 문서·리뷰로만 관리 | 버림. 이번 과제의 원인이 바로 "아무 람다나 넣을 수 있음"이다. 타입으로 막으면 리뷰 누락에도 우회가 안 된다 |
| 블랙리스트를 체인 안에 고정(빌더 필수 인자) | B. 블랙리스트도 일반 규칙으로 등록하고 순서 검사 | 버림. 빼먹거나 뒤로 미는 실수를 런타임 검사로만 잡게 된다 |
| 진입 규칙은 보호 주문을 구조적으로 건너뜀 | C. 각 규칙이 의도를 보고 스스로 판단 | 버림. 새 규칙 하나가 손절을 막는 실수(D-023 원칙 1 위반)를 규칙마다 테스트해야 한다. 청산에도 적용해야 하는 차단은 지금 블랙리스트뿐이고, 더 생기면 체인 1단계에 명시적으로 더한다 |
| 규칙 오류 시 진입 거절(닫힌 쪽) | D. 예외를 그대로 던짐 | 버림. 실험에서는 Run 전체가 실패하고, 실전에서는 상위 처리에 따라 진입이 열릴 수 있다. 손절은 진입 규칙을 거치지 않으므로 닫힌 쪽 실패가 보호 동작을 막지 않는다 |
| 이번 PR에 한도 규칙 값을 넣지 않음 | E. RSK-03 기본 한도를 `[가정]` 값으로 바로 추가 | 버림. 실전 한도 값은 Q-008 사용자 결정이고, 모의 한도는 프로필 파라미터(D-027 `ManagedStrategy`)로 이미 비교 중이다. 계좌 한도 규칙은 필요한 상태(일일 손익 이력)가 `AccountSnapshot`에 없어 계약 확장이 먼저다 |

되돌릴 조건: 청산까지 막아야 하는 새 차단 규칙이 확정되면(사용자 결정) 체인 1단계 구성을 바꾼다. 실전 엔진 주문 파이프라인(7단계)이 다른 체인 구성을 요구하면 새 결정 번호로 바꾼다.

## 위험과 한계

- **[사실] 블랙리스트가 시스템이 보유한 종목의 손절·청산도 막는다**(`RiskChain.java` 블랙리스트 단계가 의도와 상관없이 거절, `RiskChainTest#제외_종목은_진입_청산_손절_모두_막는다`). 이는 RSK-02·안전 불변식 6("청산 로직에도 적용")을 따른 것이지만 D-023 공통 원칙 1("손절·청산은 어떤 차단 규칙으로도 막지 않는다")과 부딪친다. [추론] 위험한 경로: 블랙리스트는 전역이고 AUTO_ASSET은 대사에서 자동 등록되므로(RSK-12), 사용자가 다른 계좌에서 같은 종목을 수동으로 사면 시스템이 보유한 쪽의 손절이 알림 없이 막힐 수 있다. 서버 측 손절이 없는 계좌는 그 종목이 무방비가 된다. 지금 영향은 없다: 이 체인을 쓰는 실전 코드가 없고, 리플레이 실험은 시작 시점 스냅샷으로 고정된다. 실전 영향이고 확정 결정끼리 충돌하므로 **Q-018로 사용자에게 묻는다**(지침 8장 2·4번). 7단계 실전 주문 파이프라인은 Q-018 결정 뒤에 체인 1단계를 확정한다. (risk-ops 검토 A14)
- 실전 엔진에는 아직 주문 파이프라인이 없어 이 체인을 쓰는 실전 코드가 없다. SIM-12 인수 조건 중 "가상·실전이 같은 체인을 쓰는 테스트"와 "체인 밖 submit 호출 금지 ArchUnit"은 7단계 주문 파이프라인 작업에서 완성한다. 지금 보장하는 것은 (1) 규칙 코드가 리스크 모듈 한 곳에만 있음, (2) 실험 실행기가 그 체인 말고는 받지 않음이다.
- 진입 규칙은 리스크 모듈 밖에서 람다로 더할 수 있다(ArchUnit은 람다를 클래스로 보지 않는다). 다만 진입 규칙은 진입을 더 막을 수만 있고 블랙리스트를 건너뛰거나 청산을 막을 수 없다.
- 멱등 키 발급과 주문 상태머신은 SIM-12 체인의 뒤 단계지만 이번 범위가 아니다. 가상 실행기는 자체 `SimOrderKeys`와 `VirtualExchange` 상태를 쓴다(ADR-004).
- 블랙리스트 영속화(DB), 수동 보유 자동 감지(대사), 실험 메타에 블랙리스트 지문 기록(RSK-12)은 아직 없다. 녹화 데이터 실험 진입점은 영속 블랙리스트의 시작 시점 스냅샷을 넣어야 하며, 그 전까지 `StudyMain`은 합성 시세 전용이다.
