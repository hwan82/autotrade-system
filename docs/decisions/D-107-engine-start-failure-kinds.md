# D-107 실전 엔진 기동 실패를 설정 오류와 프로그램 오류로 나눠 표시(PR #144 독립 QA R2)

- 날짜: 2026-10-17
- 상태: 확정 · **추천안 채택(자율)**(지침 8장). 실전 엔진(`autotrade-app-engine`, 보호 경로)의 기동 실패 표시와 종료 코드만 바꾼다. 기동 순서, RealTradingGuard(모든 계좌 OFF로 시작), 명령 채널·잠금, 알림 채널 구성(D-100·D-103), 주문 경로는 바꾸지 않는다. 보호 경로라 사용자 머지로 확정한다.
- 머지 순서: D-106(PR #148)을 링크하므로 PR #148 뒤에 머지한다(architect·risk-ops 지적 1).
- 담당: risk-ops 결정·구현. 교차 검토: architect(코드), risk-ops(실전 관련)
- 근거: [PR #144 독립 QA](../reviews/pr-144/qa.md) R2, 감시의 같은 결정 [D-106](D-106-watchdog-start-failure-kinds.md)(PR #148), [D-103](D-103-settings-notification-test-send.md) 2026-10-17 반영 기록(채널 이름 코드 실수는 기동 예외)

## 문제

`EngineMain.main`은 기동 중 `IOException`(명령 채널을 열지 못함)만 잡았다. PR #144부터 알림 채널 이름이 어긋나는 코드 실수는 `IllegalArgumentException`으로 엔진 기동을 멈추는데, 이 예외는 잡히지 않아 `main` 스레드의 처리되지 않은 예외(JVM 기본 스택 출력)로 끝났다. 원인 문구는 보이지만 운영자가 볼 첫 줄이 없고, 설정 폴더 경로가 틀린 경우(`AUTOTRADE_CONFIG_DIR`에 따옴표 등, `InvalidPathException`)도 같은 모양이라 설정 문제인지 코드 문제인지 가를 수 없었다. 감시는 D-106으로 이 둘을 종료 코드 2·1로 나눈다.

## 결정

1. **설정 오류(종료 코드 2)**: 설정 폴더 경로(`autotrade.config-dir`·`AUTOTRADE_CONFIG_DIR`)가 경로 형식이 아니면 "실전 엔진 설정이 틀려 기동하지 않습니다: 설정 폴더 경로가 틀렸습니다(...)"(`EngineRefusal`, 패키지 전용). 감시 D-106 4번과 같은 기준이다. 일반 설정 파일(`runtime-config.json`·`secrets.json`)이 틀린 것은 지금처럼 경고 뒤 기본값으로 뜬다(기동 거부 아님).
2. **명령 채널을 열지 못함(종료 코드 1, 그대로)**: `IOException`(다른 실전 엔진이 이미 돎, 소켓 경로가 너무 김 등)은 예전 문구 "실전 제어 명령 채널을 열지 못해 기동을 중단합니다"와 종료 코드 1 그대로다. runbook 표의 "1 = 기동 실패"와 CI 기동 점검(두 번째 엔진은 0이 아님)이 바뀌지 않는다.
3. **프로그램 오류(종료 코드 1)**: 그 밖의 `RuntimeException`(알림 채널 이름 검사 실패 같은 `IllegalArgumentException` 포함)은 "실전 엔진이 기동 중 프로그램 오류로 멈췄습니다(설정 파일 문제가 아닙니다. 로그의 예외를 개발 쪽에 알려 주세요)"로 표시하고 종료 코드 1로 끝낸다. 로그(ERROR)에는 예외 흐름도 남긴다.
4. 세 경우 모두 로그 ERROR 한 줄과 표준 오류 한 줄("(실전 엔진이 뜨지 않았습니다)"와 실제 원인)을 남긴다. 판정은 `EngineMain.StartFailure.of`, 출력은 `report`, 진입점 절차는 `EngineMain.launch`(시험이 종료 동작과 알림 설정 옮기기를 바꿔 끼움)다.
5. **Guard**: 어느 실패든 엔진 객체를 돌려주지 않고 끝난다. Guard는 메모리 상태라 프로세스와 함께 사라지고, 다음 기동도 모든 계좌 OFF로 시작한다(절대 규칙 1, ADR-002). 알림 단계 실패는 명령 채널을 열기 전이라 소켓·잠금이 남지 않는다.

## 대안

| 대안 | 판단 |
|---|---|
| A. 감시와 같은 판정 레코드로 종류를 나눔(채택) | D-106과 같은 문구 구조·종료 코드라 운영자가 두 프로세스를 같은 방식으로 읽는다. `IOException`의 기존 문구·코드를 그대로 둔다 |
| B. `main`의 catch를 `IOException | RuntimeException`으로 넓히고 한 문구로 표시 | 가장 작지만 설정 폴더 경로 오류와 코드 실수가 같은 문구라 무엇부터 볼지 못 고른다. 버림 |
| C. 명령 채널 실패도 설정 오류(2)로 | 다른 엔진이 이미 도는 경우는 설정 문제가 아니고, runbook·CI가 보는 1이 바뀐다. 버림 |
| D. 감시의 `StartFailure`를 공용 모듈로 옮겨 함께 씀 | PR #148이 아직 열려 있고, 공용 모듈(보호 경로 여러 곳)에 새 계약이 생긴다. 두 프로세스 문구가 달라 얻는 것이 적다. 버림(두 PR이 머지된 뒤 세 번째 프로세스가 같은 것을 필요로 하면 다시 본다) |

되돌릴 조건: 실전 엔진 자동 재기동 체계가 생겨 종료 코드로 재시도 여부를 고르게 되면 그 체계 기준으로 다시 정한다(D-106과 같음).

## 위험과 한계

- 기동 거부 조건을 새로 더하는 사람이 `EngineRefusal` 대신 다른 예외를 던지면 프로그램 오류(종료 코드 1)로 보인다. 기동은 똑같이 막혀 보호가 약해지지 않고 문구만 덜 정확하다.
- 명령 채널을 연 뒤의 단계(하트비트 시작, 시작 알림 넣기)에서 예외가 나면 명령 채널을 닫지 않고 프로세스가 끝난다(예전과 같음). `main`에서는 프로세스 종료로 소켓·잠금이 풀리고, 지금 그 단계는 설정 값으로 던지지 않는다(하트비트 쓰기 실패는 로그만, 기존 시험). 시험의 `launch`도 이 경로를 만들지 않는다.
- `Error`(메모리 부족 등)는 잡지 않고 JVM 기본 처리로 둔다.
