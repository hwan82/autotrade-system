## 점검표 밖 발견
- F-1 (순서) 2단계가 끝나지 않은 상태에서 3·4·5단계 PR이 머지되었다. 3단계 완료 기준은 "녹화 데이터로 골든 테스트 통과"인데 녹화 데이터가 없으므로 3단계도 완료 판정 대상이 될 수 없다 [추론]. 4단계 실험(EXP-20261008-STR01)은 합성 시세라 D-027도 "후보를 고르지 않음"으로 두었다. 이후 단계 완료 판정 요청 시 같은 이유로 실패한다.
- F-2 (기록) 1단계 완료 기록이 결정 로그에 없다(0단계 D-022만 있음). 지침 11장은 단계 완료 기록을 QA 승인 뒤에 하라고 하므로, 1단계도 QA 판정을 받지 않은 상태로 보인다 [추론].
- F-3 (PR #10 머지 시 위험) PR #10은 8,425줄·107파일, 증권사 플러그인 3개와 시세 장애 전환·보호 시세 경로를 넣는 실전 관련 PR이며 main과 충돌 중이다. 충돌 해결 과정에서 #18·#19·#21의 보호 규칙(`ArchitectureTest`, `ModuleOwnershipTest.OWNERS`, RiskChain)이 빠지거나 약화될 수 있다 [추론]. 머지 전에 "PR #10 검토해줘"로 점검표 A 전체 + B1·B6 + 과금 검사를 충돌 해결 후 head 기준으로 받아야 한다. 특히 과금 8.3·8.4: 토스 폴링(요금 미확인, Q-020)이 `priority`에 토스가 없을 때도 `toss-polling-scope: HELD_ONLY` 기본값으로 동작하는지, 재연결·토큰 재발급 루프의 상한이 테스트로 검증되는지.
- 오류·순서·장애 시나리오(QA 지침 5장 5번): 이번 관문은 main에 시세 코드가 없어 잘못된 주문·중복 주문·보호 공백을 만들 2단계 경로가 존재하지 않는다. 시나리오 시도는 PR #10 검토로 넘긴다. (1) 시세 소스 전환 중 같은 종목 이벤트 중복 → 전략 중복 신호, (2) 녹화 순번 부여와 리플레이 순서 불일치 → 결정론 위반, (3) 키움·한투 모두 끊김 시 보유 종목 보호 시세 공백 — 세 가지를 PR #10 검토 때 우선 확인 대상으로 제안한다.

### 점검표 밖 발견 (재검토)
- G-1 (가장 큰 위험, C1) 리플레이 결정론이 증명된 것은 코드로 만든 이벤트뿐이다. 실제 증권사 메시지는 필드 순서·가격 스케일·시각 형식이 `[가정]`이라, 실데이터에서 `RecordingCodec` 왕복이 값을 바꾸면(예: 가격 소수 자릿수, 수신 시각 정밀도) 같은 녹화를 두 번 리플레이해도 동일하지만 **원래 받은 값과 다른** 이벤트가 나올 수 있다 [추론]. 두 번 리플레이 동일성 검사만으로는 이 오류를 잡지 못하므로, 실녹화 확인 때 원본 수신 메시지와 리플레이 값의 대조도 함께 해야 한다.
- G-2 (보호 공백) 구독 거절(`SUBSCRIBE_REJECTED`)이 장애 전환으로 이어지지 않는다(ADR-003 5장). 보유 종목 구독이 거절되면 그 종목은 연결 상태가 정상인데 시세가 오지 않고, 재배분도 되지 않는다 [추론]. 7단계 전 data-engineer·risk-ops 과제로 등록돼 있다.
- G-3 (실전 키 충돌) 게이트웨이가 실전 계좌 증권사 키를 피하는 판단은 기동 시 1회다(PR #10 qa.md R-2). 게이트웨이 실행 중 실전 계좌를 설정하면 같은 키로 토큰을 받는 상태가 이어져 실전 엔진의 토큰·세션을 밀어낼 수 있다 [추론]. 7단계 전 필수 과제로 남아 있다.
- G-4 (순서) 1단계 완료 기록도 결정 로그에 없다(첫 판정 F-2 그대로).

- **H-4 (가장 큰 위험, C1 (3)·C5 ⑥) 비정상 종료 뒤 재기동하면 디스크에 있던 마지막 줄들이 지워지고, 짧은 녹화는 재기동 표시도 없다.**
  - 원인 [사실]: `RecordedDay.readLines`(`RecordedDay.java:78~89`)는 `BufferedReader(InputStreamReader(GZIPInputStream))`로 줄을 읽다가 끝나지 않은 gzip 멤버에서 `EOFException`이 나면 잡고 끝낸다. 이때 리더 안에 이미 풀렸지만 아직 줄로 돌려주지 않은 글자(디코더·버퍼 몫, 탐침에서 끝 15~45줄)는 버려진다. `DayWriter` 생성자는 이렇게 읽은 줄만으로 파일을 다시 쓴다(`DayWriter.java:90` `rewrite(events, previous)`, `REPLACE_EXISTING`). 그래서 `flush()`로 디스크에 내려간 줄이 재기동 순간 지워진다.
  - QA 탐침(나) 결과 [사실]: `DayWriter`로 N줄 쓰고 `flush()` 뒤 닫지 않고 다시 연 결과(읽힌 줄 / 재기동 뒤 남은 줄 / 재기동 공백 수):
    - N=1, 2, 10 → 0 / 0 / **0**(줄 전부 사라지고 재기동 `DataGap`도 없음)
    - N=100 → 55 / 55 / 1, N=1,000 → 977 / 977 / 1, N=10,000 → 9,973 / 9,973 / 1, N=100,000 → 99,985 / 99,985 / 1
  - 탐침(가): 두 번 비정상 종료한 세 번 기동에서 첫 프로세스의 두 줄이 모두 사라지고, 첫 재기동 공백이 없었다(기대 4건 중 1건).
  - 영향 [추론]: 게이트웨이 `FLUSH_INTERVAL`이 1초(`Gateway.java:29`)라, 창을 닫거나 PC가 꺼지는 비정상 종료 때 디스크에 이미 있던 마지막 수십 줄(장중 수 초 분량)이 재기동 때 지워진다. 줄이 충분히 많으면 공백 시작이 "읽힌 마지막 줄"로 앞당겨져 지워진 구간도 끊김으로 덮이므로 리플레이 판정은 맞게 나온다. 그러나 장 시작 직후처럼 줄이 적을 때 죽으면 녹화가 통째로 사라지고 재기동 표시도 남지 않아(`unmarkedRestarts()`도 `firstSeq ≤ 1`이라 건너뜀, `RecordedDay.java:155`) 그 구간이 "체결 없음"으로 읽힌다. 녹화 손실은 기획서 MD-05와 "녹화·실험 결과 삭제는 되돌리기 어려운 일"(지침 8장 3번)에 걸린다.
  - 고치는 방향 제안(개발 쪽 판단): 끝나지 않은 gzip 멤버는 바이트 단위로 `EOFException`까지 풀린 바이트를 모두 모은 뒤 줄로 나누고, 재기동 때 원본 파일을 덮어쓰기 전에 보관본을 남긴다. "flush 뒤 닫지 않고 다시 열기" 테스트(N=1, 100)를 둔다.
- H-1 해소: 지난 판정의 "74분 공백이 체결 없음으로 읽힘"은 새 녹화에서는 `RECORDER_RESTART`로 막혔다. 2026-10-12 녹화 자체는 표시 없이 남아 있고, 어댑터가 `unmarkedRestarts()`를 읽어야 한다(C4).
- H-2 일부 해소: 영웅문 통합 시세는 저장소 해석 코드(`KiwoomStreamProtocol.unsigned`)를 거치지 않는 독립 출처라 부호·자릿수 같은 큰 오류는 배제된다고 본다 [추론]. 네 값 일치는 KRX 단독 화면으로 확인해야 한다.
- H-3 그대로: QA가 실녹화 결과를 재현할 근거 파일이 없다.
- 오류·순서·장애 시나리오(QA 지침 5장 5번): (1) 정상 종료 뒤 재기동: 공백 표시 정상(`RecordingReplayTest` 새 테스트). (2) 비정상 종료 뒤 재기동: 줄 손실·표시 누락(H-4, 탐침 재현). (3) 재기동 뒤 시계가 앞 구간보다 이름: 공백 시작을 새 수신 시각으로 맞춤(`재기동_뒤_첫_수신이_…` 테스트 통과).
