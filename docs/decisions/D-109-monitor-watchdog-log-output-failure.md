# D-109 감시·모니터 로그 출력 실패 정책: 못 낸 줄은 다시 내고, 판정·알림은 끊지 않음(PR #155·#157 후속)

- 날짜: 2026-10-17
- 상태: 확정 · **추천안 채택(자율)**(지침 8장). 감시 에이전트 코어(`autotrade-monitor-agent-jar`)와 감시(`autotrade-app-watchdog`)의 로그 출력 실패 처리, 결측 로그 문구, 시험만 바꾼다. 임계 판정, 정지 요청 판정(D-092·D-095), 하트비트 판정, 알림 종류·억제(D-100), 결측 경고 간격(D-096·D-108), 감시 설정, 보호 테스트는 바꾸지 않는다. 보호 경로라 사용자 머지로 확정한다.
- 담당: risk-ops 결정·구현. 교차 검토: architect(코드), risk-ops(실전 관련)
- 근거: [PR #155 독립 QA](../reviews/pr-155/qa.md) R1·Q1·Q2, [PR #155 risk-ops](../reviews/pr-155/risk-ops.md) K1·K3, [PR #155 architect](../reviews/pr-155/architect.md) N3·N4·N5, [PR #157 risk-ops](../reviews/pr-157/risk-ops.md) K2·K3, [PR #157 독립 QA](../reviews/pr-157/qa.md) Q1·R2, [D-090](D-090-monitor-agent-and-screen.md), [D-108](D-108-watchdog-missing-after-recovery-and-disk-cause.md)
- MON-05 행의 "내지 못한 WARN·INFO는 다음 주기에 다시 낸다"(v14.47, PR #155)를 아래 1번으로 구체화한다.

## 문제

1. **감시 점검의 로그가 던지면 알림이 영영 빠짐**(PR #155 risk-ops K1, 이 PR에서 범위를 넓혀 확인): 감시 단계는 상태를 바꾼 뒤 로그를 낸다. `HeartbeatWatch.check`의 바뀜 로그가 던지면 상태는 이미 STALE로 바뀌어 다음 점검에서 바뀜으로 안 보이므로 **엔진 멈춤 알림이 나가지 않는다**. `StopRequests.update`의 "만듭니다" 로그가 던지면 그 점검의 정지 요청 파일 쓰기를 건너뛴다. 결측 WARN이 던지면 "자원 값 빠짐" 알림과 그 점검의 압력 판정을 건너뛴다. `tick()`의 catch 안 로그가 던지면 뒤 단계를 건너뛴다.
2. **모니터 에이전트 catch 안 로그**(architect N4): 듣는 쪽 실패 로그가 던지면 남은 듣는 쪽과 스냅샷 반환을 건너뛴다. `start()`의 예약 작업 catch 안 로그가 던지면 예약이 취소돼 실험실 모니터 수집이 멈춘다.
3. **되돌림 방식의 부작용**(PR #155 방식): 출력 실패 시 실패 상태를 되돌려 ① 연속 실패 횟수가 적게 셈(architect N5·risk-ops K3), ② 회복 INFO 출력 실패 뒤 다시 실패하면 사이의 성공 주기가 사라지고 횟수가 이어서 셈(QA Q2), ③ "바뀜" WARN 재출력과 경합 비교에 시험이 없음(QA Q1, architect N3).
4. **반복 출력**(QA R1): 핸들러가 여럿이고 앞이 출력한 뒤 뒤가 던지면 같은 줄이 매 주기 반복된다.
5. **결측 문구**: 미룬 회복 INFO 본문에 이미 회복을 알린 값까지 합쳐 적힘(PR #157 risk-ops K3), 드라이브 원인 문구에 탭·ESC가 남음(QA R2), 드라이브 여럿일 때 원인 짝짓기 시험 없음(QA Q1), 생성자 지역 `Threshold disk`가 필드를 가림(K2).

## 결정

1. **모니터 에이전트: 실패 상태는 실제대로, 못 낸 줄은 들고 있다가 다시 냄**. WARN·INFO 줄 출력이 실패하면 상태를 되돌리지 않고 그 줄을 수집원마다 하나 들고 있다가, 그 수집원에 새 WARN·INFO가 생기기 전까지 다음 주기마다 다시 낸다. 새 줄이 생기면 들고 있던 줄은 버린다(최근 상태가 맞는 줄). 출력 중 다른 호출이 같은 수집원의 새 줄을 만들었으면 실패한 옛 줄은 다시 들지 않는다(줄 번호 비교). DEBUG 반복 줄은 다시 내지 않는다.
2. **반복은 상한 없이 둠(R1)**: 출력됐는지 알 수 없는 경우 유실보다 반복을 고른다. 첫 WARN이 빠지면 운영자가 실패를 모르고, JUL 핸들러·logback 어펜더는 출력 오류를 스스로 삼켜 부분 출력 뒤 예외는 드물다 `[추론]`. 클래스 설명과 MON-05 행에 적는다.
3. **모든 점검 중 로그는 출력 실패를 삼킴**: 모니터 에이전트의 임계·듣는 쪽·예약 작업 로그, 감시의 `tick()`·`reportMissing`·`HeartbeatWatch`·`StopRequests` 로그(`WatchdogLog`), 하트비트 기록기(`HeartbeatWriter`)의 기록 실패·복구·삭제 실패 로그(`beat()`는 던지지 않는다는 약속, `tick()`도 `beat()`를 감쌈, PR #163 architect N1). 결측 알림은 로그보다 먼저 넣는다. 기동 때 로그(설정·채널 안내, 기동 실패 출력)는 대상이 아니다(기동 실패는 표준 오류에도 나감, D-106).
4. **결측 문구**: 회복 INFO·알림 본문은 마지막 회복 INFO 뒤 결측 WARN에 실제로 적은 값만. 드라이브 원인 문구의 제어 문자(CR·LF·탭·ESC 등 `Character.isISOControl`)는 공백으로. 생성자 지역 이름은 `diskThreshold`.

## 대안

| 대안 | 판단 |
|---|---|
| ① 상태는 실제대로 + 못 낸 줄 재출력(채택) | 횟수가 맞고, 회복·재실패가 섞여도 낡은 줄이 나가지 않는다. 대가는 수집원마다 줄 하나와 번호 하나 |
| ② PR #155 되돌림 유지 + 문구만 고침 | 회복 INFO 실패 뒤 재실패(Q2)의 횟수 합산을 고칠 수 없다. 버림 |
| ③ 재출력 횟수 상한(예: 3번, R1 제안) | R1의 반복은 줄지만 핸들러가 3주기 넘게 고장 나면 첫 WARN이 영영 빠진다(PR #119 QA Q1로 되돌아감). 버림 |
| ④ 재출력 간격을 늘려 감(1·2·4…주기) | 반복은 로그 함수로 줄지만 핸들러가 고쳐진 뒤에도 최대 간격만큼 늦고 코드가 늘어난다. 드문 경우라 버림 |
| 감시 로그: 단계마다 try를 더 쪼갬 | 로그 줄마다 같은 처리를 흩어 놓게 된다. 한 곳(`WatchdogLog`)이 낫다. 버림 |

되돌릴 조건: 6단계 운용에서 같은 수집원 줄이 반복돼 로그를 묻는 일이 실제로 보이면 ③·④를 다시 본다.

## 위험과 한계

- 부분 출력 뒤 예외(R1)인 핸들러가 붙으면 그 줄이 핸들러가 고쳐질 때까지 매 주기 반복된다(위 2번).
- 들고 있던 첫 실패 WARN이 출력되기 전에 수집원이 회복하면 그 WARN은 버리고 회복 INFO만 나간다(INFO에 실패 종류와 횟수가 있어 정보는 남는다). 들고 있던 "바뀜" WARN 뒤 다시 바뀌면 새 줄의 "이전 종류"는 운영자가 본 마지막 종류와 다를 수 있다.
- 로그 출력 실패 자체는 어디에도 남지 않는다(출력이 안 되는 로그로 알릴 수 없음). 감시 판정·알림은 이어지므로 운영자는 알림으로 상태를 본다.
- 결측 알림을 로그보다 먼저 넣는 순서는 이제 `WatchdogLog`가 삼키므로 이중 방어다(순서만 바꾸는 변이는 시험이 잡지 않는다).
