# 수집기 실행 절차 (일봉·상장주식수·재무·공시)

[ADR-008](../adr/ADR-008-collector.md), D-050, D-051. 수집기는 4개 프로세스와 따로 도는 단발 명령이다. 증권사 키를 읽지 않고 증권사 API를 부르지 않지만, **같은 PC의 CPU·메모리·디스크를 실전 엔진과 나눠 쓴다.** 그래서 수집기는 스스로 물러난다(ADR-008 2.7): 국내·미국 장 시간 보호 구간에는 실행하지 않고, 힙은 2GB로 고정, 디스크 여유가 20GB 미만이면 멈춘다. 감시 프로세스는 아직 수집기를 멈추지 못한다(Q-041).

## 1. 준비 (한 번)

1. 인증키 발급(사용자 작업, 무료)
   - KRX Open API(`openapi.krx.co.kr`): 회원 가입 → 인증키 신청 → **서비스 이용 신청**: 유가증권 일별매매정보, 코스닥 일별매매정보, 코넥스 일별매매정보. 승인까지 시간이 걸릴 수 있다.
   - OpenDART(`opendart.fss.or.kr`): 인증키 신청(회원당 1개).
2. 설정 폴더(기본 `~/.autotrade`, Windows는 `C:\Users\<사용자>\.autotrade`, `AUTOTRADE_CONFIG_DIR`로 바꿀 수 있음)에 `collector-secrets.json`을 만든다. **`secrets.json`이 아니다.**

   ```json
   { "krx": { "auth-key": "<KRX_OPEN_API_AUTH_KEY>" }, "opendart": { "crtfc-key": "<OPENDART_CRTFC_KEY>" } }
   ```

   - 다른 항목을 넣으면 수집기가 파일 전체를 거부한다(오타·증권사 키 혼입 방지). 키 하나만 있어도 그 명령은 돈다.
   - 이 파일은 저장소에 넣지 않는다(`.gitignore`에 있음). 파일 권한은 본인만 읽게 둔다.

## 2. 첫 실행 확인 (KRX 요청 형식 `[가정]` 확인)

하루만 받아 응답 형식을 확인한다(저장소 루트에서).

```
./gradlew :autotrade-app-collector:run --args="krx-daily --from 2026-10-08 --to 2026-10-08"
./gradlew :autotrade-app-collector:run --args="dart-financials --from 2026-03-01 --to 2026-03-31"
```

- 성공하면 스냅샷 폴더와 품질 리포트 경로가 출력된다. 리포트(`experiments/_data-quality/<스냅샷ID>.md`)의 오류 건수와 "수집 요약"을 확인한다.
- `HTTP 401/403`, `OutBlock_1 목록이 없습니다`, `응답 날짜가 요청과 다릅니다`가 나오면 메시지를 그대로 스레드에 붙여 준다(키는 메시지에 나오지 않는다). 서비스 이용 승인 전이면 403이 날 수 있다 `[가정]`.

## 3. 전체 수집 (여러 날에 나눠 자동으로 이어짐)

```
./gradlew :autotrade-app-collector:run --args="krx-daily --from 2010-01-04"
./gradlew :autotrade-app-collector:run --args="dart-financials --from 2016-01-01"
./gradlew :autotrade-app-collector:run --args="dart-disclosures --from 2010-01-01"
```

- KRX는 하루 9,000회(약관 10,000회의 90%, `--max-calls`는 10,000까지)에서 멈추고 **종료 코드 3**으로 끝난다. 하루 호출 수는 `<설정 폴더>/collector-state/`에 키 단위로 기록돼 `--cache-dir`를 바꿔도 합산된다. 받은 날은 캐시(`<설정 폴더>/collector-cache/`)에 남으니 다음 날 같은 명령을 다시 돌리면 이어 받는다. 2010년부터 전체는 이틀쯤 걸린다.
- `dart-financials`는 훑은 구간을 기억하므로 2장에서 짧게 돌린 뒤 `--from`을 앞당겨도 앞 구간을 빠짐없이 훑는다(이미 훑은 구간은 다시 부르지 않는다).
- OpenDART는 같은 키의 하루 호출을 **몫으로 나눠** 센다(D-123). 재무(`dart-financials`) 몫 기본 10,000회, 공시(`dart-disclosures`) 몫 기본 2,000회(`--max-calls`로 10,000까지), 두 몫 합 20,000회 `[가정]`. 공시 몫은 재무 몫을 깎지 않으므로 재무 전체 수집을 매일 10,000회씩 돌리는 중에도 공시 수집을 함께 돌려도 된다. 몫이나 합이 차거나 한도 초과(020) 응답을 받으면 그날 멈춘다(020이면 두 몫 모두). 오늘 몫별 호출 수는 콘솔 끝 줄(`오늘 공시 몫 호출 N, 같은 키 합 M`)에 나온다.
- `dart-disclosures`는 기본으로 유형 B(주요사항보고)·I(거래소공시)만 받는다(선정 프로필 (라)가 쓰는 유형). 다른 유형을 쓰는 프로필을 만들면 `--types B,I,D`처럼 늘린다. 유형을 늘리면 새 유형은 처음부터 다시 받는다. 최근 달부터 거꾸로 받으므로 전체가 끝나기 전에도 최근 구간 스냅샷이 매일 만들어진다. 2010년부터 B·I 전체 호출 수는 아직 모른다 `[가정]`(첫 실행의 품질 리포트에 나온다).
- 힙은 2GB로 고정돼 있다. 수집기는 스냅샷 쓰기와 품질 리포트를 한 줄씩 읽어 처리하므로 2010년부터 전체(약 1,100만 행)도 이 안에서 돈다. 메모리 부족(`OutOfMemoryError`)이 나면 **상한을 올리지 말고** 메시지를 스레드에 붙여 준다. 실험실이 전 기간 스냅샷을 통째로 읽을 때는 메모리가 모자랄 수 있다(ADR-008 4장).
- 전체 수집은 이틀 이상 걸리므로 장 시간 보호 구간에 걸려 멈출 수 있다(종료 코드 4). 구간이 끝난 뒤 같은 명령을 다시 돌리면 이어 받는다.
- KRX가 거래소 캘린더상 거래일(2026년부터)에 빈 목록을 주면 `캘린더상 거래일에 빈 목록` 메시지로 멈춘다(종료 코드 1, 그날은 캐시하지 않음). 일시 오류면 나중에 같은 명령을 다시 돌린다. 그날이 실제 휴장일이면(임시공휴일 등) 3.6 절차로 캘린더를 고쳐야 하니 메시지를 스레드에 붙인다.
- 최근 7일 안 날짜에 KRX가 빈 목록을 주면 아직 게시 전으로 보고 캐시 없이 넘기며, 콘솔에 `게시 전으로 보고 넘긴 시장·날짜: 2026-10-07 KOSPI, ...` 한 줄을 출력한다(다음 실행이 다시 받는다). 같은 날 다른 시장은 자료가 있으면 줄 끝에 `그날 일봉에서 빠지는 시장`을 따로 적는다(`--no-snapshot`이면 `지금 스냅샷을 만들면 그날 일봉에서 빠지는 시장`). 모든 시장이 빈 날은 그 날이 스냅샷 거래일에서 빠져 스냅샷이 앞 거래일에서 끝난다. 그래서 이 한 줄이 보이면 부분이든 전체든 이 스냅샷으로 그날 선정 결과를 내지 말고, 다음 날 다시 수집한 스냅샷을 쓴다(PR #141 strategy-researcher R3, PR #143 strategy-researcher R2).
- 수정 계수 표본 대조: 분할 사례(예: 2018-05-04 삼성전자 50:1) 전후 며칠의 수정 종가(`종가 × adj_factor`)를 HTS 수정주가 차트와 비교해 결과를 스레드에 남긴다.

## 3.5 실행 시간과 장 시간 보호 구간

수집기는 아래 구간(거래일만, 거래소 캘린더 기준)에는 시작하지 않고, 실행 중 들어서면 다음 호출 전에 멈춘다(종료 코드 4).

| 시장 | 서울 시각 보호 구간 |
|---|---|
| 국내(KRX) | 08:00~16:00 (정규장 09:00~15:30의 60분 전~30분 뒤) |
| 미국 | 서머타임 중 21:30~05:30, 아닐 때 22:30~06:30 |

- 매일 실행은 **서울 18:30~21:30 사이**에 맞춘다(서머타임이 아니면 22:30 전).
- 실전 엔진을 끈 날에만 `--allow-during-session`으로 풀 수 있다.
- 거래소 캘린더 수록 범위 밖이면(KRX 캘린더는 2027-12-31까지, 미국은 2028-12-31까지) 장 시간인지 판단할 수 없어 멈춘다. 다음 날까지 보므로 실제로는 **서울 2027-12-31 00:00**부터 멈춘다. 그 전에 3.6 절차로 갱신한다(data-engineer).
- 거래소 공지로 확인되지 않은 휴장일(`verified: false`, 2027년 전부와 2026-12-25·12-31)은 장이 열릴 수도 있으므로 정규장이 있는 날처럼 막는다. 확인 안 된 특별 운영일(연초 개장일, 수능일)은 정규장과 늦춘 구간을 합쳐 막는다(D-064 5번).
- **감시의 정지 요청**(D-058): 설정 폴더에 `collector-state/stop-request` 파일이 있으면 PC 자원이 모자란다는 감시 프로세스의 요청이다. 수집기는 시작하지 않고, 실행 중이면 다음 호출 전에 멈춘다(종료 코드 4). `--allow-during-session`으로도 풀리지 않는다. **이 파일은 직접 지우지 않는다.** 자원이 회복되면 감시가 지우고, 그 뒤 다시 돌리면 캐시에서 이어 받는다.
  - 수집기는 시작할 때 `감시 정지 요청 확인 위치:`로 보는 경로를 출력한다. **감시 프로세스와 같은 설정 폴더(`AUTOTRADE_CONFIG_DIR` 또는 `--config-dir`)로 실행한다.** 다르면 감시의 요청을 보지 못한다.
  - **요청이 오래 남아 있을 때(예약 실행이 며칠째 종료 코드 4로 끝나고 메시지에 "정지를 요청"이 나올 때)**: ① 감시 프로세스가 살아 있는지 확인하고, 죽었거나 멈췄으면 감시를 다시 띄운다(장애표 #9·#10). 살아 있는지는 거부 메시지에 찍힌 파일 시각으로 본다. 메시지는 "만든 시각"이라고 적지만 실제로는 **감시가 이 파일을 마지막으로 다시 쓴 시각**이고 **UTC**다(끝의 `Z`. 한국 시각은 9시간을 더한다). 감시는 요청이 켜진 동안 점검마다(`watchdog.properties`의 `interval-seconds`, 기본 5초) 이 파일을 다시 쓰므로, 그 시각이 지금(UTC)보다 점검 주기의 3배(기본 15초) 넘게 앞이면 감시가 죽거나 멈춘 것이다. `<설정 폴더>\heartbeat\watchdog.hb`의 `written-at`(역시 UTC)도 같은 뜻이고, 이 파일이 없으면 감시가 꺼져 있는 것이다(D-092). 감시는 설정이 틀리거나 `disks`에 적은 폴더가 없으면 뜨지 않는다. 감시가 설정 오류로 뜨지 않으면 콘솔의 `감시 설정이 틀려 기동하지 않습니다` 줄을 보고 `watchdog.properties`를 고친다. 그 줄 뒤에 "설정 폴더 경로가 틀렸습니다"가 나오면 파일이 아니라 환경 변수 `AUTOTRADE_CONFIG_DIR`(따옴표 없이 폴더 경로만)를 고친다. 콘솔에 `감시가 기동 중 프로그램 오류로 멈췄습니다` 줄이 나오면(종료 코드 1) 설정 파일 문제가 아니므로 고치지 말고 그 줄과 감시 로그를 개발 쪽에 넘긴다(D-106). 살아 있는 감시는 자원이 해제 기준 아래면 파일을 지운다. ② 감시가 살아 있는데도 남아 있으면 실제로 자원이 모자란 것이다. 실험실·녹화 부하를 줄이거나 디스크를 비운다. ③ 감시를 띄울 수 없으면 감시를 먼저 고친다. 그동안 수집은 쉰다(받은 것은 캐시에 남아 나중에 이어 받는다). 파일은 감시만 지운다(D-058). 사람이 지우는 예외는 두지 않는다.

## 3.6 거래소 캘린더 연간 갱신 (data-engineer, D-064)

캘린더는 `autotrade-marketdata/src/main/resources/com/autotrade/marketdata/calendar/krx.json`, `us.json`이다. 수집기, 실험 실행 명령, 리플레이 점검이 모두 이 파일을 읽는다.

1. **매년 7월(월력요항 발표 뒤)**: 우주항공청 다음 해 월력요항(한국천문연구원 `https://astro.kasi.re.kr/kor/life/post/calendarData?year=<연도>`)의 공휴일·대체공휴일 중 평일인 날, 근로자의 날(노동절), 연말 마지막 거래일을 휴장일로, 연초 첫 거래일(10:00 개장)과 수능일(10:00~16:30)을 특별 운영일로 넣고 모두 `"verified": false`로 둔다. 수능일 날짜는 교육부의 수능 시행일 보도자료(시험 약 2년 3~5개월 전 발표, 예: 2028학년도분 2025-06-02, 2027학년도분 2024-08-16)로 확인해 출처를 그 보도자료로 둔다. 캘린더에 없는 날의 특별 운영은 보호가 넓어지지 않아(날짜가 틀리면 그날 16:00~17:00 보호가 빠짐, PR #53 QA R1) 날짜 확인이 필요하다. `coverageTo`를 그해 12-31로 올린다.
2. **매년 3~4월(평가원 그해 수능 시행기본계획 발표 뒤)**: 그해 수능일이 캘린더 날짜와 같은지 다시 대조한다. 다르면 날짜를 고치고 출처 키를 새 키로 바꾼다(PR #54 QA Q1). **공고 뒤 시험일 변경·연기 공지(교육부·평가원, 예: 지진·감염병으로 인한 연기)가 나오면 계절과 상관없이 그날 바로** 새 시험일을 `"verified": false` 특별 운영일로 더하고, **옛 시험일은 지우지 않고** 거래소 공지로 그날 운영 시간이 확인될 때까지 `"verified": false` 특별 운영일로 남긴다(이미 `true`였으면 `false`로 되돌린다). 미확인 특별 운영일은 정규장과 합쳐 보호하므로(`ExchangeCalendar.protectionSession`) 거래소가 옛 날짜를 정규장으로 되돌리든 늦춘 시간을 유지하든 08:00~17:00이 덮인다. 두 날짜 모두 출처 키를 그 공지를 가리키는 새 키로 바꾼다(PR #62 QA Q2). 캘린더는 jar에 묶인 리소스라 고친 뒤 PR·사용자 머지를 거쳐 6번의 반영 단계를 밟아야 한다. **반영이 새 시험일까지 끝나지 않으면 그날 서울 16:00~17:00에는 수집기·실험 명령을 수동으로 시작하지 않고 그 시간대 예약 실행도 끈다. 옛 시험일이 이미 `"verified": true`였다면 반영 전까지 옛 날짜 서울 08:00~09:00에도 같은 조치를 하고, 08:00 전에 시작해 그 시간대로 이어질 수동 실행도 하지 않는다. 공지 때 이미 돌고 있는 수집기·실험 명령(예약 실행 포함)은 옛 날짜 08:00 전에 멈춘다(콘솔에서 중단하거나 작업 스케줄러에서 끝내기, PR #62 QA Q1). 멈출 때는 그 명령의 콘솔 창이나 그 예약 작업만 끝낸다. 작업 관리자에서 `java.exe`를 골라 끝내지 않는다. 실전 엔진·시세 게이트웨이·감시도 같은 `java.exe`로 돈다(PR #63 QA R2)**(거래소가 옛 날짜를 정규장으로 되돌리면 확인된 10:00 개장 기준 보호가 08:00~09:00을 덮지 못한다). 캘린더에 없는 새 시험일은 정규장 보호만 받아 거래소가 1시간 늦추면 서울 16:00~17:00 보호가 빠진다. 거래소가 시간 변경 공지를 내면 3번처럼 대조한다(PR #55 QA Q1). **남겨 둔 옛 시험일 항목은 거래소 공지로 그날 운영이 확인되면 정리한다**: 정규장(09:00 개장)으로 운영하면 특별 운영일 항목을 지우고, 늦춘 시간(10:00~16:30)을 유지하면 `"verified": true`로 바꾼다. 어느 쪽이든 출처 키를 그 공지를 가리키는 새 키로 바꾸고 6번 절차를 밟는다. 그날이 지나도록 공지가 없으면 한국거래소 정규장 체결로 운영 시간을 확인한다. 녹화 원본에 그날 서울 09:00:00~09:29:59 체결이 있으면 정규장으로 운영한 것이고, 없고 10:00부터 체결이 이어지면 늦춘 시간을 유지한 것이다. 녹화에는 장전·장후 시간외 체결이 장구분 없이 섞여 있어 첫·마지막 체결 시각은 개장·폐장을 보여 주지 않는다(`KiwoomStreamProtocol.java:223-229`, 2026-10-12 녹화의 15:40~15:43 시간외 체결). 장전 시간외(정규장일 08:30~08:40, 늦춘 날은 1시간 뒤 `[가정]`, KRX 공식 안내로 확인)는 이 구간에 들지 않는다. `replayCheck` 보고서의 첫·마지막 체결 칸은 확인하려는 캘린더 항목으로 정규장을 잘라 세므로 이 판단에 쓰지 않는다(`ReplayCheck.java:197`). 녹화가 없으면 HTS의 **KRX 단독** 분봉(KRX+NXT 통합 아님)으로 같은 기준을 본다. 둘 다 아닌 시각으로 운영했으면 특별 운영일 항목을 확인한 시각으로 고치고 `"verified": true`로 둔다. 어느 경우든 새 출처 키 값에 확인 방법을 적는다(PR #65 architect-2 F1, risk-ops-2 R3). 정리 전에는 그날 녹화를 실험에 쓰지 않는다(PR #63 QA R1).
3. **한국거래소 다음 해 휴장일 공지가 나오면(보통 12월)**: 공지와 날짜를 하나씩 대조해 맞으면 `"verified": true`로 바꾸고, 다르면 공지를 따른다. 연중 추가 공지(선거일, 임시공휴일)도 같은 방법으로 넣는다. **날짜나 `verified`를 바꿀 때는 그 날짜들의 출처를 반드시 새 출처 키(예: `KRX-2027-NOTICE`, 값은 공지 링크)로 바꾼다.** 선정 결과의 `calendar_digest`는 출처 표와 수록 범위만 해시하므로(`SnapshotSelectionData.calendarDigest`), 출처 키를 그대로 두고 날짜만 고치면 거래일이 달라져도 같은 다이제스트가 남는다.
4. **미국**: NYSE는 3년치를 미리 발표한다(`https://www.nyse.com/markets/hours-calendars`). 수록 범위가 2년 아래로 남으면 다음 해를 더한다.
5. 늦어도 **매년 12월 초**에 다음 해 KRX가 들어 있는지 본다. 서울 기준 12-31 00:00부터 다음 해 1월 1일이 범위 밖이 되어 수집기와 실험 명령이 멈춘다.
6. 바꾼 뒤 `./gradlew :autotrade-marketdata:test`(연도별 평일 휴장 수 테스트를 그해 값으로 더함)와 `./gradlew build`를 돌린다. 출처 표나 수록 범위가 바뀌면 선정 결과의 `calendar_digest`가 바뀐다(조합 실험의 거래일 요약 해시는 거래일 목록 자체도 넣는다). 바꾼 사실을 결정 로그에 남긴다. 머지 뒤에는 캘린더를 쓰는 실행본에 반영한다. 반영 단계는 다음과 같다: 수집기 설치본(`./gradlew :autotrade-app-collector:installDist`)을 다시 만들고, 실험 명령과 리플레이 점검(`./gradlew :autotrade-app-gateway:replayCheck`)은 main을 받은 작업 트리에서 돌린다. 날짜가 바뀐 날의 녹화가 있으면 리플레이 점검을 다시 돌린다. 시세 게이트웨이는 캘린더에서 시간대만 읽으므로(`Gateway.java:63`) 날짜가 바뀌어도 게이트웨이 설치본은 다시 만들지 않는다. 장중에 돌고 있는 게이트웨이의 설치 폴더를 건드리지 않는다(PR #56 QA Q1·Q2, risk-ops-2 N1·N2, architect-2 N2). **반영 작업(`build`, `installDist`, `replayCheck`)을 하는 시간**: `build`·`installDist`는 장 시간 보호와 정지 요청 파일을 확인하지 않으므로(PR #62 QA Q3. `replayCheck`는 D-085부터 확인해 보호 구간이면 종료 코드 4로 시작하지 않는다) 3.5의 보호 구간과 매일 실행 시간(18:30~)을 피해 **서울 16:00(수능일과 2번에서 남겨 둔 옛 시험일은 17:00)~18:30**에 하고, 18:30 전에 끝나도록 시작한다. 그때 못 하면 미국장 보호가 끝난 뒤(서머타임 중 05:30, 아닐 때 06:30)~08:00에 하고, 08:00 전에 끝나도록 시작한다(PR #63 QA Q1). 끝나지 않으면 다음 보호 구간 시작(저녁에는 미국장 보호 시작인 서머타임 중 21:30·아닐 때 22:30, 새벽에는 08:00) 전에 멈추고 다음 창에 이어 한다. 멈출 때는 2번처럼 그 명령의 콘솔에서 중단하고 작업 관리자에서 `java.exe`를 골라 끝내지 않는다. 저녁 창에서 18:30을 넘기면 그날 예약 실행은 반영 작업이 끝난 뒤로 미룬다(PR #65 architect N1·N2, architect-2 N1·N2, risk-ops N2, risk-ops-2 R1·R2).

## 3.7 빈 평일·시장 공백·수정 이벤트 몰린 날 확인 (4단계 사전 등록 전 한 번, D-104)

거래일 하나가 휴장일처럼 빈 목록으로 캐시되면 다음 거래일에 그 시장 종목 거의 전부에 가짜 수정 이벤트가 생기고, 그 앞 기간 수정 계수가 모두 틀어진다. 수집기는 거래소 캘린더 범위 안(2026년부터)의 거래일 빈 목록은 받지 않지만, 2010~2025년은 캘린더가 없어 사람이 한 번 대조해야 한다.

1. 전체 수집이 끝난 뒤(또는 이 변경 전에 이미 끝냈다면 `git pull` 뒤) 같은 명령을 한 번 더 돌린다. 캐시에 있는 날은 다시 부르지 않으므로 API 호출은 최근 며칠뿐이고, 내용이 같으면 같은 스냅샷 ID가 나온다. 품질 리포트는 새 칸을 붙여 다시 쓴다.
   ```
   ./gradlew :autotrade-app-collector:run --args="krx-daily --from 2010-01-04"
   ```
   끝에 `빈 평일 N일(캘린더상 거래일 N), 시장 하나만 빈 날 N건, 같은 날 여러 종목 수정 이벤트 N일` 줄이 나온다.
2. 품질 리포트(`experiments/_data-quality/<스냅샷ID>.md`)의 세 칸을 본다.
   - **빈 평일**: 연도별 개수와 날짜. 한 해 평일 휴장일은 보통 10~15일이다 `[추론]`(공휴일·대체공휴일·선거일·근로자의 날·연말 마지막 거래일). "캘린더상 거래일(오류)"은 0이어야 한다. "최근·게시 전(캐시 안 함)"은 KRX가 아직 올리지 않은 최근 날이라 오류가 아니다(다음 실행이 다시 받는다). 날짜 뒤 `[n]`은 그 뒤 첫 자료 있는 날의 수정 이벤트 종목 수다. 실제 휴장일이면 0이거나 몇 건이고, 거래일이 빈 날로 캐시됐으면 그 시장 종목 대부분(수백~수천)이다. 그래서 **"다음 날 이벤트 30 이상" 칸이 0이 아닌 해의 큰 `[n]` 날짜가 먼저 의심할 날**이다. 캘린더 범위 밖 날짜는 이 표를 스레드에 붙이면 Claude가 연도별 공휴일·KRX 휴장일 공지와 대조한다. 날짜와 건수만 있어 붙여도 된다.
   - **시장 하나만 빈 날**: "없음"이어야 한다.
   - **같은 날 여러 종목 수정 이벤트**: "직전 공백"에는 직전 자료 있는 날 이후의 빈 평일·시장 공백이 모두 나온다. 실제 휴장일은 다음 거래일에 이벤트를 만들지 않으므로, **직전 공백이 있고 비율이 높으면(예: 그날 종목의 절반 이상) 공백 날짜가 모두 휴장일로 보여도 가짜 이벤트로 보고** 그 공백 날짜들의 캐시를 다시 받는다(3번). 직전 공백이 없을 때만 권리락이 몰린 날일 수 있으니, 표본 2~3종목을 HTS 수정주가 차트로 확인한다.
3. 휴장일이 아닌 빈 평일이나 시장 공백이 있으면(위의 가짜 이벤트 직전 공백 포함) 그 날짜·시장의 캐시 파일 `<설정 폴더>/collector-cache/krx/<시장>/<연도>/<yyyyMMdd>.json`을 지우고 1번 명령을 다시 돌린다(그 날만 다시 받는다). 캐시는 원문 응답이라 지워도 다시 받을 수 있다. 다시 받아도 빈 목록이면 스레드에 알린다.
4. 결과(세 칸 요약)를 4단계 스레드에 알린다. 이 확인이 끝나야 사전 등록을 한다.

## 4. 매일 운영 (장 마감 뒤)

순서: `krx-daily` → `dart-financials` → `dart-disclosures` → (ADR-007 구현 뒤) 선정 결과 일괄 명령.

- `krx-daily`는 기본 `--to`가 서울 18:00 전이면 어제, 뒤면 오늘이다. 18:30 이후, 미국 장 보호 구간 전에 돌린다(3.5).
- `dart-financials`는 어제까지 접수된 공시를 훑는다. **매일 돌려야** 정정 공시가 나오기 전에 원 공시 값을 받아 둔다(MD-10 기본 규칙). 건너뛴 날의 공시는 다음 실행에서 받지만, 그 사이 정정이 나오면 원 공시 값은 "값 모름"(대체 규칙 대상)이 된다.
- `dart-disclosures`도 **어제까지** 받는다. 단타 선정(`PRE_OPEN_DAILY`)은 T 전날까지 접수된 공시를 쓰므로(c와 T 사이 주말·휴장일 포함), **T 날 00:00 뒤 08:00 전**(장 시간 보호 구간 전)에 돌린다. 그 전에 돌린 스냅샷은 T 전날을 덮지 않아 그 스냅샷으로 T 선정을 내면 `STALE_INPUT`으로 멈춘다(0종목 결과를 내지 않는다). 예약 작업은 07:00 `[가정]`쯤 둔다. 종목 코드를 붙이려고 가장 늦은 KRX 일봉 스냅샷의 종목 이력을 읽는다(`--krx-snapshot ID`로 지정 가능). 그래서 같은 날 `krx-daily`를 먼저 돌린다.
- 공시 품질 리포트 `<--report-dir>/dart-disclosures-<스냅샷 ID>.md`를 첫 전체 수집 뒤 한 번 보고 아래 네 가지를 스레드에 붙인다(PR #196 strategy-researcher M2, 생존편향 확인). 이것을 확인하기 전에는 공시 조건 선정 (라)의 과거 구간 결과를 선정 엣지 근거로 쓰지 않는다.
  1. "종목 코드" 표: 못 붙인 행을 유형·법인 구분별로 본다. 상장폐지 회사는 `E`(기타)로 나올 수 있으니 `E`도 함께 본다 `[추론]`.
  2. "상장폐지 종목 공시 확인": 수집 구간 안에 상장폐지된 종목(종목 코드 단위, 이력 구간이 모두 닫힌 종목) 중 상장 기간(날짜 단위) 안 공시가 붙은 비율과, 같은 방식으로 센 상장 유지 종목 비율(기준선). 폐지 종목 비율이 기준선보다 크게 낮으면 생존편향이 남은 것이다.
  3. "접수 연도별 못 붙인 행": 옛 연도일수록 비율이 오르는지.
  4. 손 확인: KRX 종목 이력에서 상장폐지 종목 세 개를 정해진 규칙으로 고른다: 같은 `code`의 `instrument_history.csv` 행이 모두 `valid_to`가 찬 종목(이름·소속부 변경으로 닫힌 행 뒤에 열린 행이 있으면 상장 유지) 중 마지막 `valid_to`가 2015~2020년인 종목을 `code` 오름차순으로 앞 3개. DART 전자공시 누리집(`dart.fss.or.kr`) 공시 통합검색에서 그 회사 이름으로 상장 기간 중 주요사항보고·거래소공시를 찾는다. 같은 접수번호가 공시 스냅샷 `disclosures.csv`에서 그 종목 코드로 붙어 있는지 본다(키가 필요 없는 누리집이라 키가 남지 않는다). 셋 중 하나라도 코드가 비어 있으면 결과를 스레드에 붙인다.
  - "보고서명 대괄호 머리말" 표는 선정에서 세지 않는 정정·첨부 공시의 종류별 건수다. `[연장결정]`·`[변경등록]`이 많으면 함께 붙인다(새 사건일 수 있음).
- 예약 작업은 설치본을 **낮은 우선순위로** 돌린다. `./gradlew :autotrade-app-collector:installDist` 뒤:
  - Windows 작업 스케줄러: 동작에 `cmd /c start "" /low /wait <저장소>\autotrade-app-collector\build\install\autotrade-collector\bin\autotrade-collector.bat krx-daily --report-dir <저장소>\experiments\_data-quality --experiments-dir <저장소>\experiments --keep-snapshots 3`. 작업 설정의 우선순위도 낮게(기본 7) 둔다.
  - Linux·macOS: `nice -n 19 <저장소>/autotrade-app-collector/build/install/autotrade-collector/bin/autotrade-collector krx-daily --report-dir <저장소>/experiments/_data-quality --experiments-dir <저장소>/experiments --keep-snapshots 3`
  - 힙 상한(2GB)은 설치본 실행 스크립트에 들어 있다. `JAVA_OPTS`로 올리지 않는다.
- 종료 코드: 0 완료, 1 오류(키·형식·네트워크), 2 사용법 오류, 3 호출 상한·한도 초과(다음 날 이어 받음), 4 실전 PC 자원 보호로 멈춤(감시의 정지 요청, 장 시간 보호 구간, 디스크 여유 부족. 요청이 풀리거나 구간이 끝나거나 공간을 비운 뒤 다시 돌리면 이어 받음).

### 5.1 디스크 용량과 보관

- 추정 `[추론]`: 2010년부터 전체 일봉 스냅샷 하나 약 1,100만 행, 수백 MB. 원문 캐시(KRX 날짜·시장별 응답)는 수 GB. 재무 스냅샷·캐시는 수십~수백 MB. 매일 새 스냅샷을 만들면 정리하지 않을 때 한 달에 수 GB~수십 GB가 쌓인다.
- 시작할 때와 스냅샷을 쓰기 전에 캐시·스냅샷 폴더 디스크 여유가 20GB(`--min-free-gb`로 바꿈) 미만이면 멈춘다. 실전 엔진의 상태 기록·DB가 같은 디스크를 쓸 수 있기 때문이다.
- `--keep-snapshots K`를 주면 **일봉(`krx-daily`)과 공시(`dart-disclosures`)만** 그 명령이 만든 종류에서 최근 K개, 방금 만든 것, `experiments/`(`--experiments-dir`) 아래 파일에 ID가 적힌 것만 남기고 옛 스냅샷 폴더를 지운다. 품질 리포트(`_data-quality`)는 참조로 치지 않는다. 실험 폴더를 못 찾으면 지우지 않는다. **실험실 DB에만 적힌 스냅샷 참조는 보지 못한다**: 실험을 돌리면 `experiments/<실험ID>/`에 쓴 스냅샷 ID를 꼭 남긴다. 주지 않으면 지우지 않는다. 지운 일봉 스냅샷은 같은 `--from`·`--to`로 다시 만들면 원문 캐시가 남아 있는 한 같은 ID로 복원된다. 지운 공시 스냅샷은 같은 ID로 복원된다는 보장이 없다(이번 달 창이 실행마다 늘고, 이름 대조에 쓴 KRX 스냅샷도 바뀜). 공시 스냅샷은 전 기간 공시 행을 담아 매일 커지므로 정리 대상으로 두되, 실험에 쓴 ID는 실험 폴더에 남겨 지워지지 않게 한다. **재무 스냅샷(`dart-financials`)은 지우면 같은 내용으로 다시 만들 수 없어(공시·정정·대기 확정이 실행마다 늘어남) `--keep-snapshots`를 줘도 지우지 않는다.** 크기가 작아 그대로 둔다. 손으로 지우면 되돌릴 수 없다. 원문 캐시는 지우지 않는다(다시 받으려면 호출 한도를 다시 써야 한다).
- 실험에 쓴 스냅샷은 실험 설정(`experiments/<실험ID>/`)에 스냅샷 ID를 적어 두어야 정리 대상에서 빠진다.
- 같은 하위 명령을 동시에 두 개 돌려도 호출 기록은 잠금으로 합산된다. 그래도 같은 캐시를 함께 쓰므로 한 번에 하나만 돌린다.

옵션 전체는 `CollectorMain` 주석 또는 인자 없이 실행했을 때 나오는 사용법을 본다.
