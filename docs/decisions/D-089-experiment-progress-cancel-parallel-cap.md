# D-089 실험 실행기 진행 보고·취소·병렬 상한(SIM-14)

- 날짜: 2026-10-15
- 상태: sim-engine 추천안. **실전 관련 PR(지침 10장)로 처리**: 장애 설계 5.2 정지 순서 0번(장애표 #10)의 정지 확인이 지나가는 실험 실행 명령의 관문 배선을 바꾸므로(같은 경로를 바꾼 D-063·D-085 선례, PR #113 risk-ops·architect F2) risk-ops 검토 후 독립 QA를 거쳐 **사용자가 PR을 직접 머지하면 확정**. 정지 요청 파일 규칙(감시만 지움, 판단 못 하면 멈춤, 해제 옵션으로 안 풀림)과 보호 테스트는 바꾸지 않는다. 실전 엔진·게이트웨이·감시 코드 변경 없음.
- 담당: sim-engine. 교차 검토: architect(코드·모듈 경계, REST 계약, 아래 결정 4의 설정 키 변경 제안), risk-ops(정지 확인 배선, 장애표 #10).
- 근거: [ADR-004](../adr/ADR-004-simulation-engine.md) 4장 후속 표 "실험 진행 보고·취소, 실험실 자원 상한(SIM-14)" 행(`lab.max-parallel-runs`를 `parallelism`으로), [D-079](D-079-stage-5-scope.md) 이연 표(UI-02 진행 상태·UI-01 SSE의 선행 작업), 기획서 SIM-14·UI-02, [D-062](D-062-lab-loads-result-bundle.md)(실험실은 실험을 돌리지 않음), [D-063](D-063-experiment-command-stop-gate.md)(실험 명령의 정지 확인)

## 결정

1. **실행기 제어 통로는 `RunGate` 하나**: 실행기(`SimulationExperimentRunner`)는 이미 실험 시작·Run 시작 전·거래일 마감마다 `RunGate`를 묻는다(D-063). 같은 통로에 기본 메서드 두 개를 더한다.
   - `onProgress(ExperimentProgress)`: 실험 시작(`STARTED`), Run 시작·거래일 마감·Run 끝(`RUNNING`), 실험 끝(`FINISHED`)에 진행 상태를 넘긴다. 값: 실험 ID, Run 수·시작·끝·실패 수, Run당 거래일 수, 마감한 거래일 합(끝난 Run은 남은 날까지 채움). Run 스레드들이 한 잠금 안에서 값을 바꾸고 넘겨 받는 쪽이 보는 값이 뒤로 가지 않는다. 받는 쪽이 예외를 던지면 그 실험의 남은 보고를 끄고 실험은 계속한다.
   - `maxParallelRuns()`: 실행기는 등록 파일의 `parallelism`과 이 값 중 작은 쪽으로 스레드 풀을 만든다(1~64, 기본 64 = 상한 없음).
   - 두 가지 모두 결과에 영향이 없다: 진행 보고는 실행기에 돌려주는 값이 없고 Run 상태를 건드리지 않으며, 병렬 수는 원래 결과를 바꾸지 않는다(SIM-09). 골든 스냅샷이 상한 1·2·64와 진행 보고 유무에 상관없이 바이트로 같음을 시험으로 고정(`RunProgressTest`).
2. **취소는 정지 확인의 한 종류, 종료 코드 3**: `ExperimentCancelledException extends ExperimentStoppedException`. 실행기는 정지와 같은 지점(Run 시작 전, 거래일 마감)에서 결과 없이 실험 전체를 끝낸다. 실행 명령 본체 6개는 `e.exitCode()`(정지 4, 취소 3)로 끝난다. 실행기는 처음 받은 정지 예외 하나만 올리므로, 취소로 끝난 뒤 실행 명령이 정지 확인을 한 번 더 보고 감시의 정지 요청이나 장 시간 보호가 있으면 종료 코드 4와 그 정지 이유로 올린다(`ExperimentJob.afterCancel`, 독립 QA PR #113 R1). 장애표 #10의 감지 단서(종료 코드 4)가 취소와 겹친 회차에도 남는다.
3. **실행 명령(`autotrade-app-experiment`)의 작업 파일**(`ExperimentJob`, 위치는 `ExperimentJobFiles`): `<설정 폴더>/experiment-state/jobs/`
   - `<실험ID>.lock`: OS 파일 잠금. 같은 실험 ID를 두 명령이 함께 돌리면 뒤 것은 종료 코드 1(결과 폴더 덮어쓰기 방지). 프로세스가 죽으면 OS가 푼다.
   - `<실험ID>.status`: 상태 파일(`experiment-job-v1`, `키: 값` 줄, 16 KiB 상한). 임시 파일에 쓰고 바꿔 넣는다. 단계가 바뀌면 바로, 진행 중에는 1초에 한 번까지, 따로 5초마다 갱신 시각만 다시 쓴다(심장박동). 끝나면 종료 코드에 맞는 상태(`COMPLETED` 0, `INPUT_ERROR` 1, `NEEDS_REVIEW` 2, `CANCELLED` 3, `STOPPED` 4, `FAILED` 그 밖)와 정지·취소 이유 한 줄을 남긴다. 파일 쓰기 실패는 실험을 멈추지 않는다(경고 한 번).
   - `<실험ID>.cancel-request`: 취소 요청. 실험실이 만들고 실행 명령이 시작(지난 요청 무시)·끝에 지운다. 정지 요청 파일(감시만 지움, D-058)과 달리 "있는지 판단 못 함"을 취소로 보지 않는다(취소는 사람의 선택이고 자원 보호는 정지 요청 파일 몫). 감시의 정지 요청이 취소보다 먼저다(종료 코드 4).
   - 작업 ID는 실험 ID(합성 시세 비교는 `EXP-20261008-STR01`). 실험 ID 형식(`[A-Z0-9][A-Z0-9-]{0,47}`)만 파일 이름에 쓴다. 실험 ID 인자가 없거나 형식이 틀리면 잠금·상태 파일 없이 본체를 돌리지 않고 종료 코드 1.
   - 작업 폴더를 쓸 수 없거나(디스크 고갈 등) 같은 실험이 이미 돌아도, 정지 확인이 멈추라고 하면 종료 코드 4와 정지 이유를 낸다(장애표 #10의 감지 단서 유지, PR #113 risk-ops F1).
   - 상태 파일(실험실 REST로 나감)의 메시지에서는 설정 폴더 절대 경로를 `<설정 폴더>`로 바꾼다(ADR-005 live `stopReason`과 같은 기준).
   - 결정론 확인 기록(`inputs.yaml` 등)과 로그는 실제로 쓴 병렬 수(등록 파일 `parallelism`과 상한 중 작은 쪽)를 적고, 그 값이 1이면 두 실행이 모두 직렬이라 "확인 안 함"으로 적는다(PR #113 architect F1).
4. **병렬 상한의 출처는 실행 명령 옵션**: 실행 명령은 `--max-parallel-runs=N`(Gradle `-PmaxParallelRuns`, 1~64, 기본 4)을 `maxParallelRuns()`로 준다. 기본 4는 설정 키 `lab.max-parallel-runs`의 기본값과 같다 `[가정]`(ADR-001 3장 예산). ADR-004 4장 후속 표는 "`lab.max-parallel-runs`를 `parallelism`으로"라고 적었지만, 실행 명령은 설정 로더(`ConfigLoader`·`RuntimeConfig`)에 의존하지 못한다(보호 테스트 `ArchitectureTest.EXPERIMENT_COMMAND_READS_NO_PROCESS_CONFIG`, D-063 "설정 폴더 위치만 쓰고 증권사 키·계좌·주문을 다루지 않는다"). 이 규칙을 좁히거나 감싸는 클래스로 돌아가는 것은 보호 테스트 약화(지침 11장, 실전 관련 PR)라서 하지 않는다. **변경 제안(architect)**: 실험실 설정 화면의 `lab.max-parallel-runs`를 실행 명령에도 적용하려면 ① 실험실이 설정을 저장할 때 `experiment-state/limits` 같은 비밀값 없는 파일을 함께 쓰고 실행 명령이 그 파일만 읽거나 ② 규칙을 `LabSettings` 같은 좁은 읽기 전용 타입만 허용하도록 바꾸는 안이 있다. ②는 보호 테스트 변경이라 사용자 머지 대상이다. 그 전까지 `config-keys.md`의 이 키 적용 범위는 "실험실" 그대로다.
5. **실험실 REST(읽기와 취소 요청만)**: `GET /api/experiment-jobs`(갱신 시각 내림차순, 페이징, 읽지 못한 파일 수 `unreadable`, 500개 상한 `truncated`), `GET /api/experiment-jobs/{id}`, `POST /api/experiment-jobs/{id}/cancel`(CSRF, 202, 실행 중이 아니거나 60초 넘게 갱신이 없으면 409). 실행 중인데 60초 넘게 갱신이 없으면 상태를 `UNRESPONSIVE`로 보여 준다(강제 종료 등). 실험실은 실험을 돌리지 않고(D-062), 프로세스에 신호를 보내거나 종료하지 않는다(PID는 표시용). 화면(UI-02 진행 상태)과 SSE(UI-01)는 ui-dev 후속.

## 대안

| 대안 | 판단 |
|---|---|
| A. `RunGate`에 기본 메서드로 진행 보고·병렬 상한을 더함(채택) | 정지 확인이 이미 지나가는 길(실행 명령 6개: 조합·녹화·워크포워드·합성 비교·리플레이 확인·주간 점검, 실행기 생성 지점 7곳)을 고치지 않고 모든 실행 명령에 한 번에 적용된다. 기본 메서드라 기존 문·시험은 그대로(진행 보고 없음, 상한 없음) |
| B. 실행기 생성자에 `ProgressListener`·상한 인자를 더함 | 생성자가 이미 13개 인자이고 생성 지점 7곳·실행 명령 6개 서명을 다 바꿔야 한다. 같은 목적지(실행 명령)에서 오는 제어가 두 갈래로 나뉜다. 버림 |
| C. 실험실이 실험을 직접 돌리고 진행을 메모리로 보여 줌 | D-062에서 버린 안(힙 2~4 GB를 넘는 실험, 5.2 정지 순서 1번 장치 없음). 버림 |
| D. 상태를 JSON으로 쓰기 | 실행 명령에 Jackson 의존을 더하고, 두 프로세스가 같은 코덱을 공유하려면 순수 모듈(sim)에 Jackson이 들어와야 한다. 값이 숫자·열거형·한 줄 문장뿐이라 `키: 값` 줄로 충분. 버림 |
| E. 실험실이 실행 명령 프로세스를 PID로 종료해 취소 | PID 재사용 시 다른 프로세스(실전 엔진 포함)를 죽일 수 있다(PR #37 architect F6, 감시도 프로세스를 죽이지 않음 D-058). 버림 |
| G. 실행 명령이 `runtime-config.json`에서 `lab.max-parallel-runs`를 읽음 | ADR-004 후속 표의 문장 그대로지만 D-063 보호 규칙(실행 명령은 설정 로더를 모름)에 걸린다. 규칙을 감싸는 새 클래스로 우회하면 PR #21에서 본 검사 범위 우회와 같은 꼴이다. 옵션으로 받고 변경 제안으로 남김(결정 4) |
| F. 응답 없음 판정을 OS 잠금으로(실험실이 잠금을 잡아 봄) | 실험실이 잠깐 잠금을 쥔 순간 시작하는 명령이 "이미 실행 중"으로 거부될 수 있다. 심장박동 시각으로 판정. 버림 |

되돌릴 조건: 결과 DB 저장(ADR-004 4장)이 생기면 진행 상태도 DB 행으로 옮기고 상태 파일은 같은 값의 사본으로 남긴다. 화면 실행 버튼(D-074 대안 B)이 생겨 실험실이 실행 명령을 띄우게 되면 작업 ID에 실행 순번을 붙인다.

## 위험과 한계

- 진행률은 거래일 기준이다. 날마다 이벤트 수가 다르면(녹화 하루 수십만 줄 대 일봉 한 줄) 시간 진행과 어긋난다. 워크포워드처럼 한 명령이 실험을 여러 번 부르면 상태 파일은 지금 실험의 진행과 시작한 실험 수(`experimentsStarted`)만 보여 주고 명령 전체 진행률은 없다 `[추론]`. 필요하면 워크포워드가 전체 실험 수를 미리 알려 주는 후속으로.
- 취소는 다음 확인 지점에서 걸린다. 녹화 실험은 거래일 하나가 길어 취소가 그날 마감까지 늦을 수 있다(정지 요청과 같은 한계, D-063).
- 응답 없음 판정은 실험실 시계와 실행 명령 시계가 같은 PC라는 전제다. GC가 60초 넘게 멈추면 실행 중인데도 응답 없음으로 보이고 취소 요청이 409가 된다(다음 심장박동에서 회복).
- Windows에서 실험실이 상태 파일을 읽는 순간 바꿔 넣기가 겹치면 그 조회에서만 `unreadable`로 센다(다음 조회에서 읽힘).

## 검증
