## 점검표 밖 발견

- **N1 (수정 필요) 적용 기록이 없는 기록일을 되살리기·리플레이가 조용히 MISSING으로 본다.** `SessionSelections.verify`는 적용 기록이 없으면 그냥 돌아온다(SessionSelections.java `verify`: "적용 기록이 없는 날은 확인할 것이 없다"), `LiveReplayCheck.verifiedSelections`는 기간의 날짜마다 그것만 부른다. 실시간 경로는 그날 첫 이벤트를 기록하기 전에 반드시 `apply`로 적용 기록을 쓰므로(LiveSession.accept), **입력 기록에 이벤트가 있는 거래일에 applied.json이 없다는 것은 파일이 지워졌거나 옮겨졌다는 뜻**이다. 이때 되살리기는 그날을 MISSING으로 계좌를 다시 만들고(원래 실시간은 APPLIED였음), 같은 날 중간 재기동이면 `appliedDay`가 전날로 잡혀 다음 이벤트에서 `apply(today)`가 지금 있는 파일(늦게 온 결과 포함)로 새 적용 기록을 쓴다. 이미 되살린 오늘 앞부분은 `LiveSelectionDays.byDay`에 MISSING으로 남아 있고 리플레이는 새 applied.json(APPLIED)을 읽어 서로 달라진다. D-124 6항이 막으려던 "재기동·리플레이에서 다른 선정"이 이 경로로 열린다. 고칠 것: 선정 계좌가 있으면 **입력 기록에 줄이 있는 거래일마다 적용 기록이 있어야 한다**고 verify에서 실패시키고(세션 열지 않음, 리플레이 확인 종료 코드 1), 시험 하나(applied.json 삭제 후 `LiveSession.open`·`LiveReplayCheck.run` 거절)를 더한다. 지금 `SessionSelectionsTest.verifyFailsWhenAppliedFileIsMissingOrChanged`의 "Missing"은 결과 파일 삭제이고 적용 기록 삭제가 아니다.
- **N2 (수정 필요) CI 실패 두 건.** c584598은 `ExperimentJobStatus.COMMANDS`에 `live-prepare`가 없어 준비 명령이 상태 파일을 만들다 바로 실패하는 실제 결함이었다(6a57bef가 고침, 코드로 확인). 6a57bef는 RecordingSelectionTest 고정 데이터가 번들 캘린더 범위(2026-01-01~) 앞 날짜를 만들어 실패한다. 고정 데이터 날짜를 캘린더 범위 안으로 옮기거나, 범위 앞 일봉이 필요하면 그 이유와 함께 고정 캘린더를 넣는다. 고친 뒤 sim 뒤 모듈(app-lab, architecture-test)까지 전부 통과한 CI를 확인해야 한다.
- **R1 (권고) "덮어쓰지 않음" 쓰기가 원자적이지 않다.** `writeAtomic(..., replace=false)`는 `Files.exists(target)` 확인 뒤 `Files.move(..., ATOMIC_MOVE, REPLACE_EXISTING)`이다(SessionSelections.java `writeAtomic`). D-124 위험 절이 인정한 "밖 명령과 실험실 준비가 같은 날 파일을 동시에 씀"에서, 둘이 서로 다른 `latest` 스냅샷을 골랐다면 확인과 이름 바꾸기 사이에 뒤에 온 쪽이 이미 적용된 결과 파일을 바꿀 수 있고, 그러면 그 세션은 재기동에서 내용 해시 불일치로 열리지 않는다. 창은 짧지만 없앨 수 있다: 결과 파일·적용 기록은 `Files.createLink(target, tmp)`(있으면 FileAlreadyExistsException) 후 tmp 삭제, 또는 밖 명령이 세션 폴더 잠금(`LiveSession.LOCK_FILE`)을 공유 잠금으로라도 잡게 한다. 사용자 PC가 Windows라 ATOMIC_MOVE의 교체 동작을 시험으로 고정해 두는 것도 권한다.
- **R2 (권고) 계산 실패가 밤새 5분마다 전체 스냅샷을 다시 읽는다.** `SelectionPreparer.prepare`의 PRODUCER_FAILED는 problem 파일만 남기고 `nothingToDo`는 결과 파일 유무만 보므로, 장 밖 창 동안 5분마다 일봉 스냅샷 전체를 다시 올린다(LiveSelectionPrep.prepare → SnapshotInputs.load). 실험실 힙·디스크를 세션과 나눠 쓰므로, 같은 스냅샷 ID로 같은 사유가 이미 있으면 다음 스냅샷이 나올 때까지 건너뛰는 것을 권한다.
- **R3 (권고) 준비 스레드 OOM.** `prepareOnce`는 RuntimeException만 잡는다. `heapFits`는 행 수 × 1KB `[가정]`이라 틀리면 OutOfMemoryError가 실험실 전체(선정 없는 계좌 포함)를 흔든다. 실제 KRX 일봉 전체로 1회 측정해 D-124 위험 절의 `[가정]`을 숫자로 바꾸는 후속을 남기길 권한다.
- **R4 (참고)** 녹화 실험 `SelectionStage.prepare`는 힙 검사 없이 녹화 데이터와 같은 힙(기본 `-Pheap=3g`)에 스냅샷 전체를 올린다. 명령 프로세스라 실시간에는 영향이 없지만, 실패 시 안내 문구(`-Pheap`)가 있으면 좋다. 또 `runAndWrite`는 이전 실행이 남긴 `selections/<날짜>/` 파일을 지우지 않아, 기간을 줄여 다시 돌리면 옛 날짜 파일이 남는다(gitignore라 커밋엔 안 들어감).
- 확인한 좋은 점: 선정 계좌는 profiles 뒤에 붙어 앞 계좌 번호·시드 불변(LiveSetup.of, RecordingExperiment.run), 적용 기록은 첫 이벤트 기록 전 + 실패 시 이벤트 미기록·세션 멈춤(LiveSession.accept, 시험 sessionStopsWithoutRecordingWhenAppliedRecordCannotBeWritten), 이벤트 스레드에서 계산하지 않음(준비 스레드 MIN_PRIORITY, 정지 관문 매 선정), 스냅샷 ID 정규식으로 경로 밖 접근 차단(RegisteredSelections.SNAPSHOT), 녹화 실험은 `latest` 거부, 선정 계좌 있는 등록의 녹화 판정 거절(LiveJudgement).
