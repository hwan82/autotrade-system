## 점검표 밖 발견 (실패 시나리오)

### F1. 상태 파일 읽기에 상한이 없음 → 실전 엔진·감시 OOM 가능 (A8·A9) — 수정 필요
- 계약: 판정 0번 `PRODUCER_FAILED`는 "그 거래일을 적용 범위에 넣는 그 선정의 기록 중 가장 늦은 것"을 찾는다(:193). 이를 위해 엔진은 `_status/<MARKET>/` 아래 상태 파일을 읽어야 한다. 결과 파일에는 크기 상한 16 MiB와 "같은 ISO 주 안" 읽기 범위가 있지만(:204, :206) **상태 파일에는 크기 상한도, 읽을 파일 범위도 없다.** 상태 파일 정리 정책도 후속(:307)이라 매일 2개씩 영원히 쌓인다.
- 시나리오 1: 일괄 명령 버그·디스크 오류로 상태 파일 하나가 수 GB가 되거나(또는 손으로 잘못 복사) 엔진이 장전 고정 때 이를 통째로 파싱 → 엔진 힙 소진 → `OutOfMemoryError`는 :205의 "파싱·I/O 예외를 그 계좌 판정에 가둔다"로 잡히지 않는 경우가 많다(다른 스레드에서도 할당 실패) → 실전 엔진 프로세스 다운 → 보유 종목 손절 감시 중단. 같은 파일을 감시 프로세스(킬스위치, :228)도 읽는다.
- 시나리오 2: 1년 운영 뒤 상태 파일 ~500개. 엔진이 매 장전 전부 열면 30초 고정 예산(:206)을 잠식 → F3와 겹쳐 계좌들이 `MISSING`.
- 덧붙여: 시작 시 `RUNNING` 기록 쓰기가 실패해도 계산을 계속하는지 정하지 않았다(:217). 기록이 하나도 없으면 "판정은 파일로만"(:196, 열린 쪽)이므로, 첫 상태 기록 쓰기 실패 시 일괄 명령이 결과 파일을 쓰지 않고 끝나야 닫힌 쪽이 유지된다.
- 고칠 방향: 상태 파일에도 크기 상한(초과 시 그 선정 `PRODUCER_FAILED`)과 읽기 범위(파일 이름의 실행 날짜가 대상 거래일 기준 최근 N거래일 이내)를 계약으로 정하고, 감시 프로세스에도 같은 상한을 둔다. 첫 `RUNNING` 기록 실패 시 일괄 명령은 아무 결과 파일도 쓰지 않고 실패 종료.

### F2. 자원 부족 정지 신호 우회와 중복 실행 (A8) — 수정 필요
- 계약: "시작할 때 오래된 `stop-request`(자기 시작 시각 이전)는 지우고 시작한다"(:223). 감시는 "자원 임계치에서 파일을 만든다"(:222)고만 하고, 계속 임계치일 때 다시 만드는지, 일괄 명령이 압박 중 시작을 거부하는지 정하지 않았다. 단일 실행 잠금도 없다.
- 시나리오 3: 장 마감 뒤 실험실 리플레이로 메모리 압박 → 감시가 `stop-request` 생성 → 실행 중이던 일괄 명령 A가 `ABORTED` 종료 → OS 예약 작업 재시도(또는 사용자의 손 실행) B가 시작하며 그 `stop-request`를 "오래된 것"으로 지우고 압박 속에서 계산을 시작. 5.2 1번 "신규 실행 중단"이 지켜지지 않는다.
- 시나리오 4: 예약 작업과 손 실행이 겹치면 JVM 2개(각 512 MiB)가 돌아 :225 "영향의 상한이 정해져 있다"가 깨지고, 같은 이름 상태 파일(`<날짜>-POST_CLOSE.json`, :217)을 서로 덮어써 한쪽의 `RUNNING`이 다른 쪽의 `OK`로 지워질 수 있다(크래시한 실행의 흔적이 사라짐).
- 고칠 방향: 일괄 명령은 `stop-request`가 있으면 **지우지 않고 시작을 거부**(종료 코드 2)하고, 지우는 것은 감시가 압박 해소 시에만 하거나 파일에 만료 시각을 넣는다. 시장별 단일 실행 잠금(파일 잠금)으로 동시 실행을 거부하고, 상태 파일 이름에 실행 ID를 넣어 덮어쓰기를 없앤다.

### F3. 장전 고정 예산이 계좌 사이에 공유됨 (A7) — 수정 필요
- 계약 :206 "고정 작업 전체에 시간 상한, 넘으면 남은 계좌는 `MISSING`".
- 시나리오 5: 계좌 X의 선정 폴더에 같은 주 `apply_from` 파일이 5개(재수집으로 내용 해시가 다른 파일들, :142) 있고 각각 상한 근처 크기 → X의 읽기가 30초를 다 씀 → 순서상 뒤의 계좌 Y·Z는 정상 파일이 있어도 그날 신규 진입 0건. 한 계좌의 입력 이상이 다른 계좌 운용에 번진다.
- 고칠 방향: 계좌(또는 선정)별 시간 예산을 두고, 예산 초과는 그 계좌만 닫는다. 서로 다른 선정을 병렬로 읽거나 선정 해시별로 한 번만 읽어 공유하는 방식도 가능.

### F4. 주간 갱신 선정의 주중 재생산이 막혀 있지 않음 — 권고(차단 아님)
- `POST_CLOSE_WEEKLY`의 생산 시점은 "그 주 마지막 거래일 장 마감 뒤"(:174)인데, 일괄 명령의 "하는 일"은 목록의 선정마다 "다음 적용 거래일 결과"를 계산한다(:217). 예약 작업이 매일 돌면 화요일에 `apply_from`=수요일, `apply_to`=금요일인 주간 결과가 생기고, 판정(:182-189)과 선택 규칙("입력 기준일이 가장 늦은 것", :199)상 이 파일이 `VALID`로 월요일 파일을 이긴다. [추론] 실전·실시간 모의에서 주간 선정이 사실상 매일 바뀌고, 실험실 리플레이(주 단위)와 입력이 달라져 D-044 "모의와 실전 같은 입력"이 흔들린다. 안전 경로(Guard·블랙리스트)는 영향 없음.
- 고칠 방향: 일괄 명령은 주간 선정을 그 주 마지막 거래일에만 생산하고, `SelectionValidity`는 주간 결과의 `apply_from`이 "직전 주 마지막 거래일의 다음 거래일"이 아니면 `MALFORMED`로 본다.
