# 6단계 실시간 모의 세션 운용 절차(사용자 PC)

- 근거: [D-076](../decisions/D-076-live-feed-and-session.md), [ADR-010](../adr/ADR-010-live-feed-and-session.md)
- 대상: 장중에 게이트웨이 실시간 시세로 실험실의 모의 계좌 여러 개를 돌리고, 끝난 뒤 리플레이와 같은지 확인한다. 실전 주문은 없다(게이트웨이는 주문 API를 부르지 않음, MD-01).
- 실제 운용 등록과 날짜별 명령: 시험 운용 `EXP-20261020-LIVE00`, 본 운용 `EXP-20261026-LIVE01`([D-113](../decisions/D-113-stage-6-live-operation.md)). 장 시작 전 복사·붙여넣기 순서는 [6단계 시작 점검표](stage-6-start-checklist.md), 판정 기준은 [6단계 계획](../strategy/stage-6-plan.md) 4장. 아래 예시의 `EXP-20261015-LIVE01`은 형식 설명용이다.
- 실험실 화면의 **실시간 모의** 메뉴(http://127.0.0.1:8480/#/live)에서 등록 파일을 골라 시작·멈춤·끝내기를 하고, 계좌별 상태와 최근 공백을 본다(3초마다 갱신). 계좌 ID를 누르면 그 계좌의 체결 내역과 거절 사유를 최근 것부터 본다(D-120, 그 기능이 들어간 코드로 실험실을 띄운 뒤부터). 끝낸 세션의 체결은 `experiments/<ID>/live-detail.txt`의 `fill` 줄로 본다. 아래 PowerShell API 호출은 화면 없이 할 때 쓴다.

## 1. 운용 전(장 시작 전날까지)

1. 등록 파일을 만들고 **커밋**한다(사전 등록, 운용 중 고치지 않음). 예: `experiments/EXP-20261015-LIVE01/experiment.yaml`

   ```yaml
   id: "EXP-20261015-LIVE01"
   question: "장중 프로필들이 실시간 시세에서 리플레이와 같은 결과를 내는가"
   input: "live"
   market: "KRX"
   from: "2026-10-15"
   to: "2026-12-11"
   seed: "20261015"
   seed-capital: "10000000"
   benchmark: "005930"
   profiles:
     - "kr-bh-baseline@1"
     - "kr-random-control@1"
   boards:              # 게이트웨이 감시 종목 중 받을 종목. 여기 없는 종목은 세션에 넣지 않는다
     - "005930 KOSPI"
   ```

2. `boards` 종목이 게이트웨이 감시 목록에 들어 있는지 확인한다(없으면 세션에 이벤트가 오지 않음).
3. 설정 폴더(`AUTOTRADE_CONFIG_DIR`, 기본 `~/.autotrade/`) 디스크 여유를 본다. 입력 기록(`live-sessions/<ID>/journal/`)이 게이트웨이 녹화와 비슷한 크기로 하루치씩 쌓인다.

## 2. 장 시작 전

1. 게이트웨이: `./gradlew :autotrade-app-gateway:run`. 로그에 `실험실 시세 전달 소켓을 열었습니다`가 나와야 한다. `열지 못해 녹화만 합니다`가 나오면 설정 폴더 경로가 길거나(약 100자) 다른 게이트웨이가 떠 있는 것이다. 녹화는 그대로 된다.
2. 실험실: `./gradlew :autotrade-app-lab:bootRun`.
3. 세션 시작(CSRF 토큰은 `GET /api/session`의 응답에서 읽는다):

   ```powershell
   $s = Invoke-RestMethod http://127.0.0.1:8480/api/session -SessionVariable web
   $h = @{ "X-CSRF-Token" = $s.csrfToken }
   Invoke-RestMethod -Method Post -Headers $h -WebSession $web http://127.0.0.1:8480/api/live/sessions/EXP-20261015-LIVE01/start
   Invoke-RestMethod http://127.0.0.1:8480/api/live/status
   ```

4. 상태에서 `restoring`이 `false`가 된 뒤(입력 기록으로 계좌를 되살리는 중에는 `true`, 게이트웨이에 아직 붙지 않음) `feedState`가 `CONNECTED`, 장중에 `session.events`가 늘어나는지 본다. 시작이 실패하면 `stopReason`에 `시작 실패: …`가 남는다.
5. 설정 폴더 디스크 여유가 20GB(`autotrade.lab.live.min-free-gb`)보다 적으면 시작하지 않고, 운용 중이면 멈춘다(`stopReason`). 이 값은 1GB 이상이어야 하고, 0이나 음수면 실험실이 뜨지 않는다(0이면 하한이 꺼져 실전 엔진 기록과 같은 디스크를 채울 수 있음, risk-ops PR #87 P1, QA R2).

6. **선정 조합 계좌가 있는 등록(`selections`, D-124)만**: 순서는 전날 저녁 KRX 일봉 수집([수집기 runbook](collector.md)) → 세션 열림 → 준비 완료 확인이다.
   - 세션이 열려 있으면 실험실이 장 시간 밖(16:00~08:30)에 5분마다 다음 거래일 선정을 준비한다. 장 시작 전에 `GET /api/live/status`의 `prepare`가 그 거래일이고 `outcomes`가 모두 `WRITTEN`·`EXISTS`인지 본다(화면 `#/live` "선정 조합 계좌" 구역에도 보임). 장중에 세션을 열었으면 화면의 "지금 준비"(`POST /api/live/selections/prepare`)로 손으로 준비한다.
   - `PROBLEM`·`STALE_INPUT`이면 저녁 수집이 그날 일봉을 덮지 않은 것이다(ADR-012 3.7). 그날 그 조합 계좌는 신규 진입 0건으로 돈다.
   - `PRODUCER_FAILED`에 힙 안내가 나오면 실험실 밖에서 준비한다(장 시간 밖, 실험실은 켜 둔 채로 됨):

     ```powershell
     ./gradlew :autotrade-app-experiment:runLiveSelectionPrepare -Pexperiment=EXP-…-LIVE02 -Pdate=2026-10-27 -Pheap=8g
     # 종료 코드 0 준비됨, 2 못 만든 선정 있음(출력에 사유), 4 장 시간 보호·정지 요청
     ```

   - 선정 결과와 적용 기록은 `live-sessions/<ID>/selections/<날짜>/`에 쌓인다. 리플레이 확인이 이 파일을 읽으니 지우지 않는다.

7. **장중 순위 선정 계좌가 있는 등록(`refresh: INTRADAY_AT`, [D-127](../decisions/D-127-intraday-at-selection.md))만**: 준비 작업도 `selection-input`도 없다. 그날 `at`(예 09:30) 전에 받은 boards 체결로 실험실이 순위를 매긴다.
   - 세션을 **정규장 시작(09:00) 전에** 열어 둔다. 그날 처음 받는 이벤트가 09:01(개장 + 60초) 뒤이거나(장중에 처음 열었음), 09:00 ~ `at` 사이에 다시 띄워 재기동 공백이 붙으면 boards 전 종목이 누락으로 보여 그날 그 계좌는 후보 0(신규 진입 0건)이다. `at` 뒤 재기동은 입력 기록으로 순위를 되살려 그대로 이어 간다.
   - 상태 `GET /api/live/status`의 `session.intraday`가 `at` 전에는 `AWAITING`, 뒤에는 `RANKED`(후보·적용 시작 순번)인지 본다.
   - 녹화 판정(`runLiveJudgement`)은 아직 이 계좌를 받지 않는다(D-127 후속).

## 3. 운용 중

- 실험실·게이트웨이를 껐다 켜도 된다. 실험실은 세션을 자동으로 다시 열지 않으니 2-3을 다시 한다. 입력 기록으로 계좌를 되살리고 끊긴 구간은 공백으로 남는다.
- 감시 프로세스가 정지 요청 파일을 만들면 세션이 멈춘다(`stopReason`). 요청이 사라진 뒤 다시 시작한다.
- 주간 점검(D-088): 주마다(마지막 거래일 장 마감 뒤, 수신이 멈춘 다음) 아래 명령을 돌리고 생긴 `experiments/<ID>/weekly/<날짜>.md`를 커밋한다. 상태 화면의 `dataGaps`·`inboxDropped`·`feedReconnects`를 손으로 옮기지 않아도 된다(같은 값을 입력 기록과 게이트웨이 녹화에서 다시 센다). 녹화와 입력 기록을 날마다 줄 단위로 읽으므로 힙은 기간과 상관없고, 걸리는 시간은 운용 기간에 비례한다(D-115, 10종목 첫 주 약 20분·8주차 약 2~3시간 `[추론]`). 리포트 5장 "중간가 체결"은 입력 기록의 반 칸 가격 체결 수와 거래량 비중을 종목별로 보여 주는 참고 표이며 판정 기준이나 종료 코드와 상관없다(D-118).

  ```powershell
  ./gradlew :autotrade-app-experiment:runLiveWeeklyCheck -Pexperiment=EXP-20261015-LIVE01
  # 지난 주를 다시 볼 때: -Pto=2026-10-23, 폴더가 기본과 다르면 -PsessionsDir=… -PrecordingsDir=… -PsnapshotsDir=…
  ```

  결과 파일 머리의 `- 수집:` 줄과 4장은 KRX 일봉 수집이 멈췄는지 본다(D-105). 수집 스냅샷의 마지막 거래일이 점검 마지막 날보다 2거래일 이상 뒤처지면 **멈춤 의심**, 스냅샷이 없으면 **확인 필요**이고 콘솔에도 `수집 확인 필요` 줄이 나온다(종료 코드는 바뀌지 않음). 멈춤 의심이면 수집기를 다시 돌려 콘솔 메시지를 보고, "캘린더상 거래일에 빈 목록"이면 그날이 캘린더에 없는 임시공휴일인지 KRX 공지로 확인한 뒤 [수집기 runbook](collector.md) 3.6대로 캘린더를 고친다(보호 경로라 사용자 머지). 고칠 때까지 새 스냅샷이 없어 선정 결과에 공백이 생긴다. 지금의 6단계 계좌는 일봉 스냅샷을 입력으로 쓰지 않으므로(선정 프로필 미연결) 3장 계좌 성과는 수집 멈춤과 무관하다. `-Pto`로 지난 주를 다시 점검하면 그 뒤 수집된 스냅샷 때문에 이 칸은 정상으로 나오고 머리 줄과 4장에 "그 주의 멈춤은 보이지 않음"이라고 적힌다. 마지막 거래일 칸이 없는 옛 형식 스냅샷은 깨진 폴더와 따로 적히고, 옛 형식만 있으면 머리 줄이 "셀 수 있는 일봉 스냅샷이 없음(옛 형식 N개)"으로 나온다(수집기를 다시 돌리면 새 형식이 생긴다).

  - 종료 코드 0이면 설명되지 않는 차이가 없다. 2면 표의 "설명 없음" 칸(공백 없이 빠진 이벤트)이나 "녹화에 없는 기록 줄"이 있으니 그 날짜와 함께 알린다(전달·기록 경로 결함일 수 있음).
  - 1장 "빠짐"의 원인 칸: 세션 밖(실험실이 꺼져 있었거나 그날 세션을 열지 않음, "기록 없음" 행), 끊김, 재기동, 게이트웨이 큐, 실험실 큐. 세션이 열려 있었는데 공백 없이 빠지면 "설명 없음"이다. 2장의 재연결 수가 `feedReconnects`, 1장 실험실 큐 칸이 `inboxDropped`에 해당한다.
  - 3장 계좌 대조는 운용 시작부터 누계다. 게이트웨이 녹화가 빠진 날이 하나라도 있으면 하지 않는다(그날도 게이트웨이를 켜 두면 녹화된다).
  - 장 시간에는 시작하지 않는다(D-063). 읽는 동안 기록이나 녹화 파일이 바뀌면 "아직 쓰이는 중"으로 멈추니 수신이 멈춘 뒤 다시 돌린다.
- 실험실을 재기동한 날은 되살리기에 걸린 시간(시작 요청부터 상태의 `restoring`이 false가 될 때까지)도 적는다. 실험실 로그의 `실시간 모의 세션 연결: … 되살리기 N초` 줄에도 남는다. 되살리는 중의 정지 요청은 기록일 하나를 다 읽은 뒤에 반영되므로, 하루치가 길면 그만큼 늦게 멈춘다(QA PR #87 R6). 이 시간이 몇 분을 넘기기 시작하면 알린다: 되살리기는 마지막 기록일을 한 번 더 읽는데(architect PR #94 R2), 고치려면 실전 경로 보호 모듈(`autotrade-marketdata`)을 바꿔야 해서 필요할 때만 고친다.

## 4. 끝내기와 확인(운용 기간이 끝난 뒤, 장 밖에)

1. `Invoke-RestMethod -Method Post -Headers $h -WebSession $web http://127.0.0.1:8480/api/live/finish` → `experiments/<ID>/live-detail.txt`가 생긴다.
2. `./gradlew :autotrade-app-experiment:runLiveReplayCheck -Pexperiment=EXP-20261015-LIVE01`
   - 종료 코드 0이면 실시간 결과와 입력 기록 리플레이가 같다(합격). `inputs.yaml`, `results.md`, `detail.txt`가 등록 파일 옆에 생긴다.
   - 2면 실시간 경로 결함이거나 실패한 계좌가 있다. `results.md`를 보고 알린다.
   - 선정 조합 계좌가 있으면 적용 기록이 가리키는 결과 파일이 없거나 바뀌면 1이다. 입력 스냅샷이 남아 있으면 선정을 다시 계산해 `inputs.yaml`의 `selection-recompute:` 줄에 "같음·다름·재계산 생략"을 적고, 다름이 있으면 2다(계산 코드가 바뀐 경우, 실시간 경로 결함과 따로 출력). 스냅샷 폴더가 다르면 `-PsnapshotsDir=…`.
   - 장 시간에는 시작하지 않는다(D-063). 꼭 필요하면 `-PallowDuringSession`.
3. 리플레이 확인이 0으로 끝나면 녹화 판정(D-116): `./gradlew :autotrade-app-experiment:runLiveJudgement -Pexperiment=EXP-20261015-LIVE01` → `experiments/<ID>/judgement.md`. 장중 승격 기준 L1~L11(D-114)을 계산한다. 종료 코드 0 판정함(후보 0개 포함), 1 입력 오류, 2 무사고 I1~I3 깨짐(파일은 씀), 3 취소, 4 장 시간 보호·정지 요청. LIVE01(10종목 40일)은 4코어에서 약 1.5~2시간 `[추론]`이다. 이 결과로 판정 리포트를 쓴다.
   - 선정 조합 계좌가 있으면(D-126) 판정도 세션의 같은 선정 고정 파일을 읽는다. 리플레이 확인과 같이 파일이 없거나 바뀌었으면 1이다. 판정 대상이 있는 선정마다 같은 선정의 대조군(`선정 x kr-random-control`)이 등록돼 있어야 하고, 대조군 시드를 선정 묶음마다 돌려 시간이 그만큼 늘어난다 `[추론]`. `judgement.md` 9장에 날짜별 선정·커버리지가 나온다.
   - 준비 작업이 같은 입력 스냅샷으로 계산에 실패한 날은 장 밖 5분마다 다시 읽지 않는다(D-126 7번). 계산 코드를 고친 뒤 그날을 다시 준비하려면 `live-sessions/<ID>/selections/<날짜>/*.problem.json`을 지우고 "지금 준비"를 누른다.
4. 결과 세 파일, `live-detail.txt`, `judgement.md`는 커밋한다. 입력 기록(설정 폴더)은 커밋하지 않는다(녹화와 같은 재배포 금지).

## 5. 첫 운용일 확인 항목(Windows `[가정]` 확인)

- 게이트웨이 로그에 소켓을 열었다는 줄이 나오는지, 실험실 상태 `feedState`가 `CONNECTED`인지.
- 설정 폴더 `run` 폴더를 다른 사용자 계정이 열 수 없는지(폴더 속성 > 보안).
- 감시 기동 로그의 CPU·메모리 값(임계를 넘거나 결측일 때 남는 줄, 또는 장 밖에서 `cpu.system=1:2:1`처럼 낮춘 임계로 잠깐 띄워 본 값. 정지 요청 파일이 생기므로 확인 뒤 원래 값으로 되돌리고 감시를 다시 띄운다)이 작업 관리자 "성능" 탭의 CPU 사용률·메모리 사용 중 비율과 비슷한지. 메모리는 감시(JDK 여유 메모리)와 실험실 모니터링 화면(OSHI 사용 가능 메모리)이 다를 수 있다(D-095, D-096, PR #122 QA R2). 크게 다르면 기록해 기본 임계(85/95%)를 다시 정한다.
- 감시 로그에 "자원 값을 읽지 못함"이 10분마다 나오는지 확인한다. 나오면 그동안 그 값으로는 정지 요청을 만들지 못하므로 원인(성능 카운터 등)을 찾는다(D-096). 드라이브 값이면 줄 끝 "원인:"에 OS 오류 문구가 있다. "자원 값을 다시 읽음" 뒤에 다시 빠지면 바로 다시 나온다(D-108).
- 감시·게이트웨이 로그의 한글이 `??`로 깨지지 않는지(PR #116·#118 QA R2). 깨지면 콘솔 코드 페이지를 UTF-8(`chcp 65001`)로 바꾸거나 로그 파일로 확인한다.
