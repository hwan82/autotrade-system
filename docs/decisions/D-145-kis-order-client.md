- 독립 QA [원문](../reviews/pr-247/qa.md) 수정 필요 발견 1(A4·A12·A14): "없음"이 시계 오차(S1)·호출자가 잰 보내기 시각(S3)·반영 대기 가정이 틀리면 중복 주문 쪽으로 틀리는데, 이 기록과 클래스 주석이 반대로 "모름으로 기운다"고 적었다. 고친 것:
  - 보내기 시작·끝 시각을 `KisOrderClient`가 실제 POST 직전(간격 대기·토큰 발급 뒤)과 응답 직후 세션 시계로 재서 `KisOrderResult.Unknown`에 담는다. `Fingerprint`는 공개 생성자 없이 `Fingerprint.of(주문, Unknown)`으로만 만든다(주문 날짜도 그 시각에서 정함). 반영 대기는 응답 받은 시각부터 센다(요청 시간 상한 입력 없앰).
  - 시계 오차는 가정하지 않고 잰다. 일별 체결 조회 첫 쪽 응답의 HTTP `Date`(초 단위 절사)와 우리 요청·응답 시각으로 "한국투자 시계 − 우리 시계"의 하한을 구해 창을 그만큼 옮긴다. `Date`가 없거나 읽지 못하면 모름. 60초 여유는 그 위에 더한다(웹 게이트웨이 시계와 주문시각 시계의 차이, 절사).
  - 반영 대기 30초는 근거가 없어 고치지 못한다. 아래 위험 1과 "연결 조건"에 사실대로 적었다.
  - 권고 Q1(S2): 토큰 만료 응답을 받은 요청에 쓴 토큰이 지금 캐시의 토큰일 때만 버린다(`TokenCache.invalidateIfCurrent`). 옛 토큰의 늦은 만료 응답이 새 토큰을 버려 60초 동안 손절 매도까지 "보내지 않음"이 되던 보호 공백을 없앴다(risk-ops 재검토 G4와 같은 원인).
  - 권고 Q2는 Q-015 확인 항목에, Q3·Q4는 아래 "연결 조건"에, Q5는 "안 한 것" 1행에 반영.
  - 시험: S1(우리 시계 61초·3분 빠름 → 찾음), `Date` 없음 → 모름, 시계 차이 하한 계산, S3(토큰 발급 40초 → 보내기 시작은 POST 직전, 호출자 기준 반영 대기 뒤여도 모름), S2(늦은 만료 응답 뒤 손절 매도가 새 토큰으로 나감), `TokenCache.invalidateIfCurrent`.

## 연결 조건(묶음 E에서 `NotFound`로 재발주하기 전, 독립 QA PR #247)

1. **반영 지연 실측**: Q-015에서 접수 뒤 일별 체결 조회에 보이기까지의 시간을 장 시작·혼잡 시간대 포함으로 재고, `SETTLE`이 그보다 충분히 길다는 근거를 남기기 전에는 `NotFound`를 재발주 근거로 쓰지 않는다(그때까지 모름과 같게 다룬다).
2. **시계 근거 실측**: 같은 접수 응답의 `ORD_TMD`와 HTTP `Date`의 차이를 재서 `CLOCK_SKEW` 60초 여유가 웹 게이트웨이 시계와 주문시각 시계의 차이를 덮는지 확인한다.
3. **토큰 무효 뒤 조회 순서(QA Q4)**: 토큰을 버린 직후 60초 하한 동안 PANIC 대사 조회가 실패할 수 있다. 장애표 7번(토큰 만료)과 함께 처리 순서를 정한다.
4. **주문 코드가 실릴 프로세스(QA Q3, risk-ops G2)**: 수집기·실험·게이트웨이는 `RealPathReflectionTest` 범위 밖이고 수집기는 `kis-news` 한국투자 키를 갖는다. 주문 패키지를 실전 엔진만 의존하는 모듈로 나누거나 리플렉션 범위를 넓히는 것을 연결 PR의 승인 조건으로 둔다(D-136 `kis-news` 키 검사, 점검표 D8과 함께).

## 위험과 한계

1. **"없음"을 틀리게 하는 가정 `[가정]`, 틀리면 중복 주문 쪽**: 반영 지연 30초, 게이트웨이 `Date`와 주문시각 시계의 차이가 60초 안이라는 것은 공식 문서에 없다. 이 둘이 틀리면 실제로 접수된(또는 아직 반영 전인) 주문에 "없음"이 나오고, 그대로 재발주하면 중복 주문이 된다. 그래서 위 "연결 조건" 1·2를 실측으로 채우기 전에는 `NotFound`로 재발주하지 않는다. 시계 차이 자체와 보내기 시각은 이제 재서 쓰므로 PC 시계가 몇 분 어긋나도 창이 따라 옮겨진다. 그 밖의 형식 가정(주문번호 자릿수(앞 0), 취소 주문 행의 `orgn_odno`, 종목코드 접두, 장 마감 뒤 남은 잔량 표시)은 틀려도 창 안 행 전체를 세므로 모름 쪽으로 기운다(결정 5). Q-015에 더했다.
2. **사용자 직접 주문**: 우리 주문이 실제로 접수되지 않았고 HTS에서 같은 종목·방향·수량·가격으로 낸 주문 하나만 창 안에 있으면 우리 것으로 잡을 수 있다(둘 다 있으면 모름). 재발주를 하지 않는 쪽으로 틀려 중복 주문은 없지만, 그 주문을 우리 것으로 다룰 위험이 남는다. 결과에 `byOrderNo=false`를 표시하고, 묶음 E에서 특징 대조로 찾은 주문을 취소·청산 대상으로 삼기 전 확인 조건을 정한다.
3. **모름이 늘어남**(risk-ops 재검토 G5): 창 안의 묶이지 않은 행은 종목과 상관없이 확정을 막으므로, 같은 계좌에서 여러 종목을 짧게 이어 주문하거나 사용자가 같은 시간대에 HTS 주문을 내면 모름이 늘어난다. 안전한 쪽이지만 재발주가 늦어진다. 호출자가 묶인 번호를 빠짐없이 넘겨야 한다.
4. **취소 경합**: 취소를 보낸 사이 체결이 날 수 있다. 상태는 일별 체결 조회의 체결·취소확인 수량으로 다시 확인한다(`CANCEL_REQUESTED`는 종결 아님).
5. **연결 전이라 실제 동작 미검증**: 모든 시험은 가짜 HTTP로 한다. 실주문 시험은 7단계 절차서(I)와 사용자 결정 뒤.
