## 점검표 밖 발견

### 발견 1 (수정 필요, A4·A5·A6) "활성화를 막는다"가 OFF → PROTECTIVE 상향(PANIC D-140 ①, `enterProtective`)을 막는지 정하지 않음
- [사실] ADR-015는 막는 조건을 모두 "활성화를 막는다" 또는 "OPEN 불가"로 적는다: 기동 기록 실패(2.5 92행, 2.7 ⑤), `key-floor` 기록 실패(2.6 102행), 계좌 원장 손상(2.7 ③ 123행), 블랙리스트 원장 손상(같은 행), 두 쓰기 주체(2.9 144행), UNKNOWN 확정 전(2.7 126행), 원장 밖 미체결 주문(2.7 129행), 시험 4·5·7·11·13.
- [사실] 같은 ADR 2.7 ⑦(118행)은 "사람이 활성화(**또는** PANIC으로 보호 모드, D-140 ①)"로 둘을 나눠 쓴다. D-140 ①은 OFF 계좌 PANIC을 "2차 확인 뒤 OFF → PROTECTIVE로 올려 매도"로 정했고, `enterProtective`(재기동 후 보유 보호, `RealTradingGuard.java` main 228-237행)는 ADR-006 188행·7단계 계획 C14의 별도 명령이다. 둘 다 `beginActivation`을 거치지 않는다. 그래서 B1~B6 구현자가 "활성화 차단"을 `beginActivation`·OPEN에만 걸어도 이 ADR과 5장 시험을 모두 만족한다.
- 시나리오 1 (A6) [추론, 코드 경로 근거]: 블랙리스트 원장 중간 줄 손상 → ③ 모든 계좌 활성화 차단, 긴급 알림 → 사용자가 급락을 보고 OFF 계좌 X에 PANIC → D-140 ① 확인 통과로 X는 PROTECTIVE → 대사는 원장에 없는 보유만 AUTO_ASSET으로 되살리고, 사용자가 시스템 보유 종목에 걸어 둔 MANUAL 제외는 손상 원장과 함께 사라짐 → `PanicLiquidator`가 그 종목을 매도. 절대 규칙 3(블랙리스트는 어떤 경로로도 자동 매매되지 않음) 위반. 2.7 123행의 이유("블랙리스트를 확신할 수 없으므로")가 PROTECTIVE 매도에도 그대로 해당한다.
- 시나리오 2 (A5) [추론, 2.6 계산식 근거]: 부팅 1에서 그날 `keyFloor` F1 = 10,000 기록, 키 10,001~10,005 기록 → 부팅 2에서 F2 = 20,005를 계산했으나 `key-floor` 기록 실패(원장 쓰기 불가) → "활성화 막음"이지만 PANIC(D-140 ①)이나 `enterProtective`로 PROTECTIVE → 청산·손절은 2.5 88행대로 기록 없이 키 20,006…로 전송 → 부팅 3에서 F3 = max(원장 최대 10,005, 기록된 이전 바닥값 10,000) + 10,000 = 20,005 → 첫 키 20,006이 부팅 2의 전송 키와 같음. 102행의 "어차피 열 수 없다"는 OPEN에만 맞다. 기동 기록 실패(2.5 92행)도 사본만 잃는 것이라 계좌 원장이 살아 있으면 괜찮지만, 같은 문장 "모든 계좌의 활성화를 막고"가 PROTECTIVE를 막는지는 역시 정하지 않음.
- 시나리오 3 (A4) [추론]: 손절 매도 의도 기록 직후 엔진이 죽음 → 재기동, 그 주문 `UNKNOWN` → 사용자가 `enterProtective`로 X를 보호 모드에 올림(2.7 ⑦ 대사는 "활성화 또는 PANIC"에만 묶여 있음) → 보호 모드 손절 로직은 원장 보유(체결 기록 없음)를 그대로 보고 같은 보유에 새 키로 손절 매도 → 첫 주문이 접수·체결됐다면 "조회 전 재주문"(지침 4장 2번)이 된다. 매도 가능 수량 검사가 증권사에서 막아 줄 수 있으나 그것은 증권사 동작에 기대는 것이다.
- 고칠 것: ADR-015에 "막는다"의 범위를 한 번 정의한다. 추천: 위 차단 조건은 모두 **Guard를 올리는 모든 전이**(`beginActivation`·OPEN, `enterProtective`, PANIC의 OFF → PROTECTIVE)를 막는다. 예외를 두려면(예: 원장 밖 주문이 있어도 보호 모드 매도는 허용) 조건별로 명시하고, PROTECTIVE로 올리는 경로도 ⑦ 대사(UNKNOWN 확정) 뒤에만 주문을 내게 한다. 5장 시험 4·5·7·11·13에 "PANIC(OFF 계좌)·`enterProtective`도 거부, 주문 세션 허가 0건" 경우를 넣고, D-141 결정 3·5에도 같은 범위를 적는다.

### 발견 2 (수정 필요, A14) `keyFloor` 원본 위치가 색인·위험 표에서 옛 설계로 남음
- [사실] 결정 로그 색인 D-141 행: "재기동 키는 기동 기록의 키 바닥값(+10,000) 위에서". ADR-015 179행: "키 바닥값(간격 10,000, 기동 기록에 보존, 2.6)". 반면 ADR 2.6 102행·D-141 결정 3은 원본이 계좌 `orders` 원장의 `key-floor` 기록이고 기동 기록은 사본이다(architect 재검토 R1 반영, 10장 267행).
- 영향 [추론]: 구현자가 색인이나 위험 표를 기준으로 `boot` 원장에서 바닥값을 읽으면 `boot` 손상이 "경고만"(2.7 ③)인 상태에서 키 간격이 사라진다(R1이 막은 결함이 그대로 돌아옴).
- 고칠 것: 두 곳을 "계좌 `orders` 원장의 `key-floor` 기록(기동 기록에는 사본)"으로 고친다.

### 권고(수정 요구 아님)
- **Q1** (2.7 ④) "기록이 빠졌을 수 있는 계좌" 판정이 "`degraded` 파일이 있거나, 직전 종료 비정상 **이고** 끝 잘린 줄·다시 시도 흔적"이다. [추론] 디스크가 가득 차 `degraded` 파일도 못 만든 채 청산을 기록 없이 보냈고, 여유가 돌아온 뒤 대기열이 다 비지 못한 상태에서 사람이 엔진을 정상 종료하면(정상 종료 기록은 성공) 어느 조건도 남지 않는다. 정상 종료 기록에 "이번 부팅에 저장소 장애가 있었음·비우지 못한 대기열 건수"를 싣고 그것도 ④의 조건으로 보라고 권한다. 저장소 장애 상태의 청산 의도 대기열 상한과 넘칠 때 처리도 2.5 표에 없다(내림 감사만 1,000줄).
- **Q2** (2.9, 4장 183행) "운영 PC가 Windows면 잠긴 파일 삭제가 막혀 위험이 더 작다 `[추론]`"은 PR #235 QA Q3과 반대다. [사실] main `ControlServer.java:374`는 `lockKey == null`이면 교체 감지를 통과시키고, [추론] Windows의 `BasicFileAttributes.fileKey()`는 null을 돌려주므로 2.9 (가) 파일 키 감시는 Windows에서 동작하지 않는다. [추론] JDK는 Windows에서 기본으로 FILE_SHARE_DELETE로 열어 잠긴 `writer.lock`도 지워질 수 있다. 그러면 Windows에서는 (나) 부팅 번호 검사(다음 복구 때에야 발견)만 남는다. 문장을 고치고, B1에서 Windows 파일 식별 수단(예: 파일 생성 시각+크기, 또는 `NOSHARE_DELETE`로 열기)과 3-R 운영 PC 시행을 정하라고 권한다. 이 환경에서 Windows 실측은 못 했다.
- **Q3** (2.4·2.7 ③) 날짜 파일 첫 줄 체크포인트가 깨졌을 때 2.4 74행은 "앞 날짜 파일을 처음부터 다시 읽어 만든다"이고 2.7 ③은 "중간 줄 CRC 불일치는 손상 → 그 계좌 복구 실패"라 체크포인트 줄이 어느 쪽인지 갈린다. 하나로 정하라고 권한다(더 막는 쪽이면 ③).
- **Q4** (2.5 91행) 기록 못 한 블랙리스트 등록은 재기동하면 사라진다. 재기동 긴급 알림에 넣을지를 B5로 미뤘는데, 사라지면 다음 부팅에서 그 종목이 자동 매매될 수 있으므로(절대 규칙 3) "넣는다"로 정해 두기를 권한다(화면에 실패를 알렸더라도 사용자가 재기동 사이 다시 등록한다는 보장이 없음).
- **Q5** (2.5 94행) 올림 2단계의 ①에서 2차 확인을 소비하므로 ③에서 적용되지 않으면 사용자는 새 확인이 필요하다. 동작은 막는 쪽이라 문제는 없으나, 화면이 "전이 미적용(기록 상한 초과/내림이 먼저)"을 구별해 보여 주도록 B1·묶음 H에 적기를 권한다. 또 ADR이 인용한 `RealTradingGuard.java:297-307`은 main(#240 뒤)에서 324-328행으로 밀렸다.
