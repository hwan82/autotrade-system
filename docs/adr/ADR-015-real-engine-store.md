# ADR-015 실전 엔진 저장소: 엔진 전용 추가 기록 원장, 재기동 복구 순서

- 상태: 제안(D-141, 실전 경로 설계라 risk-ops 검토 뒤 사용자 머지. 기획서 문구와 다른 저장 수단은 Q-062 사용자 결정 2026-10-25 "파일 원장")
- 날짜: 2026-10-24
- 담당: architect. 검토: risk-ops(실전 경로·장애 대응), architect(계약)
- 근거: [7단계 준비 계획](../team/stage-7-readiness-plan.md) 2.3장 B0·3장 묶음 B, [ADR-002](ADR-002-real-trading-guard.md) 2.1·2.3·4·6장, [ADR-006](ADR-006-real-control-channel.md) 2.2·2.5·6장, [ADR-001](ADR-001-module-structure.md) 2.7장(Q-009), [D-086](../decisions/D-086-real-path-reflection-ban.md), [D-140](../decisions/D-140-stage7-panic-and-first-broker.md), 기획서 ORD-02·03·07·08, RSK-03·04·12, STR-19, TST-07, [broker-and-fault-design.md](../team/broker-and-fault-design.md) 6장 #8·7장 3번
- 범위: **설계 문서만**. 코드, 설정, `RealTradingGuard`, 보호 테스트는 바꾸지 않는다. 구현은 묶음 B의 B1~B7 PR(6장)에서 한다.

## 1. 배경과 문제

- `[사실]` 실전 엔진에는 영속 저장소가 없다. Guard 전이 감사는 프로세스 로그뿐이고(`autotrade-app-engine/.../order/LoggingGuardAuditLog.java`), 명령 감사도 프로세스 로그다(`.../command/CommandAuditLog.java`의 `LOGGING`). 둘 다 "영속 저장은 실전 엔진 저장소 작업에서 바꾼다"고 적혀 있다.
- `[사실]` 멱등 키 타입은 있지만 발급기는 없다. `IdempotencyKey` javadoc은 "새 키는 계좌별 영속 발급기만 만든다"고 한다(`autotrade-domain/.../order/IdempotencyKey.java:17`).
- `[사실]` 7단계 항목 중 B1(영속 감사), B4(멱등 키 영속), B5(블랙리스트 영속), B7(포지션별 진입 조합 해시)가 모두 "무엇을 어디에 저장하고 재기동 때 어떤 순서로 되살리는가"를 먼저 정해야 시작할 수 있다(7단계 준비 계획 2.3장).
- `[사실]` Guard 상태는 저장하지 않는다. 재기동 = 새 Guard = 모든 계좌 OFF(ADR-002 2.3, `RealTradingGuard` 생성자는 상태를 받지 않음). 저장소가 생겨도 이 불변식은 그대로여야 한다.
- `[사실]` 실전 경로 런타임은 외부 jar 허용 목록(Jackson 4개)과 JDK 패키지 허용 목록 밖을 쓰면 빌드가 실패한다(`RealPathReflectionTest.EXTERNAL_ALLOWLIST`, `ALLOWED_JDK_PACKAGES`, D-086). `java.sql`과 JDBC 드라이버는 허용 목록에 없다. `java.nio.channels`·`java.nio.file`·`java.util.zip`은 있다.
- `[사실]` 기획서는 저장 수단을 일부 정해 두었다. RSK-12는 "블랙리스트 영속화(DB)", 장애표 #8은 "자동 재기동 → DB 상태 복구 → 증권사 대사 통과 후에만 재개", ARC-07은 "메타·상태 DB"(1단계 테이블은 실험 5개)다. ADR-001은 Q-009로 그 DB를 PostgreSQL 16으로 정했고, 지금 PostgreSQL은 실험실 마이그레이션(`autotrade-app-lab/.../db/migration/V1~V4`)에만 쓰이며 어느 프로세스도 JDBC로 연결하지 않는다.

## 2. 결정

### 2.1 원칙 6개

1. **실전 엔진 상태의 원본은 엔진 전용 추가 기록 원장(파일)이다.** 실전 엔진은 PostgreSQL을 포함해 다른 프로세스나 서비스에 저장을 기대지 않는다(지침 4장 6번, ARC-03). PostgreSQL에 두는 실전 엔진 상태는 **없다**.
2. **쓰기 주체는 한 번에 하나.** 원장 폴더의 쓰기 잠금을 가진 프로세스 하나만 쓴다(2.9). 다른 프로세스는 엔진이 내보낸 읽기용 파일만 읽는다.
3. **먼저 기록하고 나서 보낸다.** 주문 의도(멱등 키 포함)는 원장에 기록되고 디스크에 강제 기록된 뒤에만 증권사로 나간다. 그래서 "기록이 없는 주문은 보낸 적이 없다"가 성립한다(2.6). **예외 하나**: 저장소 장애 상태의 청산·손절·취소는 기록 없이도 보낸다(2.5, D-023 공통 원칙 1). 그래서 저장소 장애 표시가 있었거나 직전 종료가 비정상인 계좌는 이 문장을 믿지 않고, 재기동 때 원장 밖 주문 대조(2.7 ⑦)로 빈 곳을 메운다.
4. **복구는 제한하는 쪽으로만.** 재기동 때 원장에서 되살리는 것은 막는 상태(킬스위치·서킷·주문 실패 정지·블랙리스트·미확정 주문)와 사실(보유 로트, 주문 이력)뿐이다. 여는 상태(Guard OPEN·PROTECTIVE, 활성화 단계 통과, 2차 확인)는 원장에 감사 기록으로만 남고 **복구 입력으로 읽지 않는다**(ADR-002 A1 유지).
5. **계좌끼리 분리.** 계좌마다 원장 파일과 쓰기 스레드가 따로다. 한 계좌의 쓰기 지연·손상이 다른 계좌의 주문·킬스위치를 늦추지 않는다(지침 4장 6번, TST-07 (3)).
6. **증권사가 진실, 원장은 기억.** 수량·미체결은 증권사 조회가 기준이다(broker-and-fault-design.md 4.3). 원장은 증권사가 모르는 것(멱등 키, 진입 조합 해시, 손절 기준, 감사)을 기억하고, 증권사 결과와 대조할 기준을 준다.

### 2.3 폴더

`<설정 폴더>/engine-store/` (기본 `~/.autotrade/engine-store/`, `AUTOTRADE_CONFIG_DIR`을 따른다). 설정 폴더 안이라 엔진·실험실·감시가 같은 위치를 따로 맞출 필요가 없다(ADR-006 2.2와 같은 이유).

```
engine-store/
  writer.lock                         쓰기 잠금(2.9)
  boot/boot.jsonl                     기동 기록
  audit/commands/<날짜>.jsonl          명령 감사
  accounts/<계좌 별칭>/
    audit/<날짜>.jsonl                Guard 전이 감사
    orders/<날짜>.jsonl               주문·체결 원장(첫 줄은 체크포인트)
    risk/risk.jsonl                   리스크 제한 상태
  blacklist/
    blacklist.jsonl                   등록·해제 원장(쓰기는 엔진만)
    snapshot.json                     읽기용 스냅샷(원자적 교체, 2.8)
```

- `<날짜>`는 거래소 현지 거래일(`MarketRules.tradingDate`, 지침 4장 9번)이다.
- 폴더 권한은 POSIX에서 700·파일 600, Windows는 사용자 프로필 기본 ACL에 기댄다 `[가정]`(ADR-006 2.2와 같은 한계, K10 검토 대상).
- 폴더나 그 위가 심볼릭 링크면 엔진은 기동을 거부한다(ADR-006 2.2와 같은 규칙).

### 2.4 기록 형식과 내구성

- 한 줄에 기록 하나인 JSON(UTF-8, LF). 직렬화는 이미 허용된 Jackson으로 하고, 이름으로 타입을 고르는 바인딩은 쓰지 않는다(D-086). 칸: `v`(형식 버전), `stream`(원장 이름), `rseq`(**기록 일련번호**: 원장마다 1부터 끊김 없이 증가, 날짜 파일이 바뀌어도 이어짐. 멱등 키 번호 `keySeq`와 다른 번호다), `boot`(부팅 번호), `at`(주입된 `Clock`의 시각, ARC-04), `type`, 본문, `crc`(**`crc` 칸을 뺀 나머지를 정해진 칸 순서로 직렬화한 UTF-8 바이트**의 CRC32C, `java.util.zip.CRC32C`. 칸 순서는 B1에서 고정).
- 이 문서에서 "키 번호 `keySeq`"는 멱등 키 `{date}-{code}-{side}-{seq}`의 마지막 번호(`IdempotencyKey.seq`)를 뜻한다. 주문 의도 기록 본문에 키 전체와 `keySeq`를 싣는다.
- 쓰기: 계좌 원장마다 쓰기 스레드 하나가 줄을 붙이고 `FileChannel.force(true)`까지 마친 뒤 호출자에게 "기록됨"을 돌려준다. 같은 원장에 동시에 온 기록은 한 번의 강제 기록으로 묶을 수 있다(묶음 커밋). `[추론]` Windows에서 `force`는 `FlushFileBuffers`로 이어진다(JDK 구현, B1 PR에서 운영 PC 실측으로 확인).
- 날짜 파일의 첫 줄은 **체크포인트**: 그 시점의 열린 보유 로트, 종결되지 않은 주문(당일 유효가 아닌 서버 측 손절 포함), 직전 파일의 마지막 `rseq`와 `crc`. 복구는 가장 최근 날짜 파일의 체크포인트부터 읽으면 된다. 체크포인트 줄이 깨졌으면 중간 줄 손상과 같이 2.7 ③의 손상으로 본다(더 막는 쪽). 앞 날짜 파일을 처음부터 다시 읽어 체크포인트를 다시 만드는 것은 사람이 원인을 본 뒤 I1 절차로만 한다.
- 끝이 잘린 마지막 줄(줄바꿈 없음, 전원 차단 중 쓰기)은 "보내지 않은 기록"이다(원칙 3, 저장소 장애 표시가 있는 계좌는 원칙 3의 예외대로 대조로 확인). 복구는 그 줄을 별도 파일로 옮겨 두고 잘라 낸 뒤 긴급 알림에 "잘린 기록 1줄"을 적는다. **중간 줄**의 CRC 불일치, `rseq` 건너뜀·되돌아감, 모르는 `v`는 손상이다(2.7 ③).
- 마스킹: 증권사 응답 원문은 플러그인의 마스킹을 거쳐 들어온다. 저장소는 기록 직전에 엔진이 메모리에 가진 계좌번호·키 값이 문자열 안에 있는지 한 번 더 보고, 있으면 그 칸을 가린 뒤 기록하고 경고한다(지침 4장 4번의 이중 장치).

### 2.5 쓰기 시간 상한과 실패 처리

값은 모두 `[가정]`이며 B1 PR에서 운영 PC 실측으로 정한다(ORD-06 신호→주문 1.5초 예산 안).

| 기록 | 기다림 | 상한 안에 "기록됨"이 안 오거나 실패하면 |
|---|---|---|
| Guard **올림** 전이 감사 | 호출자가 기다림, 상한 2초. **계좌 잠금 밖에서 기다린다**(아래 "올림 감사와 계좌 잠금") | 전이 실패, 출발 상태 유지(ADR-002 2.1 "올라가는 전이는 기록이 성공해야"). 활성화 기한(ADR-006 6장 C3)에도 이 시간이 들어간다. 대기열에 남은 그 줄은 취소하고, 이미 쓰였으면 같은 원장에 "전이 미적용(기록 상한 초과)" 보정 기록을 붙인다 |
| Guard **내림** 전이 감사 | 기다리지 않음(전이 먼저, 기록은 잠금 밖 대기열). 어댑터는 `GuardTransition`의 from·to로 내림을 가려 대기열에 넣고 바로 돌아온다 | 전이는 이미 일어남. 대기열 상한(`[가정]` 계좌당 1,000줄)을 넘거나 기록이 실패하면 프로세스 로그로 남기고 긴급 알림 |
| 명령 감사 | 기다리지 않음 | 프로세스 로그 + 경고. 올림 명령은 위 Guard 감사가 막는다 |
| 신규 진입 주문 의도 | 기다림, 상한 0.5초 | 그 진입 버림(`STORE_UNAVAILABLE`), 그 계좌를 보호 모드로 내림(자동 하향은 허용, ADR-002), 긴급 알림 |
| 청산·손절·취소·서버 측 손절 재설정 의도 | 기다림, 상한 0.5초. 그 계좌가 이미 저장소 장애 상태면 **기다리지 않고** 대기열에 넣은 뒤 바로 보낸다 | **그대로 보낸다**(D-023 공통 원칙 1: 새 차단은 신규 진입만 막고 손절·청산은 막지 않음). 그 계좌는 "저장소 장애" 상태가 되고(`degraded` 표시 파일 만들기 시도), 그 뒤 키는 메모리에서 이어서 발급, 보호 모드로 내림, 긴급 알림. 재기동 때 2.6의 키 바닥값과 2.7 ⑦의 원장 밖 주문 대조가 빈 기록을 메운다. 기록을 기다리는 의도 대기열 상한은 계좌당 10,000줄 `[가정]`이고, 넘치면 그 의도를 프로세스 로그(키 포함, 비밀값 없음)에 남기고 긴급 알림을 낸 뒤 **주문은 그대로 보낸다** |
| 상태 전이·체결 기록 | 기다림, 상한 0.5초 | 메모리 상태는 진행. 실패한 기록은 대기열에서 다시 시도하고 저장소 장애 상태로 표시. 재기동 때 빠진 체결은 대사가 증권사 체결로 메운다(2.7 ⑦) |
| 리스크 제한 상태(킬스위치·서킷·주문 실패 정지) | 기다림, 상한 0.5초 | **제한은 메모리에 먼저 적용**(더 막는 쪽, 기록 실패로 늦추지 않음). 기록은 다시 시도하고 저장소 장애 상태로 표시. 재기동 때 처리는 2.7 ④ |
| 블랙리스트 등록·해제 | 기다림, 상한 2초 | 등록 실패면 화면에 실패를 알리고 엔진은 **메모리에 등록을 적용**(더 막는 쪽). 재기동하면 그 등록이 사라질 수 있으므로(절대 규칙 3) 엔진은 원장과 다른 파일 `blacklist/unrecorded`에 그 종목을 덧붙이기를 시도하고 `blacklist` 원장을 장애로 표시한다. 재기동 때 이 파일의 종목은 다시 적용하고(더 막는 쪽) 긴급 알림에 넣는다. 이 파일도 쓰지 못했으면 다음 기동에서 블랙리스트 원장 장애로 보아 2.7 ③대로 모든 계좌의 올리는 전이를 막는다. 해제 실패면 해제하지 않음 |
| 기동 기록(2.7 ⑤) | 기다림, 상한 2초 | **모든 계좌의 올리는 전이를 막고**(2.7 "차단의 범위") 긴급 알림. 원본인 계좌 원장의 `key-floor`는 따로 쓰지만, 원장 폴더에 쓰지 못하는 상태이거나 두 쓰기 주체를 가릴 부팅 기록이 없는 채로 여는 것보다 막는 쪽을 고른다. 명령 채널 STATUS·내리기는 동작한다 |
| 정상 종료 기록 | 기다림, 상한 2초 | 정상 종료 기록에 "이번 부팅에 저장소 장애가 있었는지"와 "비우지 못한 대기열 건수"를 싣는다. 2.7 ④가 이 값도 "기록이 빠졌을 수 있는 계좌" 조건으로 본다. 쓰지 못하면 비정상 종료와 같이 다룬다 |

**올림 감사와 계좌 잠금 (같은 계좌 킬스위치 지연 없애기)**: `[사실]` 지금 `RealTradingGuard.raise`는 계좌 잠금 안에서 `audit.record`를 부른다(`RealTradingGuard.java` `raise`, main `99b30c2d` 기준 324-328행). 지금은 프로세스 로그라 바로 끝나지만, 원장 강제 기록(상한 2초)으로 바꾸면 그동안 같은 계좌의 `deactivate`·`shutdown`·`failActivation`(내림, 킬스위치·PANIC 1단계)이 잠금을 기다린다. 그래서 B1에서 올림을 두 단계로 바꾼다. ① 잠금 안에서 검사(상태, 2차 확인 소비)와 출발 스냅샷·세대 확인, ② 잠금 밖에서 감사 기록(상한 2초), ③ 다시 잠금 안에서 스냅샷이 ①과 같을 때만 적용하고(같은 상태로 되돌아온 경우에 속지 않도록 전이마다 하나씩 오르는 전이 번호로 비교한다. main 합친 뒤(D-142, 묶음 A)에는 명령이 연결별·계좌별 실행기에서 처리되어 같은 계좌의 올림과 내림이 겹칠 수 있으므로 이 비교가 필수다), 그 사이 내림이 끼어들었으면 적용하지 않고 "전이 미적용(내림이 먼저)" 보정 기록을 붙인다. 이렇게 하면 같은 계좌의 내림도 감사 기록을 기다리지 않는다(TST-07 (3) F-4). 상한은 어댑터가 지킨다: `GuardAuditLog.record`에는 시간 인자가 없으므로 어댑터가 상한 안에 예외를 던지고, 강제 기록이 멈춘 쓰기 스레드가 잠금을 붙잡는 일은 구조상 없다. 이 변경은 `RealTradingGuard`와 그 시험(보호 테스트)을 고치므로 B1은 보호 테스트 변경 PR이다(6장). ①에서 2차 확인을 소비하므로 ③에서 적용되지 않으면 사용자는 다시 확인해야 한다. 명령 응답과 화면은 "전이 미적용(기록 상한 초과)"과 "전이 미적용(내림이 먼저)"을 구별해 보여 준다(B1·묶음 H).

한 계좌의 저장소 장애는 그 계좌만 내린다. 디스크가 가득 차는 것처럼 모든 계좌가 함께 실패하는 경우도 계좌마다 같은 규칙을 따로 탄다. 드라이브 여유는 감시가 이미 본다(D-092).

### 2.6 멱등 키 발급(B4)

- 키는 계좌별 발급기만 만든다. 다음 키 번호 `keySeq` = max(그날·종목·방향의 원장 최대 `keySeq`, 이번 부팅의 `keyFloor`) + 1이다. 발급은 주문 의도 기록과 같은 줄이다(따로 세는 카운터 파일 없음).
- 의도가 "기록됨"이 된 뒤에만 보낸다(원칙 3). 기록됐지만 보냈는지 모르는 주문(기록 직후 종료)은 재기동 때 `UNKNOWN`으로 보고 조회로 확정한다(ORD-07).
- **키 바닥값 `keyFloor`**(재기동 간격): 부팅마다 계좌·거래일별로 `keyFloor` = max(그날 원장의 모든 `keySeq`, 그날 이전 부팅들의 `keyFloor`) + 10,000(`[가정]` 간격)을 계산해 **그 계좌의 `orders` 원장에 `key-floor` 기록으로** 남긴다(원본). ⑤ 기동 기록에는 사람이 보기 위한 사본만 싣는다. 그래서 이전 부팅들의 `keyFloor`는 계좌 원장에서 읽고, `boot` 원장이 깨져도 키 간격은 지켜진다. `key-floor` 기록을 쓰지 못하면 그 계좌의 **올리는 전이를 모두 막는다**(OPEN뿐 아니라 PANIC의 OFF → PROTECTIVE, `enterProtective`도, 2.7 "차단의 범위"). 보호 모드로 올려 기록 없이 청산을 보내면 그 키가 다음 부팅 키와 겹칠 수 있어서다(QA PR #239 발견 1 시나리오 2). 2.5의 저장소 장애 상태에서 메모리로만 발급한 키는 원장에 없을 수 있지만, 그 키들은 모두 그 부팅의 `keyFloor` + 9,999 안에 있고 다음 부팅의 바닥값은 그 위에서 시작하므로 겹치지 않는다. "재기동 → 바로 저장소 장애 → 메모리 발급 → 또 재기동"이 이어져도 직전 부팅의 `keyFloor`가 계좌 원장에 남아 있어 같다.
- 엔진이 켜진 채 거래일이 바뀌면 새 날짜 파일의 체크포인트 바로 뒤에 그날 `keyFloor`를 0으로 하는 `key-floor` 기록을 남긴다(그날 이전 부팅이 없으므로 원장 최대 키 번호부터 이어짐). 이 기록이 없는 거래일은 바닥값 0으로 본다.
- 부팅 번호는 `boot` 원장 마지막 번호와 모든 원장 기록의 `boot` 칸 최댓값 중 큰 값 + 1로 정한다. `boot` 원장이 깨져도 부팅 번호가 되풀이되지 않는다.
- 저장소 장애 상태에서 메모리 발급 키 번호가 그 부팅의 `keyFloor` + 9,999에 닿으면 `[추론: 한 종목·방향의 하루 청산·손절·재설정 주문은 수십 건 이하]` 그 뒤 청산·손절은 **계속 보내고**(D-023 공통 원칙 1) 긴급 알림을 낸다. 이때 다음 부팅 키와 겹칠 수 있으므로 그 계좌는 다음 기동에서 대사 대기(2.7 차단의 범위 (나))로 두고 "원장 밖 주문 가능"으로 보고 2.7 ⑦대로 사람이 확인하기 전 OPEN을 막는다. 한국투자는 증권사에 키를 싣지 않으므로(아래) 겹침의 영향은 원장 안 대조가 모호해지는 것이고, 모호하면 `UNKNOWN`으로 둔다.
- 타임아웃이면 다시 보내지 않고 조회부터 한다. 미접수로 확정됐을 때만 새 키로 한 번 다시 보낸다(ORD-02, 지침 4장 2번). "원키당 재발주 1회"도 원장 기록(`retryOf`)으로 센다.
- 한국투자는 주문에 우리 키를 실을 칸이 없다(7단계 준비 계획 D4). 그래서 증권사 쪽 중복 판정은 키가 아니라 원장의 주문 의도(종목·방향·수량·시각 창)와 일별 주문 조회를 맞춰 본다. 맞추는 규칙은 묶음 D 한국투자 PR에서 정하고, 하나로 맞지 않으면 `UNKNOWN`으로 둔다.

### 2.7 재기동 복구 순서

```
① Guard 생성(모든 계좌 OFF) ─ 원장을 읽기 전에, 원장과 상관없이
② engine.lock(ADR-006) → writer.lock(2.9) 잡기. 못 잡으면 기동 거부
③ 원장 검사: 계좌·공통 원장마다 체크포인트부터 rseq·crc 대조, 끝이 잘린 줄만 잘라 냄
④ 상태 다시 만들기: 주문(종결 안 된 것은 모두 UNKNOWN), 보유 로트와 조합 해시, 리스크 제한, 블랙리스트
⑤ 기동 기록·계좌별 key-floor 쓰기(부팅 번호 +1, 직전 종료 정상 여부, 2.6). 실패하면 해당 범위의 올리는 전이 차단(2.5)
⑥ 명령 채널·하트비트 시작. STATUS에 계좌별 "복구 결과·대사 필요" 표시
⑦ 사람이 올리는 전이(활성화, PANIC으로 보호 모드 D-140 ①, enterProtective)를 시작하면 주문 전에 증권사 대사
⑧ 대사 통과 계좌만 OPEN 가능, 보호 모드로 올린 계좌도 대사 통과 전에는 주문 0건
```

**차단의 범위**: 이 문서의 차단은 두 종류다.

- **(가) 전면 차단**: Guard를 올리는 **모든** 전이를 거부한다. `beginActivation`(→ ACTIVATING → OPEN), `enterProtective`(OFF → PROTECTIVE), PANIC의 OFF → PROTECTIVE(D-140 ①)가 모두 거부되고, 그 계좌는 OFF 그대로이며 주문 세션 허가(`OrderSessionPermit`)는 0건이다. 해당 조건: 계좌 원장 손상(그 계좌, ③), `key-floor` 기록 실패(그 계좌, 2.6), 블랙리스트 원장 손상(모든 계좌, ③), 기동 기록 실패(모든 계좌, 2.5·⑤), 두 쓰기 주체(모든 계좌, 2.9). 이 조건들은 원장으로 블랙리스트·키·기록 주체를 확신할 수 없는 상태라, 시스템이 고른 매도가 절대 규칙 3이나 지침 4장 2번을 어길 수 있다(QA PR #239 발견 1 시나리오 1·2). 막힌 계좌의 청산은 긴급 알림에서 증권사 앱 매도를 안내하고, 사람이 원인을 처리하면(I1 절차) 풀린다. **D-140 ①과의 관계**: OFF 계좌 PANIC의 보호 모드 상향(D-140 ①, 사용자 결정)을 이 조건에서만 더 막는 쪽으로 좁힌다. 사용자 확인 대상이다(8장).
- **(나) 대사 대기**: 올리는 전이는 허용하지만, 올린 뒤 증권사 대사(⑦)를 통과하기 전에는 **주문 0건**이고 OPEN은 대사 통과 뒤에만 된다. 해당 조건: `UNKNOWN` 주문이 남음(ORD-07), 원장 밖 미체결 주문(⑦), 키 상한 도달 뒤 기동(2.6). `UNKNOWN` 확정과 원장 밖 주문 확인은 올린 뒤의 대사에서만 할 수 있으므로(활성화 중 `FIRST_RECONCILIATION` 단계, 보호 모드로 올린 계좌는 주문 전 같은 대사) 이 조건으로 올리는 것까지 막으면 그 계좌를 다시 열 길이 없다(architect 재검토 3 R3-1).
- 이미 OPEN·PROTECTIVE인 계좌에 실행 중 저장소 장애가 나면 두 차단과 상관없이 내리기만 하고 청산·손절은 계속한다(2.5, D-023 원칙 1). 그날 신규 진입 차단(④)은 (나)와 별개로, 대사를 통과해도 보호 모드까지만 연다.

- ① 순서를 바꾸지 않는다. 원장이 무엇을 말하든 Guard는 OFF로 시작한다. 원장에 "직전 OPEN" 전이가 있어도 그 계좌는 OFF다(5장 시험 1).
- ③ 손상 처리: **그 원장의 계좌만** "복구 실패"로 두고 전면 차단한다(차단의 범위 (가), OFF 유지, 긴급 알림). 다른 계좌는 계속 복구한다. 공통 원장 중 `blacklist`가 손상이면 블랙리스트를 확신할 수 없으므로 **모든 계좌를 전면 차단한다**(차단의 범위 (가), 지침 4장 3번이 절대 규칙이라). `boot`·`audit/commands` 손상은 활성화를 막지 않고 경고한다. `audit/commands`는 복구 입력이 아니고, `boot`가 주던 키 바닥값과 부팅 번호는 계좌 원장과 각 기록의 `boot` 칸에서 다시 얻기 때문이다(2.6). 손상 원장은 지우지 않고 그대로 둔다. 사람이 원인을 본 뒤 조치하는 절차는 7단계 절차서(I1)에 넣는다.
- ④ 리스크 제한 상태는 원장 그대로 되살린다. 재기동이 킬스위치·서킷·주문 실패 정지를 푸는 길이 되지 않는다(ORD-08 "자동 해제 금지"). 하루 단위로 정의된 제한의 날짜 경계 해제 여부는 Q-008 값과 함께 묶음 C에서 정한다.
- ④ 기록이 빠졌을 수 있는 계좌: 그 계좌에 `degraded` 표시 파일이 있거나, 정상 종료 기록이 "저장소 장애 있었음" 또는 "비우지 못한 대기열 1건 이상"을 적었거나, 직전 종료가 비정상인데 그 계좌 원장에 끝 잘린 줄·다시 시도하던 기록 흔적이 있으면, 다시 계산할 수 없는 제한(사람이 건 킬스위치, 서킷 단계, 주문 실패 정지)이 빠졌을 수 있다. 이 계좌는 **그날 신규 진입을 막고**(활성화해도 보호 모드까지만), 사람의 해제 명령으로만 푼다(명령은 묶음 C에서 정의). 체결로 다시 계산할 수 있는 제한(일 손실 한도 등)은 ⑦에서 다시 판정한다.
- ⑦ 대사(B6·ORD-07): 증권사 미체결·체결·잔고 조회로 `UNKNOWN`을 하나씩 확정한다. 확정 전에는 그 계좌의 주문이 0건이다. OPEN으로 가는 활성화는 물론, PANIC·`enterProtective`로 보호 모드에 올린 계좌도 `UNKNOWN`을 모두 확정하기 전에는 청산·손절을 새로 내지 않는다(조회 전 재주문 금지, 지침 4장 2번, ORD-07). 하나로 확정되지 않는 `UNKNOWN`이 남으면 그 계좌는 주문 없이 머물고 긴급 알림으로 증권사 앱 확인을 안내한다. 그날 일 손실·하루 진입 수 누계는 증권사 체결 조회로 다시 계산해 원장 계산과 비교하고 **더 막는 쪽 값**(손실이 큰 쪽, 진입 수가 많은 쪽)을 쓴다. 다시 계산한 값이 한도를 넘으면 그 제한을 다시 건다. 보유 차이는 다음처럼 다룬다.
  - 증권사에 있고 원장에 없는 보유 → AUTO_ASSET(RSK-12 "시스템 주문 원장에 없는 보유"). 보유 중 등록 경고(D-035)를 낸다.
  - 원장에 있고 증권사에 없거나 적은 보유 → 외부 매도(D-047 ③). 서버 측 손절을 남은 수량에 맞게 조정한 뒤에만 그 종목의 다른 주문.
  - 증권사에 있고 원장에 없는 **미체결 주문** → "원장 밖 주문". 저장소 장애 동안 보낸 주문일 수 있으므로 자동으로 취소하지 않고, 그 계좌를 대사 대기(차단의 범위 (나))로 두어 주문 0건·OPEN 불가로 머물게 하고 긴급 알림에 올린다. 사람이 증권사 앱에서 확인하고 확인 명령(B6에서 정의)을 낸 뒤 계속한다.
- OFF로 남은 계좌의 미확정 주문(대사 전 `UNKNOWN`)은 ⑥ 직후 재기동 긴급 알림에 계좌·종목·건수로 넣는다(B6, TST-07 (5) F-6). 증권사 조회는 OFF 계좌에서 하지 않는다(주문 세션 없음, ADR-002 2.2). 그래서 원장만으로 알린다.
- 복구 시간 목표: 그날 파일과 체크포인트만 읽어 1초 안 `[추론]`. B1 PR에서 하루치 최대 기록 수 가정으로 시험한다.

### 2.8 블랙리스트(B5)

- 쓰기는 엔진만 한다. 등록·해제는 명령 채널로 들어온다(ADR-006 명령 추가는 B5 PR에서 개정). 해제는 2차 확인, 보유 중인 AUTO_ASSET 해제는 거부(RSK-12).
- 엔진은 변경마다 `snapshot.json`(버전, 항목 전체, 원장 마지막 `rseq`, sha256)을 임시 파일에 쓰고 원자적으로 교체한다. 실험실(실시간 모의 계좌, RSK-12 전역 적용)과 화면은 이 파일만 읽는다. 엔진 원장 파일은 다른 프로세스가 읽지 않는다.
- 엔진이 꺼져 있어도 스냅샷은 남아 있어 실험실은 마지막 블랙리스트를 계속 쓴다. 엔진이 꺼진 동안 화면에서 등록하는 길(추가 요청 파일을 두고 엔진이 기동 때 받아들임 등)은 B5 PR에서 정한다. 해제는 어떤 경우에도 엔진 명령으로만 한다.
- 읽는 쪽이 스냅샷을 못 읽거나 sha256이 맞지 않으면 직전에 읽은 스냅샷을 유지하고, 처음부터 읽은 적이 없으면 그 쪽의 신규 진입을 막는 것을 추천안으로 두고 B5에서 확정한다.
- `[추론]` Windows에서 백신 등이 파일을 잡고 있으면 원자적 교체가 실패할 수 있다. 실패하면 엔진은 다시 시도하고 경고하며, 읽는 쪽은 직전 스냅샷을 그대로 쓴다. 이 경우에도 엔진 자신의 판정은 원장 기준이라 막히지 않는다.

### 2.9 쓰기 주체 하나 지키기

- `writer.lock`을 `FileChannel.tryLock`으로 잡지 못하면 기동을 거부한다. `NOFOLLOW_LINKS`로 연다.
- `[사실]` 리눅스·macOS는 잠긴 파일도 지울 수 있다(ADR-006 2.2 한계). 그래서 두 겹을 더 둔다. (가) 실행 중 엔진은 `writer.lock`에 자기 부팅 번호와 PID를 적어 두고 주기적으로 파일이 그대로 있는지, 내용이 같은지(POSIX에서는 `fileKey`도) 확인해 다르면 긴급 알림을 낸다. `[사실]` main `ControlServer.java:374`는 `lockKey == null`이면 교체 감지를 통과시키는데, `[추론]` Windows의 `BasicFileAttributes.fileKey()`는 null이고 JDK가 파일을 FILE_SHARE_DELETE로 열어 잠긴 파일도 지워질 수 있으므로 `fileKey`만으로는 Windows에서 감지하지 못한다. 그래서 내용 대조를 기본으로 하고, Windows 실제 동작(삭제 가능 여부, 감지 시간)은 B1에서 운영 PC로 확인하고 3-R을 운영 PC에서 시행한다(묶음 A C6의 `engine.lock` 감지와 같은 장치, 장애 테스트 3-R). (나) 기록마다 `boot` 번호를 싣는다. 복구 때 더 큰 부팅 번호가 시작된 뒤에 작은 부팅 번호의 기록이 이어지면 "쓰기 주체 둘"로 보고 모든 계좌의 활성화를 막는다.
- 감시 프로세스의 긴급 청산 경로(묶음 F, Q-048·Q-059)가 생기면 그 경로도 같은 원장에 같은 규칙으로 쓴다. 엔진이 살아 있는 동안에는 쓰지 않고, 엔진이 멈춰 `writer.lock`이 풀렸을 때만 잡는다. 감시가 잡고 있는 동안 엔진 기동은 거부된다. 자세한 것은 묶음 F ADR에서 정한다. 이 ADR은 "한 번에 쓰기 주체 하나, 같은 원장, 같은 키 발급 규칙"만 고정한다.

### 2.10 코드 위치

- 새 순수 모듈 `autotrade-real-store`(패키지 `com.autotrade.realstore`)를 B1 PR에서 만든다. 원장 쓰기·읽기·복구·키 발급기·Guard·명령 감사 어댑터를 둔다. 의존은 `autotrade-domain`·`autotrade-risk`·Jackson까지.
  - 엔진 패키지(`app.engine.store`)에 두지 않는 이유: 감시 긴급 경로(2.9)가 같은 코드를 써야 하는데 프로세스 모듈끼리는 참조할 수 없다(ADR-001).
  - 실험실·게이트웨이·수집기·실험 명령은 이 모듈에 의존하지 못하게 한다(게이트웨이·수집기·실험 명령은 `processIsolation`의 금지 목록과 ArchUnit. **실험실은 `autotrade.process-conventions`가 아니라서 `processIsolation`이 없으므로**(`autotrade-app-lab/build.gradle.kts`) ArchUnit 규칙이 유일한 장치다. B1이 빠뜨리지 않는다). 실험실이 읽을 블랙리스트 스냅샷 형식 클래스의 위치는 B5 PR에서 architect가 정한다(후보: `autotrade-config`).
  - 새 모듈은 `ModuleOwnershipTest.OWNERS`와 실전 경로 모듈 목록 갱신이 필요하다. 보호 테스트 변경이라 B1 PR은 실전 관련 PR이다(지침 11장).
- `GuardAuditLog` 인터페이스는 바꾸지 않는다. `RealTradingGuard`는 올림 감사를 잠금 밖으로 옮기는 변경만 B1에서 한다(2.5 "올림 감사와 계좌 잠금", 공개 생성자·불변식은 그대로). 엔진 배선(`EngineMain.startGuard`)에서 `LoggingGuardAuditLog` 자리에 저장소 어댑터를 넣는다.
- 외부 jar와 JDK 허용 목록(D-086)은 늘리지 않는 것이 목표다. 쓰는 JDK API는 `java.nio.channels`·`java.nio.file`·`java.util.zip`·`java.util.concurrent`이며 모두 이미 허용돼 있다 `[사실: RealPathReflectionTest.ALLOWED_JDK_PACKAGES]`. Jackson과 `java.io`는 **클래스 단위** 허용 목록이라(`RealPathReflectionTest`의 Jackson 허용 클래스, `ALLOWED_JDK_CLASSES`) JSON 줄 쓰기에 목록 밖 클래스(예: `SequenceWriter`)를 쓰면 늘려야 한다. 늘리면 보호 테스트 고정 값 변경이고, 그 PR에서 이유를 적는다.

### 2.11 보관

- 저장소는 원장 파일을 **자동으로 지우지 않는다**(지우는 일은 되돌릴 수 없어 사용자 결정, 지침 8장 3번). 하루 기록은 수백 KB 수준 `[추론: 주문 1건당 기록 5~10줄 × 1KB]`이라 몇 년을 두어도 부담이 작다.
- 체크포인트 덕분에 오래된 날짜 파일은 복구에 필요 없다. 사용자가 백업·보관 위치로 옮기는 절차는 I1 절차서에 넣는다. 원장 폴더를 사용자 백업 대상에 넣으라는 안내도 같이 둔다.

## 3. 대안 검토

| 안 | 장점 | 단점 | 판단 |
|---|---|---|---|
| A. PostgreSQL(ADR-001 Q-009 DB)을 엔진 원본으로 | SQL 조회, 화면·분석에 바로 씀, 기획서 "DB" 문구와 일치 | 실전 엔진이 다른 서비스의 생존·속도에 묶임(서비스 중지·업데이트·연결 고갈 때 손절 기록 지연, 지침 4장 6번). 실험실의 무거운 조회와 같은 서버를 나눔. JDBC 드라이버·`java.sql`을 실전 경로 허용 목록에 넣어야 하고 드라이버는 `ServiceLoader`·리플렉션을 쓴다(D-086 보호 테스트 변경). 개인 PC에 DB 서버 상시 실행 필요 | 버림 |

| C. **엔진 전용 추가 기록 원장(JSON 줄, 강제 기록, CRC, 일련번호, 체크포인트)** | 외부 의존 0, 허용 목록 변경 0, 계좌별 분리 쉬움, "기록 먼저 보내기"를 코드로 증명 가능, 손상 범위가 줄 단위로 보임 | 조회·집계는 직접 구현, 형식 버전 관리 필요 | **채택** |
| D. 상태 파일을 통째로 원자적 교체 | 단순 | 전이 이력이 남지 않음(ORD-07 "전이마다 기록" 불충족). 교체 실패·백신 잠금 때 상태 전체가 늦어짐 | 원장에는 버림. 읽는 쪽용 블랙리스트 스냅샷에만 사용(2.8) |
| E. 메모리 매핑 큐(Chronicle Queue 등) | 빠름 | 외부 jar, `Unsafe`·리플렉션 사용(D-086), 우리 쓰기 규모(초당 수 건)에 과함 | 버림 |
| F. C를 원본으로 두고 다른 프로세스가 PostgreSQL에 복사본을 만듦 | 화면·분석에서 SQL 사용 | 지금 필요 없음 | **나중에 허용**: 복사본은 엔진이 다시 읽지 않는 읽기 전용이어야 하고, 복사하는 쪽은 실험실 등 엔진 밖에서 스냅샷 파일만 읽는다. 화면 요구(UI-08, I3)가 생길 때 ui-dev가 제안 |

- 되돌릴 조건: (1) B1 실측에서 운영 PC의 강제 기록 지연이 2.5 상한을 자주 넘으면 묶음 커밋 주기를 조정하고, 그래도 안 되면 저장 장치 권고(SSD)를 절차서에 넣는다. (2) 화면 조회 요구가 원장 직접 집계로 감당이 안 되면 F를 연다. A로 되돌리는 것은 엔진이 DB 서비스에 기대게 되므로 지침 4장 6번 재검토와 사용자 결정이 필요하다.

## 8. 추천안 채택(자율)과 사용자 확인

추천안 채택(자율, architect): 원칙 2~6(2.1), 폴더 구조(2.3), 기록 형식(2.4), 쓰기 상한 표의 구조(2.5, 값은 `[가정]`), 올림 감사를 계좌 잠금 밖으로(2.5), 키 발급과 키 바닥값(2.6), 복구 순서(2.7), 블랙리스트 단일 쓰기·스냅샷(2.8), 쓰기 주체 하나(2.9), 새 모듈 위치(2.10), 자동 삭제 없음(2.11). 실전 경로 설계라 risk-ops 검토와 사용자 머지를 거친다.

**Q-062 (architect → 사용자, 2026-10-25 결정: 파일 원장)**: 실전 엔진 상태(주문 원장, 블랙리스트, 감사, 리스크 제한)를 PostgreSQL이 아니라 엔진 전용 파일 원장에 둘까? 추천: **파일 원장(안 C)**. 이유: 실전 엔진이 DB 서비스의 생존에 묶이지 않고, 실전 경로 허용 목록(D-086)을 늘리지 않는다. 대안: PostgreSQL(안 A, 기획서 RSK-12 "(DB)" 문구 그대로). 기획서 문구와 다른 선택이라 물었고, 사용자가 파일 원장을 골랐다.

**D-140 ① 범위 확인 (architect → 사용자)**: 2.7 "차단의 범위" (가)의 조건(원장 손상, `key-floor` 기록 실패, 블랙리스트 원장 손상, 기동 기록 실패, 두 쓰기 주체)에서는 OFF 계좌 PANIC의 보호 모드 상향(D-140 ①)도 거부하고 증권사 앱 매도를 안내한다. 추천: 거부(시스템이 블랙리스트·키를 확신할 수 없는 채로 매도하지 않음). 대안: 이 조건에서도 PANIC 상향 허용(빠른 청산, 블랙리스트 종목 매도·키 겹침 위험). 사용자가 PR에 확인 댓글을 남기거나 머지하면 확정한다.
