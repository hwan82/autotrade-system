# ADR-010 실시간 시세 전달(게이트웨이 → 실험실)과 실시간 모의 세션

- 상태: 채택(D-076, PR #87 머지 `40388a4`, QA 승인 docs/reviews/pr-87/qa.md). 작성 architect, 구현 data-engineer(전달·입력 기록)·sim-engine(실행기 공통부·세션·리플레이 확인). 교차 검토: risk-ops(게이트웨이는 7단계에 실전 엔진과 함께 쓰므로 절대 규칙 6), architect(모듈 경계).
- 날짜: 2026-10-14
- 단계: 6단계(실시간 모의 운영) 선행. ADR-003 5장 "게이트웨이 → 실전 엔진·실험실 실시간 전달(IPC): 녹화까지만" 행 중 **실험실** 쪽을 닫는다. 실전 엔진 쪽 전달은 7단계에서 따로 정한다.
- 근거 결정: D-004(실시간 모의 실험실), D-013(프로세스 4개), D-063(실험 명령 장 시간 보호·정지 요청 파일), D-065(녹화 재기동 공백), D-068·D-069(녹화 어댑터·녹화 실험), 지침 4장 6번(실전 매매는 다른 기능에 영향받지 않음)·5장(결정론)
- 실전 주문 경로·RealTradingGuard·블랙리스트 코드·리스크 한도·장애 대응 규칙은 바꾸지 않는다. 게이트웨이는 주문 API를 부르지 않는 그대로이고(MD-01), 이 ADR로 게이트웨이에 생기는 것은 "녹화하는 줄을 같은 PC의 받는 쪽에도 내보내는 출구" 하나다.

## 1. 배경

- [사실] 게이트웨이(`autotrade-app-gateway`)는 실시간 시세를 받아 녹화만 한다(`MarketHub` → `MarketEventRecorder`). 실험실은 녹화 파일을 리플레이할 뿐 실시간 시세를 받을 길이 없다(ADR-003 5장).
- [사실] 6단계는 "실전 API 실시간 시세 위에서 자체 모의 계좌 여러 개를 병렬 운용"을 8주 이상 돌리는 단계다(team-design.md 6장). 그 전제가 실시간 전달과 실시간 모의 계좌 실행이다.
- [사실] 실험 결과는 결정론적이어야 하고(지침 5장), SIM-13은 "같은 녹화일·프로필로 실시간 모의 결과와 리플레이 결과의 차이를 측정·기록"을 요구한다.
- [사실] 게이트웨이는 7단계에 실전 엔진에도 시세를 줄 프로세스다. 실험실 쪽 느림·장애가 게이트웨이 수신·녹화(나아가 실전 엔진 전달)를 막으면 절대 규칙 6 위반이다.
- [사실] 같은 PC 프로세스 사이 로컬 통신은 ADR-006(실전 제어 채널)이 Unix 도메인 소켓(설정 폴더 아래, 폴더 700·소켓 600)으로 이미 정했다.

## 2. 결정

### 2.1 전달 방식: 설정 폴더 아래 Unix 도메인 소켓 `run/market-feed.sock`

- 게이트웨이가 서버(`FeedServer`), 실험실이 받는 쪽(`FeedClient`). 둘 다 `autotrade-marketdata`의 `com.autotrade.marketdata.feed`(순수 모듈, 스프링 없음).
- 경로 `<AUTOTRADE_CONFIG_DIR>/run/market-feed.sock`(`FeedSocket.path`). 폴더는 소유자만(700), 소켓 파일은 600(POSIX에서). Windows는 Unix 도메인 소켓(AF_UNIX) 파일의 ACL을 따른다 `[가정]`(ADR-006과 같은 가정, 사용자 PC 확인 대상).
- 게이트웨이 기동 때 열고(`GatewayMain.openFeed`) 못 열면(경로 길이, 다른 게이트웨이가 이미 듣는 중, 권한) **경고만 남기고 녹화만 한다**. 전달은 실험실용 부가 기능이라 수신·녹화를 막지 않는다. 비정상 종료로 남은 소켓 파일은 아무도 듣고 있지 않을 때만 지우고 다시 연다.
- 대안은 3장.

### 2.2 규약(JSONL, 녹화 형식 재사용)

1. 받는 쪽이 구독 줄 한 줄: `{"subscribe":["KRX"],"client":"lab"}`(시장 목록, 이름은 `[a-z0-9-]{1,32}`, 1KB 이내, 5초 안에 와야 함).
2. 게이트웨이가 인사 줄 한 줄: `{"feed":"autotrade-market-feed","formatVersion":1}`. 녹화 형식 버전(`RecordingCodec.FORMAT_VERSION`)이 다르면 받는 쪽이 끊는다.
3. 그 뒤 게이트웨이가 **녹화와 같은 줄 형식**(`RecordingCodec`)으로 이벤트를 보낸다. `seq`는 연결마다 1부터, `src`·`srcSeq`는 원래 소스 이름과 소스 순번 그대로. 받는 쪽은 `srcSeq`를 이벤트 순번으로 되돌린다.
4. 받는 쪽은 구독 뒤 아무것도 보내지 않는다. 무엇이든 오거나 끊기면 게이트웨이가 그 연결을 닫는다(장 밖처럼 보낼 이벤트가 없을 때도 끊긴 받는 쪽이 자리를 차지하지 않게).
- 줄 형식을 녹화와 같게 둬서 형식이 하나뿐이고, 녹화 형식 변경(버전 올림)이 전달에도 그대로 걸린다.

### 2.3 게이트웨이는 기다리지 않는다(절대 규칙 6)

- `MarketHub`가 녹화기에 넣는 바로 그 자리에서 `FeedServer.publish`를 부른다(같은 이벤트, 소스 전환 공백 포함). 한 소스 안의 순서는 녹화와 같다. 두 소스가 동시에 받는 SHARDED 모드에서는 두 수신 스레드가 "녹화 → 전달"을 따로 하므로 소스 사이 순서가 녹화와 다를 수 있다(risk-ops PR #87 N1). 게이트웨이 수신 경로에 잠금을 더하지 않으려고 맞추지 않는다. 실시간 모의의 기준 입력은 실험실 입력 기록이라 결정론에는 영향이 없다. `publish`는 기다리지 않고 예외를 던지지 않는다.
- 연결 받기(`accept`) 실패가 이어지면 10ms에서 1초까지 늘려 쉬고 로그는 1·2·4·8…번째에만 남긴다(risk-ops R3). 받는 쪽 큐가 차서 버린 수는 게이트웨이 로그에 1분에 한 번까지 남긴다(N3).
- 받는 쪽마다 고정 크기 큐(50,000줄)와 전용 쓰기 스레드(데몬). 큐가 차면 그 줄을 버리고, 다음에 넣을 수 있을 때 그 종목에 `DataGap(CONSUMER_OVERFLOW, src "FEED")`을 먼저 넣는다.
- 한 줄 쓰기가 30초 넘게 끝나지 않는(받는 쪽이 읽지 않아 소켓 버퍼가 찬) 받는 쪽은 끊는다(`STALL_LIMIT`). 오래 조용하다가 첫 이벤트가 온 정상 연결은 끊지 않는다(architect PR #87 R3).
- 게이트웨이 기동이 중간에 실패하면 이미 연 허브·녹화기·전달 소켓을 닫고 실패를 올린다.
- 받는 쪽은 최대 4개(`MAX_SUBSCRIBERS`). 넘으면 새 연결을 바로 닫는다.
- 게이트웨이 종료 때 전달을 마지막에 닫고 소켓 파일을 지운다.
- 시험: 읽지 않는 받는 쪽이 붙은 상태에서 큐가 넘칠 때까지 `publish`를 불러도 기다리지 않고 버린 수만 늘며(10초 상한 안), 다시 읽기 시작하면 넘친 구간이 공백으로 온다(`FeedServerTest.slowSubscriberNeverBlocksPublishAndGetsOverflowGap`, 컨테이너 `[사실]`).

### 2.4 실험실: 실시간 모의 세션

- 등록 파일 `experiments/<실험ID>/experiment.yaml`, `input: "live"`(`LivePlan`). 키는 녹화 실험과 같고(`id, question, market, from, to, seed, seed-capital, benchmark, profiles, boards, blacklist`), `boards`가 받을 종목 목록이다. 지금은 KRX만, 선정 프로필 없음(녹화 실험과 같은 범위).
- 사전 등록: 운용 전에 커밋하고 운용 중 고치지 않는다. 바꾸려면 새 실험 ID.
- 실험실 API(`/api/live`, ADR-005 웹 보안 그대로): `GET /status`, `POST /sessions/{id}/start`, `POST /stop`, `POST /finish`. 한 번에 한 세션. 화면은 후속(ui-dev).
- 세션 하나 = 계좌(프로필) N개. 계좌는 리플레이 실행기와 **같은 코드**로 움직인다: 실행기의 Run 한 개 단계를 `RunStepper`(`autotrade-sim` `run` 패키지)로 떼어 리플레이 실행기(`SimulationExperimentRunner`)와 실시간 세션(`LiveSession`)이 같이 쓴다. 리스크 체인·주문 상태머신·블랙리스트·가상 거래소 그대로(지침 5장).
- 계좌 하나가 예외로 멈춰도 그 계좌만 실패로 남고 나머지는 계속한다(계좌 격리).

### 2.5 결정론: 입력 기록을 먼저 쓰고, 쓴 줄을 계좌에 준다

- 세션은 받은 이벤트를 **먼저 입력 기록(journal)에 쓰고**(`JournalWriter`, 동기, 녹화와 같은 형식·폴더 구조) 기록이 돌려준 줄(순번 포함)을 그대로 계좌에 준다. 계좌가 본 입력 = 기록, 줄 단위로 같다.
- 입력 기록 위치: `<설정 폴더>/live-sessions/<실험ID>/journal/KRX/<날짜>/`(저장소 밖, 녹화와 같은 재배포 금지 규칙, ADR-003 4장).
- 이벤트 순번 = 기록 전체 위치(녹화 실험 `RecordedMarketDataSet`과 같은 번호). 그래서 기록을 녹화 실험처럼 다시 돌리면 같은 순서·같은 순번이다.
- **재기동**: 실험실이 다시 세션을 열면 기록을 처음부터 다시 돌려 계좌를 되살리고(기록에는 다시 쓰지 않음), 그날 기록에 이어 쓸 때 녹화와 같은 재기동 공백(`RECORDER_RESTART`, D-065)이 남고 계좌에도 그대로 간다. 다음 날로 넘어가 이어 받으면(앞 날 장중에 멈춘 경우 등) 새 날 파일 첫 줄 앞에 앞 날 종목마다 같은 공백(시작은 앞 날 마지막 수신 시각, 끝은 새 날 첫 수신 시각)을 남긴다. 앞 날 파일은 다시 열지 않는다. 기준이 되는 앞 날은 읽을 줄이 있는 마지막 기록일이다(새 날 파일만 열고 첫 줄을 내리기 전에 다시 죽은 빈 날은 건너뜀)(`JournalWriter.resumeAfter`, QA PR #91 R1, risk-ops PR #94 N1). 게이트웨이 녹화기는 이 동작을 쓰지 않는다(날마다 새로 뜨는 녹화는 앞 날 공백을 남기지 않음, D-065 그대로). 받는 쪽이 끊겼다 다시 붙으면 그 사이 본 종목마다 `DataGap(DISCONNECTED, src "FEED-CLIENT")`을 넣는다. 받는 큐(100,000)가 차면 `DataGap(CONSUMER_OVERFLOW, src "LAB-INBOX")`.
- 운용 기간 밖 이벤트, `boards`에 없는 종목은 기록에도 계좌에도 넣지 않고 세기만 한다.
- 계좌는 모든 종목을 주식 호가 단위로 본다(녹화 실험과 같음, D-075 4번). 체결가·호가가 주식 호가 단위에 맞지 않는 이벤트(ETF·ETN 등)가 오면 기록에 쓰지 않고 세션을 멈춘다(`stopReason`). 그런 종목은 `boards`에서 빼고 새 실험 ID로 등록한다. 리플레이 확인도 입력 기록에서 같은 검사를 한다(architect PR #87 R1).
- 세션 잠금 파일(`session.lock`, 운영체제 파일 잠금)로 한 세션을 두 프로세스가 같이 열지 못한다. 실험실이 재기동해도 세션을 자동으로 다시 열지 않는다(사용자가 다시 시작).
- **끝내기**(`POST /finish`): 마지막 거래일을 마감하고 상세 보고서를 `experiments/<실험ID>/live-detail.txt`에 쓴다(`ReportWriter` 형식).

### 2.6 리플레이 확인 명령(SIM-13)

- `./gradlew :autotrade-app-experiment:runLiveReplayCheck -Pexperiment=<실험ID>`(`ExperimentMain live-check`): 끝난 세션의 입력 기록을 리플레이 실행기로 다시 돌려 `live-detail.txt`와 바이트로 비교한다(`code` 줄 제외: 실험실과 명령이 커밋을 다르게 알 수 있음). 같은 입력·같은 코드라 **차이 0이 합격선**이고, 다르면 실시간 경로 결함이다(종료 코드 2).
- 결과는 녹화 실험(D-069)과 같은 세 파일(`inputs.yaml`, `results.md`, `detail.txt`)을 등록 파일 옆에 쓴다. `inputs.yaml` 머리에 `clock-mode: REALTIME`.
- 무거우므로(기록 전체를 메모리에) 실험실 안이 아니라 실험 명령으로만 돌리고, D-063 장 시간 보호·정지 요청 파일 확인을 그대로 받는다. 세션이 열려 있으면(잠금) 거부한다.

### 2.7 자원 양보(절대 규칙 6, D-063)

- 입력 기록 폴더 디스크 여유가 하한(기본 20GB, `autotrade.lab.live.min-free-gb`, 수집기 `--min-free-gb`와 같은 기준, 설정 범위 1~1,000,000GB이고 밖이면 실험실이 뜨지 않음) 미만이면 시작하지 않고, 운용 중이면 1초 안에 멈춘다. 실전 엔진 상태 기록이 같은 디스크일 수 있다(장애표 #8·#10, risk-ops PR #87 R1).
- 재기동 되살리기는 시작 요청 스레드가 아니라 최저 우선순위 스레드에서 기록일 하나씩 읽고(전체를 메모리에 올리지 않음), 날마다 정지 요청·디스크를 본다. 그동안 상태는 `restoring`이고 게이트웨이에 아직 붙지 않는다. 실험실 `bootRun` 힙 상한 4GB(`-PlabHeap`)(risk-ops R2, SIM-14).

- 실험실의 세션 처리 스레드는 가장 낮은 우선순위이고, 1초마다 감시의 정지 요청 파일(`experiment-state/stop-request`, D-058·D-063)을 본다. 파일이 있거나 있는지 판단할 수 없으면 세션을 멈춘다(기록을 닫고 전달 연결을 끊음). 요청이 있는 동안은 시작도 거부한다.
- 실시간 세션 자체에는 D-063 장 시간 보호를 걸지 않는다. 장중에 도는 것이 목적이고, 증권사 호출이 없으며, 계좌 계산이 이벤트당 가볍기 때문이다(무거운 리플레이 확인은 2.6처럼 보호를 받는다).
- 세션이 느려지면 실험실 받는 큐 → 게이트웨이 받는 쪽 큐 순서로 차고, 둘 다 버리고 공백을 남긴다. 게이트웨이 수신·녹화는 기다리지 않는다(2.3).

## 3. 대안 검토

| 대안 | 내용 | 판단 |
|---|---|---|
| A. 채택 | Unix 도메인 소켓 + 녹화 줄 형식, 받는 쪽마다 고정 큐·버림·공백 | ADR-006과 같은 로컬 채널 방식, 파일 권한으로 접근 제한, 형식 하나. 느린 받는 쪽이 게이트웨이를 못 막는다 |
| B. TCP 루프백(127.0.0.1) | 포트 열기 | 같은 PC의 다른 사용자·프로세스가 붙을 수 있어 토큰 인증이 더 필요. 포트 충돌. 버림 |
| C. 실험실이 녹화 파일을 따라 읽기(tail) | 게이트웨이 변경 없음 | 녹화기는 1초 단위로 내려(flush) 지연이 생기고, 파일 회전·gzip·재기동 공백을 따라 읽기가 까다롭다. 디스크를 두 번 읽는다. 지연이 실시간 모의 품질(체결 시점)에 바로 들어감. 버림. 되돌릴 조건: 소켓이 Windows에서 안 되면 이 안으로 |
| D. 실험실 안에 시세 수신을 직접 둠 | 게이트웨이 없이 | 증권사 연결·구독 한도를 게이트웨이와 나눠 써야 하고(키움 토큰당 세션 1개, D-024), 실험실이 증권사 키를 갖게 된다. D-013 프로세스 분리와 어긋남. 버림 |
| E. 받는 쪽이 느리면 게이트웨이가 기다림(무손실) | 공백 없음 | 절대 규칙 6 위반. 버림 |
| F. 입력 기록 없이 실시간 이벤트를 바로 계좌에 | 디스크 절약 | 재기동하면 계좌를 되살릴 길이 없고, 리플레이 확인(SIM-13)이 게이트웨이 녹화와 실험실이 본 입력의 차이(버림·끊김)를 구분 못 한다. 버림 |
| G. 계좌 상태를 주기 저장(스냅샷)하고 재기동 때 불러옴 | 재기동이 빠름 | 계좌·전략 상태 직렬화 계약이 새로 필요하다. 지금은 기록 재실행으로 같은 결과를 보장하고, 8주 운용에서 재기동 시간이 문제가 되면 후속(5장) |

## 4. 위험과 한계

- **디스크**: 입력 기록이 게이트웨이 녹화와 거의 같은 양을 한 번 더 쓴다(받는 종목이 `boards`로 줄어든 만큼 적음). 8주 운용 전에 디스크 여유를 확인해야 한다(6단계 주간 점검 항목).
- **재기동 시간**: 기록 전체를 다시 돌리므로 운용 기간이 길수록 재기동이 느려진다. 되살리기는 별도 스레드에서 하루씩 하므로 요청·상태 조회는 막히지 않는다(architect PR #87 R5, risk-ops R2). 몇 주 분량에서 얼마나 걸리는지 미측정 `[가정]`. 되살리는 동안 게이트웨이 연결은 아직 열지 않으므로 그 구간은 재기동 공백으로 남는다.
- **멈출 때 버리는 이벤트**: 멈춤·끝냄 때 받는 큐에 남은 이벤트는 기록에 없으므로 버린다. 다시 시작하면 재기동 공백이 그 구간을 덮는다(결정론은 유지, 입력만 줄어듦).
- **실험실이 본 입력 ≠ 게이트웨이 녹화**: 전달 큐·받는 큐 버림, 끊김이 있으면 실험실 입력이 녹화보다 적다. 공백으로 남으므로 결과에 표시되지만, "실시간 모의 대 같은 날 게이트웨이 녹화 리플레이" 비교에서는 차이가 날 수 있다. 이 ADR의 합격선은 "실시간 대 입력 기록 리플레이 차이 0"이고, 녹화와의 차이 측정은 6단계 주간 점검에서 한다.
- **Windows**: AF_UNIX 소켓 파일 권한과 경로 길이(약 100자) `[가정]`. 열지 못하면 게이트웨이는 녹화만 하고 실험실 상태에 연결 오류가 보인다.
- **게이트웨이 메모리**: 받는 쪽 4개 × 50,000줄이 최대. 이벤트 객체 크기로 수십 MB 수준 `[추론]`.
- **실전 엔진 전달은 아님**: 7단계 실전 엔진 전달은 무손실·지연 기준이 달라(보유 종목 보호 폴링 D-024 등) 이 채널을 그대로 쓸지 따로 정한다.

## 6. 검증

- `FeedServerTest`(8): 구독 시장만·원래 소스·순번 전달, 소켓 600·폴더 700, 두 번째 게이트웨이 거부, 남은 소켓 파일 정리, 받는 쪽 재연결과 끊김 공백, 느린 받는 쪽에서 `publish`가 기다리지 않고 넘친 구간 공백, 멈춘 받는 쪽 끊기, 받는 쪽 상한·틀린 구독 줄 거부.
- `JournalWriterTest`(6): 돌려준 줄 = 파일 줄, 같은 날 이어 쓰기의 재기동 공백, 다음 날로 넘어가 이어 쓸 때 새 날 첫 줄 앞 공백(앞 날 마지막 수신 시각부터, 앞 날 파일은 그대로), 같은 날 이어 쓰기는 같은 날 공백만, 날짜 나눔, 다른 시장 거부.
- `GatewayFeedTest`(2): 게이트웨이가 녹화한 줄과 실험실이 받은 줄이 소스·순번·내용·순서까지 같음(소스 전환 공백 포함), 전달 소켓을 못 열어도 녹화는 그대로.
- `LiveSessionTest`(10): 이틀치 시세, 중간 실험실 재기동과 끊김 공백이 있어도 **실시간 결과 = 입력 기록 리플레이**(상세 보고서 바이트 일치), 비정상 종료(메타 미종료, 기록 꼬리 잘림) 뒤 같은 날 이어 돌리거나 1일차 중간·끝에서 죽은 뒤 2일차로 재개해도 같고 두 경우 모두 재기동 공백이 남음(QA PR #87 R5, PR #91 R1), 주식 호가 단위 밖 가격이면 기록하지 않고 멈춤, 블랙리스트 종목은 실시간 세션에서도 사지 않음(같은 시세의 대조와 비교, risk-ops N2), 보고서를 바꾸면 리플레이 확인이 "다름"을 냄, 기간·종목 밖 제외, 세션 잠금, 이벤트 없이 끝내기.
- `LiveLabServiceTest`(6): 디스크 여유 하한 설정 1GB 미만·상한 초과 거부와 경계값(1GB·상한) 허용(QA PR #87 R2, PR #91 R2), 게이트웨이 전달 → 세션 → 끝내기에서 보고서 작성, 게이트웨이 없이 시작하고 감시 정지 요청으로 멈춤·시작 거부, 디스크 여유 하한 미만이면 시작 거부·운용 중 멈춤, 되살리는 중 멈추고 다시 시작하면 기록으로 되살림, 틀린 ID 거부.
- `AcceptBackoffTest`(2): 연결 받기 실패 쉬는 시간 10ms→1초, 성공하면 초기화, 로그는 2의 거듭제곱 번째만.
- `ExperimentGateTest` 2개 추가: 리플레이 확인도 장 시간·정지 요청이면 시작하지 않음, 인자 오류.
- 실행기 공통부 분리 뒤 골든 보고서(`krx-golden.report`)와 실패 Run 시나리오가 분리 전과 같음(기존 테스트 그대로 통과).
