# D-105 주간 점검에 수집 멈춤 여부 추가(PR #141 strategy-researcher R4)

- 날짜: 2026-10-17
- 상태: 확정 · **추천안 채택(자율)**(지침 8장). 주간 점검 명령(`runLiveWeeklyCheck`, D-088)의 결과 파일에 4장 하나와 머리 한 줄을 더하고 콘솔에 알린다. 수집기·거래소 캘린더·스냅샷 형식·설정 키·보호 경로·실전 경로는 바꾸지 않는다. D-088의 1~3장 대조와 종료 코드는 그대로다.
- 담당: pm-lead 결정, sim-engine 구현. 교차 검토: architect(코드), strategy-researcher(6단계 선정 입력)
- 근거: [PR #141 strategy-researcher 검토](../reviews/pr-141/strategy-researcher.md) R4, [D-104](D-104-krx-empty-trading-day-guard.md) 1번(캘린더상 거래일 빈 목록이면 수집 중단), [D-088](D-088-stage-6-weekly-check.md), 지침 10장 "6단계 주간 점검"

## 문제

D-104부터 KRX 일봉 수집기는 캘린더상 거래일에 빈 목록이 오면 그날을 휴장일로 캐시하지 않고 멈춘다. 캘린더(`krx.json`, 보호 경로)에 없는 임시공휴일이 생기면 7일 뒤부터 매 실행이 멈추고, 캘린더를 고칠 때까지 새 일봉 스냅샷이 나오지 않는다. 멈추는 쪽이 맞지만(가짜 수정 이벤트보다 낫다) 6단계 실시간 모의 운용 중이면 그동안 선정 결과에 공백이 생긴다. 수집 콘솔은 그날 실행한 사람만 보므로, 매주 보는 점검표에 드러나야 한다.

## 결정

1. **기준**: 수집 스냅샷 폴더(`<설정 폴더>/snapshots/krx-daily/<ID>/manifest.json`, D-019 계약)에서 읽을 수 있는 스냅샷 중 `coverage.lastTradingDate`가 가장 늦은 것을 고른다(같은 날이면 ID가 큰 쪽). 그 날 다음부터 점검 마지막 날까지의 번들 KRX 캘린더 거래일을 "수집 안 된 거래일"로 센다.
2. **판정**: 0~1거래일이면 정상(점검 마지막 날은 아직 수집 전일 수 있다 `[가정]`: 수집기와 주간 점검 모두 장 마감 뒤에 돌린다), 2거래일 이상이면 **멈춤 의심**, 읽을 수 있는 스냅샷이 없으면 **확인 필요**(수집기를 안 돌렸거나 폴더가 다름). KRX가 아닌 시장은 일봉 수집이 없어 해당 없음.
3. **보고**: 결과 파일 머리에 `- 수집: …` 한 줄, 끝에 "4. 수집 멈춤 여부" 장(최근 스냅샷 ID, 수집 안 된 거래일 목록, 읽지 못한 스냅샷 폴더, 할 일). 멈춤 의심이면 할 일에 수집기를 다시 돌려 콘솔 메시지를 보고, "캘린더상 거래일에 빈 목록"이면 KRX 공지로 임시공휴일인지 확인해 캘린더를 고친다(수집기 runbook 3.6, 사용자 머지)를 적는다.
4. **종료 코드는 그대로**: 종료 코드 2는 D-088의 "전달·기록 경로의 설명되지 않는 차이"에만 쓴다. 수집 멈춤은 다른 프로그램의 상태라 콘솔에 `수집 확인 필요: …` 줄로 알리고 결과 파일에 남긴다.
5. **폴더**: 기본 `<설정 폴더>/snapshots`, `-PsnapshotsDir=…`(`--snapshots-dir`)로 바꾼다. 벽시계는 읽지 않는다(점검 마지막 날 기준).
6. 캘린더 수록 범위 밖 날짜(지금은 2028년부터)는 휴장일을 모르므로 평일로 세고 그렇게 적는다(더 많이 세어 놓치지 않는 쪽).

## 대안

| 대안 | 판단 |
|---|---|
| A. 스냅샷 manifest 마지막 거래일로 셈(채택) | D-019 계약 파일이라 수집기 내부 형식에 묶이지 않고, 선정·실험이 실제로 읽는 입력이 어디까지 있는지 그대로 보인다 |
| B. 수집기 캐시(`collector-cache/krx/<시장>/<연도>/<날짜>.json`)의 빈 날을 셈 | 멈춘 날짜를 시장별로 더 정확히 짚지만 수집기 내부 형식에 실험 모듈이 묶이고, 캐시가 있어도 스냅샷을 못 만들었으면(디스크·정지 요청) 선정 공백을 놓친다. 버림 |
| C. 수집기가 실패 때 상태 파일을 남기고 점검이 읽음 | 원인까지 보이지만 수집기·감시 쪽 계약이 하나 더 생긴다(data-engineer 영역). 스냅샷 뒤처짐만으로 멈춤은 드러나므로 지금은 버림. 원인을 점검표에서 바로 봐야 하면 되돌린다 |
| D. 멈춤 의심이면 종료 코드 2 또는 새 코드 | 종료 코드 2의 뜻(전달·기록 결함)이 흐려지고, 수집을 아직 안 돌린 주에도 점검이 실패로 끝난다. 버림 |

되돌릴 조건: 6단계에서 수집을 하루 한 번보다 드물게 돌리기로 하면 허용 뒤처짐(`ALLOWED_LAG` 1)을 그 주기에 맞춘다. 선정 일괄 명령이 생겨 6단계 세션이 매일 선정 결과를 쓰면, 스냅샷 대신 선정 결과 날짜를 기준으로 바꾸는 것을 검토한다.

## 위험과 한계

- 점검을 돌린 때의 스냅샷 폴더를 본다. 같은 `-Pto`로 나중에 다시 돌리면 그 사이 수집이 이어져 정상으로 바뀔 수 있다(1~3장과 달리 이 칸은 결과 파일 재현성의 예외). 주중에 멈췄다가 점검 전에 다시 이어진 경우는 잡지 못한다(그 사이 공백은 스냅샷이 메운다).
- `--keep-snapshots`로 옛 스냅샷을 지워도 가장 최근 것은 남으므로 판정에는 영향이 없다.
- 캘린더가 실제 거래일을 휴장일로 잘못 적으면 그날은 세지 않는다(2026년 휴장일 대부분 `verified: false`). 그 경우 수집은 멈추지 않으므로 선정 공백 문제는 아니다.
- 원인(임시공휴일·호출 상한·디스크·정지 요청)은 이 칸이 가르지 않는다. 수집기 콘솔 메시지로 본다.

## 검증

- `CollectionFreshnessTest`(7, 후속으로 10): 스냅샷 폴더 없음은 확인 필요(예외 아님), 1거래일 뒤처짐은 정상·2거래일은 멈춤 의심, 주말 제외, 한글날(2026-10-09) 휴장일은 세지 않음, 여러 스냅샷 중 가장 늦은 것을 고르고 깨진 manifest는 목록에 적고 만들다 만 폴더는 무시·같은 폴더면 같은 보고서, 캘린더 범위 밖은 평일로 셈·표시, KRX 밖 시장은 해당 없음.
- `LiveWeeklyCheckTest` 깨끗한 세션 시험에 덧붙임: 스냅샷 없음은 머리·4장에 나오고 결함(종료 코드 2 조건)이 아님, 하루 전 스냅샷은 정상, 이틀 뒤처지면 멈춤 의심과 날짜 목록.

## 후속(PR #145 검토 권고, 2026-10-17)

결정 내용은 그대로이고 4장 표시와 시험만 보탠다(새 결정 번호 없음).

- strategy-researcher R2: 4장 설명과 runbook에 "지금의 6단계 계좌는 일봉 스냅샷을 입력으로 쓰지 않으므로(`LivePlan` 선정 프로필 미연결) 3장 계좌 성과는 바뀌지 않고, 공백은 4단계 실험과 선정 결과 입력 쪽에 생긴다"를 적는다.
- strategy-researcher R3·architect N2: 스냅샷 마지막 거래일이 점검 마지막 날보다 뒤면(`-Pto`로 지난 주를 다시 점검) 판정은 정상 그대로 두고 4장에 "그 주에 있었던 멈춤은 이 칸에 보이지 않는다"를 적는다(`Status.newerThanEnd`). 시험 `recheckingAnEarlierWeekSeesNewerSnapshotsAsNormal`.
- architect N1: `coverage`(또는 `lastTradingDate`)가 없는 ADR-008 이전 형식 manifest는 "읽지 못함"이 아니라 "마지막 거래일 칸이 없는 옛 형식이라 세지 않은 스냅샷 폴더(깨진 것 아님)"로 따로 적는다(`Status.noCoverage`). 판정은 그대로(이것만 있으면 확인 필요). 시험 `oldManifestWithoutCoverageIsListedApartFromBrokenOnes`.
- strategy-researcher R1(KRX 게시가 T+1이면 매주 거짓 멈춤 의심)은 첫 실데이터 주간 점검에서 스냅샷 `lastTradingDate`와 실행 시각을 대조해 정한다. R4(더 빠른 감지)는 대안 C 방향으로 남긴다.
