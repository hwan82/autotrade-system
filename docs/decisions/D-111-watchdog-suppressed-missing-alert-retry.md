# D-111 감시: 큐가 받지 않은 결측 알림은 반복 경고 때 한 번 다시, 사유 실패가 판정을 바꾸지 않음(PR #166 QA 후속)

- 날짜: 2026-10-18
- 상태: 확정 · **추천안 채택(자율)**(지침 8장). 감시(`autotrade-app-watchdog`)의 결측 알림 재전송 조건, 자원 단계의 판정·사유 분리, 점검 단계 표(`Watchdog.Stage`)와 시험용 단계 주입점, 시험만 바꾼다. 임계 판정, 정지 요청 판정(D-092·D-095), 하트비트 판정, 알림 종류·억제 규칙(D-100), 결측 경고 간격(D-096·D-108의 10분), 결측 "새 값" 판정(D-110 결정 1), 로그 출력 실패 정책(D-109), 감시 설정, 보호 테스트는 바꾸지 않는다. 보호 경로라 사용자 머지로 확정한다.
- 담당: risk-ops 결정·구현. 교차 검토: architect(코드), risk-ops(실전 관련)
- 근거: [PR #166 독립 QA](../reviews/pr-166/qa.md) R1·R2·Q1·Q2, risk-ops PR #166 K1·K2, architect N3, [D-110](D-110-watchdog-rewarn-after-recovered-value.md)

## 문제

1. **R1(main에도 있던 결함)**: cpu 결측 → cpu 회복 → 드라이브 결측 → 드라이브 회복·cpu 재결측이면 cpu 결측 알림은 알림 큐가 같은 대상(`readings`)·종류 10분 억제로 버린다. 그 뒤 cpu가 계속 빠져도 반복 경고는 로그로만 나므로(D-096) **채널에는 cpu 결측이 끝까지 오지 않고**, 마지막 결측 알림은 이미 돌아온 드라이브 이름이었다(QA 탐침 PB). 감시는 큐가 알림을 받았는지 보지 않았다(`Alerts.send`가 `void`).
2. **R2**: D-110이 자원 단계를 판정·사유를 한 람다로 묶어, 사유(`detail`)가 던지면 이미 낸 위험(CRITICAL) 판정도 버리고 판단 못 함(UNKNOWN)이 됐다. 그러면 정지 요청을 새로 만들지 못한다. PR #166 이전에는 판정을 먼저 대입해 남았다. 지금 `detail`이 던질 경로는 찾지 못했다 `[추론]`.
3. **Q1**: 자원 값이 빠진(UNKNOWN) 점검에서도 엔진 멈춤 알림이 나가는지 시험이 없었다(QA 변이 V2 생존).
4. **Q2·N3·K2**: `tick()`이 넘기는 단계 실패 로그 수준·문구(V1·V6 생존), 단계 구조, 자원 단계 실패 때의 대신 값(UNKNOWN)을 고정하는 시험이 없었다. 운영에서 단계를 던지게 할 주입점이 없었다.

## 결정

1. **억제된 결측 알림은 한 번 다시**: `Alerts.send`는 큐가 받았는지(`NotificationQueue#offer`의 반환값)를 돌려준다. 결측 알림을 넣지 못했으면(억제·상한·큐 가득·닫힘·던짐) 표시해 두고, 다음 결측 경고(간격이 찬 반복 경고 포함) 때 **지금 빠진 값으로** 한 번 다시 넣는다. 받으면 표시를 지운다. 반복 경고는 마지막 경고에서 10분이 지난 뒤라 큐의 같은 종류 억제 창도 지나 있어 받는다(큐가 "직전 10분 동안 같은 알림 n건 생략"을 붙임). 받은 알림의 반복 경고는 예전대로 로그로만 낸다(D-096). 회복 INFO 뒤 첫 결측 경고는 어차피 알림을 넣으므로(D-108) 회복 때 표시를 따로 지우지 않는다.
2. **판정을 먼저, 사유는 따로**: 자원 단계 안에서 압력 판정을 먼저 내고, 사유는 별도 단계(`DETAIL`, 실패 로그 "정지 요청 사유 작성 실패", WARNING)로 만든다. 사유가 던지면 사유만 "사유를 만들지 못함"으로 바꾸고 판정은 그대로 정지 요청 처리에 넘긴다. 자원 단계 자체(수집·결측 경고)가 던지면 예전대로 UNKNOWN·"자원 값을 읽지 못함"이다.
3. **점검 단계 표와 시험용 주입점**: 단계 이름·실패 로그 수준·문구를 `Watchdog.Stage` 열거형 한 곳에 둔다(문구는 D-110 결정 2대로 예전과 같음, `DETAIL`만 새것). 패키지 전용 생성자에 `Consumer<Stage>` 탐침을 받아 단계 본문 앞에서 부른다. 운영(`WatchdogMain`이 쓰는 생성자)은 아무것도 하지 않는 탐침이다. 시험은 탐침으로 한 단계를 던지게 해 `tick()` 경로의 실패 로그와 나머지 단계 진행을 고정한다.
4. **시험 추가**: 실제 `NotificationQueue`로 R1 순서 재현(억제 → 간격 찬 반복 경고 때 cpu 결측 알림 받음 → 그 뒤 반복은 로그만), 받은 알림은 다시 넣지 않음, 넣다 던지면 다음 반복 때 넣음, 드라이브를 못 읽는 점검에서도 엔진 멈춤 알림(Q1), 단계 다섯 각각 실패 시 로그 수준·문구와 다른 단계 결과(Q2·N3), 자원 단계 실패 동안 켜진 정지 요청 유지(K2), 사유 실패에도 위험 판정으로 정지 요청 생성(R2).

## 대안

| 대안 | 판단 |
|---|---|
| ① 큐가 받지 않았을 때만 다음 경고 때 다시(채택) | 채널에 빠진 값 이름이 반드시 한 번은 간다. 받은 경우는 알림 수가 그대로다 |
| ② 반복 경고 때마다 알림 | 큐가 10분 억제하므로 실제 전송은 10분마다 한 번이지만, D-096이 반복을 로그로 둔 이유(알림 소음)를 깬다. 버림 |
| ③ 결측 알림 대상(subject)을 값 이름별로 | 억제가 값마다 따로라 R1은 사라지지만 값이 여럿 빠질 때 알림이 값 수만큼 늘고, 회복 알림(같은 `readings` 대상)과 종류 바뀜 관계도 바뀐다. 버림 |
| 사유를 판정과 한 단계로 두고 그대로 둠 | 던질 경로는 없지만, 생기면 정지 요청이 조용히 빠진다(안전 쪽 판정이 약해짐). 비용이 작아 나눈다 |
| 시험 주입점 없이 `Stage` 상수만 시험 | V1·V6은 잡지만 `tick()`이 엉뚱한 단계를 넘기거나 단계 사이 결합(V2)은 못 잡는다. D-110은 "catch 넷이 따로 바뀔 수 있다"는 이유로 주입점을 버렸는데, 실행기를 한 곳으로 모은 지금은 그 이유가 없어져 주입점을 둔다 |

되돌릴 조건: 6단계 운용에서 재전송 알림이 운영자에게 소음이 되면 ①을 "간격이 찬 반복 경고 때만"으로 좁힌다(지금도 실제로는 대부분 그때다).

## 위험과 한계

- 재전송은 지금 빠진 값으로 보낸다. 억제됐던 값이 그 사이 돌아왔으면 그 값은 채널에 오지 않지만 이미 돌아왔으므로 놓칠 상태가 아니다.
- 큐가 계속 받지 못하면(큐 가득·닫힘) 결측 경고마다 한 번씩 다시 넣는다. 경고는 간격마다 묶여 있어 폭주하지 않는다 `[추론]`.
- 탐침은 운영 경로에서 빈 람다 호출 하나다. 탐침 생성자는 패키지 전용이라 같은 패키지(감시 모듈 안)에서만 부를 수 있고, 운영 코드에서 감시를 만드는 곳은 `WatchdogMain` 하나이며 탐침 없는 생성자를 쓴다(architect PR #170 N1).
- 재전송을 큐가 받는 것은 감시의 반복 간격(`Watchdog.MISSING_REPEAT`, 10분)이 큐의 같은 종류 억제 시간(`NotificationQueue.QUIET`, 10분)보다 짧지 않아서다. 큐 쪽이 길어지면 재전송도 억제될 수 있지만 표시가 남아 다음 반복 경고 때 다시 넣으므로 늦어질 뿐 사라지지 않는다(architect N2, risk-ops K2). 두 값을 바꿀 때 함께 본다.
- 재전송 표시는 값이 잠깐 모두 읽혀도 지우지 않는다. 회복 INFO가 간격 때문에 미뤄진 채 값이 다시 빠지면 그 값을 채널에 보내는 길은 재전송뿐이다(risk-ops PR #170 K1, 시험 `#억제된_결측_알림은_값이_잠깐_다_읽혀도_잊지_않는다`).

## 후속 반영(2026-10-19, PR #170 독립 QA Q1·R1)

- **Q1 배선 시험**: 결정 1은 운영 배선(`WatchdogMain`이 `Watchdog`에 넘기는 `notifications::offer`)이 큐가 받았는지를 그대로 돌려줄 때만 효과가 있다. 지금까지 재전송 시험은 시험 안에서 만든 람다로만 큐에 넣어, 배선을 "넣고 늘 true"로 바꾸는 변이(QA Q1)가 살아남았다. `WatchdogMainTest#운영_배선은_알림_큐가_받았는지를_그대로_감시에_넘긴다`가 실제 기동(`WatchdogMain.start`)으로 만든 감시의 알림 출구로 같은 대상·종류를 두 번 넣어 두 번째가 false(억제), 종류가 바뀌면 true, 닫은 뒤 false인지 본다. 이를 위해 `Watchdog`에 패키지 전용 읽기 `alerts()` 하나를 더했다(`notifications()`와 같은 시험용). 운영 동작 변경은 없다. 변이 "늘 true"·"늘 false" 둘 다 이 시험이 잡는다(개발 쪽 직접 실행).
- **R1(참고)**: 억제됐던 값이 재전송 전에 돌아오면 그 값은 "읽지 못함" 없이 다음 회복 INFO에 "다시 읽음"으로만 보일 수 있다(위 위험과 한계 1번, risk-ops K3와 같음). 놓친 위험 상태가 아니라 그대로 둔다.
