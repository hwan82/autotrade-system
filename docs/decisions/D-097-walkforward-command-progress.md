# D-097 워크포워드 명령 전체 진행률(SIM-14 진행 보고, UI-02 진행 상태)

- 날짜: 2026-10-16
- 상태: 확정 · **추천안 채택(자율)**(지침 8장). 실험 진행 보고(D-089)의 후속이다. 상태 파일 형식을 `experiment-job-v2`로 올리고(이전 v1도 읽음), 워크포워드 명령과 진행 상태 화면만 바꾼다. 결과 파일, 결정론, 정지 확인(D-063)·취소(D-089) 규칙, 실전 주문 경로·RealTradingGuard·블랙리스트·리스크 한도·장애 대응 규칙과 보호 테스트는 바꾸지 않는다.
- 담당: sim-engine(+ui-dev 화면). 교차 검토: architect
- 근거: [D-089](D-089-experiment-progress-cancel-parallel-cap.md) 위험과 한계 2번째 항목("워크포워드가 전체 실험 수를 미리 알려 주는 후속"), [D-093](D-093-experiment-progress-screen-sse.md) 위험과 한계 1번째 항목, [ADR-004](../adr/ADR-004-simulation-engine.md) 이연 표 SIM-14 행, 기획서 SIM-14·UI-02

## 문제

워크포워드 명령 하나는 실행기를 구간 수 × (학습 1 + 검증 1 + 스트레스 1 + 대조군 시드 수)번 부른다. 4단계 사전 등록 값(구간 3, 대조군 시드 400)이면 1,209번이고, 결정론 확인을 켜면 그 두 배다. 지금 상태 파일은 지금 실험 하나의 진행률과 시작한 실험 수만 실어서, 화면 막대는 실험마다 0%에서 100%를 다시 오가고 명령이 얼마나 남았는지 알 수 없다 `[사실]`(`ExperimentJobStatus` v1, `pages/jobs.js`).

## 결정

1. **`RunGate.onExperimentsPlanned(int count)`**(기본 메서드, 아무것도 안 함). 실행 명령이 실행기를 몇 번 부를지 시작 전에 셀 수 있을 때 한 번 알린다. 돌려받는 값이 없어 결과에 영향이 없고, 부르는 쪽은 예외를 삼키고 계속한다(진행 보고와 같은 규칙).
2. **워크포워드가 센다.** 계산을 시작하기 직전(스냅샷·후보·지수 준비가 끝난 뒤) `experimentsPerCompute(구간 수, 조합 묶음, 대조군 시드 수)`를 알린다. 구간마다 학습·검증·스트레스·대조군 시드 각각이 조합 128개(실행기 상한)를 넘으면 나눠 부른 만큼 센다(`runAll`과 같은 규칙). 결정론 확인이 실제로 도는 경우(병렬 2 이상)는 두 배. 계산 코드와 세는 코드가 같은 조합 묶음(`ComboSets`)을 쓴다. 로그 "계산 시작" 줄에 "실험 N회"를 더한다.
3. **상태 파일 `experiment-job-v2`.** 키 `experiments-planned`(0 = 모름)를 더한다. 실험실은 v1 파일도 읽고(전체 실험 수 0), v1에 이 키가 있거나 v2에 없으면 거부한다. 실행 명령은 알림을 받으면 바로 쓴다(한 명령에 한 번).
4. **명령 전체 진행률 `commandPermille`**(0~1000, 모르면 비어 있음) = (끝난 실험 수 × 1000 + 지금 실험의 `permille`) ÷ 전체 실험 수. 실험마다 같은 무게다. 시작한 실험이 알린 수를 넘으면 1000에서 멈춘다.
5. **실험실 REST·화면.** `GET /api/experiment-jobs` 항목에 `experimentsPlanned`, `commandPermille`(모르면 null)를 더한다. 화면은 `commandPermille`이 있으면 막대를 명령 전체 진행률로 그리고 "전체 x% · 실험 n/N번째"를 보이며, 지금 실험의 진행률·Run·거래일은 아래 줄로 내린다. 없으면(조합·녹화 등 한 번 부르는 명령) 화면은 그대로다.

## 대안

| 대안 | 장점 | 단점 | 판단 |
|---|---|---|---|
| A. 실험 수로 세고 실험마다 같은 무게(채택) | 시작 전에 정확히 셀 수 있다(조합 수·구간 수·시드 수만 씀). 시험으로 "알린 수 = 실제 시작 수"를 고정할 수 있다 | 학습 실험(조합이 많고 기간이 김)과 대조군 실험(한 조합, 검증 기간)의 실제 시간이 다르다 | **채택**. 대조군 시드가 구간마다 수백 번이라 학습 실험의 비중은 1% 아래다 `[추론]`(구간당 실험 403번 중 학습 1번) |
| B. Run × 거래일로 무게를 둠 | 시간 진행에 더 가깝다 | 구간별 데이터셋(`DailyBarMarketDataSet`)의 거래일 수는 구간 데이터를 읽어야 정해진다. 미리 세려고 데이터셋을 모두 만들면 메모리를 다시 쓴다(지금은 구간마다 만들고 놓음). 달력으로 세면 데이터셋과 어긋나 100%를 넘거나 못 채울 수 있다 | 버림 |
| C. 화면이 `experimentsStarted`만으로 추정 | 상태 파일 변경 없음 | 전체 수를 모르면 비율을 낼 수 없다 | 버림 |
| D. 형식 숫자를 올리지 않고 키만 선택으로 더함 | v1 그대로 | "형식을 바꾸면 숫자를 올린다" 규칙과 맞지 않고, 이전 실험실이 새 파일을 모르는 키로 거부할 때 이유가 드러나지 않는다 | 버림. 새 실험실은 v1도 읽어 남은 끝난 작업이 읽기 실패로 빠지지 않는다 |

되돌릴 조건: 6단계 운영에서 전체 진행률과 실제 경과 시간이 크게 어긋나면(예: 학습 조합이 크게 늘어 학습 실험 비중이 커짐) B처럼 실험마다 무게(조합 수 × 구간 길이)를 함께 알리는 v3를 검토한다.

## 위험과 한계

- 전체 진행률은 실험 수 기준이라 실제 남은 시간 추정이 아니다. 화면은 남은 시간을 보이지 않는다.
- 스냅샷 읽기와 지수 계산(준비 단계)은 알리기 전이라 그동안 전체 진행률이 없다(화면은 지금처럼 "첫 실험 시작 전").
- 실행기는 받는 쪽이 예외를 던지면 그 실험의 남은 진행 보고를 끈다(D-089). 그 실험의 STARTED가 빠지면 시작한 실험 수가 실제보다 적게 남아 전체 진행률이 낮게 보일 수 있다. 결과에는 영향이 없고, 명령이 끝나면 상태(완료 등)가 맞게 남는다(PR #124 architect R3).
- 실행 명령과 실험실은 같은 저장소 빌드를 쓴다는 전제다(4단계 런북에 같은 커밋으로 맞추라고 적음). 이전 빌드의 실험실은 v2 파일을 형식 오류로 읽지 못하고 "읽지 못한 상태 파일"로 센다.
- 다른 명령(조합·녹화·합성 시세 비교·실시간 모의 점검·주간 점검)은 알리지 않는다. 결정론 확인으로 실행기를 두 번 부르는 명령은 지금처럼 실험마다 진행률이다. 필요하면 같은 메서드로 넓힌다.

## 검증

- `ExperimentJobStatusTest` 2건 추가: v1 읽기(전체 수 0)와 v1·v2 키 규칙, 전체 진행률 계산(시작·절반·끝·넘침·알리지 않음).
- `ExperimentJobTest` 1건 추가: 알림을 바로 쓰고 끝난 뒤에는 바꾸지 않음.
- `WalkForwardStudyTest` 3건 추가: 알린 실험 수 = 실제 시작한 실험 수(결정론 확인 없음 69, 있음 138), 알리다 실패해도 결과 파일이 같음, 128개 넘는 조합 나눔 세기.
- `ExperimentJobControllerTest`: REST 항목의 `experimentsPlanned`·`commandPermille`(알리지 않은 작업은 null).
- 기존 워크포워드 골든(병렬 1 대 N 바이트 일치)이 그대로 통과해 결과가 바뀌지 않음을 확인한다.
- 화면: `bootTestRun` 데모에 워크포워드 작업(`DEMO-20261016-WF01`, 실험 24번)을 더해 브라우저로 확인한다. 화면 JS 자동 시험은 D-093과 같이 화면 Playwright CI 때 넣는다.
