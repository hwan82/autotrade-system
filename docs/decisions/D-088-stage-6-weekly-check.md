# D-088 6단계 주간 점검 명령(실시간 모의 입력 기록 대 같은 날 녹화)

- 날짜: 2026-10-14
- 상태: 확정 · **추천안 채택(자율)**(지침 8장). 실험 명령 하나와 결과 파일 하나를 더한다. 실전 주문 경로·RealTradingGuard·블랙리스트·리스크 한도·장애 대응 규칙은 바꾸지 않는다(게이트웨이·실험실 실행 코드도 그대로, 읽기만 한다).
- 담당: sim-engine. 교차 검토: architect(코드·모듈 경계). 결과 해석은 strategy-researcher(ADR-010 5장 "실시간 모의 대 같은 날 게이트웨이 녹화 리플레이 차이" 행)
- 근거: [ADR-010](../adr/ADR-010-live-feed-and-session.md) 4장 "실험실이 본 입력 ≠ 게이트웨이 녹화"·5장, 절차서 [stage-6-live-session](../runbooks/stage-6-live-session.md) 3장(지금은 `dataGaps`·`inboxDropped`·`feedReconnects`를 손으로 옮김), SIM-13, 지침 10장 "6단계 주간 점검"

## 결정

1. **명령**: `./gradlew :autotrade-app-experiment:runLiveWeeklyCheck -Pexperiment=<실험ID> [-Pto=YYYY-MM-DD]`(`ExperimentMain live-weekly`, 본체 `LiveWeeklyCheck`). D-063 장 시간 보호·정지 요청 파일을 그대로 받는다. 기본 마지막 날은 운용 기간 안 입력 기록의 마지막 날, 주는 그 앞 7일(운용 시작 앞으로는 가지 않음).
2. **입력 대조(날마다)**: 같은 날 게이트웨이 녹화(`<설정 폴더>/recordings`, `-PrecordingsDir`)에서 등록 파일 `boards`·운용 기간에 드는 줄과 입력 기록(`live-sessions/<ID>/journal`)의 줄을 원래 소스·소스 순번·내용(녹화 순번 빼고)으로 맞춘다. 전달은 녹화와 같은 줄 형식이고 수신 시각도 게이트웨이 값이라(ADR-010 2.2) 같은 이벤트면 같은 열쇠다.
   - 점검 날짜는 입력 기록이 있는 날과 게이트웨이 녹화가 있는 날을 합친 것이다. 실험실을 하루 통째로 끈 날은 "기록 없음" 행으로 나오고 그날 boards 줄은 모두 세션 밖 빠짐이다(architect PR #107 R2).
   - 녹화에만 있는 줄(빠짐)은 그 이벤트 수신 시각을 덮는 실험실 쪽 공백으로 먼저 원인을 나눈다: 받는 쪽 끊김(`FEED-CLIENT`), 실험실 재기동(`RECORDER`), 게이트웨이 전달 큐 넘침(`FEED`, 그 종목), 실험실 받는 큐 넘침(`LAB-INBOX`, 그 종목). 끊김·재기동 공백 줄은 앞 구간에 나온 종목마다 하나씩이지만 그 사이에는 연결이나 프로세스 자체가 없었으므로 종목과 상관없이 시각 구간으로 본다.
   - 덮는 공백이 없으면 입력 기록 메타의 구간(실험실이 그날 파일을 연 시각 ~ 닫은 시각, `RecordingMeta.segments`)으로 가른다. 구간 밖이면 **세션 밖**(실험실이 꺼져 있었음), 구간 안이면 **설명 없음**(세션이 열린 채 공백 없이 빠짐)이다. 첫 줄·마지막 줄 수신 시각만 보면 열린 세션에서 공백 없이 끊긴 뒤 빠진 줄이 모두 세션 밖으로 숨는다(architect PR #107 R1).
   - 기록에만 있는 줄은 녹화기 공백(`RECORDER`: 녹화 큐 넘침은 그 종목, 재기동은 모든 종목) 안이면 녹화 쪽 손실로, 아니면 **설명 없음**(전달 결함)으로 센다.
   - 설명 없음이 하나라도 있으면 종료 코드 2(MD-05 "버린 구간은 공백으로 남긴다"가 깨졌거나 전달이 줄을 바꿨다).
3. **공백 출처(날마다)**: 입력 기록의 실험실 쪽 공백 줄을 출처별로 센다. 받는 쪽 재연결 수(= 상태 화면 `feedReconnects`)는 `FEED-CLIENT` 공백의 서로 다른 구간 수, 실험실 큐 칸의 빠짐(= `inboxDropped`)은 2번의 `LAB-INBOX` 원인 수다. 실험실을 다시 띄우면 사라지는 메모리 값 대신 디스크의 두 기록에서 다시 세므로 손으로 옮기지 않는다.
4. **계좌 대조(운용 시작부터 마지막 날까지 누계)**: 같은 등록 파일·같은 코드로 입력 기록 리플레이(= 실시간 결과, D-076 합격선)와 같은 날 녹화 리플레이(boards만, 녹화 순서대로 다시 번호)를 돌려 계좌별 총수익률·체결·비용과 상세 보고서 일치 여부를 나란히 놓는다. 녹화가 없는 기록일이 있으면 계좌 대조는 하지 않고 이유를 적는다(같은 조건 비교만, 지침 5장). 입력 기록이 없는 날의 녹화는 녹화 리플레이에 넣는다: 계좌 대조는 "실험실이 받지 못한 이벤트가 성과에 준 영향"을 재는 것이고, 하루 통째로 못 받은 것도 그 영향에 든다(대안: 그날이 있으면 대조를 생략 — 버림, 6단계 8주 중 하루만 꺼도 이후 모든 주에 대조가 사라짐).
5. **결과 파일**: `experiments/<ID>/weekly/<마지막 날>.md` 한 장. 건수와 성과만 담아 커밋한다(시세 내용 없음, ADR-003 4장 재배포 금지와 무관). 실행 시각 같은 메타가 없어 같은 입력이면 같은 파일이다.
6. **세션이 열려 있어도 돈다**: 실험실 세션 잠금은 보지 않고, events·meta 파일을 읽기 전후 SHA-256이 다르면(아직 쓰이는 중) 그날을 거부한다. 장 마감 뒤 수신이 멈춘 다음 돌린다.

## 대안

| 대안 | 판단 |
|---|---|
| A. 입력 기록 대 녹화 줄 대조 + 두 리플레이(채택) | 디스크에 남은 두 기록만으로 다시 셀 수 있고, 빠진 이벤트가 성과에 준 영향까지 한 장에 나온다 |
| B. 실험실 상태 API의 `dataGaps`·`inboxDropped`·`feedReconnects`를 날마다 파일로 떨굼 | 구현은 가볍지만 실험실 재기동·되살리기 때 값이 사라지거나 두 번 세지고(PR #94 남은 참고: 앞 날 기록 두 번 읽음), 녹화와의 차이(실제로 못 받은 이벤트 수)는 여전히 모른다. 버림 |
| C. 실험실 안에서 주간 점검을 돌림 | 녹화 하루치를 다 읽고 리플레이를 두 번 돌아 무겁다. 실험실은 장중에 실시간 세션을 돌리는 프로세스라 D-063 보호 밖에서 자원을 다툰다. 버림 |
| D. 줄 맞추기를 소스 순번만으로 | 게이트웨이를 다시 띄우면 소스 순번이 다시 1부터일 수 있어 같은 날 열쇠가 겹친다 `[추론]`. 내용까지 넣어 버림 |

되돌릴 조건: 녹화 줄 형식이 바뀌어(형식 버전 올림) 전달 줄과 녹화 줄이 달라지면 열쇠를 다시 정한다. 8주 분량 누계 리플레이가 힙 4GB를 넘으면 계좌 대조를 주 단위 창으로 바꾼다.

## 위험과 한계

- 원인 나누기는 수신 시각 기준이다. 받는 쪽 끊김 공백의 끝은 실험실 시계, 녹화 수신 시각은 게이트웨이 시계라 같은 PC여도 밀리초 경계에서 어긋날 수 있다 `[추론]`. 그때는 설명 없음으로 나오므로(놓치지 않는 쪽) 줄 번호로 확인한다.
- 공백 표시 없는 옛 녹화(D-065 이전)의 재기동 경계는 다루지 않는다. 6단계 녹화는 D-065 뒤라 해당 없음.
- 세션 구간으로도 가를 수 없는 경우: 실험실이 비정상 종료해 메타에 닫힌 시각이 없는 구간은 그 구간 마지막 줄 수신 시각에서 끝낸다. 그래서 공백 없이 끊긴 뒤 같은 구간에서 비정상 종료하면, 끊긴 뒤 빠진 줄은 세션 밖으로 나온다. 같은 날 다시 열면 재기동 공백이 앞 구간 마지막 줄부터 덮어 "재기동"으로 나오므로, 비정상 종료 여부는 1장 "기록 정상 종료" 칸(아니오)과 함께 본다. 구간 시작은 실험실 시계로 첫 줄을 받은 뒤에 찍히므로 첫 줄 수신 시각으로 당긴다. 세션을 열고 첫 이벤트를 받기 전 구간은 기록에 남지 않아 세션 밖이다.
- 녹화 하루치를 다 메모리에 올리고, 계좌 대조용으로 운용 시작부터 boards 녹화 이벤트를 모두 모은다(하루 50만 줄대 `[가정]`). 힙은 `-Pheap`(기본 4g). 6단계 첫 2주 실측 때 힙 사용량을 주간 점검과 함께 적는다(architect PR #107 N4).
- 계좌 대조의 "실시간"은 입력 기록 리플레이다. 운용 중간에는 `live-detail.txt`가 없으므로, 둘이 같다는 보증은 운용이 끝난 뒤 `runLiveReplayCheck`(D-076)가 한다.

## 검증

- `LiveWeeklyCheckTest`(8): 깨끗한 세션은 녹화와 줄 단위로 같고 두 리플레이 상세 보고서가 같음, 세션 시작 전·끝난 뒤·게이트웨이 큐 넘침·받는 큐 넘침·끊김·실험실 재기동으로 빠진 이벤트가 손으로 센 수와 원인별로 같음(설명 없음 0, 재연결 1), 공백 없이 빠진 줄과 녹화에 없는 줄은 결함, 세션이 열린 채 공백 없이 끊긴 뒤 빠진 줄은 설명 없음(R1), 실험실을 하루 통째로 끈 날은 기록 없음 행·세션 밖 빠짐·녹화 리플레이에 포함(R2), 녹화 없는 날은 표시하고 계좌 대조 생략, 열린 세션에서도 내린 기록은 읽음·운용 기간 밖 마지막 날 거부·같은 입력이면 같은 보고서, 정지 확인이면 결과를 쓰지 않음.
- `ExperimentGateTest` 2개 추가: 장 시간·정지 요청이면 시작하지 않음, 인자 오류.
