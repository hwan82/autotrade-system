# D-019 데이터 수집 언어: Java 코어 + Python 배치 수집기 허용 (D3)

- 날짜: 2026-10-08
- 상태: 확정, **추천안 채택(자율)** (project-instructions.md 8장)
- 근거: team-design.md 8장 D3, D-002(Java 21·Spring Boot 3.x), D-013(4프로세스)
- 담당: data-engineer(수집기), architect(경계 검토)

## 결정
1. 시스템 코어(시세 게이트웨이, 실전 엔진, 실험실, 감시)는 Java로만 만든다(D-002).
2. **과거 데이터 배치 수집에 한해 Python 수집기를 허용한다.** 예: 일봉 OHLCV, 수정주가, 종목 상태·상장폐지 이력, 거래소 캘린더 보조 자료(pykrx 등 공개 라이브러리).
3. Python 수집기의 경계
   - 실시간 시세 수신, 주문, 잔고 조회, 증권사 인증 토큰을 다루지 않는다. 실시간 시세는 Java 게이트웨이만 받는다.
   - 4개 프로세스 어디에도 들어가지 않는 **오프라인 배치**로, 장 마감 후 또는 수동 실행만 한다. 실전 엔진은 Python 수집기의 실행 여부와 무관하게 동작한다.
   - 결과는 버전이 붙은 파일 스냅샷(Parquet 또는 CSV)과 메타데이터(출처, 라이선스, 수집 시각, 스크립트 버전)로만 넘긴다. Java는 이 스냅샷을 읽기만 한다.
   - 위치는 저장소 안 별도 디렉터리(예: `collectors/python/`), 의존성은 버전 고정(lock 파일).
4. 실험은 수집 시점이 아니라 **스냅샷 버전**을 입력으로 삼는다. 같은 스냅샷이면 같은 결과(시뮬레이션 결정론, 5장).

## 대안 비교
| 대안 | 장점 | 단점 | 판단 |
|---|---|---|---|
| A. Java만 사용 | 언어 1개, 빌드·배포 단순 | 국내 공개 시세·상장폐지 이력 라이브러리가 부족해 직접 구현 부담 `[추론]` | 버림 |
| **B. Java 코어 + Python 배치 수집기** | 공개 라이브러리 활용, 실시간·주문 경로와 분리 | 언어 2개, 런타임 관리 필요 | **채택** |
| C. Python으로 게이트웨이까지 | 수집 코드 재사용 | 프로세스 격리(D-013)·Java 코어(D-002)와 충돌, 실전 경로에 두 번째 런타임 유입 | 버림 |

## 위험과 한계
- 공개 라이브러리는 비공식 스크래핑에 기대는 경우가 있어 원천 사이트 변경 시 깨질 수 있다 `[추론]`. 완화: 스냅샷 버전 고정, 수집 실패 시 직전 스냅샷 유지, 품질 검사(role-guides.md 3장) 통과분만 승격.
- 라이선스·이용 약관은 수집기마다 data-engineer가 확인해 메타데이터에 남긴다. 확인 못 한 소스는 실험 입력으로 쓰지 않는다.

## 되돌릴 조건
- Java만으로 같은 데이터를 같은 품질로 확보할 수 있게 되면 Python 수집기를 걷어내고 새 결정 번호로 기록한다.
- Python 수집기가 실시간·주문 경로에 들어가야 하는 요구가 생기면 이 결정의 범위를 넘으므로 사용자에게 묻는다.
