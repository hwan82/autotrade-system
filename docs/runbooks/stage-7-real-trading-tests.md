# 7단계 실전 연동 실행·시험 절차서 (뼈대)

- 상태: **뼈대**(2026-10-24, [7단계 준비 계획](../team/stage-7-readiness-plan.md) 2.7장 I1). 지금은 시행할 수 없다. 장애 테스트는 묶음 A·B·C·D-H·E·F가 머지된 뒤 시행하고, 그때 각 칸의 명령·화면 이름·기준값을 채운다.
- 담당: risk-ops. 바꾸는 PR은 실전 관련 PR이다(장애 대응 절차, 지침 10장): risk-ops·architect 검토, 독립 QA, 사용자 머지.
- 원본 관계: 장애 테스트의 **합격 기준 원본**은 [장애 설계](../team/broker-and-fault-design.md) 7장·7.1과 [D-140](../decisions/D-140-stage7-panic-and-first-broker.md)이다. 이 문서는 그 기준을 **어떤 순서로, 무엇을 보고, 무엇을 기록하며** 시행하는지만 적는다. 둘이 다르면 원본이 이기고, 이 문서를 고친다.
- 이 문서는 실전 활성화를 뜻하지 않는다. RealTradingGuard 기본 OFF, 재기동 시 OFF는 그대로다. 실전 활성화는 장애 테스트 8종 합격, TST-07 대응표(I2), 승격 후보, 독립 QA 뒤 **사용자 결정**으로만 한다(지침 10장).
- 키·계좌번호·토큰이 보이는 화면이나 로그는 채팅·저장소·시험 기록에 남기지 않는다. 시험 기록에는 계좌를 별칭(`kis-1` 등)으로만 적는다.

## 1. 시험 기록 규칙

시험마다 아래 한 줄 형식으로 `experiments/`가 아닌 시험 기록 파일(위치는 묶음 I 시행 PR에서 정함 `[가정]`: `docs/reviews/stage-7-fault-tests/<시험>.md`. 보호 경로가 있는 `docs/qa/` 아래에는 두지 않는다, PR #238 architect A-5). `docs/reviews/`는 고치지 않는 검토 원문 보관소라(`docs/reviews/README.md`) 재시험·정정이 있는 시험 기록과 규칙이 엇갈리므로, 시행 PR에서 위치를 다시 정한다(독립 QA PR #238 Q3)에 남긴다.

| 칸 | 내용 |
|---|---|
| 판정 | **합격** / **불합격** / **해당 없음**(시행 조건이 성립하지 않음, 사유 필수) / **시행 불가(미구현)**(해당 없음으로 치지 않음, 장애 설계 7.1) |
| 도메인 | **모의 도메인으로 충분** / **실전 도메인 소액 필요**(D-140 후속, 독립 QA PR #235 권고 Q6). 한국투자 모의 도메인은 한도·지원 API가 실전과 다를 수 있다 `[추론]` |
| 대상 | 커밋 해시, 운영 PC OS(Windows 버전), JDK 배포판·버전, 계좌 별칭, 시험 시각(KST) |
| 관측 | 합격 기준 항목마다 본 값과 근거(로그 줄, 화면, 증권사 앱 조회) |
| 남은 위험 | 시험이 못 본 것 |

공통 전제(모든 실전 도메인 시험):
- 시험 대상 계좌와 **같은 증권사 키를 쓰는 모든 계좌**에 보유와 미체결이 없는지 증권사 앱으로 먼저 확인한다(7.1 1-T·1-TR·1-K와 같은 원칙). 예외는 시험이 보유를 요구할 때뿐이며, 그때는 TST-05처럼 횟수·금액·손실 상한을 사용자에게 먼저 승인받는다.
- 시험용 우회(규칙을 일부러 어기는 설정)는 **코드 플래그로 만들지 않고**, 시험 프로세스만 별도 설정 폴더(`AUTOTRADE_CONFIG_DIR`)로 띄워서 한다. 시험 뒤 원래 설정 폴더로 돌아왔는지 확인한다(PR #23 risk-ops M-1). 시험 하네스는 운영 모듈 밖(시험 전용)에 둔다(장애 설계 7.1 1-TR).
- 6단계 LIVE01(10-26~12-18) 기간에는 게이트웨이를 멈추거나 설정을 바꾸는 시험을 하지 않는다. 한국투자 실전 계좌를 설정하는 순간 게이트웨이 실시간 소스가 키움 하나가 되므로(D-140 후속, `GatewayMain.java:97-104`) 실전 계좌 설정 시점도 LIVE01과 조율한다.

## 4. 매일 운영 절차 (실전 계좌가 설정된 날)

1. 아침: 2장 P7·P9를 다시 본다(1분). 엔진 기동 → 모든 실전 계좌는 OFF로 시작한다(ADR-002).
2. **보유가 있는 날 엔진을 재기동하면** 엔진 손절 감시는 멈추고 서버 측 손절만 남는다. 재기동 직후 `#/real`에서 보유 계좌를 2차 확인으로 **보호 모드**(`RealTradingGuard.enterProtective`, `RealTradingGuard.java:210`)로 올린다(PR #103 risk-ops 권고 3). 화면 단추는 묶음 H(C14) 뒤 채운다.
3. 내리기는 Guard OFF가 아니라 보호 모드다(실행 매뉴얼). 장 외 PANIC에서도 Guard는 끄지 않는다(D-140 ②).
4. 마감: 15:20 일괄 취소(RSK-11)는 엔진이 낸 미체결 일반 주문만 취소하고 서버 측 손절은 남긴다(D-140 ⑤). 엔진이 꺼져 있으면 일괄 취소는 일어나지 않으므로 증권사 앱에서 미체결을 직접 확인한다.

## 6. 3-R 상세 절차 (엔진 실행 중 `run` 폴더 삭제)

합격 기준은 [장애 설계](../team/broker-and-fault-design.md) 7장 3번 행과 [D-140](../decisions/D-140-stage7-panic-and-first-broker.md) ③. 묶음 A의 C6은 지워진 소켓을 다시 만들어 화면 명령이 첫 엔진에 닿는 (a) 분기를 기본으로 구현한다.

0. **전제(시험 범위)**: 3-R은 **시험 전용 설정 폴더**(`AUTOTRADE_CONFIG_DIR`, 1장 공통 전제)로 하고, 그 폴더의 실전 계좌는 시험 계좌뿐이며 모두 모의 도메인이다. 운영 설정 폴더로 하지 않는다. 엔진 종료(5번·6번)는 그 엔진의 모든 계좌에 걸리므로, 시험 계좌 밖 실전 계좌가 같은 엔진에 있으면 시행하지 않는다. 5-3과 정리 단계의 미체결 확인은 **한국투자 모의투자** 화면(모의 도메인 계좌)에서 한다(독립 QA PR #238 Q1).
1. 시험 계좌를 OPEN(모의 도메인)으로 둔다. 시각을 기록한다. 원본 (a) 분기는 OPEN·PROTECTIVE 계좌를 함께 말하므로 PROTECTIVE 계좌로도 같은 절차를 한 번 더 한다(계좌 둘을 하나씩 OPEN·PROTECTIVE로 두고 한 번에 해도 된다, PR #238 risk-ops R2).
2. `run` 폴더(또는 `engine.lock`·소켓)를 지운다. 무엇이 실제로 지워졌는지(잠금·소켓 각각) 기록한다. Windows에서는 엔진이 잡은 `engine.lock`이 남고 소켓만 지워질 수 있다 `[추론]`(ADR-006 2.2).
3. 같은 설정 폴더로 두 번째 엔진 기동을 시도한다.
   - 기동이 거부되면 거부 메시지·종료 코드를 기록하고 **4번으로 간다**(거부돼도 소켓이 지워진 첫 엔진에 화면 명령이 닿는지는 따로 봐야 한다, 원본 시험 순서, 독립 QA PR #238 F1).
   - 거부되지 않으면(OS 한계) 첫 엔진의 긴급 알림 도착 시각, 두 번째 엔진의 주문 세션 허가 0건·증권사 토큰·접속키 발급 0건(증권사 쪽 토큰 발급 기록으로 확인)을 기록한다.
4. 화면에서 내리기·PANIC을 누른다.
   - **(a) 명령이 첫 엔진에 닿는 경우**: 첫 엔진 계좌가 실제로 내려갔는지(Guard 상태, 엔진 로그) 확인한다. 내려갔으면 6번으로 간다. 닿은 것처럼 보이는데 **계좌가 내려가지 않았으면 불합격**으로 기록하고 5번 조치를 한다(독립 QA PR #238 F2 시나리오 3).
   - **(b) 닿지 못하는 경우**: 두 번째 엔진이 **없거나** 명령·상태에 응답하지 않고 화면이 "실전 상태 확인 불가"를 표시하는지 확인한다(화면이 첫 엔진의 OPEN 계좌를 OFF로 보이거나 "가상"으로 바뀌면 불합격). 그리고 5번 조치를 한다.
5. **사용자 조치: 엔진 프로세스 종료.** 묶음 F(감시 긴급 경로 W1) 전까지 쓸 수 있는 조치는 이것뿐이다. 지금 감시 프로세스는 어떤 프로세스도 죽이거나 띄우지 않는다(`WatchdogMain.java:22-24`, D-058, PR #235 QA Q7).
   1. **두 번째 엔진을 먼저 끝내고, 그다음 첫 엔진을 끝낸다**(또는 둘을 함께). 첫 엔진이 먼저 내려가면 두 번째 엔진이 잠금을 넘겨받아 기동을 이어 갈 수 있다 `[추론]`(독립 QA PR #238 Q2). 실전 엔진 java 프로세스를 모두 찾아 끝낸다. 명령은 묶음 I 시행 때 채운다 `[가정]`: `Get-CimInstance Win32_Process -Filter "Name='java.exe'" | Where-Object CommandLine -match 'com.autotrade.app.engine.EngineMain'` 로 찾고 `Stop-Process -Id <PID>`(두 번째 엔진 PID 먼저). 첫 엔진은 그 창에서 Ctrl+C로 끝내도 된다.
   2. **조치가 들었는지 확인**: 1차 확인은 위 프로세스 조회 결과가 **0줄**인 것이다. 그 뒤 몇 분 동안 증권사 앱에 엔진발 새 주문이 없는지 본다. 감시 알림은 보조 신호다: Ctrl+C면 "engine 종료", 강제 종료면 "engine 멈춤"이 오고(3장 N3a·N3b), 두 번째 엔진이 같은 하트비트 파일을 쓰고 있었으면 알림이 오지 않을 수 있다(PR #238 architect A-1). 알림이 없다고 조치가 안 들은 것으로, 알림이 왔다고 들은 것으로 판정하지 않는다.
   3. **증권사 앱에서 미체결 일반 주문을 확인하고 취소한다**(이 시험은 0번 전제대로 한국투자 모의투자 화면, 실전 운영에서 같은 일이 생기면 실전 앱). 서버 측 손절 조건주문은 남긴다. 엔진이 없으므로 15:20 일괄 취소(RSK-11, D-140 ⑤)도 일어나지 않는다. 엔진 종료 훅이 증권사 미체결을 취소한다고 가정하지 않는다 `[추론]`(`EngineMain.java:73-76`은 엔진을 닫기만 한다)(PR #235 QA Q8).
   4. 걸린 시간(긴급 알림 → 엔진 종료 확인 → 미체결 취소 끝)을 기록한다.
6. **정리(어느 분기든 반드시)**: 시험 뒤 잠금 없는 첫 엔진이나 기동 미완료 두 번째 엔진이 남으면, 이후 중복 기동을 막을 잠금이 없고 실험실이 "가상"으로 보이거나 두 번째 엔진이 토큰을 발급할 수 있다(독립 QA PR #238 F2).
   1. 5번을 아직 하지 않았으면 5-1·5-2를 한다(두 번째 엔진 먼저, 조회 0줄 확인). 5-3 미체결 확인도 한다.
   2. 엔진을 **한 개만** 다시 띄운다. `run` 폴더·`engine.lock`·소켓이 새로 생겼는지, 실험실 `#/real`이 "가상"이 아닌 실전 상태를 보이는지 확인한다.
   3. 모든 계좌 OFF로 시작하는지, **재기동 대사가 5-3에서 앱으로 취소한 주문과 남은 주문을 잡는지**(계획 B6, TST-07 (5) F-6) 기록한다. 보유가 있으면 4장 2번대로 보호 모드로 올린다.
7. 기록: 어느 분기든 중복 주문 0건, 화면이 "가상"으로 바뀌지 않음, 두 번째 엔진으로 인한 토큰 무효화·재발급 없음(첫 엔진의 정상 선제 갱신은 해당 없음)을 기록한다. 6번 정리가 끝난 뒤의 상태(엔진 1개, 잠금·소켓 있음)까지 확인해야 시험을 끝낸 것으로 본다.

## 9. 근거, 대안, 한계

- [사실] 감시는 프로세스를 멈추지 못한다: `WatchdogMain.java:22-24` javadoc "어떤 프로세스도 죽이거나 띄우지 않는다(D-058) … 실전 계좌 긴급 정지·청산 경로와 자동 재기동은 후속 작업". 계획 W1 "안 됨".
- [사실] 엔진 종료 훅은 `engine.close()`만 부른다(`EngineMain.java:73-76`). 증권사 주문 연동이 아직 없으므로 종료 때 미체결을 취소하는 코드는 없다. 묶음 E가 종료 동작을 정하면 6장 5-3을 다시 본다.
- 대안 검토(문서 모양): (가) 한 문서에 설치본·알림·운영·시험을 모음(고름: 후속이 모두 "7단계 절차서" 하나를 가리키고, 뼈대 단계에서는 빠진 것을 한눈에 보는 것이 중요). (나) 시험마다 파일을 나눔(버림: 지금은 칸 대부분이 비어 파일만 늘어남). 되돌릴 조건: 묶음 I 시행 때 한 시험 절차가 한 화면을 넘으면 그 시험만 별도 파일로 나누고 여기서 링크한다.
- 대안 검토(3-R (b) 조치): (가) 엔진 프로세스 종료(고름: 지금 실제로 있는 수단). (나) 감시 킬스위치(버림: 묶음 F 전에는 없다. W1이 구현되면 이 절차에 둘째 수단으로 더하고 그때도 "조치가 들었는지 확인"을 둔다). (다) 증권사 앱에서 수동 매도까지 함(버림: 3-R 합격 조건이 아니고, 매도는 사용자 판단이다. 미체결 취소만 둔다).
- 위험: 엔진 종료와 미체결 취소 사이에 엔진이 이미 낸 주문이 체결될 수 있다. 서버 측 손절은 남아 있으므로 보유 하방은 그것으로 막지만, 앱 취소 전 체결분은 재기동 대사에서만 드러난다(6장 6번이 기록).
- 한계: 명령·화면 이름·기준값 대부분이 비어 있다(뼈대). 검증하지 못했다: Windows에서 `run` 폴더 삭제가 실제로 (b) 분기를 만드는지, 한국투자 모의 도메인의 조회 한도.
