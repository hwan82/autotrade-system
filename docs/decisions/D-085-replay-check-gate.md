# D-085 리플레이 점검의 장 시간 보호와 정지 요청 파일 (Q-050)

- 날짜: 2026-10-14
- 상태: Q-050 추천안(data-engineer). broker-and-fault-design 5.2 정지 순서 0번과 장애표 #10을 바꾸므로 실전 관련 변경(지침 8장 2번)이다. architect·risk-ops 검토 후 **사용자가 PR을 직접 머지하면 확정**한다(지침 10장)
- 담당: data-engineer. 교차 검토: architect, risk-ops
- 근거: [Q-050](README.md)(PR #62 QA Q3, PR #63 QA R3·architect N3·risk-ops N2), [D-063](D-063-experiment-stop-gate.md)(실험 실행 명령의 같은 관문), [D-058](README.md)(단발 일괄 명령 정지 요청), [D-064](D-064-krx-2027-calendar.md) runbook 3.6 6번, [broker-and-fault-design.md](../team/broker-and-fault-design.md) 5.1·5.2·6장 #10, 지침 4장 6번(실험실·녹화는 자원 부족 시 먼저 멈춤)
- 범위: 리플레이 점검(`./gradlew :autotrade-app-gateway:replayCheck`)만. 같은 모듈의 `symbolMaster`(공개 종목 마스터 내려받기)·`kiwoomDaily`(일봉 조회 TR)는 게이트웨이를 끈 뒤 돌리는 짧은 조회라 범위 밖이다. 감시 쪽(임계치 감시, 파일 생성·해제)은 D-058 ④와 같은 감시 구현 후속 과제다

## 배경

[사실] `replayCheck`는 녹화일 하나를 디스크에서 두 번 따로 읽어 리플레이하는 단발 명령이다(`ReplayCheck.java`). 2026-10-12 실녹화는 528,156줄이고(PR #72) 회차마다 `RecordedDay.open`이 파일 해시 대조(정상 종료 녹화)와 전체 줄 파싱을 새로 한다(`RecordedDay.java:63-70`). 수집기(`RunGuard`)·실험 실행 명령(`ExperimentGate`, D-063)과 달리 장 시간 보호와 정지 요청 파일을 보지 않아, 장중에 돌리면 실전 엔진·게이트웨이와 CPU·디스크를 다툴 수 있었다. 지금까지는 D-064 runbook 3.6 6번의 시간 제한(서울 16:00~18:30)이 절차로만 막았다.

## 결정

1. **관문 `ReplayCheckGate`(autotrade-app-gateway)**: 실험 실행 명령(D-063 `ExperimentGate`)과 같은 규칙이다.
   - 정지 요청 파일 `<설정 폴더>/experiment-state/stop-request`(실험 명령·실험실 실시간 모의 세션과 같은 파일). 있으면(있는지 판단할 수 없어도) 멈추고, 명령은 지우지 않으며, 해제 옵션으로도 풀리지 않는다.
   - 장 시간 보호: 수집기·실험 명령과 같은 구간(`SessionProtection`: 국내·미국 거래일 정규장 60분 전 ~ 폐장 30분 뒤, 캘린더 수록 범위 밖이면 판단 못 해 멈춤).
   - 해제: 실전 엔진을 끈 날에만 `-PallowDuringSession`(인자 `--allow-during-session`). 값이 없거나 `true`일 때만 풀고 그 밖의 값(`false` 포함)은 입력 오류(종료 코드 2)다. 시작 때 확인하는 정지 요청 파일 경로와 해제 여부를 표준 오류로 출력한다(표준 출력은 보고서 본문이라 섞지 않음).
2. **확인 지점**: 명령 시작 때(녹화·종목명 표를 읽기 전), 회차마다 시작 때와 종목 수집 뒤, 회차 안에서 50,000줄마다(종목 수집 읽기와 리플레이 모두). 2026-10-12 실녹화 규모면 회차마다 약 23번이다 `[추론]`(528,156 / 50,000 × 2 + 2).
3. **종료 코드 4**: 정지 확인으로 멈추면 4(수집기·실험 명령과 같은 "실전 PC 자원 보호로 멈춤")이고 보고서를 출력하지도 쓰지도 않는다(이전 보고서 파일은 그대로). 0 동일, 1 다름, 2 읽기 실패·입력 오류, 3 불완전은 그대로다.
4. **진입점 `ReplayCheckMain`**: 시스템 시계와 설정 폴더는 진입점에서만 만든다(ArchUnit `NO_SYSTEM_TIME`은 `com.autotrade.app.*Main`만 허용). `ReplayCheck`의 `main`은 없앴고 Gradle 작업 이름은 그대로다. 녹화일 날짜 인자의 기준 설정 폴더도 진입점이 넘긴다.
5. **파일 위치 일치 검사**: 게이트웨이 모듈은 실험 모듈·실험실을 의존할 수 없어(빌드 격리 `processIsolation`) 상수를 공유하지 못한다. 모든 모듈이 올라오는 `autotrade-architecture-test`에 `StopRequestPathTest`를 두어 `ExperimentGate`·`LiveLabService`·`ReplayCheckGate`의 정지 요청 파일 위치가 같은지 본다.

## 위험과 한계

- **감시 쪽은 아직 없다**(D-058 ④). 지금 이 파일을 만드는 주체가 없어, 실제로 동작하는 보호는 장 시간 보호뿐이다(D-063과 같음).
- **멈춤은 확인 지점 사이만큼 늦다**: 가장 긴 단계는 `RecordedDay.open`이다. 정상 종료 녹화의 파일 해시를 대조하고 모든 줄을 메모리로 파싱하는 동안은 묻지 않는다(회차마다 1번, 그 앞뒤에서 묻는다). 줄 간격 확인은 메모리에 올라온 줄을 도는 동안이라 이 단계보다 짧다 `[추론]`. 실녹화에서 단계별 시간은 측정하지 않았다 `[가정]`. 첫 실녹화 점검 때 콘솔 시간으로 확인하고, `open`이 길면 `RecordedDay`에 정지 확인을 넣는 변경을 따로 제안한다(marketdata 소유).
- **국내 번들 캘린더가 2027-12-31까지**(`krx.json` `coverageTo`, D-064)라 다음날 조회가 범위 밖이 되는 서울 2027-12-31 00:00부터 해제 옵션 없이 시작하지 않는다. 수집기·실험 명령과 같은 판정이다.
- **해제 옵션의 남용**: `-PallowDuringSession`은 `gradle.properties`·환경 변수로도 들어온다. 시작 때 해제 여부를 출력하지만 표준 오류라 보고서 파일에는 남지 않는다.
- runbook의 반영 작업 시간 제한(서울 16:00~18:30)은 `build`·`installDist`가 여전히 보호를 보지 않으므로 그대로 둔다.

## 검증

- `ReplayCheckTest`(app-gateway) 새 테스트 8개: 장 시간 보호 구간이면 시작하지 않고 4·보고서 안 씀·확인 위치 출력, 해제 옵션으로만 풀림(값 없음·`=`·`=true`), 그 밖의 값은 입력 오류 2, 미국 장 시간과 캘린더 범위 밖도 멈춤, 정지 요청 파일은 해제 옵션과 상관없이 멈추고 지우지 않음, 정지 요청 판단 불가도 멈춤, 실행 중 정지면 회차 안에서 멈추고 보고서를 쓰지 않음(4), 확인 횟수(회차 시작·줄 간격)와 멈추지 않으면 보고서가 문 없을 때와 같음.
- 기존 테스트는 명령 진입 경로를 고정 시각(토요일)·임시 설정 폴더로 부르게 바꿨다(벽시계를 쓰면 평일 장중에 CI가 실패하므로). 기대값은 바꾸지 않았다.
- `StopRequestPathTest`(architecture-test): 세 명령의 정지 요청 파일 위치가 같음.
- `./gradlew build` 전체 통과(ArchitectureTest·ModuleOwnershipTest 포함).
