## 점검표 밖 발견
시나리오 시도(잘못된 주문·중복 주문·보호 공백). 모두 7단계 구현 계약의 빈틈이며 현재 main에서 실행되는 경로는 없다(PanicLiquidator.java:28-32). 7단계 `PanicLiquidator` 구현 PR 전에 ADR-006:203 행 또는 2.5 계약에 보강할 것.

1. **[중] 재설정 순서가 정해지지 않음 → 재설정 실패 또는 이중 매도.** ADR-006:203은 "마감 전까지 매도가 체결되지 않으면 남은 보유에 서버 측 손절을 다시 건다"고만 한다. ④의 매도 주문(국내 시장가 잔량, 미국 지정가+여유폭)이 아직 살아 있는 채로 재설정하면 (a) 증권사가 매도 가능 수량 0으로 재설정 주문을 거절해 보유가 서버 측 손절 없이 남거나, (b) 재설정 주문이 접수되고 뒤이어 원래 매도가 체결되면 손절 주문이 보유보다 큰 수량으로 남는다 `[추론, 증권사별 매도 가능 수량 처리 미확인]`. 계약에 "남은 매도 주문 취소 → 취소 확인 → 보유 수량 조회 → 확인된 수량으로 재설정"의 순서와, 부분 체결 시 남은 수량 기준을 적고, 합격 테스트에 "매도 미체결 잔량이 살아 있는 상태에서 재설정하지 않음"을 추가할 것.
2. **[중] RSK-11 "일괄 취소" 구간과 재설정 시각의 관계가 없음.** RSK-11(autotrade-spec.md:186)은 국내 15:20·미국 15:55 `[가정]`에 "일괄 취소" 구간을 두지만, 그 대상에 서버 측 손절이 포함되는지 어디에도 정의되지 않았다(`grep '일괄 취소'` 결과 RSK-11 두 곳뿐). ADR-006:203의 재설정이 일괄 취소 시각 뒤에 이뤄지거나, 일괄 취소가 방금 다시 건 서버 측 손절을 지우면 "마감 전 재설정"이 무력화된다 `[추론]`. 재설정 상한 시각을 "일괄 취소 구간 시작 전"으로 두고, 일괄 취소는 서버 측 손절을 지우지 않는다고 RSK-11·ADR-006에 함께 적을 것.
3. **[중] 판정 시점이 ② 전 한 번뿐 → 판정 뒤 정지가 생기면 보호 공백.** ADR-006:203은 판정을 "② 전에" 한다. ②(미체결 취소 확인)에 시간이 걸리는 동안 종목 거래정지·LULD 정지가 걸리면, 판정은 "매도 가능"인데 ③에서 서버 측 손절을 지우고 ④가 나가지 못한다. 정지가 마감까지 이어지면 정지 중에는 재설정 주문도 접수되지 않을 수 있어 `[추론]` 보유가 서버 측 손절 없이 밤을 넘긴다. ③ 직전에 같은 판정을 다시 하고(바뀌었으면 ③을 하지 않음), 재설정이 거절·불가하면 기존 2.5 계약대로 FAILED·긴급 표시로 끝난다는 점을 ADR-006:203에 명시할 것. 합격 테스트 "미체결로 남은 보유가 서버 측 손절 없이 마감을 넘기지 않음"은 증권사 거절 시 보장할 수 없으므로 "넘기지 않거나, 넘기면 긴급 FAILED로 알림"으로 고칠 것.
4. **[하] VI 분류 변경의 결정 절차가 빠짐.** ADR-006:205는 VI를 "매도 가능으로 옮길지 정한다"고 하고 담당을 risk-ops로만 둔다. VI를 매도 가능으로 옮기면 서버 측 손절을 지우는 경우가 늘어나는 실전 영향 변경이고, VI를 매도 불가 예시로 적은 확정 결정 D-037·RSK-13을 바꾸는 일이다(지침 8장 2·4번). 같은 표 23행(잠금 남용 대책)처럼 "결정은 Q 번호로 사용자에게 묻는다"를 적을 것. 지침 자체가 사용자 결정을 요구하므로 이번 머지는 막지 않는다.
5. **[하] "다음 코드 PR에서 바로"는 이미 지나간 시점.** ADR-006:202는 `PanicLiquidator.java:11` 주석을 "다음 코드 PR에서 바로" 고친다고 하지만, 이 PR이 열린 뒤 코드 PR #27(307ca00, 게이트웨이 코드)이 먼저 머지되었고 주석은 그대로다(현재 main PanicLiquidator.java:11 "장 외 시간에는 취소만 하고 매도하지 않는다"). 담당·시점이 특정 PR에 묶이지 않아 계속 미뤄질 수 있다. "7단계 첫 PR 전, TST-07 진입 관문 확인 항목" 같은 확인 가능한 시점으로 바꾸거나 이 주석만 고치는 작은 PR을 바로 낼 것을 권고.
6. [하] PR 제목은 "지적 3건"인데 실제 등록은 4건(QA pr-25 발견 1~4)이다. 기록 추적에 혼동을 줄 수 있으나 내용은 본문과 일치.
7. 확인했지만 문제 아님: (a) risk-ops 원문(5eb711a·431d64f)은 메인이 고치지 않음(`git log --name-only` 상 c97a468은 ADR 파일만 변경). (b) ADR-006:205가 인용한 risk-ops pr-25 61·96행 메모 실재. (c) 새 행이 기존 191행("서버 측 손절 재설정 계약을 `PanicLiquidator` 구현 테스트로 고정", 7단계 완료 조건)과 같은 방향이며 충돌 없음.
