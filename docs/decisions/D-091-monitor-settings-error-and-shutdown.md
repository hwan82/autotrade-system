# D-091 모니터링 설정 오류에도 실험실 기동, 종료 때 SSE 먼저 닫기, 첫 표본 전 수집 멈춤(D-090 4번 대체)

- 날짜: 2026-10-15
- 상태: 확정 · **추천안 채택(자율)**(지침 8장). 실험실 모니터링(MON-05)의 설정 오류·종료·멈춤 표시만 바꾼다. 실전 주문 경로·RealTradingGuard·블랙리스트·리스크 한도·장애 대응 규칙과 보호 테스트는 바꾸지 않는다.
- 담당: ui-dev. 교차 검토: architect, risk-ops(실전 운영 화면을 싣는 실험실의 기동·종료 동작)
- 근거: [docs/reviews/pr-114/qa.md](../reviews/pr-114/qa.md) 권고 R1~R3(탐침 P1·P1b·P2·P3), [D-090](D-090-monitor-agent-and-screen.md) 3·4번, risk-ops PR #114 R1("화면용 부가 기능이 실험실 기동을 막으면 안 된다")
- 대체: **D-090 4번의 "형식·범위가 틀리거나 지표 이름이 `MetricNames.ALL`에 없으면 실험실이 뜨지 않는다"**. D-090 4번의 나머지(속성 이름·기본값·범위·임계 형식)는 그대로다.

## 결정

1. **설정 오류는 모니터링만 끈다.** `autotrade.lab.monitor.*` 값이 하나라도 틀리면(`enabled`가 true·false가 아님, 정수가 아님, 주기·기록 크기 범위 밖, 임계 형식 오류·중복·모르는 지표 이름) 실험실은 그대로 뜨고 모니터링만 "사용 불가"(`problem`에 오류 문구)가 된다. 로그에 경고 한 줄을 남기고 수집원은 만들지 않는다. 값은 문자열로 받아 직접 읽으므로 Spring 바인딩 단계에서도 기동이 실패하지 않는다.
   - 이유: 실험실은 실전 운영 화면(내리기·PANIC SELL)을 싣는다. 장중에 임계를 고쳐 다시 띄우다 오타가 나면, D-090 4번대로는 고칠 때까지 그 화면을 쓸 수 없다(QA P1·P1b). D-090 3번이 수집원 생성 실패에 이미 같은 원칙을 썼다.
   - D-090 4번이 지키려던 "잘못 쓴 임계를 모르고 지나치지 않게"는 화면의 "사용 불가" 표시와 오류 문구, 경고 로그로 지킨다.
2. **종료 때 SSE를 먼저 닫는다.** 실험실 종료 때 `SmartLifecycle` 빈(기본 위상)이 웹 서버 graceful shutdown(기본 위상 - 1024)보다 먼저 열린 SSE를 끝내고 새 연결을 409로 거절한다. 전에는 graceful shutdown이 열린 SSE를 진행 중 요청으로 보고 30초를 기다렸다(QA P3: 30,045ms).
3. **첫 표본 전 멈춤도 "수집 멈춤"이다.** 마지막 표본이 없으면 수집 시작 시각(`View.startedAt`)부터 잰다. 수집 주기의 3배가 지나도록 첫 표본이 없으면 `stale`이고, 화면이 "수집을 시작했지만 첫 표본이 없다"는 경고를 띄운다(QA P2). 화면도 1초마다 같은 기준으로 다시 잰다.

## 대안

| 대안 | 장점 | 단점 | 판단 |
|---|---|---|---|
| 1-A. 설정 오류면 모니터링만 사용 불가 | 실전 운영 화면이 설정 오타에 막히지 않음. 수집원 실패(D-090 3번)와 같은 원칙 | 오류를 화면·로그로만 알림 | **채택** |
| 1-B. 지금처럼 실험실 기동 거부, D-090에 예외 이유만 적기 | 오류를 놓칠 수 없음 | 장중 재기동 오타 한 번에 내리기·PANIC SELL 화면이 막힘 | 버림 |
| 1-C. 틀린 항목만 버리고 나머지로 켜기 | 모니터링이 최대한 돎 | 틀린 임계를 모르고 기본 임계로 도는 일이 생김(D-090 4번이 막으려던 것) | 버림 |
| 2-A. `SmartLifecycle`로 SSE 먼저 닫기 | 실험실 다른 요청의 graceful shutdown은 그대로 | 빈 하나 추가 | **채택** |
| 2-B. 실험실 `server.shutdown=immediate` | 설정 한 줄 | 실험 등록 같은 다른 진행 중 요청도 기다리지 않고 끊음 | 버림 |
| 3-A. 수집 시작 시각 기준 | 서버·화면 같은 기준, 코어 변경 없음 | `View`에 필드 하나 추가 | **채택** |
| 3-B. 수집원별 시간 상한 | 막힌 수집원만 골라 냄 | 코어(감시 런타임) 변경과 스레드가 늘어남 | 버림(7단계 감시 구현 때 다시 봄) |

되돌릴 조건: 화면 "사용 불가"를 놓쳐 잘못된 임계로 장시간 운영한 일이 생기면 1-B를 다시 본다.

## 위험과 한계

- `enabled`는 이제 `true`·`false`만 받는다. 전에는 Spring 변환으로 `on`·`off`·`yes`·`1` 등도 받았다. `off`로 끈 사용자는 "꺼짐" 대신 "설정 오류로 사용 불가"를 보지만 수집하지 않는 결과는 같다(architect PR #115 A3, config-keys.md에 적음).
- 종료 중 표시(`closing`)는 다시 풀리지 않는다. 컨텍스트를 `stop()` 뒤 `start()`하면 SSE가 계속 409다. 실험실은 이렇게 쓰지 않는다(architect PR #115 A5).
- 화면 `isStale`·`staleText`는 자동 시험이 없다. 화면 Playwright CI(5단계 QA 권고 R3)가 들어올 때 이 경계를 넣는다(architect PR #115 A4).

## 검증

- `MonitorConfigurationTest` 3건: 잘못된 설정 6가지가 모니터링만 끄고 이유를 남김, 그때 수집원을 만들지 않음, 올바른 설정은 그대로 읽음.
- `MonitorBadSettingsBootTest` 1건: QA P1 그대로 임계 이름 오타(`cpu.sytem`)로 띄워도 `/api/real/status` 200, `/api/monitor` 사용 불가, SSE 409.
- `MonitorShutdownTest` 1건: 실제 웹 서버에 SSE를 연 채 닫아도 10초 안에 끝남(약 5.7초). `closeStreams()` 호출을 빼면 32,044ms로 실패함을 확인했다(architect PR #115 변이 확인).
- `MonitorServiceTest` 2건: 첫 read가 막힌 수집원으로 첫 표본 전 멈춤 경계(주기 3배 = 아님, 1초 넘김 = 멈춤), 종료 첫 단계에서 SSE를 닫고 새 연결을 거절함.
