# D-110 감시: 회복을 알린 값이 다른 값의 경고 뒤 다시 빠져도 바로 경고, 점검 단계 한 곳으로(PR #163 QA 후속)

- 날짜: 2026-10-18
- 상태: 확정 · **추천안 채택(자율)**(지침 8장). 감시(`autotrade-app-watchdog`)의 결측 경고 "새 값" 판정, 점검 단계 실패 처리 구조, 시험만 바꾼다. 임계 판정, 정지 요청 판정(D-092·D-095), 하트비트 판정, 알림 종류·억제(D-100), 결측 경고 간격(D-096·D-108의 10분), 로그 출력 실패 정책(D-109), 감시 설정, 보호 테스트는 바꾸지 않는다. 보호 경로라 사용자 머지로 확정한다.
- 담당: risk-ops 결정·구현. 교차 검토: architect(코드), risk-ops(실전 관련)
- 근거: [PR #163 독립 QA](../reviews/pr-163/qa.md) R1·Q1·Q2, [D-108](D-108-watchdog-missing-after-recovery-and-disk-cause.md), [D-109](D-109-monitor-watchdog-log-output-failure.md)

## 문제

1. **R1(main에도 있던 결함)**: cpu 결측 WARN → cpu 회복 INFO → 드라이브 결측 WARN → 드라이브 회복·cpu 다시 빠짐이면 cpu에 대한 WARN·알림이 최대 10분 없었다. "새로 빠진 값" 판정이 간격 안에서 합친 경고 목록(`warnedReadings`, 회복 전에 경고한 cpu가 남아 있음)만 보고, "회복 뒤 다시 빠짐"(D-108)은 그 사이 드라이브 WARN으로 거짓이 되기 때문이다. 그동안 cpu의 마지막 로그·알림은 "다시 읽음"이라 D-108이 막으려던 상태다. 압력은 UNKNOWN이라 정지 요청을 새로 만들지 못하고 켜진 것은 유지해 안전 쪽이었다.
2. **Q1**: D-109의 점검 중 로그 삼킴 가운데 재기동 감지, 하트비트 UNREADABLE·ALIVE 바뀜, 정지 요청 해제·쓰기 실패, `tick()` 단계 catch 안 로그를 고정하는 시험이 없었다(QA 변이 QM1~QM4·QM7·QM8 생존, QM2·QM7은 알림 영구 유실). `tick()`의 단계 catch 넷은 운영에서 단계를 던지게 할 주입점이 없어 시험으로 닿지 않았다.
3. **Q2**: 모니터 에이전트가 DEBUG가 켜진 주기에도 들고 있던 줄을 DEBUG 줄 앞에 다시 내는지 시험이 없었다(QM12 생존).

## 결정

1. **"이미 알린 값"은 두 집합 모두에 있어야 함**: 빠진 값이 간격 안에서 경고한 값(`warnedReadings`)과 마지막 회복 INFO 뒤 경고한 값(`missingSinceRecovery`, D-109에서 회복 본문용으로 나눈 집합) **모두에** 들어 있을 때만 간격을 기다린다. 어느 한쪽에라도 없으면 바로 WARN·알림. 두 집합은 각각 간격마다 한 번만 비워지므로(앞은 간격이 찬 경고에서, 뒤는 간격마다 한 번인 회복 INFO에서) 점검마다 오가는 값도 간격마다 경고 수가 묶인다.
2. **점검 단계는 `Watchdog.stage` 한 곳에서 돌림**: 자기 하트비트, 자원 점검, 하트비트 점검, 정지 요청 처리 네 단계를 같은 실행기(던지면 그 단계만 버리고 대신 값을 돌려줌, 실패 로그는 `WatchdogLog`)로 돌린다. 단계마다 같은 catch를 두면 그중 하나만 바뀌어도 시험이 못 잡던 것을 한 곳으로 모아 직접 시험한다. 실패 로그 문구(단계 이름 + 예외 클래스 이름)는 그대로다.
3. **시험 추가**(Q1·Q2): 감시·감시 에이전트 코어의 모든 로그에 던지는 핸들러 아래에서 재기동 알림, 하트비트 읽기 실패·회복 알림, 정지 요청 해제 알림, 정지 요청 파일 하나 쓰기 실패 중 다른 파일과 켜짐 알림, 단계 실패 로그가 던져도 다음 단계 진행. 모니터 에이전트는 DEBUG가 켜진 주기에 못 낸 WARN을 DEBUG 줄 앞에 다시 냄.

## 대안

| 대안 | 판단 |
|---|---|
| ① 두 집합 모두에 있어야 "이미 알림"(채택) | R1을 고치면서 PR #123 QA Q1(간격이 찬 반복 경고에서 빠진 값이 다시 빠지면 바로 경고)도 지킨다 |
| ② QA 제안대로 `missingSinceRecovery`만 봄 | R1은 고치지만 0분 {cpu, 드라이브} 경고 → 10분 {cpu}만 반복 → 11분 드라이브 재결측에서 조용해진다(`간격이_찬_경고_뒤에_다시_빠진_값은_바로_알린다`가 실패). 버림 |
| ③ 회복 INFO 때 `warnedReadings`도 비움 | 회복 INFO는 미뤄질 수 있어(D-108) 간격 안 반복 억제가 깨지는지 따로 따져야 하고 상태 의미가 섞인다. 버림 |
| 단계 catch는 그대로 두고 시험용 주입점(단계 대체 생성자)을 둠 | 운영 코드에 시험 전용 경로가 생기고, catch 넷은 여전히 따로 바뀔 수 있다. 버림 |

되돌릴 조건: 6단계 운용에서 오가는 값의 결측 알림이 간격당 셋 이상 반복돼 알림을 묻으면 ③을 다시 본다.

## 위험과 한계

- 결측 WARN은 간격마다 값 하나당 최대 두 번 더 늘 수 있다(두 집합이 서로 다른 때 비워지므로). 알림 큐가 같은 대상·종류를 10분에 한 번만 보내므로(D-100) 알림 수는 늘지 않고 로그만 는다 `[추론]`.
- `stage`의 대신 값 경로(자원 점검 실패 → 판단 못 함)는 예전 catch와 같다. 단계가 던지는 실제 경우는 여전히 시험으로 만들 수 없고, 실행기를 직접 시험한다.
