## 결정

1. **하트비트 파일**: 상주 프로세스(실전 엔진 `engine`, 시세 게이트웨이 `gateway`, 실험실 `lab`, 감시 `watchdog`)가 5초마다 `<설정 폴더>/heartbeat/<이름>.hb`를 덮어쓴다(임시 파일에 쓴 뒤 옮김). 내용은 `process`, `pid`, `started-at`, `written-at`, `seq` 다섯 줄이다. 기록기 `HeartbeatWriter`는 감시 에이전트 코어(`autotrade-monitor-agent-jar`, JDK 허용 목록 안)에 두어 실전 엔진이 새 외부 의존 없이 쓴다.
   - 기록기는 붙은 프로세스를 멈추게 하지 않는다. 쓰기 실패는 그 주기만 버리고, 실패·복구 로그는 상태가 바뀔 때만 한 줄 남긴다(PR #114 risk-ops K5와 같은 원칙). 데몬 스레드 하나다.
   - **정상 종료는 파일을 지운다.** 그래서 감시는 "꺼짐"(파일 없음)과 "죽음·멈춤"(오래된 파일)을 가른다.
   - 실험실은 스프링 빈이 아니라 진입점(`AutotradeLabApplication.main`)에서 시작한다. 스프링 시험이 사용자 PC의 실제 실험실 하트비트를 덮어쓰거나 지우지 않게 하려는 것이다.
2. **감시 루프**(`Watchdog`, 주기 기본 5초, 스레드 하나): 점검마다 ① 자기 하트비트를 쓰고 ② 드라이브 여유를 읽어 감시 에이전트 코어로 임계를 판정하고 ③ 상주 프로세스 하트비트를 판정하고 ④ 정지 요청 파일을 켜고·갱신하고·끈다. 단계 하나가 던져도 그 단계만 버리고 다음 단계와 다음 점검은 계속한다. 자기 하트비트를 점검 루프 안에서 쓰므로 감시 하트비트가 멈추면 루프가 멈춘 것이다.
3. **하트비트 판정**: 살아 있음(`written-at`이 기준 15초 이내), 멈춤(기준 초과: 비정상 종료는 파일을 남기므로 크래시도 여기), 꺼짐(파일 없음), 읽을 수 없음. 상태가 바뀔 때만 로그를 남긴다. 실전 엔진 멈춤은 ERROR(장애표 #8), 나머지는 WARNING(#9). **감시는 이 판정으로 아무것도 멈추거나 죽이거나 띄우지 않는다**(D-058, 자동 재기동은 아래 범위 밖).
4. **PC 자원은 드라이브 여유만 본다**: 감시 런타임은 OSHI·JNA·`java.lang.management`를 들이지 않는 경계를 지킨다(D-086, D-090 대안 B). JDK `FileStore`로 설정한 경로(기본: 설정 폴더 드라이브. 녹화·실시간 모의 입력 기록·수집 캐시가 있는 곳)의 여유 GB를 읽는다. 기본 임계 `[가정]`: 경고 50GB, 위험 20GB 이하, 1회(실험실 모니터링 D-090 5번과 같고, 20GB는 실시간 모의 입력 기록 하한 D-076과 같음). CPU·메모리는 이 경계 안에서 읽을 수단이 없어 [Q-053](README.md)으로 사용자 결정에 넘긴다.
5. **정지 요청 파일(D-058 ④)**: 드라이브 하나라도 위험이면 수집기 `<설정 폴더>/collector-state/stop-request`와 실험 `<설정 폴더>/experiment-state/stop-request`(실험 실행 명령·리플레이 점검·실험실 실시간 모의 세션이 봄)를 만든다.
   - **켜진 동안은 점검마다 두 파일을 다시 쓴다**(없으면 만들고 있으면 `confirmed-at`과 수정 시각을 갱신, ADR-007 2.7의 레벨 신호). 내용은 `requested-at`, `confirmed-at`, `reason`.
   - **끄기(해제)**: 모든 드라이브가 정상(경고 경계 위)으로 해제 유지 시간(기본 5분 `[가정]`, ADR-007 2.7) 동안 이어질 때만 지운다. 경고 수준이거나 값을 읽지 못한 점검이 끼면 유지 시간을 처음부터 다시 센다. **해제 기준은 경고 경계**로 둔다: ADR-007 2.7의 "임계치 − 10%p"는 사용률 지표 기준이고, 기본 CPU·메모리 임계(85/95%)에서 경고 경계가 곧 위험 경계 −10%p다. 여유 GB처럼 단위가 다른 지표에도 같은 규칙이 통한다.
   - **값을 읽지 못하면 판단 못 함**: 새로 만들지 않고, 켜져 있으면 풀지 않는다.
   - **남은 파일**: 감시가 뜰 때 파일이 이미 있으면(이전 감시가 죽은 채 남긴 파일) 켜진 상태로 이어받고, 자원이 정상이면 해제 유지 시간 뒤 지운다(D-058 "남은 파일은 감시를 고쳐 거두게 하고 사람이 지우지 않는다"). 감시를 정상 종료해도 파일은 그대로 두어 다음 감시가 이어받는다.
   - 선정 일괄 명령(`<results-dir>/_status/<MARKET>/stop-request`, ADR-007 2.7)은 아직 그 명령이 없어(배치표 5번) 이번에 만들지 않는다. 그 명령을 만드는 PR이 감시 쪽 경로도 더한다.
6. **감시 생존 확인(D-058 ④에서 넘긴 "누가 감시를 볼지")**: ① 감시 하트비트 파일 `heartbeat/watchdog.hb`(감시 점검 루프 안에서 씀)와 ② 정지 요청 파일의 수정 시각이다. 일괄 명령(수집기 `RunGuard`, 실험 `ExperimentGate`, 리플레이 점검 `ReplayCheckGate`)은 이미 거부 메시지에 정지 요청 파일 수정 시각을 찍으므로, **그 시각이 점검 주기보다 많이(기본 15초 넘게) 오래됐으면 감시가 죽거나 멈춘 채 파일이 남은 것**이다. 명령 코드는 바꾸지 않는다. 사람이 볼 절차는 [수집기 runbook](../runbooks/collector.md) 3.5에 적었다. 감시 하트비트를 화면에 띄우거나 알림으로 보내는 일은 아래 후속이다.
7. **감시 설정은 별도 파일, 틀리면 기동 거부**(PR #115 risk-ops K2): `<설정 폴더>/watchdog.properties`(`키=값`, `#` 주석, 없으면 기본값). 모르는 키(오타), 중복 키, 형식·범위 오류, 없는 드라이브 경로가 하나라도 있으면 문제를 모두 모아 ERROR 로그와 표준 오류로 알리고 **종료 코드 2로 뜨지 않는다**. 키는 [config-keys.md](../config/config-keys.md) "감시 프로세스 설정 파일". 실험실 모니터링(D-091)과 반대인 이유: 실험실은 실전 운영 화면을 싣는 프로세스라 부가 기능이 기동을 막으면 안 되지만, 감시가 "사용 불가"로 뜨면 지키는 척하며 아무것도 지키지 않는다.

## 위험과 한계
- 하트비트는 그 JVM과 하트비트 스레드가 돈다는 증거다. 실전 엔진의 업무 스레드가 막혀도 하트비트는 계속될 수 있다. 업무 진행 신호(예: 계좌 워커 마지막 처리 시각)를 하트비트에 싣는 것은 7단계 계좌 워커 구현 때 본다.
- 실전 엔진에 스레드 하나와 5초마다 작은 파일 쓰기가 늘었다. 디스크가 차서 실패해도 로그 한 줄 뒤 계속 돈다(`HeartbeatTest` 실패 주입). 실전 경로 리플렉션·허용 목록 검사(D-086)는 그대로 통과한다.
- 실험실·게이트웨이·감시를 강제 종료(작업 관리자)하면 파일이 남아 "멈춤"으로 보인다. 다시 띄우면 덮어써 "살아 있음"이 된다. 실전 엔진의 멈춤도 지금은 로그(ERROR)로만 알린다(알림 채널 후속).
- 감시가 아예 뜨지 않았으면 정지 요청 파일도 만들어지지 않는다. 그동안 단발 명령은 각자의 장 시간 보호·디스크 하한(수집기 `--min-free-gb`, 실험실 실시간 20GB)으로 물러난다. 감시를 띄우는 절차는 6단계 운영 절차서에 넣는다.
- CPU·메모리 압박은 감시가 아직 못 본다(Q-053). 실험실 모니터링 화면(D-090)은 보이지만 조치하지 않는다.
- 설정 폴더가 네트워크 드라이브면 원자적 이동이 안 될 수 있어 덮어쓰기 이동으로 대신한다(읽는 쪽이 드물게 빈 파일을 볼 수 있음 → "읽을 수 없음"으로 한 주기 보였다 돌아옴). 설정 폴더는 로컬 드라이브를 권장한다.

## 검증
- 코어: `HeartbeatTest` 6건(형식 왕복, 틀린 내용 거절, 경로·이름 검사, 기록 갱신과 닫으면 삭제, 쓰기 실패 주입 뒤 복구, 주기 기록 스레드).
- 감시: `WatchdogSettingsTest` 5건(기본값, 파일 값, 모르는 키 거부, 틀린 값 모두 모아 거부, 임계 형식), `HeartbeatWatchTest` 2건(살아 있음·멈춤·꺼짐 전환과 바뀔 때만 알림, 해석 불가·다른 이름), `StopRequestsTest` 5건(위험 때 두 파일 생성과 점검마다 갱신·지워도 다시 만듦, 해제 유지 시간·경고·판단 못 함, 판단 못 할 때 새로 안 만듦, 남은 파일 이어받아 지움, 쓰기 실패 주입), `WatchdogTest` 5건(드라이브 여유 주입으로 생성·경고 유지·회복 뒤 해제, 읽기 실패 주입 시 해제 안 함, 자기 하트비트·다른 프로세스 판정, 닫아도 파일 유지·다음 감시 이어받음, 주기 스레드), `WatchdogMainTest` 3건(설정 없음 기동, 틀린 설정 종료 코드 2, 기동·종료 하트비트).
- 아키텍처: `StopRequestPathTest`에 감시가 만드는 두 파일이 수집기(`CollectorMain.Options.stopRequest()`)·실험 명령(`ExperimentGate.STOP_REQUEST`)과 같은지 더함. `RealPathReflectionTest`·`WATCHDOG_KILLS_NO_PROCESS`는 바꾸지 않고 통과.
- 검증하지 못한 것: Windows에서 `ATOMIC_MOVE` 덮어쓰기와 `FileStore` 값(이 환경은 Linux). 사용자 PC 6단계 운영 첫 주 점검 항목으로 둔다.
