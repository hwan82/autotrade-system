## 권고 (막지 않음)

1. **시드를 지금 고정한다.** 등록 파일 예시의 `seed: "<등록 때 정한 정수>"`는 등록 시점에 정하게 되어 있다. 판정 전이라 시드 고르기 여지는 작지만, 사전 등록의 취지대로 값(예: 테스트와 같은 `1`, 또는 등록일 정수)을 절차서에 지금 적어 두면 "결과를 보고 시드를 바꿨는가"라는 질문 자체가 없어진다. `parallelism`은 결과에 영향이 없어 자리표시자로 두어도 된다.
2. **2026-04-01 이후 데이터를 손대지 않는 표본 외 구간으로 남긴다고 적는다.** 수집이 끝나면 일봉이 2026년 10월까지 있는데 4구간 판정은 2026-03-31에서 끝난다. 이 6개월 남짓은 등록 실험이 보지 않는 구간이다. 절차서 4장이나 계획 6장에 "이 구간은 첫 실험에서 쓰지 않고, 통과 조합의 표본 외 재확인(2027-03-31 뒤 5구간째 또는 6단계 실시간 모의와 대조)에 남긴다"를 한 줄 넣으면, 나중에 이 구간을 보고 기준을 고치는 일을 막는다. 같은 이유로 등록 전에는 실데이터 스냅샷 위에서 이 후보들로 시험 실행(시간 측정용 포함)을 하지 않는다는 문장도 권한다. 시간 측정이 필요하면 합성 시세나 결과를 열지 않는 방식으로 한다.
3. **등록 파일이 커밋된 그대로인지 확인하는 단계.** `gitDirty`는 `experiments/`를 빼고 보므로(`build.gradle.kts` 36행) 사용자 PC에서 `study.yaml`이 고쳐져 있어도 dirty로 잡히지 않는다. `inputs.yaml`이 조합·대조군·시드·구간을 되풀이해 사후 대조는 가능하지만, 절차서 5장에 실행 전 `git status experiments/EXP-<등록일>-WF01`이 깨끗한지 보는 한 줄을 넣거나, 후속으로 `inputs.yaml`에 `study.yaml` SHA-256을 넣기를 권한다(sim-engine 영역, 변경 제안).
4. **주말 창을 넘길 때의 처리.** 결정론 확인까지 하면 시간이 두 배 넘게 들고, 월요일 08:00에 들어서면 종료 4로 결과 없이 멈춘다. 계산량은 아직 `[가정]`(ADR-009 4장)이다. 절차서 5장에 "한 주말에 끝나지 않으면 실전 엔진·게이트웨이가 꺼져 있는 날 `-PallowDuringSession`으로 이어서 돌리거나 다음 주말에 다시 시작한다. 대조군 수를 줄이려면 N+1 ≥ 20m을 지키는 선에서 새 실험 ID로 한다"를 적어 두면 등록 파일을 고치고 싶은 압력을 미리 막는다.
5. **Q-013 행 갱신.** D-073 3번은 "Q-013의 스윙 KPI 중 선발 판정 부분은 이 결정으로 정해졌다"고 하지만 README 미확정 표 Q-013 행은 여전히 "남은 것: 스타일별 KPI 전반, 장중 프로필 기준"이다. "스윙 선발 판정은 D-073" 정도로 고쳐 결정 로그가 한 곳에서 맞게 읽히게 한다(pm-lead 영역).
6. **D-073 출처.** 출처가 사용자의 "진행하십시오" 한 마디를 여러 질문 중 2번에 대한 답으로 읽은 것이다. 승격 기준 변경은 지침 8장 5번의 사용자 결정 항목이라, 원문 스레드에서 질문 목록과 답이 이어져 있는지 pm-lead가 한 번 확인해 두기를 권한다. 이 환경에서는 확인하지 못했다. 다만 이 결정이 푸는 것은 "스윙 통과 조합을 승격 후보로 넘기지 않음" 보류뿐이고, 승격은 여전히 8주 실시간 모의(D-027·STR-05)와 사용자 활성화를 거치므로 잘못 읽었을 때의 영향은 작다 `[추론]`.
7. **이전 검토 권고 이어받기**(PR #79 재검토). 등록 내용이 이 절차서로 굳어지므로 지금이 마지막 기회다.
   - R1: 한도에 걸린 날 비율이 높은 후보(예: 검증 거래일의 50% 초과)는 승격 제안 전에 진입 순서를 시드로 섞은 재현을 붙인다는 문장이 아직 어디에도 없다. 절차서 7장에 넣을 수 있다.
   - `kr-short-reversal-swing@1`의 `study.key-param`은 여전히 `signal.trend-days`다(`strategies/kr-short-reversal-swing/v1.yaml` 27행). 바꾸지 않으면 `report.md` 한계에 "핵심 신호 파라미터(연속 하락 일수)의 민감도는 보지 않았다"를 적는다.
   - C10 해석에 후보와 대조군의 보유 기간·청산 차이를 적고, 리더보드에 없는 비용 비중·평균 보유 기간·회전율은 `report.md`에서 `runs.tsv`로 계산해 보탠다.
8. **테스트와 절차서 동기화.** 새 테스트가 절차서 4장 YAML을 문자열로 복사해 두었다. 둘 중 하나만 바뀌면 테스트가 엇갈림을 잡지 못한다. 테스트 주석에 "절차서를 바꾸면 여기도 바꾼다"를 적거나, 등록 파일을 실제로 커밋할 때 그 파일을 읽는 테스트로 바꾸기를 권한다.

### 새로 본 점 (권고, 막지 않음)

- N1. `git diff --exit-code origin/main -- <path>`는 추적되지 않는 파일을 보지 않는다. `study.yaml`이 main에 아직 없는데(등록 PR이 머지되기 전) 사용자가 손으로 만든 파일이 있으면 아무것도 출력하지 않고 통과한다. 절차서 4장 순서(Claude 커밋 → 사용자 `git pull`)를 지키면 생기지 않는 경우라 막지 않는다. 더 단단히 하려면 `git ls-files --error-unmatch <path>`를 같이 쓰거나, 후속으로 `inputs.yaml`에 `study.yaml` SHA-256을 남긴다(sim-engine 변경 제안, 이전 권고 3 후단).
- N2. 테스트가 절차서의 "첫 번째" yaml 블록을 읽는다. 나중에 절차서 4장보다 앞에 다른 yaml 블록이 생기면 테스트가 엉뚱한 블록을 읽어 실패한다. 실패 쪽이라 안전하며 기록만 남긴다.
