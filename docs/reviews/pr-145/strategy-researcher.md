## 권고(머지를 막지 않음)

- R1. **허용 뒤처짐 1거래일은 KRX 당일 게시 `[가정]`에 묶여 있다.** runbook은 주간 점검을 "마지막 거래일 장 마감 뒤, 수신이 멈춘 다음"(16시대)에 돌리고, 매일 수집은 18:30 이후에 돌린다. 그러면 금요일 점검이 보는 스냅샷은 목요일 저녁 실행분이다. 프로젝트 가정(KRX 당일 18:00 게시, `CollectorMain.KRX_SAME_DAY_FROM`, ADR-008 2.3 `[가정]`)이 맞으면 마지막 거래일 = 목 → 뒤처짐 [금] 1일 → 정상이다. 그런데 2차 자료에는 KRX Open API가 "매일 오전 8시(KST)에 갱신"된다고 적혀 있다([openkrx-mcp README](https://github.com/RealYoungk/openkrx-mcp), 공식 문서 아님 `[가정]`). 이것이 맞으면 목요일 저녁 실행분의 마지막 거래일은 수요일이 되고, 매주 [목, 금] 2일로 **멈춤 의심이 늘 뜬다**. 종료 코드는 그대로라 해는 적지만 매주 뜨는 경고는 곧 무시된다. 권고: 첫 실데이터 점검에서 스냅샷 `lastTradingDate`와 실행 시각을 한 번 대조해 게시 시각을 확인하고, T+1 게시로 확인되면 `ALLOWED_LAG`를 2로 하거나 runbook에서 주간 점검을 그날 수집 뒤(18:30 이후)나 다음 날 수집 뒤로 옮긴다. 확인 전까지 runbook 4장 설명에 "멈춤 의심이 정확히 마지막 두 거래일이고 수집기 콘솔에 빈 목록 멈춤이 없으면 게시 시각 문제일 수 있다"를 한 줄 두면 좋다
- R2. **지금의 실시간 모의 계좌 성과에는 영향이 없다는 점을 적어 두면 좋다.** `LivePlan`은 선정 프로필을 받지 않는다(`LivePlan.java:46` "선정 프로필은 받지 않는다(녹화 실험과 같음, 후속)"). 그래서 수집이 멈춰도 LIVE01 계좌의 매매·성과는 바뀌지 않고, 공백은 4단계 실험과 앞으로의 선정 결과 일괄 명령 입력 쪽에 생긴다. runbook 문구 "선정 결과에 공백이 생긴다"는 맞지만, 점검표를 읽는 사람이 3장 계좌 성과를 의심하지 않도록 4장 본문에 "현재 6단계 계좌는 일봉 스냅샷을 입력으로 쓰지 않음"을 덧붙이는 것을 권한다(D-105 되돌릴 조건과 같은 방향)
- R3. 스냅샷 마지막 거래일이 점검 마지막 날보다 늦은 경우(지난 주를 `-Pto`로 다시 볼 때)는 뒤처짐 0으로 정상이 나온다. 코드상 맞지만 시험이 없다. 같은 날(뒤처짐 0)은 시험이 있으니 우선순위는 낮다
- R4. 점검이 주 1회라 금요일에 생긴 멈춤은 다음 주에야 보인다(금요일 하나만 뒤처지면 정상). 6단계 선정 공백 관점에서는 1주 지연이 허용 범위라고 본다 `[추론]`. 더 빨리 봐야 하면 수집기 예약 실행의 종료 코드 1을 감시 알림에 넣는 쪽(D-105 대안 C 방향, data-engineer·risk-ops 영역)이 맞다

## 한계

- 실제 KRX 게시 시각을 공식 자료(openapi.krx.co.kr)로 확인하지 못했다. R1의 T+1 08:00은 2차 자료뿐이라 `[가정]`이다.
- 사용자 PC의 실제 스냅샷 폴더와 주간 점검 결과로는 돌리지 않았다. 수집기 멈춤에서 스냅샷 고정까지의 연결은 코드 대조로만 확인했고 모듈을 가로지르는 시험으로는 확인하지 않았다.
