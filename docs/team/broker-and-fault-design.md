# 증권사 연동 우선순위와 실전 장애 대응 설계

작성일: 2026-10-08 · 요청: 토스·키움·한국투자 3사 모두 실전 지원, 설정된 API만 사용, 우선순위 기반 선택, 실전 동시 진행 가능, 실전 매매에 영향 없는 구조, 장애 대응 최우선

---

## 1. 결론
- 증권사마다 **"설정됨 + 정상" 일 때만 켜지는 플러그인**으로 만들고, 기능(시세 / 주문 / 잔고)별로 우선순위를 따로 둡니다.
- **시세는 우선순위에 따라 다른 증권사로 넘겨받을 수 있지만, 주문은 절대 넘기지 않습니다.** 주문과 잔고는 계좌가 있는 증권사에 묶여 있기 때문입니다.
- 실전 매매는 **계좌 단위로 독립 실행**합니다. 여러 증권사 계좌가 동시에 돌 수 있고, 한 계좌의 장애가 다른 계좌를 멈추지 않습니다.
- 실전 매매를 지키기 위해 **프로세스를 4개로 나눕니다**(실전 엔진, 시세 게이트웨이, 시뮬레이션 실험실, 감시·킬스위치). PC 자원이 부족하면 시뮬레이션부터 멈춥니다.
- 시세 연결이 끊겨도 보유 종목의 손절은 계속 돌아가야 합니다. 이를 위해 **실전 엔진 자체의 보호 시세 경로**와, 지원되는 증권사에서는 **증권사 서버 측 손절 주문**을 함께 씁니다.

---

## 2. 증권사별 확인 결과

처음 출처는 2026년 하반기 2차 자료(개발자 블로그)였습니다. 실시간 한도와 토스 실시간 여부는 공식 문서로 다시 확인했습니다([시세 조사](../research/market-data-limits.md), Q-001). 나머지 항목은 구현 전에 공식 문서로 확인합니다.

| 항목 | 한국투자증권 (KIS Developers) | 키움증권 (REST API) | 토스증권 (Open API) |
|---|---|---|---|
| 방식 | REST + WebSocket | REST + WebSocket | REST + WebSocket (2026-10 공식 문서 기준, D-024) |
| 실시간 시세 | 제공. appkey당 41건 | 제공. 토큰별 세션 1개, 세션당 200종목. 그룹 등록 요청 수 초과 시 오류 `1702` | 제공. 계정당 연결 2개(3번째 연결 시 가장 오래된 연결 종료), 연결당 100건. 시세 채널은 유실 가능(LOSSY) |
| 주문 | 제공 | 제공 | 제공. 조건주문(SINGLE, OCO, OTO) 지원 |
| 모의투자 도메인 | 있음 (포트, tr_id 구분) | 있음 (`mockapi.kiwoom.com`) | 확인 안 됨 |
| 호출 제한 | 초당 한도 있음, 초과 시 `EGW00201` | 초과 시 `429` | API 그룹별 초당 한도 (예: 시세 15, 주문 10, 계좌 1회. 09:00~09:10에는 일부 축소). 사전 공지 없이 바뀔 수 있음 |
| 재연결 시 주의 | 재접속 후 구독 재등록 필요, PINGPONG 응답 필수 | 재접속 후 LOGIN·REG 재등록, 누락 틱은 복구 안 됨(REST로 보정), PING 응답 필수, 토큰은 발급 IP에 묶임 | 재접속 후 구독 목록 전체 재선언, 180초 무수신 시 서버가 끊으므로 60초 간격 PING, 주문 상태는 REST로 재동기화 |
| 운영 환경 | 제약 언급 없음 | 제약 언급 없음 (기존 OCX 방식 불필요 `[추론]`) | 제약 언급 없음 |

기존 기획안과 달라지는 점
- (2026-10-08 갱신, D-024) 토스 Open API에 실시간 WebSocket이 생겨, 토스를 **실시간 시세 2순위**로도 씁니다. 주문·잔고·서버 측 조건주문 용도와 보유 종목 보호 폴링은 그대로입니다.
- 키움 OCX(32bit, JNA/IPC) 설계는 REST API로 대체합니다. Java에서 순수 HTTP/WebSocket으로 연동할 수 있습니다.

## 3. 설정 기반 활성화 규칙

### 3.1 증권사 플러그인 상태
```
NOT_CONFIGURED ─(UI/파일에 키 입력)─▶ CONFIGURED ─(인증·헬스체크 통과)─▶ ACTIVE
                                            ▲                                │
                                            └──(복구 확인)── DEGRADED ◀──(오류 누적)┘
```
- **NOT_CONFIGURED**: 해당 증권사는 아예 로딩하지 않습니다. 오류도 알림도 내지 않고, 화면에 "미설정"으로만 표시합니다.
- **CONFIGURED**: 키는 있지만 아직 인증 전입니다. 장 시작 전(08:30) 인증과 헬스체크를 시도합니다.
- **ACTIVE**: 기능별(시세 / 주문 / 잔고)로 사용 가능합니다.
- **DEGRADED**: 오류가 누적된 상태입니다. 시세는 다음 우선순위로 넘기고, 주문은 해당 계좌만 신규 진입을 멈춥니다.

### 3.2 기능별 능력 선언 (Capability)
각 플러그인은 자기 능력을 선언하고, 엔진은 선언된 능력만 씁니다.

| 능력 | KIS | 키움 | 토스 |
|---|---|---|---|
| REALTIME_QUOTE (실시간 체결·호가) | O | O | O (LOSSY, 계정 합계 2연결, D-024) |
| POLLING_QUOTE (REST 시세) | O | O | O |
| ORDER (주문·정정·취소) | O | O | O |
| BALANCE (잔고·체결 조회) | O | O | O |
| SERVER_SIDE_STOP (서버 측 조건주문) | 확인 필요 | 확인 필요 | O (OCO/OTO) |

### 3.3 설정 예시
```yaml
autotrade:
  brokers:
    kis:     { enabled-if-configured: true, app-key: "", app-secret: "", accounts: [] }
    kiwoom:  { enabled-if-configured: true, app-key: "", secret-key: "", accounts: [] }
    toss:    { enabled-if-configured: true, api-key: "", secret: "", accounts: [] }
  market-data:
    priority: [KIWOOM, TOSS, KIS]     # 위에서부터 ACTIVE인 것만 사용 (D-024)
    mode: FAILOVER                    # FAILOVER 또는 SHARDED(구독 한도 합산)
    toss-polling-scope: HELD_ONLY     # 토스 REST 폴링은 보유 종목 보호용으로만 (실시간 순위와 별개로 유지)
  real-trading:
    accounts:                         # 실전 계좌별 독립 실행 단위
      - { id: "KIS-1",    broker: KIS,    enabled: false }
      - { id: "KIWOOM-1", broker: KIWOOM, enabled: false }
      - { id: "TOSS-1",   broker: TOSS,   enabled: false }
```
값이 비어 있으면 그 증권사는 NOT_CONFIGURED입니다. `enabled`는 재기동 시 항상 false로 시작합니다(RealTradingGuard 원칙).

## 4. 우선순위 추천

### 4.1 실시간 시세
| 순위 | 증권사 | 이유 |
|---|---|---|
| 1 | 키움 | 세션당 200종목, 10호가, 모의 도메인으로 연동 검증 가능 |
| 2 | 토스 | 계정당 연결 2개 × 100건. 게이트웨이는 1연결만 사용(나머지 1개는 실전 엔진 주문 이벤트용) |
| 3 | 한국투자 | appkey당 41건. 장애 대비 예비 |

- D-024(D-008 대체, 사용자 결정)로 확정했습니다. 근거는 [시세 조사](../research/market-data-limits.md) 1·3장입니다.
- **토스 보유 종목 보호 폴링(`toss-polling-scope: HELD_ONLY`)은 실시간 순위와 별개로 유지합니다.** 실시간 소스가 모두 끊겼을 때 실전 엔진의 보호 시세 경로입니다(5.1, 6장 1·2번).
- **토스 연결 배분**: 토스 WebSocket은 계정 합계 2연결이다. 실전 엔진은 한 계정의 모든 토스 실전 계좌가 연결 1개를 함께 쓰고 계좌별로 나눠 처리한다. 게이트웨이는 1개까지, 실험실과 감시 프로세스는 0개다. 게이트웨이는 재접속할 때 기존 연결이 닫힌 것을 확인한 뒤에만 새로 연결한다. 실전 계좌가 켜진 토스 계정에서 게이트웨이 연결이 거부되거나 반복해서 끊기면, 게이트웨이가 토스 시세를 끄고 다음 순위로 넘어간다. 감시 프로세스는 프로세스별 연결 수 설정과 실제를 대조합니다(6장 17번).
- **키움 세션**: 토큰별 세션 1개입니다. 실전 엔진은 REST 확정을 기본으로 하고(4.2), 프로세스별 별도 토큰 사용은 다른 토큰을 무효화하지 않는다는 것을 실측한 뒤에만 허용합니다.
- **LOSSY 소스와 보유 종목**: 토스 시세 채널은 특정 종목만 빠질 수 있습니다. 보유 종목은 종목별 마지막 수신 시각도 감시하고, 기준 시간(예: 3초, 설정값)을 넘긴 종목은 소스 상태와 상관없이 즉시 보호 시세 경로(REST 폴링)로 감시합니다.
- 두 곳이 모두 ACTIVE면 **SHARDED 모드**를 쓸 수 있습니다. 감시 종목을 나눠 받아 구독 한도를 합칩니다. 한쪽이 끊기면 그쪽 종목을 남은 쪽으로 옮기고, 넘치는 종목은 감시 대상에서 우선순위가 낮은 것부터 뺍니다(보유 종목은 절대 빼지 않음).

### 4.2 실전 주문
- 주문은 **계좌의 증권사로만** 나갑니다. 증권사 간 대체 주문은 없습니다.
- 여러 실전 계좌를 동시에 켤 수 있습니다. 같은 종목을 두 계좌가 동시에 사지 않도록 **계좌 간 종목 배정 규칙**을 둡니다(기본: 한 종목은 한 실전 계좌만 보유).
- 전략 프로필을 실전 계좌에 배정할 때 "어느 계좌가 어떤 전략을 실행하는지"를 UI에서 명시합니다.
- 실전 엔진의 주문·체결 상태는 **REST 조회로 확정**합니다. WebSocket 주문 이벤트(토스 `personal:order`, 키움 `00`)는 조회를 앞당기는 보조 신호로만 씁니다. 실전 계좌의 앱키·토큰은 실전 엔진 전용이며, 게이트웨이·실험실은 그 키로 토큰 발급, WebSocket 연결, REST 호출을 하지 않습니다. 같은 키를 써야 하면 계좌·API 그룹별 토큰 버킷에서 실전 엔진 몫(손절·조회 우선)을 먼저 떼어 둡니다 (D-024).

### 4.3 잔고 대사
각 실전 계좌는 자기 증권사 잔고 API로 5분마다 대사합니다. 증권사 잔고가 기준(진실)입니다.

## 5. 실전 매매 보호를 위한 격리 구조

### 5.1 프로세스 4개
```
                ┌───────────────────────────────┐
                │ ④ 감시·킬스위치 (Watchdog)       │  최고 우선순위, 가장 작음
                │  - 모든 프로세스 하트비트 감시       │
                │  - PC 자원 감시 (monitor-agent)   │
                │  - 실전 계좌별 긴급 정지/청산 명령  │
                └──────────────┬────────────────┘
                               │ 하트비트·명령
   ┌───────────────────┐  로컬 큐  ┌──────────────────────────┐
   │ ② 시세 게이트웨이     │────────▶│ ① 실전 매매 엔진 (높은 우선순위) │
   │  - 키움/토스/KIS WS   │         │  - 계좌별 독립 워커             │
   │  - 장애 시 소스 전환   │         │  - 계좌별 주문 직렬 큐·레이트리밋 │
   │  - 녹화 (같은 큐)     │         │  - 보호 시세 경로(REST 폴링)    │
   └─────────┬─────────┘         └──────────────────────────┘
             │ 같은 큐를 읽기 전용으로 (느려도 실전에 영향 없음)
             ▼
   ┌───────────────────────────────┐
   │ ③ 시뮬레이션 실험실 (낮은 우선순위)   │
   │  - 다중 모의 계좌, 실험, 리포트      │
   │  - 자원 부족 시 가장 먼저 일시정지    │
   └───────────────────────────────┘
```

| 원칙 | 구현 |
|---|---|
| 실전 엔진은 다른 프로세스가 죽어도 산다 | JVM 분리. 실험실·UI·게이트웨이가 죽어도 실전 엔진은 보유 종목 보호를 계속함 |
| 시세 전달은 실전 쪽을 막지 않는다 | 게이트웨이는 메모리 매핑 로컬 큐(예: Chronicle Queue `[추론]` 적합)에 쓰기만 함. 실험실이 느려도 생산자는 기다리지 않음. 이 큐가 곧 녹화 파일이 됨 |
| 실험실은 자원을 빼앗지 않는다 | OS 프로세스 우선순위 낮춤, 힙·스레드 상한 고정. 감시 프로세스가 CPU·메모리 임계치에서 실험실부터 일시정지 |
| 계좌끼리 영향 없음 | 계좌별 워커, 주문 큐, 레이트리밋 버킷, 킬스위치, 상태머신을 따로 둠. 한 계좌 예외는 그 계좌만 정지 |
| UI는 읽기 전용 경로 | UI 조회는 실전 엔진의 스냅샷만 읽음. 실전 제어 명령(활성화, PANIC SELL)은 별도 명령 채널로 검증 후 반영 |
| 감시는 독립 | 킬스위치는 실전 엔진과 다른 프로세스. 실전 엔진이 멈춰도 긴급 청산 명령을 증권사에 직접 보낼 수 있는 최소 경로 보유. 이 경로는 REST만 쓰고 WebSocket을 열지 않음(토스 연결 수 보호, D-024) |

### 5.2 자원 부족 시 정지 순서 (Load Shedding)
1. 시뮬레이션 실험의 신규 실행 중단
2. 시뮬레이션 실험실 일시정지
3. 시세 녹화를 보유·감시 종목으로 축소
4. UI 실시간 스트림 주기 완화(1초 → 5초)
5. 실전 신규 진입 중단 (서킷브레이커 1단계)
6. 실전 보유 종목 보호만 유지 (손절·익절 감시)

실전 보유 종목 보호(6번)는 끝까지 남깁니다.

## 6. 장애 대응 매트릭스

| # | 장애 | 감지 | 실전 대응 | 실험실 대응 |
|---|---|---|---|---|
| 1 | 1순위 시세 소스 끊김 | 하트비트·수신 간격 > 3초. 보유 종목은 종목별 마지막 수신 시각도 감시(기준 초과 종목은 즉시 보호 시세 경로) | 2순위로 전환, 전환 구간 신규 진입 보류, 보유 종목은 보호 시세 경로로 감시 | 공백 구간 표시, 해당 구간 결과는 별도 표기 |
| 2 | 모든 실시간 시세 끊김 | 위 + 2순위 실패 | 신규 진입 전면 중단, 보유 종목은 REST 폴링(가능한 증권사 아무거나)으로 손절 감시, Slack 긴급 | 일시정지 |
| 3 | 특정 증권사 주문 API 장애 | 주문 오류·타임아웃 누적 | **그 계좌만** 신규 진입 중단, 보유 종목 손절은 재시도·조회 우선, 다른 계좌는 정상 진행 | 영향 없음 |
| 4 | 주문 타임아웃 | 응답 없음 | 상태 UNKNOWN → 조회 먼저 → 미접수일 때만 새 키로 1회 재발주 | 동일 로직(가상) |
| 5 | 부분 체결·중복 체결 | 체결 통보·대사 | 잔량 기한 후 취소, 중복분 즉시 정리 후 원인 분석 | 동일 로직(가상) |
| 6 | 잔고 불일치 | 5분 대사 | 증권사 잔고 기준으로 동기화, 불일치 계좌 신규 진입 중단 | 해당 없음 |
| 7 | 토큰 만료·인증 실패 | 401 계열 | 선제 갱신(만료 전), 실패 시 해당 증권사 DEGRADED | 시세 소스만 전환 |
| 8 | 실전 엔진 프로세스 크래시 | 감시 프로세스 하트비트 | 자동 재기동 → DB 상태 복구 → 증권사 대사 통과 후에만 재개. 재기동 동안 서버 측 손절 주문이 보호 | 영향 없음 |
| 9 | 실험실·UI·게이트웨이 크래시 | 하트비트 | 실전 영향 없음 (게이트웨이는 #1·#2로 처리), 자동 재기동 | 재기동 후 공백 표시 |
| 10 | PC 자원 고갈 | monitor-agent 임계치 | 5.2 정지 순서 적용 | 가장 먼저 정지 |
| 11 | 인터넷 단절 | 핑·모든 연결 실패 | 신규 진입 불가, 복구 시 대사 후 재개. 단절 동안은 서버 측 손절 주문만 보호 | 정지 |
| 12 | PC 전원 차단 | 해당 없음 (UPS 권장) | 서버 측 손절 주문만 보호. 재기동 시 #8 절차 | 정지 |
| 13 | VI·거래정지 | 종목 상태 수신 | 해당 종목 신규 주문 금지, 보유분 유지 | 동일 규칙 |
| 14 | 레이트리밋 초과 | 오류 코드(`EGW00201`, `429` 등) | 계좌·API 그룹별 토큰 버킷으로 사전 차단, 초과 시 지수 백오프. 손절 주문이 우선순위 최상 | 해당 없음 |
| 17 | 연결 수·레이트리밋 공유로 실전 연결이 끊기거나 조회가 막힘 | 실전 엔진 연결의 서버 측 종료 프레임, 재접속 횟수, 실전 몫 토큰 버킷의 `429` 비율, 감시 프로세스가 프로세스별 연결 수 설정과 실제를 대조 | 끊긴 동안 REST 조회로 주문 상태 확인, 게이트웨이 쪽 연결을 먼저 정리, Slack 경고 (D-024) | 영향 없음 |

### 6.1 서버 측 손절 주문 (PC가 멈췄을 때의 마지막 방어선)
- 진입 체결 직후, 해당 증권사가 지원하면 **증권사 서버에 손절 조건주문**을 함께 걸어 둡니다(토스는 OCO/OTO 지원 확인, KIS·키움은 확인 필요).
- 시스템이 정상일 때는 자체 추적 손절이 먼저 동작하고, 청산하면 서버 측 주문을 취소합니다. 둘이 겹쳐 이중 매도가 나지 않도록 **청산 전 서버 측 주문 취소 확인**을 상태머신에 넣습니다.
- 지원하지 않는 증권사 계좌는 실전 활성화 화면에 "PC 장애 시 보호 수단 없음"을 경고로 표시합니다.

| # | 시나리오 | 합격 기준 |

| 5 | 한 증권사 주문 API 차단 | 다른 증권사 계좌 정상 진행 |
| 6 | 네트워크 전체 차단 30초 | 복구 후 대사 통과, 서버 측 손절 주문 상태 정합 |
