## 수정 필요 항목

**M1. 검증 리더보드의 비용 비중·회전율을 같은 배율로 계산할 것** (`WalkForwardReport.java` 리더보드, 값 출처 `Pooled.of` → `MetricsCalculator.compute`)

[사실] `Pooled.of`는 자산 곡선을 구간 수익률의 복리로 이어 붙이고(`Pooled.java:58-64`), 체결 원장은 구간마다 시드머니로 새로 시작한 원 금액 그대로 합친다(`Pooled.java:66`). `MetricsCalculator.compute`는 비용 비중을 `Σ구간 비용 ÷ (이은 최종 평가금액 − 시드 + Σ구간 비용)`으로(`MetricsCalculator.java:101-102`), 회전율을 `Σ구간 매매 대금 ÷ 2 ÷ 이은 곡선 평균`으로(`MetricsCalculator.java:98-100`) 낸다. 분자는 시드 배율, 분모의 손익·평가금액은 복리 배율이다.

[사실, 손 계산] 시드 1,000만 원, 4구간 순수익률 +30%·−25%·+10%·−5%, 구간 비용 각 50만 원이면 이은 순손익은 +18.9만 원(1.018875배)이라 이 PR 식의 비용 비중은 91.4%다. 같은 구간을 시드 배율로 더하면 순손익 +100만 원, 비용 전 손익 300만 원이라 66.7%다. 4구간 모두 +10%이면 30.1% 대 33.3%. 구간 성과가 엇갈릴수록 차이가 커지고, 이은 손익이 음수 근처면 100%를 넘거나 "-"가 되면서 실제로는 비용 전 이익이 난 후보가 "비용 전 손익 0 이하"로 보인다.

[추론] 판정에는 쓰지 않지만, 이 칸을 넣은 이유가 `kr-short-reversal-swing`처럼 왕복 비용이 기대 반등폭과 비슷한 후보의 비용 부담을 읽기 위해서다(PR #79 권고 2). report.md가 이 값을 인용하면 해석이 틀어진다. 결과 파일 문구("비용 비중 = 비용 ÷ 비용 전 손익")도 실제 계산과 다르다.

고치는 방법(둘 중 하나):
- (추천) 비용 비중 = Σ구간 비용 ÷ Σ구간 (최종 평가금액 − 시드 + 구간 비용), 회전율 = Σ구간 매매 대금 ÷ 2 ÷ (구간별 평균 평가금액의 관측일 가중 평균)처럼 둘 다 구간 원 금액(시드 배율)으로 계산해 리더보드에 낸다. "비용" 칸(원 금액 합)과 배율이 맞는다.
- 또는 구간 k의 비용·매매 대금에 `S_k / 시드`를 곱해 복리 배율로 맞춘다.
어느 쪽이든 결과 파일 설명 줄에 배율을 적고, 엇갈린 두 구간짜리 합성 입력으로 손 계산 값과 맞는지 테스트를 하나 둔다. `RunMetrics`(다른 경로 공용)를 바꾸지 않고 워크포워드 쪽에서 계산하는 편이 영향이 작다.

**M2. `study-sha256`이 줄바꿈 변환에 흔들리지 않게 할 것** (`WalkForwardStudy.runAt`, 절차서 7장)

[사실] `Sha256.ofFile`은 파일 원 바이트를 해시한다. 저장소에 `.gitattributes`가 없다. 절차서 7장은 `study-sha256`이 커밋된 등록 파일의 SHA-256과 다르면 결과를 쓰지 않는다고 정했다. 사용자 PC는 Windows다(CLAUDE.md QA 폴더 경로, 수집기 runbook 10·80행).
[가정] Git for Windows 설치 기본값은 `core.autocrlf=true`(체크아웃 때 CRLF)다. 사용자 PC 설정은 확인하지 못했다.
[추론] 이 경우 사용자 작업 트리의 `study.yaml`은 CRLF라 해시가 커밋된 LF 파일(`git show origin/main:… | sha256sum`)과 다르게 나온다. 절차서 5장의 `git diff --exit-code`는 줄바꿈 변환 뒤 비교라 통과하므로, 주말 실행을 다 마친 정상 결과가 7장에서 버려진다.

고치는 방법(둘 중 하나):
- (추천) 해시 전에 CRLF를 LF로 바꾼 내용의 SHA-256을 남기고 키 이름이나 주석에 "LF 정규화"를 적는다. 절차서 7장에 대조 명령(`git show origin/main:experiments/EXP-<등록일>-WF01/study.yaml | sha256sum`)을 적는다. CRLF 파일로도 같은 해시가 나오는 테스트를 하나 둔다.
- 또는 `.gitattributes`에 `experiments/**/study.yaml text eol=lf`를 넣는다(저장소 공용 파일이라 architect 확인 필요, 이미 체크아웃된 PC에서는 재체크아웃이 필요할 수 있다).

### 이전 권고 반영 상태

- R1(±33% 흔들기 폭 기록): 반영. D-083 1번에 "실제 폭 ±33%, C7에 보수적인 방향, 리포트 한계에 적는다"가 들어갔다.
- R2(C10 해석 때 청산 사유 분포), R3(`study-sha256` 정규식 삽입 대신 직접 쓰기), R4(PR #79 권고 4·5·7): 반영되지 않았다. 모두 막지 않는 항목이고, R2는 report.md 작성 때, R3은 지금 테스트가 막고 있어 그대로 두어도 된다.

### 새로 본 것 (막지 않음)

- N1. 해시는 CRLF만 맞추고 UTF-8 BOM이나 단독 CR은 그대로 둔다. git 줄바꿈 변환은 BOM을 바꾸지 않으므로 커밋된 원본과 사본이 다를 이유가 없어 대조에는 지장이 없다. 기록만 남긴다.
- N2. 회전율은 구간 수만큼 더한 값이라 구간 수가 다른 실험끼리 직접 비교하면 안 된다. 4단계 실험은 모든 후보가 같은 4구간이라 실험 안 비교에는 문제없다. report.md에서 다른 실험과 비교할 때는 구간 수로 나눠 적는다.
